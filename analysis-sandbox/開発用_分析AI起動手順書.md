## 1. まず全体像(3つの「部品」)

分析を画面から実行するには、次の3つが、**それぞれ別に動いている**必要があります。

| 部品 | 何をするか | 例えると |
|---|---|---|
| **launcher(ランチャー)** | 分析用のコードを、安全な「使い捨ての箱(Dockerコンテナ)」の中で動かす | 実験室の係員 |
| **専用ワーカー** | 画面から受けた「実行して」という依頼を、順番に処理する。launcherへ仕事を頼む | 受付係 |
| **Redis(Memurai)** | 依頼・結果・状態を、一時的に置く場所。Windowsサービスではなく、手動で起動する | 伝言板 |

画面のボタンを押す → 受付係(ワーカー)が受け取る → 実験室(launcher)で動かす → 結果が、伝言板(Redis)に載る → 画面に出る、という流れです。

**どれか1つでも止まっていると、実行できません。** PCの再起動、WSLの停止で、launcherとワーカーは止まります(自動では起動しません)。

```
画面(8501) → Django(8081) → [Redis] ← 専用ワーカー → launcher(8091) → Dockerコンテナ
```

## 2. かんたん起動(おすすめ): ダブルクリックで済ませる

手順を、自動で行う「バッチファイル」を、用意しています。`D:\pm` フォルダにあります。

| ファイル | 何をするか |
|---|---|
| `analysis-dev-start.bat` | Redis・launcher・専用ワーカーを、**止まっているものだけ**起動する(動いているものは、そのまま) |
| `analysis-dev-status.bat` | いまの状態を、色つきで表示する(何も変更しない) |
| `analysis-dev-stop.bat` | 専用ワーカーとlauncherを止める(実行中なら、確認を求める) |

**使い方**
1. `analysis-dev-start.bat` をダブルクリックする。
2. 新しい窓が、いくつか開きます(Redis・launcher・専用ワーカー)。**この窓は閉じないでください**(閉じるとそれが止まります)。
3. 元の窓に「準備ができました」と出れば、完了です。画面の「実行基盤の状態を確認」を押してください。
4. 困ったときは、`analysis-dev-status.bat` で、何が止まっているか、確認できます。

バッチファイルを使えば、次の「3. 手動の起動手順」は、読まなくても大丈夫です(仕組みを知りたいときの説明です)。

## 3. 手動の起動手順(毎回、この順番で)

### 準備: 黒い画面(ターミナル)を開く
Windowsの「PowerShell」を、**2つ**開きます。それぞれ「launcher用」「ワーカー用」とします(Redisが止まっていた場合は、3つ目も使います)。**どちらも、作業が終わるまで、閉じないでください**(閉じると止まります)。

### 手順0: Redis(Memurai)が動いているか確認
MemuraiはWindowsサービスではなく、**手動で起動する**開発用のプログラムです(PCを再起動すると止まります)。どのPowerShellでもよいです。

```powershell
Test-NetConnection 127.0.0.1 -Port 6379 -InformationLevel Quiet
```
`True` なら動いています。`False` なら、**新しいPowerShellの窓**で、次を実行し、窓を開いたままにします。
```powershell
Set-Location D:\pm
.\scripts\start-analysis-redis-dev.ps1
```

### 手順1: launcherを起動する(「launcher用」の画面)
```powershell
wsl.exe -d Ubuntu-24.04 -u root -- python3 /mnt/d/pm/analysis-sandbox/launcher/launcher.py
```
- 「起動時に孤児を削除: 0件」のような文字が出れば、起動成功です。
- この画面は、**そのまま開いておく**(文字が増えなくても、正常です)。

**動作の確認**(別の画面で):
```powershell
curl.exe -s http://127.0.0.1:8091/v1/health
```
`{"status": "ready", "busy": false, ...}` と出ればOKです。

### 手順2: 専用ワーカーを起動する(「ワーカー用」の画面)
```powershell
Set-Location D:\pm\pm_backend
& D:\pm\venv\Scripts\python.exe manage.py analysis_worker
```
- 「分析専用ワーカーを起動します。本番では実行できません。」と出れば、起動成功です。
- この画面も、**そのまま開いておく**。
- 注意: 手順1(launcher)を先に起動してください。launcherが動いていないと、起動に失敗します。

### 手順3: Django(8081)とVue(8501)を起動する
いつもの開発サーバーの起動手順と同じです(すでに動いていれば不要)。

### 手順4: 画面で確認する
1. 画面の「AI分析」を開く。
2. 分析案を作り、手順・データ範囲を承認し、コードを生成する。
3. 「SQLを試行(実データなし)」を押して「**合格**」を確認する。
4. 「確認したSQL・Pythonを承認」にチェックを入れて、承認する。
5. 画面下の「4. 分析の実行・結果」で、「実行基盤の状態を確認」を押す。
   - 「開発限定。実行は1件で、待ち行列はありません。」と出れば、準備完了です。
6. 「分析を実行」を押す。
7. 「実行状態・結果を再取得」を押して、結果を確認する(**自動では更新されません**)。

## 4. 止め方

**かんたん**: `analysis-dev-stop.bat` をダブルクリックする(実行中なら、確認が出ます)。開いていた窓は、手動で閉じます。

**手動**:
1. 実行中の分析がないことを確認する(画面の「実行」が、成功・失敗・中止のどれかになっている)。
2. 「ワーカー用」の画面で `Ctrl + C` を押す。
3. 「launcher用」の画面で `Ctrl + C` を押す。

**実行中に止めないでください。** 実行の枠が塞がり、手動で直す必要が出ます(後述)。

## 5. 画面にこう出たら(困りごと別の対処)

| 画面の表示 | 原因 | 対処 |
|---|---|---|
| 「実行基盤に接続できませんでした」 | launcherが起動していない | 手順1を実行する |
| 試行が「**未検証**」になる | 同上(コードの問題ではない) | 手順1の後、もう一度「SQLを試行」を押す |
| 「専用ワーカー未起動、実行中、または後始末未確認です」 | ワーカーが起動していない、または別の実行が残っている | 手順2を実行する。それでも出る場合は、第6章で状態を確認する |
| 「実行履歴の保存に失敗したため、結果を返しません」 | データベースの更新(`migrate`)が未実施 | 第7章の「migrate」を実行する |
| 「結果の形式が正しくありません…」(`result_invalid`) | 結果形式の最終検査が不合格(グラフ・表など)。この理由だけでは原因を断定できない | 表の列と各行の個数、グラフのxと系列valuesの個数・型を確認し、必要ならコードを再生成する |
| 「実行は受け付けられませんでした」 | 他の実行が残っている、または分析案が変わった | 「分析案の状態を再取得」を押して、状態を確認する |
| 実行したのに「受け付け済み」のまま | 画面が古い(自動更新されない) | 「実行状態・結果を再取得」を押す |
| 「中止を要求しました」のまま | 後始末の確認待ち | 少し待って、「実行状態・結果を再取得」を押す |

## 6. いまの状態を確認する方法

### (1) launcherが動いているか
```powershell
curl.exe -s http://127.0.0.1:8091/v1/health
```
- `"status": "ready"` → 正常
- `"busy": true` → 実行中、または後始末が残っている
- 何も返らない → launcherが止まっている(手順1)

### (2) 使い捨てコンテナが残っていないか
```powershell
wsl.exe -d Ubuntu-24.04 -u root -- docker ps -a --filter label=pm.analysis.job=1
```
- 一覧が空(見出しだけ)なら、正常です。
- `pmjob-…` という名前が残っていたら、後始末の失敗です。担当者に相談してください。

注意：WSL／Dockerのコマンド自体が失敗した場合は、0件とも残骸ありとも判断できません。2026-10-04の確認で、状態BATがWSLのアクセス拒否を「コンテナ5件」と数える誤表示を観測しました。実際の一覧取得に成功したこと（終了コード0）を確認し、エラーだけを根拠に停止・削除・枠解除しないでください。health取得失敗だけでlauncher停止とも断定できません。

### (3) ワーカーが生きているか、実行枠が塞がっていないか
```powershell
Set-Location D:\pm\pm_backend
& D:\pm\venv\Scripts\python.exe -c "
import redis
from dotenv import dotenv_values
r = redis.Redis.from_url(dotenv_values('.env').get('AI_ANALYSIS_REDIS_URL'), decode_responses=True)
k = 'pm:ai:analysis:execution:'
print('ワーカー生存:', bool(r.get(k + 'worker')))
print('実行枠(空ならNone):', r.get(k + 'active'))
"
```
- `ワーカー生存: True` かつ `実行枠: None` → 正常(いつでも実行できる)
- `ワーカー生存: False` → ワーカーが止まっている(手順2)
- `実行枠` に、長い英数字(ジョブID)が出ている → 実行中、または枠が塞がっている(第8章)

## 7. データベースの更新(migrate)が必要なとき

画面に「実行履歴の保存に失敗」と出る、または、新しい機能が追加された直後に、1回だけ実行します。

```powershell
Set-Location D:\pm\pm_backend
& D:\pm\venv\Scripts\python.exe manage.py migrate
```
- 適用状況の確認: `python manage.py showmigrations ai` で、`[X]` が並んでいればOKです。

## 8. 実行枠が塞がったとき(開発の応急処置)

**状況**: launcherやワーカーを、実行中に止めた、または、実行が失敗した後、「実行中、または後始末未確認」の表示が消えない。

**管理コマンドで確認します。Redisのactiveキーを直接削除しないでください。**

1. 画面で中止・実行状態・履歴を確認し、対象のジョブIDを控える。DB接続の後始末がpending／failed／unconfirmedなら解除できないため、担当者へ相談する。
2. 分析中でないことを確認してワーカーとlauncherを停止する。残コンテナはlauncherの通常の掃除・中止で削除を確認し、再度停止する。他のコンテナは操作しない。
3. ワーカー生存キーの期限（60秒）を待ち、次の確認専用コマンドを実行する。`--job-id`は実際のUUIDに置き換える。

```powershell
Set-Location D:\pm\pm_backend
& D:\pm\venv\Scripts\python.exe manage.py analysis_recover --job-id <対象のUUID>
```

4. 全項目の確認に合格した対象だけ、同じコマンドに`--apply`を付ける。更新時も再確認し、ロック・ジョブID・履歴・後始末のどれかが未確認／競合なら解除しない。
5. launcher・ワーカーを再起動する。結果本文は復元されず、状態不明を成功とは扱わない。

対象は標準Windowsワーカー＋WSL Ubuntu-24.04の8091と標準ロック配置だけです。停止済みの実環境での解除は未検証で、手順が分からなければ担当者へ相談してください。詳細は[READMEの復旧手順](README.md#未確認の実行枠の復旧開発限定管理コマンド)を参照してください。

## 9. よくある質問

**Q. Redis・launcher・ワーカーは、毎日起動する必要がありますか。**
A. はい。PCの再起動やWSLの停止で止まるため、実行したいときに、`analysis-dev-start.bat` を実行してください。自動起動の仕組みは、まだありません。

**Q. ワーカーのウィンドウを、間違って閉じました。**
A. もう一度、手順2を行ってください。実行中でなければ、問題ありません。

**Q. 本番でも使えますか。**
A. 使えません。本番では、分析の実行は無効です。本番で動かすには、自動起動・復旧・監視・権限を整えた、別の設計が必要です(未着手)。

**Q. Portainer(Dockerの管理画面)で、イメージを消してよいですか。**
A. `pm-analysis-job:dev` は、消さないでください。消すと、`python3 tools/build.py` でイメージを作り直す必要があります。

**Q. 実行すると、本番のデータが変わりますか。**
A. 変わりません。開発DBのデータを、読み取りだけして、使い捨ての箱の中で処理します。データベースへの書き込みは、実行履歴(件数・ハッシュなど)だけで、コードや結果の本文は保存しません。

## 10. 用語

| 用語 | 意味 |
|---|---|
| コンテナ | 他から隔離された、使い捨ての小さな実行環境。分析が終わると削除される |
| launcher | コンテナを作って、分析コードを動かす係。Dockerを操作できる唯一のプログラム |
| 専用ワーカー | 画面からの実行依頼を受けて処理する常駐プログラム |
| 実行枠 | 同時に実行できるのは1件だけ、という制限のための印。実行中は、この枠が使われる |
| 試行 | 実データを使わず、SQLの書き方だけを確認する事前チェック |
| Memurai | Windows用のRedis(一時的な伝言板) |
| migrate | データベースの構造を、最新にするコマンド |
