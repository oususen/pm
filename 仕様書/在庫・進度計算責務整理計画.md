# 在庫・進度計算責務整理計画

## 1. 目的

- `pm_backend/apps/production/inventory/inventory_calculator.py` および進度計算呼び出し経路から、場面ごとの差分判定をできるだけ外へ出す
- 在庫・計画在庫・進度の計算ロジック本体と、呼び出し条件の決定責務を分離する
- 連産品、BOM波及、画面別再計算などの条件差分を service 層で吸収できる構成にする

## 2. 現状認識

### 2.1 全体構造

すべての在庫・進度計算は `recalculate_inventory_for_line` を唯一の入口として通る。
この関数は1つの中に3つの責務を持っている:

1. **対象製品の決定** — LineBacklog × RoutingStep有効性で製品リストを構築
2. **データ一括取得** — 需要マップ・調整値・仕損を全製品の最大LT範囲で一括取得
3. **製品別計算ループ** — `for product_id in product_ids:` で製品1つずつ在庫→計画在庫→進度を順に実行

```
recalculate_inventory_for_line(line_id, start, end)
  ├── 対象製品を決める（LineBacklog × RoutingStep有効期間）
  ├── 需要・調整値を一括取得（全製品の最大LTの範囲で）
  └── for 製品 in 対象製品:
        ├── recalculate_stock_qty（製品個別の直親LTで開始日決定）
        ├── recalculate_planned_stock_qty（同上）
        └── recalculate_progress_qty（累積LTで開始日決定）
```

### 2.2 計算器内部に残っている条件決定

現在の在庫・進度計算系は、計算式本体だけでなく以下も一部持っている。

- 対象製品の構築（LineBacklogのdistinct product_id → RoutingStep有効性フィルタ）
- 製品ループの実行（製品ごとに在庫→計画在庫→進度の3計算を順に呼び出し）
- 開始日の2段階補正:
  - 1段階目: 全製品の最大LTでデータ取得範囲を決定（`recalculate_inventory_for_line` 内）
  - 2段階目: 製品個別のLTで実際の計算開始日を決定（`recalculate_stock_qty` / `recalculate_planned_stock_qty` 内）
- 有効ルーティングを持たない製品の除外（`build_effective_routing_range_q` による有効期間レンジ判定）
- 調整値取得範囲の補正（在庫開始日・進度開始日の最小値を使用）
- 需要取得範囲の補正（`inventory_calc_start_date` まで拡張）
- 仕損集計（`aggregate_scrap_to_backlog` の呼び出し）
- 需要マップ構築（`_build_demand_map` の呼び出し）
- LT計算とキャッシュ構築（直親LT / 累積LT を製品ごとに事前計算）
- カレンダー解決と営業日判定（`_resolve_line_calendar_id` / `_resolve_calendar_working_day`）
- `is_working_day` / `shift_working_days` / `get_prev_working_day` のローカル関数定義（`recalculate_inventory_for_line` / `recalculate_stock_qty` / `recalculate_planned_stock_qty` の3箇所で重複定義）

### 2.3 関数の分類と公開範囲の不整合

`inventory_calculator.py` 内の関数は3種類に分かれる:

1. **計算本体**: `recalculate_stock_qty` / `recalculate_planned_stock_qty`（製品ループ内から呼ばれる）
2. **内部ヘルパー**: `_` prefix の関数群（出庫計算、LT取得、カレンダー解決、需要構築など）
3. **外部利用ユーティリティ**: `calculate_actual_shipment` / `has_downstream_actual`（`_` なし、外部から呼ばれる前提）

問題: 以下の `_` prefix 関数が外部モジュールから直接 import されている:

- `_get_direct_parent_bom_lead_time` → `production/views.py`
- `_get_max_parent_bom_lead_time` → `production/views.py`, `progress_calculator.py`
- `_resolve_calendar_working_day` → `progress_calculator.py`

内部用（`_` prefix）と公開用の境界が曖昧になっている。整理時に公開APIとして切り出すか、別モジュールに移すかを検討する必要がある。

### 2.4 呼び出し元が決めていること

一方で、呼び出し元でも以下を決めている。

- どの画面・イベントから再計算するか
- どのラインを対象にするか
- どの製品を対象にするか
- 連産親を起点にするか、連産子を起点にするか
- BOM親ラインまで波及させるか

そのため、条件決定責務が `inventory_calculator.py` と service 層に分散している。

## 3. 目指す構成

### 3.1 inventory_calculator.py / progress_calculator.py の責務

- 渡された条件に基づき在庫・計画在庫・進度を再計算する
- 計算に必要な集計・日次ループを実行する
- 条件そのものの意味解釈は持ち込まない

### 3.2 service 層の責務

- 再計算開始日を決める
- 再計算終了日を決める
- 対象ラインを決める
- 対象製品を決める
- 連産品・通常BOM・親ライン波及などの展開を行う
- 再計算オプションを組み立てる

## 4. 場面ごとの差分

計算式本体ではなく、主に以下が場面ごとに異なる。

### 4.1 開始日

- 通常再計算
- 表示品番限定再計算
- deep再計算
- `force_from_start=True`
- 実績変更後の波及再計算

なお、`recalculate_inventory_for_line` 内部で開始日がさらに補正される:

- 在庫開始日: `today - (max_direct_parent_lt + 1)` 営業日（直親LT）
- 進度開始日: `today - (max_cumulative_lt + 1)` 営業日（累積LT）
- 調整値取得開始日: 上記2つと `start_date` の最小値

### 4.2 対象製品

- ライン全製品
- 指定 `product_ids`
- 連産子
- BOM波及で見つかった親品

### 4.3 対象ライン

- 現在ラインのみ
- BOM親の別ラインを含む

### 4.4 再計算モード

- 在庫のみ
- 在庫 + 進度
- 進度のみ
- ライン最終品のみ

## 5. 段階的な整理方針

一度に全面変更すると影響範囲が大きいため、段階的に進める。

### Step 1. 呼び出し元の棚卸し

対象:

- `pm_backend/apps/production/services/backlog_recalc_service.py`
- `pm_backend/apps/production/services/recalc_start_date.py`
- `pm_backend/apps/production/services/process_realtime_backlog_service.py`
- `pm_backend/apps/production/scheduler/tasks.py`（定期タスク・自動スケジューラ）
- `pm_backend/apps/purchase/views.py`（設計変更時の在庫再計算）
- `pm_backend/apps/purchase/order_proposal_views.py`（自動発注数量計算後の在庫再計算）
- `pm_backend/apps/purchase/tasks_auto_delivery_list.py`（自動納品リスト生成後の在庫再計算）
- `pm_backend/apps/production/views.py`（再計算API入口: `recalculate_inventory` / `recalculate_inventory_for_products` / `recalculate_inventory_deep`、いずれも `backlog_recalc_service` へ委譲。LTユーティリティの直接参照もあり）

確認内容:

- 指定日をどこで決めているか
- LT加味日をどこで決めているか
- 対象製品をどこで決めているか
- 対象ラインをどこで決めているか
- どのオプションを渡しているか

### Step 1 調査結果（`recalculate_inventory_for_line` 呼び出し元一覧）

開始日の見方は、いったん以下の2つに分けて整理する。

- `指定日`: 画面表示開始日、調整対象日、実績変更日、タスク基準日など、場面側が「この日から見たい/巻き直したい」と決める日
- `LT加味日`: LT を考慮して「少なくともここまでは遡らないと正しく計算できない」として決める日

この Step 1 では、まず「各呼び出し元で何を `指定日` としているか」「`LT加味日` をどこで決めているか」を棚卸しする。

補足:

- `pm_backend/apps/production/views.py` の `recalculate_inventory` / `recalculate_inventory_for_products` / `recalculate_inventory_deep` は API 入口のみで、実際の開始日・対象製品・対象ライン・オプションの組み立ては `backlog_recalc_service.py` 側で行う。
- `pm_backend/apps/production/scheduler/tasks.py` の `PROGRESS_ONLY` 経路は `recalculate_inventory_for_line` を使わず、`recalculate_progress_qty` を製品単位で直接呼ぶため、この表の対象外とする。

#### 1. `backlog_recalc_service.py:recalculate_inventory`

- **UI画面 / ボタン**:
  - 生産在庫一覧（`ProductionInventory.vue`）→「表示ライン全品番再計算」
  - 仕入在庫一覧（`PurchaseInventory.vue`）→「在庫再計算」
  - 生産計画入力（`ProductionPlanInput.vue`）→「取り込み」（`line_final_only=true`）
  - 生産計画入力（`ProductionPlanInput.vue`）→「保存」（`line_final_only=true`）
  - 仕入計画入力（`PurchasePlanInput.vue`）→「保存」/「取込＋在庫計算」
  - 在庫進度調整（`AdjustmentEditor.vue`）→ ① 再計算ボタン / ② 一括再計算
  - 進度のみ一覧（`ProductionProgressOnly.vue`）→「再計算」（`progress_only=true`）
- **どこから呼ばれるか**: `production/views.py` の `POST /recalculate_inventory` から委譲
- **指定日**: request の `start_date`
- **LT加味日**:
  - `force_from_start=True` なら LT加味日で前倒しせず、指定日をそのまま使う
  - 通常は `resolve_inventory_effective_start_date(line_id, start_dt, end_dt, product_ids=requested_product_ids or None, line_final_only=line_final_only, include_progress=include_progress or progress_only)` で決定
- **対象製品**: request の `product_ids` を `_parse_product_ids()` で解釈。未指定時は `None`（ライン全製品）
- **対象ライン**: request の `line_id`
- **渡すパラメータ**:
  ```
  line_id, effective_start_dt, end_dt,
  include_progress=include_progress,
  line_final_only=line_final_only,
  product_ids=requested_product_ids or None,
  progress_only=progress_only,
  progress_calc_start_date=(start_dt if force_from_start and (include_progress or progress_only) else None),
  force_from_start=force_from_start
  ```

#### 2. `backlog_recalc_service.py:recalculate_inventory_for_products`

- **UI画面 / ボタン**:
  - 生産在庫一覧（`ProductionInventory.vue`）→「表示品番だけ再計算」
  - 仕入在庫一覧（`PurchaseInventory.vue`）→「表示品番だけ再計算」
  - 進度のみ一覧（`ProductionProgressOnly.vue`）→「表示品番だけ再計算」
- **どこから呼ばれるか**: `production/views.py` の `POST /recalculate_inventory_for_products` から委譲し、`recalculate_inventory()` を再利用
- **指定日**: 画面の `start_date` は使わない。表示中品番再計算では「指定日を持たず、必要開始日に直接寄せる」扱い
- **LT加味日**: `resolve_product_recalc_start_date(int(line_id), end_dt, product_ids=requested_product_ids or None, progress_only=is_progress_only)` で決定し、`mutable_data['start_date']` に上書き。その後は `recalculate_inventory()` 側の処理
- **対象製品**: request の `product_ids` を `_parse_product_ids()` で解釈。表示中品番だけに絞る
- **対象ライン**: request の `line_id`
- **渡すパラメータ**: `recalculate_inventory()` と同じ。差分は `start_date` が `resolve_product_recalc_start_date()` の結果に差し替わった状態で渡ること

#### 3. `backlog_recalc_service.py:recalculate_inventory_deep`

- **UI画面 / ボタン**:

  - 仕入在庫一覧（`PurchaseInventory.vue`）→「過去から再計算」

- **対象製品**: request の `product_ids` をそのまま受け、未指定時は `None`

#### 4. `process_realtime_backlog_service.py:recalculate_inventory_for_product_impact`

- **UI画面 / ボタン**: 実績変更（`ProductionRecordEdit.vue`）→ セッション追加・数量変更・削除の各操作（ボタン操作後に自動実行）
- **どこから呼ばれるか**: 実績変更後の波及再計算。`recalculate_inventory_after_session_change` が連産品子を `_resolve_session_recalc_product_ids()` で解決した後、製品ごとに本関数を呼ぶ。影響親品探索 `_collect_impacted_line_recalc_targets(line_id, product_id, plan_date)` の結果ごとに実行
- **指定日**: 引数 `plan_date`（実績変更日）

- **対象ライン**: 起点は引数 `line_id`。BOM 親展開で見つかった親ライン `parent_line_id` ごとに再計算
- **渡すパラメータ**:
  ```
  line_id=target_line_id,
  start_date=start_date,
  end_date=end_date,
  include_progress=True,
  line_final_only=False,
  product_ids=product_ids or None
  ```

### Step 1 補足例: 一括進度調整（`AdjustmentEditor.vue` / `PROGRESS`）のフロー

一括進度調整は、「調整対象日を指定して対象製品を集める」「ライン単位の再計算開始日を決める」「計算器の中で製品ごと・日付ごとに進度を巻き直す」の3段に分かれる。

```text
[画面: 一括進度調整を開く]
  |
  | GET /line-backlogs/batch_adjust_info/
  |   adjust_type=PROGRESS
  |   line_code or process_code
  |   target_date=調整対象日
  v
[batch_adjust_info() が対象製品一覧を返す]
  |
  | 対象製品:
  | - LineBacklog から (product_id, line_id, process_id) を抽出
  | - process_code 指定時はその工程の製品群
  | - line_code 指定時はそのラインの製品群
  |
  | 各製品ごとに calc_start_date を計算:
  | - PROGRESS なので累積LTを使う
  | - calc_start_date = today - (max_parent_lt + 1営業日)
  |
  v
[画面が products[] を line_id ごとにグループ化]
  |
  | 各製品について:
  | - productStartDate = min(調整対象日, row.calc_start_date)
  |
  | 各ラインについて:
  | - lineStartDate = そのライン配下製品の productStartDate の最小日
  | - product_ids = そのライン配下製品の product_id 一覧
  |
  v
[POST /line-backlogs/recalculate_inventory/ を line_id ごとに実行]
  |
  | 渡すもの:
  | - line_id
  | - start_date = lineStartDate
  | - end_date = 画面側で決めた endDate
  | - product_ids = そのラインの対象製品
  | - progress_only = true
  |
  v
[backlog_recalc_service.recalculate_inventory()]
  |
  | 指定日:
  | - request.start_date (= lineStartDate)
  |
  | LT加味日:
  | - resolve_inventory_effective_start_date(...)
  | - 対象製品集合の max cumulative LT で計算
  |
  | 開始日:
  | - effective_start_dt = min(指定日, LT加味日, stock_start_dt)
  |
  v
[recalculate_inventory_for_line(line_id, effective_start_dt, end_date, product_ids, progress_only=true)]
  |
  | 対象製品:
  | - 渡された product_ids を起点にする
  | - ただし内部で RoutingStep 有効性フィルタを再度かける
  |
  | ライン全体の進度用開始日補正:
  | - progress_anchor_start_date =
  |   min(start_date, today - (対象製品集合の max_cumulative_lt + 1営業日))
  |
  | 調整値取得開始日:
  | - adj_start = min(start_date, inventory_calc_start_date, progress_anchor_start_date)
  | - _build_adjustment_maps(line_id, adj_start, end_date, product_ids=...)
  |
  | 計算時ループ(製品単位):
  | - for product_id in product_ids:
  |     recalculate_progress_qty(...)
  |
  v
[recalculate_progress_qty(line_id, product_id, start_date, end_date, ...)]
  |
  | 製品別開始日:
  | - calc_start_date = today - (その製品の max_parent_lt + 1営業日)
  | - calc_start_date < start_date なら effective_start = calc_start_date
  |
  | 需要取得:
  | - LineDemand を [effective_start, end_date] で取得
  |
  | 計算時ループ(日次):
  | - for plan_date in sorted(by_date.keys()):
  |     前日進度を引き継ぐ
  |     当日実績を加算
  |     当日需要(LineDemand)を減算
  |     PROGRESS調整値を加減算
  |     progress_qty / planned_progress_qty を更新
  |
  v
[結果]
  |
  | - 画面で指定した対象製品だけを進度再計算
  | - 開始日は「調整対象日」と「LT加味日」の早い方へ広がる
  | - 実際の進度計算は 製品ループ -> 日次ループ の二重ループ
```

#### 一括進度調整で見えている責務

- `開始日`
  - 画面は `調整対象日` を持つ
  - 画面は製品ごとの `calc_start_date` を使ってライン開始日を前倒しする
  - service はさらにライン全体の LT で `effective_start_dt` を決める
  - progress_calculator はさらに製品別 LT で `calc_start_date` を決める

- `対象製品`
  - 画面は `batch_adjust_info()` の結果から対象製品を集める
  - API 呼び出し時は `line_id` ごとに `product_ids` を渡す
  - calculator はその `product_ids` を受けつつ、内部で RoutingStep 有効性チェックを再実行する

- `計算時ループ`
  - `recalculate_inventory_for_line()` は製品単位のループ
  - `recalculate_progress_qty()` は日付単位のループ
  - 一括進度調整の実処理は `ライン -> 製品 -> 日付` の3段ループとして動く

### Step 1 補足例: 一括進度調整の `effective_start` 逆引きフロー

一括進度調整で `recalculate_progress_qty()` が最後に使う `effective_start` を、逆順で追うと以下になる。

```text
[最後に実際使う開始日]
recalculate_progress_qty(line_id, product_id, start_date, end_date, ...)
  |
  | 製品別LT加味日を計算
  | - calc_start_date = today - (その製品の max_parent_lt + 1営業日)
  |
  | 最終開始日を決定
  | - effective_start = min(start_date, calc_start_date)
  v
[比較相手の start_date]
recalculate_inventory_for_line(...)
  |
  | この関数に入ってきたライン単位開始日を
  | そのまま各製品の recalculate_progress_qty(..., start_date, ...) へ渡す
  v
[ライン単位開始日]
backlog_recalc_service.recalculate_inventory(...)
  |
  | request.start_date を受ける
  | さらに resolve_inventory_effective_start_date(...) で前倒し
  |
  | effective_start_dt =
  |   min(request.start_date, ライン全体LT加味日, stock_start_dt)
  v
[request.start_date]
AdjustmentEditor.vue の一括進度調整
  |
  | lineStartDate を作る
  | - 各製品ごとに productStartDate = min(調整対象日, row.calc_start_date)
  | - 同一ラインでは lineStartDate = productStartDate の最小日
  v
[row.calc_start_date]
batch_adjust_info()
  |
  | 製品ごとに計算
  | - calc_start_date = today - (その製品の max_parent_lt + 1営業日)
  v
[いちばん元の指定日]
一括進度調整画面の target_date
  |
  | = 調整対象日
```

#### この逆引きで見えること

- `effective_start` は `recalculate_progress_qty()` の中で最終確定する
- その比較相手の `start_date` は、画面起点の `調整対象日` から何段か前倒しされたライン単位開始日
- 同じ「製品LT加味日」の考え方が
  - `batch_adjust_info()` の製品別 `calc_start_date`
  - `recalculate_progress_qty()` の製品別 `calc_start_date`
  の2箇所に出てくる
- その間に service 側の「ライン全体LT加味日」も入るため、開始日決定が多段化して見えにくくなっている

### Step 1 補足例: 一括進度調整の開始日関係図

```text
[一括進度調整の開始日だけを追う]
  |
  +-- 1. 指定日
  |     - target_date = 調整対象日
  |
  +-- 2. 製品別LT加味日
  |     - row.calc_start_date
  |     - today - (その製品の max_parent_lt + 1営業日)
  |     - batch_adjust_info() が作る
  |
  +-- 3. 画面の製品別開始日
  |     - productStartDate
  |     - min(target_date, row.calc_start_date)
  |     - AdjustmentEditor.vue が作る
  |
  +-- 4. 画面のライン開始日
  |     - lineStartDate
  |     - 同一ライン内の productStartDate の最小日
  |     - AdjustmentEditor.vue が作る
  |
  +-- 5. service のライン全体LT加味日
  |     - resolve_inventory_effective_start_date(...)
  |     - 対象製品集合の max cumulative LT で計算
  |
  +-- 6. service後開始日
  |     - effective_start_dt
  |     - min(lineStartDate, ライン全体LT加味日, stock_start_dt)
  |     - backlog_recalc_service.recalculate_inventory() が作る
  |
  +-- 7. progress_calculator の製品別LT加味日
  |     - calc_start_date
  |     - today - (その製品の max_parent_lt + 1営業日)
  |     - recalculate_progress_qty() が作る
  |
  +-- 8. 最終開始日
        - effective_start
        - min(effective_start_dt, calc_start_date)
        - recalculate_progress_qty() が最後に使う
```

#### 比較して生まれる開始日

- `target_date` と `row.calc_start_date` を比較して `productStartDate` が生まれる
- 同一ライン内の `productStartDate` を比較して `lineStartDate` が生まれる
- `lineStartDate` と `ライン全体LT加味日` と `stock_start_dt` を比較して `effective_start_dt` が生まれる
- `effective_start_dt` と `calc_start_date` を比較して `effective_start` が生まれる

### Step 2. 条件決定ロジックの分類

`inventory_calculator.py` / `progress_calculator.py` 内の条件決定処理を、以下に分類する。

- service 層へ移すべきもの
- 計算器内部に残してよいもの

候補:

- 開始日補正（在庫: 直親LT、進度: 累積LT、それぞれ別ロジック）
- 進度開始日補正（`progress_calc_start_date` 指定時はそのまま使用、未指定時は累積LTで自動補正）
- RoutingStep除外（`build_effective_routing_range_q` による有効期間レンジフィルタ）
- 調整値取得範囲補正（在庫開始日・進度開始日・要求開始日の最小値に統合）
- 需要取得範囲補正（`inventory_calc_start_date` まで拡張取得）
- 仕損集計の呼び出し（`aggregate_scrap_to_backlog` は `progress_only` 時にはスキップ）
- LT事前計算（直親LT / 累積LT を全対象製品分キャッシュ構築）

### Step 3. 再計算条件の入口を揃える

service 層から `inventory_calculator.py` に渡す条件を明示化する。

現在の `recalculate_inventory_for_line` シグネチャ:

- `line_id`
- `start_date`
- `end_date`
- `include_progress`（デフォルト: True）
- `line_final_only`（デフォルト: False）
- `product_ids`（デフォルト: None = 全製品）
- `progress_only`（デフォルト: False）
- `progress_calc_start_date`（デフォルト: None = 自動補正）
- `force_from_start`（デフォルト: False）

必要であれば将来的に以下も明示化する。

- `inventory_calc_start_date`（現在は内部で自動計算）
- `routing_scope_checked`（現在は常に内部でRoutingStep有効性チェック実行）

### Step 4. 開始日決定を service 層へ寄せる

まずは開始日決定を外へ寄せる。

対象:

- 通常再計算
- deep再計算
- 表示品番限定再計算
- 実績変更波及再計算

### Step 5. 対象製品・対象ライン決定を service 層へ寄せる

対象:

- 連産親/連産子判定
- 通常BOM親ライン展開
- 画面単位の `product_ids` 絞り込み
- 製品ループの責務（現在は `recalculate_inventory_for_line` 内部で製品ループを回しているが、service層で回すか計算器内部に残すかを決める）

### Step 6. inventory_calculator.py / progress_calculator.py の内部補正を削減する

条件決定が service 層へ移ったものから順に、`inventory_calculator.py` / `progress_calculator.py` 内の補正を削減する。

対象候補:

- 自動開始日補正（在庫用 / 進度用で異なるLT計算を内部で実行）
- RoutingStep除外（`build_effective_routing_range_q` による有効期間チェック）
- 条件の再解釈（`progress_only=True` 時の `include_progress` 強制True化など）
- `is_working_day` / `shift_working_days` / `get_prev_working_day` の重複定義（3関数で同じローカル関数を繰り返し定義、共通化候補）
- LT計算の重複（`recalculate_stock_qty` / `recalculate_planned_stock_qty` 内でも個別にLT取得するが、`recalculate_inventory_for_line` でも事前キャッシュしている）
- `_` prefix 関数の外部公開整理（`_get_direct_parent_bom_lead_time` / `_get_max_parent_bom_lead_time` / `_resolve_calendar_working_day` を公開APIとして切り出すか、別モジュールへ移動）

## 6. 最初の実装単位

最初の着手は以下とする。

1. 呼び出し元の棚卸し
2. `inventory_calculator.py` / `progress_calculator.py` 内の条件決定ロジック一覧化
3. `process_realtime_backlog_service.py` を条件組み立て側として整理

理由:

- 今回の連産品不具合と直接関係する
- 変更範囲を service 層中心に留められる
- 計算式本体への影響を最小にできる

## 7. リスク

### 7.1 影響範囲が広い

- 在庫
- 計画在庫
- 進度
- 調整画面
- 実績変更
- 一括再計算
- 購買系（設計変更、自動発注、自動納品リスト）
- 定期タスク（scheduler/tasks.py）

### 7.2 開始日の2段階補正

- データ取得範囲は全製品の最大LTで決定（1段階目）
- 実計算開始日は製品個別LTで決定（2段階目）
- この2段階構造を分離する際、片方だけ変えると調整値欠落や需要不足が起きる

### 7.3 既存挙動との差分が見えにくい

- 数値自体は合っていても、開始日や対象品が変わるだけで結果がズレる

### 7.4 テスト環境整備が必要

- 再計算系は対象日、ライン、製品、BOM構成で結果が変わる
- 条件決定のテストと計算ロジックのテストを分ける必要がある

## 8. テスト方針

- 計算ロジック単体テスト
- 再計算条件決定 service のテスト
- 連産品ケース
- 通常BOMケース
- 親ライン波及ケース
- 調整画面ケース
- 実績変更ケース
- 購買系ケース（設計変更 / 自動発注 / 自動納品リスト）
- 定期タスクケース（scheduler/tasks.py の直接呼び出し）

## 9. 完了条件

以下を満たした状態を整理完了とする。

- `inventory_calculator.py` / `progress_calculator.py` が場面固有の判断を最小限しか持たない
- 再計算条件が service 層で組み立てられている
- 連産品、通常BOM、親ライン波及の再計算条件がテストで保証されている
- 画面別・イベント別の再計算結果が既存期待値と一致する
