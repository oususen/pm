PHASE 1 開発PCに PostgreSQL インストール

MySQLはそのまま残し、PostgreSQL を追加インストールする。

  • PostgreSQL 16 を Windows にインストール（ポート 5432）
  • データベース pm_db を作成
  • ユーザー作成・権限付与
  • psql で接続確認
MySQL はそのまま: 既存の MySQL :3306 には触れない。現行の pm/ アプリは引き続き MySQL で動作する。

pm/ を複製して wanoco/ を作り、PostgreSQL 接続に変更する。

現行 pm/ は変更しない: これらの修正はすべて wanoco/ 内で行う。現行の MySQL 版には一切影響しない。
PHASE 4 wanoco/ の検証

PostgreSQL版アプリが正常に動作するか、開発PCで徹底検証する。

  • python manage.py migrate — 全マイグレーション正常完了
  • python manage.py runserver 8082 — 別ポートで起動
  • MySQL版からテストデータを pgloader で移行して動作確認
  • 主要画面の動作確認（受注一覧・ガントチャート・在庫・進度）
  • 受注展開の安定性テスト（落ちるケースの再現確認）
  • 在庫計算の速度比較（MySQL版 vs PostgreSQL版）
  • APScheduler定時タスクの動作確認
  • JSONFieldの読み書き確認
並行運用: 現行 pm/ (:8081/MySQL) と wanoco/ (:8082/PG) を同時に起動して比較可能。問題があればいつでも pm/ に戻れる。
PHASE 5 在庫計算の DB関数化（オプション）

PostgreSQL版で検証OKの後、重い計算処理をDB関数に移行して高速化を狙う。

対象現状（Python）改善案（PL/pgSQL）
在庫計算 製品×日付のネストループで毎回DB往復 ウィンドウ関数で累積計算を1クエリ実行
計画在庫計算 同上 + 親工程のLTシフト計算 CTE + ウィンドウ関数で一括処理
仕損集計 Python側でフィルタ・集計・書き戻し UPDATE ... FROM で直接集計更新
受注展開 大量の個別INSERT/UPDATE ストアドプロシージャでトランザクション一括
段階的に: まず PHASE 4 でそのまま動くことを確認してから、ボトルネック順にDB関数化を進める。一気にやらない。

Django マイグレーション状態の同期
python manage.py migrate --fake でマイグレーション履歴を登録。
手順 4
シーケンス値の修正
SELECT setval('table_id_seq', (SELECT MAX(id) FROM table));
手順 5
WSL2 + Docker Engine で起動
wanoco/ の docker-compose.yml で全コンテナ起動。SSL証明書配置・HTTPS確認。
手順 6
データ整合性チェック + IP切り替え
主要テーブルのレコード数確認後、旧PCからのIP切り替え。
リスク軽減: 開発環境での並行運用（PHASE 4）で十分検証済みのため、本番移行時のリスクは大幅に低減。問題があれば旧PC（MySQL）にすぐ戻せる。
PHASE 7 ドキュメント更新 + pm/ 統合

本番移行完了後、wanoco/ を正式な pm/ として統合し、ドキュメントを更新する。

参考 併存方式のメリット
項目一括移行（旧プラン）併存方式（本プラン）
現行への影響 コード直接変更 — 戻すのが大変 変更なし — いつでも現行に戻れる
検証の深さ 移行後に問題発覚 → ロールバックが困難 並行運用で比較検証 → 確信を持って移行
DB関数化の試行 移行完了後に別タスクで着手 PHASE 5で検証と同時に試行可能
