# 進度監視画面仕様書

## 目的

各グループのリーダーが、担当ラインで注視する製品の進度を期間マトリクスで確認する。板金専用にはせず、グループとラインの既存紐付を利用する。

## 画面

- URL: `/production/progress-monitor`
- 権限リソース: `production.progress_monitor`（`進捗管理`・`進度のみ`が使う`production.progress`とは独立。2026-10-16に分離）
  - `can_view`: 画面閲覧
  - `can_edit`: 監視対象の追加・編集・無効化
- 生産管理メニューの「在庫・進度」に「進度監視」を表示する。
- 開始日の初期値は当月1日とし、表示期間は30日・60日・90日・120日から選ぶ。
- グループ、お気に入り選択、お気に入り名、★保存、開始日、期間、更新を上部に置く。
- お気に入りの `screen_key` は `production.progress_monitor`、`payload` は `unit_id` だけを保存する。

## 選択可能なグループ

- superuser: `accounts_department.level = unit` の全グループ。
- 一般ユーザー: `UserProfile.unit` と `UserProfile.leader_units` の和集合。
- グループに所属するラインは `accounts_unit_line_mapping` の現在の紐付から取得する。お気に入りへラインを固定保存しない。

## 監視対象

テーブル `production_progress_monitor_target` に以下を保存する。

| 項目 | 内容 |
|---|---|
| monitor_type | 監視モード（`progress`=進度／`inventory`=在庫、デフォルト`progress`） |
| product | 製品マスタFK |
| line | ラインマスタFK |
| display_order | 表示順 |
| memo | メモ、最大500文字 |
| is_active | 有効状態 |
| registered_by | 登録者。ユーザー削除時はNULL |
| created_at / updated_at | 登録日時・更新日時 |

- `product + line` を一意とする（監視モードは区別しない。同一製品・ラインは進度監視・在庫監視のどちらか一方のみ登録できる）。
- 監視対象追加・編集ダイアログで監視モード（進度／在庫）を選択する。既存登録分は `monitor_type='progress'`（進度）として扱う。
- 製品追加候補は `m_product.is_active = true` の全件。品番・品名・半角品名で部分一致検索する。新規の取得件数上限は設けない。
- 監視対象はユーザー個人ではなく共有する。一般ユーザーは担当グループに紐づくラインだけを参照・編集できる。
- 編集権限を持つユーザーは「対象管理」で有効・無効を含む登録済み対象を確認し、無効対象を再有効化できる。

## 進度マトリクス

1. 選択グループから `UnitLineMapping` でラインを取得する。
2. 対象ラインの監視対象を管理用一覧へ返し、そのうち有効な製品・ラインの組み合わせだけを進度表示対象とする。
3. 各監視製品を工程別カードで表示する。左側は監視モード・ライン・工程・品番・品名・メモ、右側は開始日から表示期間分の日付列とする。
4. 画面ヘッダの表示切替ボタンで、カードの数量行を2段階に切り替える。
   - 簡易表示（初期値）: `monitor_type` を問わず「計進・進度・計庫・在庫」の4項目のみ表示する。
   - 詳細表示: 上記4項目に加えて、`monitor_type` ごとのモード別項目を表示する。
     - 進度監視: モード別項目「内示・確定・計画・実績・調整」＋共通4項目
     - 在庫監視: モード別項目「計需・実需・計画・実績・調整・仕損」＋共通4項目
   - 進度監視と在庫監視のカードは同一画面内に混在表示できる。
5. 内示・確定（進度監視）は `LineDemand` を日付・ライン・製品・工程で合計する。工程一致を優先し、工程一致がない場合だけ工程未設定の需要を使用する。
6. 計需・実需（在庫監視）は `LineDemand` ではなく、`LineBacklog.sequence_no = 0` の `order_qty`（後工程の計画数量を集計した需要）・`order_qty_actual`（後工程の実績数量を集計した需要）を使う。最終ラインでは `order_qty`/`order_qty_actual` に受注（LineDemand由来）の数量が反映済みのため、結果として最終ラインの計需・実需は内示・確定と近い値になるが、取得元は常に `LineBacklog` 側である。
7. 計画は `LineBacklog.sequence_no > 0` の `plan_qty` を合計する。
8. 実績・調整・計進・進度・仕損・在庫・計庫は `LineBacklog.sequence_no = 0` の `actual_qty`・`adjust_qty`・`planned_progress_qty`・`progress_qty`・`scrap_qty`・`stock_qty`・`planned_stock_qty` を合計する（進度監視・在庫監視どちらのカードも同じ取得済みの行から読む。新規クエリ・新規計算ロジックは設けない）。
9. `demand_qty_plan` 等へのフォールバックは行わない。在庫監視の「計需・実需」は「在庫/残量一覧」画面の需要行判定ロジック（需要行判定・sequence_no最小行選択）とは別物で、対象期間の全`sequence_no=0`行の`order_qty`・`order_qty_actual`を単純合算する。
10. 期間内データがない有効な監視対象も、工程を「データなし」とした空カードで表示する。
11. 調整の負数は赤字、計進・進度・在庫・計庫の負数は強調した赤字で表示する。
12. カード部分は参照専用とし、再計算・削除操作を設けない。既存の進度計算ロジック・在庫計算ロジック（`inventory_calculator.py`/`progress_calculator.py`）と既存データは一切変更しない。

## API

- `GET/POST /api/progress-monitor-targets/`
- `GET/PATCH/DELETE /api/progress-monitor-targets/{id}/`
- `GET /api/progress-monitor-targets/options/`
- `GET /api/progress-monitor-targets/product-candidates/?search=...`
- `GET /api/progress-monitor-targets/snapshot/?unit_id=...&start_date=YYYY-MM-DD&horizon=30|60|90|120`

APIはログイン認証を要求する。`production.progress_monitor` の権限判定は既存方針どおりフロントエンドUIで行い、バックエンドには同権限のチェックを追加しない。
