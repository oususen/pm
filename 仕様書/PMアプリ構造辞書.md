# PMアプリ構造辞書

## 1. 目的と使い方

本書は、社内AIがPMの画面・業務・正規データソースを取り違えないための全体構造辞書である。ルーター、画面、API、Djangoモデルを根拠に更新する。

- AIは本書をアプリ内部の参照用知識として使う。外部AIへPMのソースコード、個票、全テーブル定義を丸ごと送らない。
- 外部AIへ渡すのは、質問に関係する本書の該当規則と、規約で許可された集計済み結果だけとする。
- 数量の回答は、画面・業務ごとに定めた「正規データソース」を必ず選ぶ。同じ生産事実を複数の実績テーブルから合算しない。
- 本書に数量定義がない機能は「定義確認待ち」とし、AIは数値を回答しない。
- 書込み、更新、削除、DDL、任意SQLは全機能共通で禁止する。詳細は[社内AI運用規約・AI用DB辞書](社内AI運用規約・AI用DB辞書.md)に従う。

## 2. PM全体の業務構造

```text
マスタ
 ├─ 製品・品番変換・BOM・ルーティング・工程・ライン・設備・カレンダ
 └─ 得意先・仕入先・容器・連絡先

受注 ──> 生産計画 ──> 工程作業・生産実績 ──> 在庫・進度 ──> 出荷
                 │              │                     │
                 │              ├─ 仕損・中断         └─ 購買・外注実績
                 │              └─ レーザー・ブレーキ・スポット
                 │
                 └─ 能力・負荷・計画乖離

共通: 品質 / 残業 / シフト / 通知・通話 / 承認 / 設定
```

## 3. 機能領域の全体カタログ

| 領域 | 主な画面・機能 | 主なアプリ | AIの初期扱い |
|---|---|---|---|
| マスタ | 製品、品番変換、BOM、ルーティング、工程、ライン、設備、カレンダ、得意先、仕入先 | `masters` | 基本キー・関連の特定のみ許可。連絡先は不可 |
| 受注 | 受注一覧、CSV取込、内示分析、手入力、未設定ルーティング監査 | `orders` | 「ルーティング未設定の注文品」だけ参照可。その他は定義確認待ち |
| 生産計画 | 生産計画、工程ガント、順序盤、ライン需要、能力・負荷、計画乖離 | `production` | 定義確認待ち。計算ロジックをAIが再実装しない |
| 生産実績 | 工程作業入力、レーザー、ブレーキ、スポット、実績照会、出来高集計 | `production` | 品番指定の生産実績は本書第4章の正規ソースを使用 |
| 在庫・進度 | 製品在庫、部品在庫、引当、安全在庫、進度 | `inventory`, `production` | 定義確認待ち |
| 購買・外注 | 購買計画、検収、納入実績、発注提案、外注進度 | `purchase`, `outsource` | 定義確認待ち |
| 出荷 | 出荷指示、実績、進度、配車、集荷、納期調整 | `shipping` | 定義確認待ち |
| 品質 | 仕損、チェックシート、教育・訓練 | `quality` | 確定仕損のみ初期許可。画像・添付は不可 |
| 勤務 | 残業申請・承認・集計、シフト | `overtime`, `shifts` | グループ集計のみ初期許可。個人情報は伏字化 |
| 通知 | 通知、連絡、通話、録音 | `notifications` | AI参照・外部送信不可 |
| 設定・権限 | ユーザー、権限、承認経路、SMTP、各種計算設定 | `accounts`, `system_settings` | AI参照・外部送信不可 |

## 4. 生産実績照会の正規構造

画面: `pm-ui/src/views/production/ProductionRecordInquiry.vue`  
API入口: `/process-realtime-records/sessions/`、レーザー実績API、ブレーキ実績API  
原則: 品番・工程・選択タブに応じて正規ソースを選び、横断合算しない。

| 実績の種類 | 正規テーブル | 品番 | 数量 | 有効条件 | AIの回答根拠 |
|---|---|---|---|---|---|
| 通常工程 | `t_process_realtime_record` | `product_code` | `qty` | `record_type='PRODUCTION'`（仕入の入荷実績は `record_type='PURCHASE'` のため含まれない） | 工程実績 |
| 工程作業セッション | `t_process_work_session` | `product_code` | `production_qty` | 画面のセッション条件（計画日／実施日、作業・終了状態）に従う | セッション実績。定義確認を終えるまで単独の標準回答には使わない |
| レーザー（板金タブ） | `t_laser_actual` + `t_laser_actual_detail` | 明細の`product_code` | 明細の`total_qty` | ヘッダが`operator_action='END'`、明細が`detail_type='COMPONENT'` | レーザー実績。START、PAUSE、未終了を除外 |
| ブレーキ | `brake_line_record` | `product_code`または製品FK | `qty` | `operator_action='END'` のみ | ブレーキ実績。START・PAUSE・TEMP_ENDは生産数に含めない |
| スポット | スポット専用実績と関連セッション | 製品・計画行 | 実績数量 | スポット画面の専用集計条件 | 定義確認待ち |

### 4.1 レーザー実績の確定例

質問が品番 `YD40006000-00` の2026年8月生産数の場合、レーザー実績は次の条件で求める。

```text
t_laser_actual_detail.product_code = 'YD40006000-00'
AND t_laser_actual.work_date BETWEEN '2026-08-01' AND '2026-08-31'
AND t_laser_actual.operator_action = 'END'
AND t_laser_actual_detail.detail_type = 'COMPONENT'
→ SUM(t_laser_actual_detail.total_qty)
```

この定義で、実績照会画面の2026年8月の93個と一致することを確認済み。レーザー実績が存在する品番は、同じ数量を`ProcessRealtimeRecord`から追加合算しない。

## 5. AIの質問処理構造

```text
質問
 ├─ DeepSeek: 読み取り専用ツールの必要な呼出順を判断
 │   ├─ 品番を含む場合は品番マスタを完全一致で照合
 │   └─ 正規データソース規則に対応する集計ツールを呼ぶ
 ├─ PM: 引数・期間・品番確定を検証し、固定集計関数だけを実行
 ├─ PM: 根拠テーブル、条件、期間、集計値を返却
 └─ DeepSeek: 伏字化済み質問と集計済み結果だけを基に回答
```

品番を会話中に指定した場合、後続の「今月の生産数」のような質問にも引き継ぐ。品番マスタに存在しない場合は、全品番集計をせず未登録として回答する。

## 6. 主な関連データ

```text
m_product
 ├─ m_bom ──< m_bom_item ──> m_product
 ├─ m_routing ──< m_routing_step ──> m_process ──> m_line
 ├─ t_process_realtime_record
 ├─ t_process_work_session ──> 開始/終了のリアルタイム記録
 ├─ t_laser_actual_detail ──> t_laser_actual
 ├─ t_scrap_record
 └─ brake_line_record

m_line / m_process
 ├─ t_line_demand
 ├─ t_line_backlog
 ├─ t_line_plan
 └─ 生産計画・進度・在庫計算
```

## 7. 外部AIへ渡す構造情報

外部AIへ渡せるのは、質問に該当する次の最小情報だけとする。

| 質問例 | 渡す構造規則 | 渡す集計結果 |
|---|---|---|
| 「品番Aの8月生産数」 | 選定した実績ソース、品番完全一致、終了済み条件 | 日別数量、合計、記録件数、根拠名 |
| 「仕損の多い理由」 | 確定仕損の条件、理由別集計規則 | 理由別の集計数量・件数 |
| 「板金の残業」 | 残業申請の対象状態、グループ条件 | グループ合計時間、承認段階別集計 |

渡さないもの: 全ソースコード、全テーブル定義、個票、氏名・ログインID・連絡先、認証情報、添付ファイル、未集計明細。

## 8. AI利用区分と拡張手順

| 区分 | 状態 | AIの動作 |
|---|---|---|
| A | 正規データソース・数量定義・期間条件を確認済み | 固定集計関数で参照可 |
| B | 個人情報を含むが伏字化方法を確認済み | 最小項目で限定参照可 |
| C | 画面・モデルは存在するが数値定義が未確認 | 回答せず「定義確認待ち」とする |
| D | 権限、認証、設定、連絡先、通話、添付 | 参照・外部送信不可 |

新しい画面をAI対象へ追加する順序は、(1)画面のAPI呼び出し、(2)バックエンドの集計ロジック、(3)実データとの照合、(4)正規ソースと二重計上防止条件の記録、(5)読み取り専用集計関数の実装、(6)外部送信項目の決定、とする。
