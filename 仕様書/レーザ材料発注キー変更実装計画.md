# レーザ材料発注キー変更実装計画

## 背景

- 対象: `LaserWeeklyMaterialOrderProgress`（`t_laser_weekly_material_order_progress`）。
- 旧キーは `(plan_start_date, material, required_date, supplier)`（条件 `is_manual=False`）。MySQL では条件付き一意制約が作られないため、DBでは効いていなかった。
- 3週間を表示する材料発注画面で、どの週から保存したかにより同じ発注が別の行になり、不具合の原因になっていた。
- これを `(material, required_date, supplier)` で1行にする。

## BOSSが確定した業務ルール

- 同じ材料・日・仕入先を複数行で持っていたのは「注文書作成後のロック」と「発注後の納期調整」のためだけ。今後は行を分けず、ロックの判定で守る。
- ロックが必要なのは「注文書作成後」と「納期調整の変更を保存した後」。納期調整中（開始〜保存の間）は、その調整期間のロックを外して編集できる。
- 納期調整で、ロック期間の外の日へ納期を移すことはない。

## BOSSの決定（Q1〜Q10）

| No | 決定 |
|---|---|
| Q1 | 重複統合で、`plan_start_date` がロックされた週に当たる行が1行ならその行を残す（2行以上なら例外で止める） |
| Q2 | ロックされた週の行がない組は、`(plan_start_date, updated_at, id)` が最大の行を残す |
| Q3 | 消す行に入荷実績（`LaserMaterialReceipt`）がつながっていたら例外で止める |
| Q4 | `plan_start_date` は残す（null 許可は現状どおり）。POST では「最後に保存した週」として書く |
| Q5 | 範囲外 |
| Q6 | A'：ロックで飛ばした組のうち、送られた `order_lots` / `order_sheets` がDBの値と違うものだけ `skipped_locked_changes` で返す（DBに行がなく送られた値が0以外の場合を含む）。`skipped_locked_count` も返す |
| Q7 | 範囲外（材料入荷で手数0の行を出さない条件は現状どおり） |
| Q8 | 手数0でも行を作成・更新し、削除しない |
| Q9 | 範囲外：`LaserWeeklyMaterialOrder.vue:424` の `toISOString` 使用と、`order_created` 未設定時のロック判定がフロント（ロックする）とバック（ロックしない）で食い違っている件 |
| Q10 | 材料発注集計の値が二重計上から正しい値に変わることの周知は、反映時にBOSSと相談する |

## 今回の実装内容（単位1a）

### モデル（`pm_backend/apps/production/models_laser_weekly_plan.py`）

- 制約 `laser_weekly_material_order_progress_unique` を削除し、条件なしの `UniqueConstraint(fields=['material', 'required_date', 'supplier'], name='laser_weekly_material_order_key_unique')` を追加。
- 手動追加用の `laser_weekly_material_order_manual_unique`（`(material, delivery_date, supplier)`、条件 `is_manual=True`）は変更していない。MySQL では条件付きのため作成されていない。

### マイグレーション

- `0116_merge_laser_material_order_duplicate_rows`（RunPython、reverse は noop）
  - 承認データから、ロックされた `(supplier, date)` → `{start_date}` を作る（`route_config.item_key='laser_material_order'`、status `created`（`order_created` が True のときだけ）/`reviewing`/`approved`/`sent`、`lock_start_date`〜`lock_end_date`、週は `context.start_date`。旧 `_build_locked_plan_starts` と同じ条件）。
  - 手動追加以外で `required_date` が NULL でない行を `(material_id, supplier, required_date)` でまとめ、2行以上の組ごとに Q1/Q2 で残す行を決める。ロックされた週の行が2行以上の組があれば対象キーを出して例外。
  - 消す行に入荷実績があれば例外（Q3）。残す行以外を削除。全体を1トランザクションで実行。
  - 統合処理は `merge_duplicate_order_rows(OrderProgress, Receipt, ApprovalRequest)` に切り出し、テストから呼べるようにした。
  - 依存: `accounts.0072`、`production.0115`。
- `0117_laser_material_order_key_unique`
  - 旧制約を RemoveConstraint、新制約を AddConstraint。統合後に一意索引を作るため 0116 と分けた。

### API（`pm_backend/apps/production/views_laser_weekly_plan.py`）

- `_build_locked_plan_starts` を削除し、`_build_locked_supplier_dates(date_start, date_end) -> set[(supplier, date)]` を新設。
  - 判定条件は旧関数と同じ。加えて `material_order_adjustments[supplier].editing` が真の承認は、調整期間（adjustment の `lock_start_date`〜`lock_end_date`）の日をロックから外す。判定は承認ごとで、どれか1つでもロックならロック（フロント `isAdjustmentEditingDate` / `isApprovalDateLocked` と同じ）。
- `material-order-progress` GET
  - `display_start` / `display_end` があれば、`required_date` が期間内の手動追加以外の行を `items` で返す。
  - `overlapping_items` / `locked_items` は空配列で返す（単位1bで削除予定）。
  - `display_start` / `display_end` がない（または日付として不正な）場合は、暫定で従来どおり `plan_start_date` で絞る。扱い（残す／400）はBOSS確認待ち。
- `material-order-progress` POST
  - 先に全件検証（不正値があれば何も保存しない）、全体を `transaction.atomic`。
  - キー `(material, required_date, supplier, is_manual=False)` で `update_or_create`、`plan_start_date` は defaults。
  - 保存範囲（送られた `required_date` の最小〜最大）で `_build_locked_supplier_dates` を求め、ロックされた `(supplier, date)` は `update_or_create` もSATO行の削除もしない。
  - 返却に `skipped_locked_count`・`skipped_locked_changes` を追加（Q6 A'）。手数0も作成・更新（Q8）。
- `material-receipts` GET
  - 週をまたいで行を選ぶループと `all_receipts_by_key` による入荷実績の集約をやめ、候補の行をそのまま使用。手数0の行を出さない条件は維持（Q7）。
  - `source_status` は新しいロック集合に `(supplier, required_date)` が含まれるかで判定。
- 注文書 Excel（`material_order_excel`）・PDF（`_build_material_order_pdf`）
  - `plan_start_date=...` の条件を外し、仕入先・期間（`delivery_date`）・手数0以外で抽出。手動追加行は従来どおり含める。`plan_start_date` は承認の検索とファイル名にだけ使う。
- `material_order_summary` と手動追加（`is_manual`）のコードは変更していない。
