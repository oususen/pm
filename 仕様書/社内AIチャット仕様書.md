# 社内AIチャット仕様書

## 目的

社内利用者が、ローカルQwenまたはDeepSeek APIを選択して質問し、社内データに基づく回答やチャート・報告書を取得する。

社内AIの業務目的、DBアクセス範囲、外部API送信、禁止操作は、[社内AI運用規約・AI用DB辞書](社内AI運用規約・AI用DB辞書.md) に従う。
画面ごとの業務構造、正規データソース、集計規則は、[PMアプリ構造辞書](PMアプリ構造辞書.md) に従う。

## 実行方式

- 画面上で「DeepSeek API」と「ローカルQwen」を切り替えられる。DeepSeek API選択時は「DeepSeek V4 Pro（高精度）」と「DeepSeek Flash（高速）」を切り替えられる。初期選択は幹部会での実演を想定して DeepSeek V4 Pro とする。
- DeepSeek API選択時は、質問・会話履歴・回答に必要なDB集計結果をDeepSeekへ送信する。APIキーはバックエンドの `DEEPSEEK_API_KEY` 環境変数だけで管理し、画面・ソースコード・Gitには含めない。
- DeepSeek API選択時は、DeepSeekが非思考モードの関数呼び出しで読み取り専用ツールを選ぶ。生産数を照会する場合は、品番マスタ検索を行ってから集計ツールを呼ぶ。PM側がツール実行とデータ範囲の検証を担当し、DeepSeekは任意SQLやDB更新を実行できない。
- ローカルQwen選択時は、PC内で動作する Ollama の `qwen3:4b-instruct`（Qwen3-4B-Instruct-2507）を使用し、外部AIサービスへ質問・データを送信しない。
- 導入済みの `qwen3:4b` は実体がThinking-2507で、Ollamaの `thinking.values` が `[true]` の思考専用モデルだった。`think:false` の指定だけでは通常回答モードに変更できないため、このチャットではInstruct版を明示して使用する。
- Instruct版の生成設定は `think:false`、`temperature:0.7`、`top_p:0.8`、`top_k:20`、`min_p:0`、`num_ctx:4096`。モデルの保持時間は10分とする。

## 処理フロー

質問を受け取った際、以下の優先順で処理を振り分ける。

1. **パターンマッチ即回答**: 「北村さんの8月の残業」のように氏名・月が明示された残業照会は、Qwen呼び出しなしでDBから直接集計して回答する。
2. **DeepSeekによるツール調査／Qwenの固定集計**: DeepSeekでは、生産数・仕損・中断・残業などDB根拠を要する質問に対し、モデル自身が品番マスタ検索・許可済み集計ツールを必要な順番で呼び、集計結果を基に自然文で回答する。ローカルQwenでは既存の固定集計を使う。いずれもチャートや報告書の生成に対応する。
   - このチャットは本社の生産管理を基本対象とする。
   - 品番を会話内で明示した場合は、続く生産数質問でもその品番を引き継ぐ。品番マスタに存在しない場合は全品番集計を行わず、未登録であることを回答する。
   - 品番に空白・ハイフン・英字大小の表記ゆれがある場合は正規化して照合する。完全一致しない場合は近い候補を最大3件提示し、AIが候補を勝手に選んで集計しない。
   - AIが示した「1. 生産数」「2. 仕損」「3. 残業」の選択肢に番号だけで返答した場合は、直前の選択肢を業務質問として復元し、直近15件の会話から正式品番と直近の対象期間を引き継いで集計する。
   - 個人別残業は `overtime.personal_summary` の閲覧権限を持つ画面だけで利用できる。DeepSeekには一時ID・期間・合計時間・しきい値超過者だけを渡し、申請明細・理由・連絡先は渡さない。
   - ローカルQwenで本人残業の集計直後に「残業多いね」「内訳は？」などの感想・説明要求を受けた場合は、前回の本人集計結果を会話文脈として渡す。新しい期間・グループ・氏名を含む質問はこの扱いにせず、従来の集計経路を使う。比較基準がないため、Qwenは残業が多い・少ないと断定しない。
3. **一般会話**: 上記に該当しない質問は、選択中のモデルへ会話を渡して回答する。質問文と起点画面に合う正式原本のMarkdown断片をRAGで最大4件付与する。対象は、AI設定で有効な「PMアプリ構造」「マニュアル」「手順書」「安全・運用規約」の区分だけとし、READMEの案内文やリポジトリ全体は渡さない。AI設定で登録したPDF、Excel（`.xlsx` / `.xls`）、CSV、TSV、画像（PNG / JPG / WEBP / BMP）も同じ区分で検索する。画像はローカルTesseract OCRで文字を抽出してから検索する。さらに利用者がチャットで明示添付した画像は、AI設定の許可時にOpenRouterの画像対応モデルへ縮小画像を一時送信して、写真・設備・帳票の見た目を判定できる。明示添付PDFは先頭3ページを画像化して同じモデルへ一時送信できる。全ページを送らないPDFでは、AIは回答内に確認済みページ数と未確認ページ範囲を明記し、未確認範囲を推測しない。元資料は `media/ai_knowledge/` に保存し、抽出本文および送信用縮小画像は保存しない。DB数値が必要な回答では、RAGの文章より読み取り専用DBツールの結果を優先する。
- チャット入力欄で資料を添付した場合は、資料をAIナレッジへ登録し、その会話では添付資料だけをRAG検索する。明示添付は利用者自身の今回限りの指定であるため、一覧上の資料有効/無効にかかわらず参照・画像化する。新しい会話にすると資料指定を解除する。添付しない会話は従来どおり全有効資料を自動検索する。
- AI設定にはOCRアプリの状態表示とOCRテストを設ける。テスト画像は永続保存せず、一時ファイルでTesseractへ渡して認識結果だけを返す。本番DockerのバックエンドイメージにはTesseract本体と日本語・英語言語データを組み込む。OCR共通機能の詳細は [OCR・文書読取仕様書](OCR文書読取仕様書.md) に従う。
- 全画面AIチャットには、`settings.ai` の編集権限を持つ利用者向けに「RAG資料庫」登録入口を表示する。登録資料は会話限定の添付ではなく、`media/ai_knowledge/` に原本を保存し、以後の通常チャットのRAG検索対象にする。資料名・区分・有効状態・保存先・登録日時はDBで管理する。一般のAI利用者は資料を登録できない。将来PostgreSQLへ移行した後は、原本の保存方法を維持しつつ、分割テキストと埋め込みベクトルをRAG用テーブルへ追加できるようにする。

## 対象データと安全性

- 業務データは読み取り専用で集計する。AIは業務データを更新しない。ただし、分析機能で利用者が承認したSQL・Python・承認状態は、PM本体DBの`ai_analysis_template`へ保存する。
- 個人の評価・順位付けには使わない。
- 作成した文書（報告書ファイル）は画面からダウンロードされ、サーバーには保存されない。会話内容は「会話履歴」のとおり本人用に保存する。
- 回答には根拠レベルを表示する。DB集計・マスタ検索・AI用DB辞書SQLに基づく回答は「DB集計済み」、正式ナレッジ原本を参照した回答は「正式ナレッジに基づく」、いずれにも該当しない回答は「一般回答（PMデータは未確認）」とする。根拠データと対象期間の表示は従来どおり行う。
- 表・Excelでの出力: 利用者が「表で出して」「Excelにして」などと求めたとき、DeepSeek/OpenRouterのAIは回答にMarkdownの表を書き、ツール `request_excel_export`（引数なし。DBへはアクセスしない）を呼ぶ。ローカルQwenは同じ要求にMarkdownの表で回答し、サーバーは表の形式を確認して `excel_export: true` を付ける。チャット画面とドロワーは、その回答にだけ「回答の表をExcelでダウンロード」ボタンを出す。Excelは回答本文のMarkdownの表をブラウザ内で `.xlsx`（表が複数ならシート分け、ファイル名 `社内AI_表_YYYY-MM-DD.xlsx`）にして保存し、サーバーには送らない・保存しない。`1,272` のようなカンマ付きの数字は数値にし、先頭が0のコード（`00833` など）は文字列のまま保つ。Excelの中身はAIが回答に書いた表であり、DBの生の値ではない。外部AIではツールを呼ばなければ、QwenではMarkdownの表で回答しなければ、ボタンは出ない。
- チャット画面・ドロワーの操作（フロントエンドのみ。API・DBは変更しない）:
  - 回答のコピー: 社内AIの各回答の下にコピーボタンを表示する（ブラウザのクリップボード権限が必要）。
  - 応答の中止: 応答待ちの間、送信ボタンが中止ボタン（■）に変わる。画面の待ちを止めて応答を捨てるだけで、サーバー側の処理（AIプロバイダへの問い合わせ）は止まらない。
  - 再送信: 応答のエラー時と中止時に、直前の質問をもう一度送る「再送信」ボタンを表示する（成功した回答の再生成ではない）。ドロワーでは添付資料も同じものを使う。
  - 履歴の切り捨て通知: AIへ渡す会話履歴は直近14件（質問直前までの発言）までで、これを超える会話では、入力欄の上に「古い発言はAIへ渡していません」と表示する。
  - 文字数: 質問は1200文字までとし、入力中に `n/1200文字` を表示する。超えたら送信できない。
  - 有料モデルの確認: DeepSeekを選択したとき、およびOpenRouterの有料モデル（`google/gemma-4-26b-a4b-it`）を利用者が選択したときは、確認ダイアログ（「DeepSeekは有料です。使いますか？」「このモデル（Gemma 4 26B A4B）は有料です。使いますか？」）を表示する。キャンセルすると選択前のAI・モデルへ戻す。同じ画面を開いている間は、それぞれ1回承認すれば再確認しない。パネルを開いた直後の初期選択モデルでは確認しない。有料モデルのIDは `AIChatDrawer.vue` の `OPENROUTER_PAID_MODELS` で管理する（フロントエンドのみ。API・DBは変更しない）。
  - 音声入力: 入力欄の横のマイクボタンで録音し（最大60秒）、もう一度押すと文字にして入力欄の末尾へ足す。自動送信はしない。録音はブラウザの `MediaRecorder` で行い、マイクの許可が必要。文字起こしは `POST /api/ai/transcribe/`（下記）で行う。スマホのキーボードの音声入力とは別に使える。

## AI分析機能（実装予定）

既存の社内AIチャットは、業務データの調査・検索と質問応答に使用する。利用者が承認した分析案に基づくSQL・Python・グラフ・報告書の作成は、別の分析画面で行う。詳細は[AI分析基盤仕様書](AI分析基盤仕様書.md)に従う。

### データ参照と分析実行

- 分析画面のAIは、PM本体テーブルを直接参照しない。`pm_db`内の`v_ai_...`ビューだけを`pm_ai_reader`で`SELECT`する。
- 初期段階では、AIは公開済みビュー内の全行を参照できる。ビュー・フィールド・期間ごとの細かな取得制限は、後段のAPI承認機能で追加する。
- AI生成Pythonは、専用Docker実行コンテナが提供する読み取り専用操作を通じて、AI用ビューを`SELECT`できる。一時DuckDB内では中間テーブルの作成、更新、削除、集計を許可する。
- Python実行はDjango本体プロセス内の`exec`では行わない。`analysis-runner`専用Dockerコンテナを`pm_internal`内に置き、Djangoから内部HTTPで実行依頼する。生成PythonへMySQL接続情報を渡さず、PM本体テーブルの更新権限、元テーブルへのアクセス権限、外部ネットワーク権限、ホスト側の任意ファイル読書込み権限を与えない。
- Djangoだけが`pm_ai_reader`で承認済みビューを取得し、runnerの一時DuckDBへ渡す。生成Pythonの`load_view()`は、この取得済みスナップショットだけを読む関数であり、MySQLへ直接接続しない。Windows開発環境でもDocker Desktopのrunnerを使用する。
- 一時DuckDBは分析処理ごとに作成し、正常終了、失敗終了、中断のいずれでも削除する。一時DuckDBの編集はPM本体データへ影響しない。
- 初期段階の分析対象は`v_ai_purchase_receipt`と`v_ai_shipment`だけとする。生産、仕損、中断、残業の分析は、対応ビューの作成・検証後に有効化する。
- 外部AIへ自動送信する情報は、ビュー定義、公開フィールド、分析目的、集計結果に限る。明細行の送信は、運用規約に従う伏字化と利用者承認がある場合だけ許可する。

### 承認とテンプレート

1. AIが分析目的・手順を提示し、利用者が承認する。
2. AIが必要なビュー・フィールド・資料を提示し、利用者が承認する。
3. AIがSQL・Python・グラフ・報告書を作成・実行し、利用者が結果を検証する。
4. 利用者が承認した分析は、PM本体DBの`ai_analysis_template`へ保存し、システム管理者へメールで確認依頼を送る。
5. 利用者が承認したテンプレートは管理者承認待ちとして利用可能にする。再利用時には「システム管理者未承認」の警告を常に表示し、実行前に確認を求める。却下時は、却下理由を保存して利用停止にし、システム管理者が正しいテンプレートを作成して利用者へ通知する。

テンプレートを本番コンテナのソースコードやGitへ保存・コミットしない。SQL、Python、利用ビュー、分析条件、利用者、管理者、状態、版、却下理由、置換先、各日時は`ai_analysis_template`で永続管理する。


## API

実装は、生産管理アプリから独立した `ai` アプリで管理する。`ai/views.py` はHTTP入口、`ai/services/chat_service.py` の `AIChatAPIView` が業務ロジックを担当する。旧 `production/views_ai_demo.py` と `/api/production-ai-demo/`（`ProductionAIDemoView`という名称だった頃の互換入口）は削除済み。`/api/ai/chat/` に一本化されている。

- `GET /api/ai/chat/`: Qwen・DeepSeek・OpenRouter各プロバイダのAPI準備状態を返す。`?screen_context=元パス` を付けると、起点画面の対応状況（`screen.supported`・`screen.coverage`・`screen.common_coverage`）も返す。
- `POST /api/ai/transcribe/`: チャットの音声入力。`multipart/form-data` の `audio`（webm・mp4・m4a・ogg・wav・mp3、10MB以内、60秒以内）を受け取り、PC内のWhisper（通話録音の文字起こしと同じ `faster-whisper` とモデル `WHISPER_MODEL_SIZE`、日本語固定、業務用語のヒント `WHISPER_INITIAL_PROMPT` を共用）で文字にして `{"text": ...}` を返す。`ai.chat` の権限が必要。音声は一時ファイルとして処理後すぐ削除し、保存しない。音声・文字とも外部へは送らない。通話の文字起こしと同時に動かないよう、モデルの推論は排他制御する。開発PC（CPU）での測定では、`large-v3` は音声の約2.2倍の時間がかかる（17.8秒の音声に約40秒）。モデルが常駐設定でない場合は、終了後にモデルを解放するため、次の利用時に読み込みの時間（10〜20秒）が加わる。
- `POST /api/ai/chat/`: `message`、直近会話、`provider`（`deepseek`・`qwen`・`openrouter`）、外部プロバイダ利用時の`model`を受け取り、以下のいずれかで回答する。
  - パターンマッチ即回答（残業個人照会、Qwen利用時のみ）
  - DB集計結果＋選択モデルの自然文回答（チャート・報告書含む。表の出力を求められたとき、外部プロバイダはツール呼び出し、ローカルQwenはMarkdown表の形式確認により `excel_export: true` も返す）
  - 選択モデルの一般会話

## 会話履歴

- 会話は `ai_conversation`（`AIConversation`）に保存する。1会話＝1行で、`messages`（JSON）に画面表示と同じ形式の発言一覧を持つ。ほかに利用者、起点画面ID、最後に使用したプロバイダ、タイトル、作成・更新日時を持つ。
- 質問に対してAIの回答を受信できた時点で自動保存する。新規会話は初回回答時に作成し、以降は同じ会話を更新する。回答取得に失敗した往復は保存しない。
- タイトルは最初の質問文の先頭40文字とする。
- 起点画面は元パスをそのまま保存せず、`resolve_screen_context` で `production` などの画面IDへ正規化して保存する（クエリ文字列や画面入力値を残さない）。
- 一覧・再開・削除は本人の会話だけが対象で、他の利用者の会話は取得・更新・削除できない。作成・更新には `ai.chat` 権限をサーバー側でも確認する。
- 保存される回答本文には、権限者の画面で復元された氏名や個人別残業時間が含まれる場合がある。閲覧は本人のみ。
- 保存期間はAI設定の「会話履歴の保存期間（日）」（`ai_data_policy.conversation_retention_days`）で決める。0は無期限（初期値）。最後に更新された日時（`updated_at`）から指定日数を過ぎた会話は、誰かが履歴一覧を開いた時、または会話を保存した時に、全利用者分まとめて削除する。定時タスクは使わない。
- 画面: フルページ画面はヘッダーの「履歴」、ドロワーは🕘ボタンで一覧を開く。項目クリックで再開、×で削除（確認あり）。「新しいチャット」／＋で新しい会話を始める。ドロワーは起点画面が変わると新しい会話になるが、それまでの会話は履歴から再開できる。

| API | 内容 |
| --- | --- |
| `GET /api/ai/conversations/` | 本人の会話一覧（本文なし、更新日時の新しい順、30件ずつ） |
| `GET /api/ai/conversations/{id}/` | 会話1件の全文 |
| `POST /api/ai/conversations/` | 新規作成 |
| `PATCH /api/ai/conversations/{id}/` | 発言一覧・プロバイダの更新 |
| `DELETE /api/ai/conversations/{id}/` | 削除 |

## AIアプリの権限

- AI画面は `ai.chat` の閲覧権限で表示する。`ai.chat` は `ai` 親権限へフォールバックしない。
- 分析画面は新規の`ai.analysis`で制御する。`can_view`で画面・利用可能テンプレートを閲覧でき、`can_edit`で分析案の承認、実行、テンプレート候補の保存をできる。`ai.analysis`は`ai`親権限へフォールバックしない。
- `管理者承認待ち`と`正式`のテンプレートは`ai.analysis`を持つ利用者が再利用できる。`却下`と`置換済み`は再利用候補に表示しない。作成者は自分の履歴を確認でき、システム管理者は全履歴を確認できる。
- テンプレートの承認・却下・訂正・置換は`settings.ai`の`can_edit`を必要とする。`ai.analysis`は、権限選択肢だけでなく`UserPermission.RESOURCE_CHOICES`へ必ず追加する。
- 個人別残業集計は、AI画面の利用可否とは別に `overtime.personal_summary` の閲覧権限を必要とする。
- 本人の残業集計（`get_my_overtime`）は、`overtime.personal_summary` の権限を必要とせず、`ai.chat` を持つ利用者なら誰でも自分の分だけ照会できる。対象ユーザーはサーバーが `request.user`（ログイン者）に固定し、AIの引数には氏名・利用者IDを含めない（他人の分は指定できない）。対象データ・集計は個人別残業と同じ（`OvertimeApplication`のうち時間外・休日出勤、状態は申請中〜最終承認済み。下書き・却下は除く。`ai` 専用の読み取り接続で取得）。結果には氏名を含めず、時間と件数だけを外部AIへ渡す。ツール管理設定（`ai_tool_policy`）で画面ごとに無効にでき、初期設定は本社横断（`ai_home`）と勤務（`overtime`）で有効（`ai/0016`）。DeepSeek/OpenRouterはツール `get_my_overtime` を呼ぶ。ローカルQwenはツールを使わず、「私／わたし／自分の(…)残業」の形の質問をサーバー側で検出して同じ集計を行い、Qwenへ氏名・利用者IDを渡さない。班・グループ・達・たち・チーム・全員・みんな・皆・部門・部署・課・係を含む質問は本人の分として答えない。月の指定がなければ今月の分を答える。ツール管理設定で `get_my_overtime` が無効な画面では、Qwenでも本人照会を行わない。権限のない利用者が他人の名前で残業を聞いた場合は、権限がないため答えられない旨を回答する。
- AI設定は `settings.ai` で画面UIを制御する。設定変更には `can_edit` を必要とする。

## AI管理設定

AI設定画面では、任意のSQL・任意テーブル・任意フィールドを登録しない。固定カタログにある安全な機能だけを有効・無効にする。

| 設定区分 | 保存先 | 内容 |
| --- | --- | --- |
| プロバイダ・モデル | `ai_provider_config` | DeepSeek / ローカルQwen の有効状態と既定モデル。APIキーは保存せず環境変数で管理する |
| 画面別ツール | `ai_tool_policy` | 画面起点ごとに公開する固定の読み取り専用ツールと、DeepSeekへ集計結果を送る可否。AI用DB辞書SQLもこの一覧で有効・無効を管理する |
| 外部送信方針 | `ai_data_policy` | 集計結果の外部送信、権限者の個人別集計、明示添付画像・PDFのOpenRouter送信、外部送信する集計行数上限、会話履歴の保存期間（日・0は無期限、上限3650日） |
| 分析実行設定 | `ai_analysis_execution_policy` | 分析案キャッシュ有効期限、Python最大実行時間、最大メモリ、CPU上限、取得行数の上限（暫定）。初期値は60分・300秒・2048MB・1コア・100,000行。編集可能範囲は5〜480分・30〜600秒・512〜4096MB・0.5〜2コア・1,000〜100,000行。次に開始する分析ジョブから適用する |
| ナレッジ登録 | `ai_knowledge_source` | PM構造は `仕様書/PMアプリ構造辞書.md` と本仕様書、マニュアルは `pm-ui/public/manual/`、安全・運用規約は `仕様書/社内AI運用規約・AI用DB辞書.md`、手順書は `apps/ai/knowledge/procedures/` を検索対象にする利用状態 |
| 追加ナレッジ資料 | `ai_knowledge_document` | AI設定から登録するPDF、Excel、CSV、TSV、画像の原本。資料名、区分、保存パス、有効状態のみを保持し、15MBを上限とする。画像はローカルOCRで文字化し、画像本文は保存しない |
| 横断参照の定義 | `ai_cross_screen_access_policy` | 起点画面、追加参照領域、利用目的、有効状態、外部AI送信可否。固定の画面領域だけを組合せとして登録する |

初期設定では集計済みのデータをDeepSeekへ送ること、利用者が明示添付した画像・PDFをOpenRouterへ送ることを許可し、個人別集計は `overtime.personal_summary` を持つ利用者に限って許可する。画像は最大辺1600px・最大4MBの送信用JPEGへ一時変換し、PDFは先頭3ページを画像化する。元画像・PDFおよび送信用画像は追加保存しない。氏名・ログインID・連絡先・未集計明細は外部送信しない。

分析実行設定は`settings.ai / can_edit`を持つ利用者だけが変更できる（権限制御はフロントエンドUIのみ。設定APIは権限判定を追加しない）。設定値は、有効期限5〜480分（1分単位）、最大実行時間30〜600秒（1秒単位）、最大メモリ512〜4096MB（128MB単位）、CPU上限0.5〜2コア（0.5コア単位）、取得行数の上限1,000〜100,000行（1,000行単位、暫定）の範囲でAPI側でも検証し、範囲外・0・空欄は保存しない。設定変更は実行中の分析には影響させず、次に開始する分析ジョブからrunnerへ渡す。Docker Composeの実行可能上限を超える設定値では、分析を開始しない。

### 横断参照（質問ごとの承認）

- 起点画面のAIは、その画面の業務領域とAI用DB辞書だけを参照する。別画面のテーブル・集計は、通常の会話中には参照しない。
- システム管理者は `/settings/ai` の「横断参照の定義」で、起点画面、追加参照領域、利用目的、外部AI送信可否を組合せとして登録する。AIは必要な別領域の参照を要求できるが、任意のテーブル名・列名を直接参照できない。未定義なら管理者へ定義を依頼する。
- AIが別領域のデータを必要とすると、定義済みの組合せに限り「今回だけ許可」「許可しない」を表示する。承認はその質問の再実行時だけに渡し、会話全体・次の質問・会話履歴には持ち越さない。
- 承認後も、追加領域のAI用DB辞書に掲載されたテーブル・列、既存の読み取り専用SQL検査、画面別ツール設定、外部送信方針がすべて適用される。回答には「承認済み横断参照：生産・勤務」のように根拠を表示する。
- 組合せが未定義の場合は、AIはデータを参照せず「横断参照は未定義です。システム管理者へ横断参照定義を依頼してください」と表示する。

### 不明・未対応時の回答

- DB集計が必要な質問で、読み取り専用ツールが実データを取得していない場合、外部AIの自由回答は表示しない。AIは「実データを確認できないため回答できません」とし、取得できない理由を表示する。
- 未定義の画面横断、正規データの結び付け不足、権限不足、対象条件不足、読み取り失敗を理由として明示する。推測した数値・氏名・仮の一覧・「取得中」は表示しない。
- 例として、ブレーキ工程の作業者を残業申請の申請者へ結び付ける正規データが未定義な間は、ブレーキ工程の個人別・日別残業を集計しない。
- 生産数と残業時間の比較で、工程・ライン・作業者などの条件を指定した場合は、工程と残業申請対象者を結び付ける正規データがない間、相関・傾向・因果を判定しない。「生産数が少ない日に残業が増えていない」などの結論を生成しない。工程を指定しない一般的な比較は、利用できる実データに基づいてAIが回答する。

## 画面起点のデータ領域

- グローバルナビの先頭にある `AI` タブ、または通常画面の右下に表示する丸い「Q&A」アイコンを押すと、メニュー（「1 AI」「2 リクエスト」「3 リクエスト履歴」。AIの権限がない場合は「1 リクエスト」「2 リクエスト履歴」）が開く。「1 AI」を選ぶと、画面遷移せず右側のAIチャットパネルを開く。元画面の入力・検索状態は保持する。「1 AI」は `ai.chat` の閲覧権限を持つ利用者だけに表示し（権限がない場合は「リクエスト」のみ表示）、AIパネルまたはリクエスト画面の表示中はアイコンを重複して表示しない。「リクエスト」は、システム管理者へ要望・不具合などをメール送信する画面（DB保存なし）である。
- AIパネルのヘッダ行は、🕘（会話履歴）・＋（新しい会話）・›（畳む）・×（閉じる）・？（マニュアルを別タブで開く）の順に並べる。「？」は `/manual?path=共通/社内AIチャット.md` を開く（フロントエンドのみ。API・DBは変更しない）。全画面版（`/ai/chat`）は、ルートの `meta.manualPath` により共通ヘッダの「？」から同じマニュアルを開く。
- サーバーは元パスを、登録済みの業務領域（生産・品質・勤務・仕入・出荷・在庫）へ変換する。URLのクエリ文字列や画面入力値を、そのまま外部APIへ送らない。
- DeepSeekには、その業務領域で許可した読み取り専用ツールだけを提示する。さらに集計実行時にも業務領域と集計種別を照合する。
- 現在の対応範囲は、生産（生産数・中断）、品質（確定仕損）、勤務（残業）、受注の「ルーティング未設定の注文品」、仕入の入荷実績（`v_ai_purchase_receipt` を読み取り専用SQLで集計）、出荷の出荷実績（`v_ai_shipment` を読み取り専用SQLで集計。現在はクボタ向けのみ）である。生産と品質・勤務・仕入などを組み合わせる質問は、横断参照の定義とその質問での利用者承認が必要である。SQL辞書にはテーブルごとの業務上の意味（`sql_queries.TABLE_NOTES`）も渡す。受注では、画面と同じくOPEN受注明細から有効なルーティングを持たない品番を抽出し、品番ごとに1件へ絞り込む。得意先名、受注番号、受注明細は外部AIへ送らない。仕入の入荷実績・出荷の出荷実績以外（入荷予定・仕入れ進度・出荷計画や便の進捗等）、在庫およびその他の受注集計は正規集計関数が未実装のため、他領域のテーブルを代用して回答しない。
- AIホームから直接開いた場合は、本社横断として現在許可済みの生産・品質・勤務ツールを使用できる。
- 画面ごとの対応範囲は `ai/context/screen_context.py` の `coverage` に定義する。起点画面の業務データに未対応の場合（`coverage` が空、またはAI設定でその画面のツールがすべて無効）は、チャット画面とドロワーに「〇〇画面の業務データには、まだ対応していません。生産数・仕損・中断・残業についての質問には回答できます。」と表示する。対応済みの画面では、最初の案内に「対応範囲: 〇〇」を表示する。

`pm_backend/apps/ai/` を社内AIの独立した実装単位とする。

| 場所 | 役割 |
| --- | --- |
| `services/chat_service.py` | HTTP入口と会話制御、DeepSeek／Qwen連携、ツール呼出しの許可判定 |
| `services/*_queries.py` | 業務別の読み取り専用集計。現在は `order_queries.py` に受注のルーティング未設定品照会を分離済み。生産・残業・仕入・出荷も同じ単位で追加する |

## MySQL検索専用ユーザー

本番運用では、AI用に `SELECT` だけを持つMySQLユーザーを作成する。アカウント名、接続元、パスワードはGitや仕様書へ保存しない。DB管理者が対象DB名・接続元を確定後、以下を値に置き換えて実行する。

```sql
CREATE USER 'pm_ai_reader'@'＜PMバックエンドの接続元＞' IDENTIFIED BY '＜強力なパスワード＞';
GRANT SELECT ON `pm_db`.* TO 'pm_ai_reader'@'＜PMバックエンドの接続元＞';
SHOW GRANTS FOR 'pm_ai_reader'@'＜PMバックエンドの接続元＞';
```

`INSERT`、`UPDATE`、`DELETE`、`CREATE`、`ALTER`、`DROP`、`EXECUTE` は付与しない。専用接続設定への切替は、ユーザー作成後に接続テストをしてから行う。

Djangoでは `DATABASES['ai_reader']` をAI専用接続とし、AIチャットの全クエリはこの別名を明示して実行する。`DB_USER` / `DB_PASSWORD` へのフォールバックは行わない。Windows開発環境ではAI専用接続だけにMySQL公式ドライバ `mysql-connector-python` を使い、通常業務の `mysqlclient` 接続は変更しない。接続情報は `.env` の `AI_DB_USER`、`AI_DB_PASSWORD`、`AI_DB_NAME`、`AI_DB_HOST`、`AI_DB_PORT` で管理する。MySQLで `REQUIRE SSL` を指定する場合は、AI接続にもSSLを必須とし、サーバー証明書を検証する場合は `AI_DB_SSL_CA` にCA証明書の配置先を設定する。クライアント証明書が必要な環境では、`AI_DB_SSL_CERT` と `AI_DB_SSL_KEY` も設定する。

MySQLのアカウントは接続元ホストごとに別アカウントである。開発バックエンドが `localhost` から接続する場合は、`'pm_ai_reader'@'localhost'` にも同じ `SELECT` 権限が必要であり、`'pm_ai_reader'@'10.0.1.36'` だけでは利用できない。
