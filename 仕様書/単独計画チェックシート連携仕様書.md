# 単独計画 チェックシート連携仕様書

## 概要

単独計画画面（`/production/single-process-plan`）から工程一体チェックシートを発行する機能。
サブ工程の品番と完成品（参照工程）の品番をマッピングし、完成品品番でチェックシートを作成する。

## データフロー

```
入力（完成品A=13, B=8）
   │
   ├──→ t_singleproc_finished_entry: 完成品A=13, B=8 をそのまま保存（再読込用）
   │
   └──→ resolveSubProductId で A→D, B→D に変換
         ├──→ t_line_backlog: サブ品D として保存
         └──→ t_line_gantt_plan: サブ品D としてガントチャート作成

読込時:
  t_singleproc_finished_entry があれば → 完成品A, B で下段グリッドを表示
  なければ → t_line_gantt_plan からサブ品D で表示（従来動作）

チェックシート発行（＋ボタン）:
  下段グリッドの完成品A, B の品番・数量でチェックシート作成
  line = サブ工程のライン
```

## テーブル

### t_singleproc_finished_entry

| カラム | 型 | 説明 |
|---|---|---|
| id | INT (PK) | 自動採番 |
| line_id | FK(Line) | 参照ライン |
| process_id | FK(Process) | サブ工程 |
| plan_date | DATE | 計画日 |
| sequence_no | INT | 順番 |
| product_id | FK(Product) | 完成品ID |
| quantity | INT | 数量 |

- ユニーク制約: (line, process, plan_date, sequence_no)
- インデックス: (line, process, plan_date)

### マッピング設定（SystemSetting）

- キー: `production.checksheet_product_mapping`
- 形式:
```json
[
  {
    "processCode": "4021",
    "mappings": [
      { "sub": "STYD40005598", "finished": ["YD60008491", "YD60003386"] },
      { "sub": "STYD40005551", "finished": ["YD60009783"] }
    ]
  }
]
```

## API

### 保存: POST `/line-gantt-plans/sub-process-save/`

既存のpayloadに `finished_entries` を追加:
```json
{
  "line_id": 11,
  "process_id": 42,
  "entries": [{"product_id": 100, "plan_date": "2026-06-29", "plan_qty": 21, "sequence_no": 1}],
  "finished_entries": [{"product_id": 200, "plan_date": "2026-06-29", "quantity": 13, "sequence_no": 1}],
  "target_dates": ["2026-06-29"]
}
```

- `entries`: サブ品に変換済み（ガントチャート・backlog用）
- `finished_entries`: 完成品のまま（再読込用、`t_singleproc_finished_entry` に保存）

### 取得: GET `/line-gantt-plans/singleproc-finished-entries/`

パラメータ: `line`, `process`, `plan_date__gte`, `plan_date__lte`

## 既知のリスク（データ整合性）

**リスク**: `t_singleproc_finished_entry` と `t_line_backlog` / `t_line_gantt_plan` は独立した2つのテーブルに保存されるため、片方だけ変更されるとデータ乖離が発生する。

**具体的なシナリオ**:
1. 他の画面から LineBacklog を手動削除した場合、`t_singleproc_finished_entry` にゴミデータが残る
2. `sub_process_save` 中に片方のテーブルへの保存だけ成功してもう片方が失敗する場合

**現在の方針**: 単独計画画面からのみ操作されるため、現時点ではリスクとして受容する。将来的に問題が発生した場合は、クリーンアップバッチやトランザクション統合を検討する。
