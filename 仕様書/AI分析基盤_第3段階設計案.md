## 3. 取得・保存・計算の案

### 3.1 保存前の取得元と判定

- 本人所有のRedis分析案を取得元とする。ブラウザから送られたSQL・Python本文や承認者IDを信用して保存しない。
- 手順承認、データ承認、現行外枠での試行合格、同一ハッシュのコード承認、分析案の版・有効期限をサーバーで照合する。管理列idは既存どおり取得列に含める。
- 保存条件の推奨は「コード承認済み」であり、分析の成功実行は必須にしない。成功実行まで必要とするかはBOSS判断とする。
- 保存・状態変更・通知予定の作成をPM本体DBの同一トランザクションにする案。通知予定の永続化は§10.3の(a)/(b)を選び3-Cを実装する場合の条件で、通知後回しの(c)では未実装として分離する。RedisとDBを一つのトランザクションにできるとは扱わない。保存時のRedis版競合・期限切れを検出したら保存を成立させないための手順を、実装時に検証する。
- 保存の重複防止には元の分析案ID・承認済みrevisionを使う。同じ保存要求を再送しても別テンプレートや別の初回通知を作らない。DB保存後に応答が消失した場合も、同じ識別子で既存の保存結果を返す。

### 3.2 `ai_analysis_template`の列案

本文は版ごとに不変とし、内容の修正は新しい行・新しい版を作る。承認状態・通知状態の更新と、内容の改変を分離する。

| 列候補 | 型・保存内容・取得元 |
|---|---|
| `id` | DjangoのBigAutoField。版ごとの行ID。推奨案では実行履歴の`template_id`にこの値を記録する。系統IDではない |
| `family_id`・`version` | UUID・PositiveIntegerFieldの案。同じ分析の系統と版。版は既存履歴の列型と合わせ、DBで系統内の版を一意にする |
| `source_plan_id`・`source_plan_revision` | Redis分析案の識別子・承認済み版。重複保存の照合用 |
| `name`・`purpose`・`procedure`・`output_spec` | 名称・目的・手順・出力案。承認した必要部分だけを取得し、AI応答の生JSONや送信本文は保存しない |
| `sql_steps`・`python_code` | JSONFieldの手順配列・TextFieldの承認済みPython。SQL手順の順番を保持する。固定外枠本文は保存しない |
| `datasets`・`conditions` | JSONField。ビュー名、承認列、id、型、日付列、条件、ビューごとの必要権限。条件は既存サービスが解釈できる形式だけを対象とし、自由なSQL条件を新設しない |
| `date_from`・`date_to`・`period_mode` | 元の承認期間と期間の扱い。初版を固定期間にするかは§6.3の承認事項で、まだ決定しない |
| `schema_snapshot`・`schema_sha256` | 公開ビュー・列・型・必要権限と業務定義の版の記録。業務定義の版の取得元は§6.4の判断が必要 |
| `wrapper_version` | 保存時に承認した固定外枠の版 |
| `sql_sha256`・`python_sha256`・`executed_code_sha256` | SQL手順、Python、外枠を含むコード全体のSHA-256。現行の計算方法と一致させる |
| `content_sha256` | 名称・目的・手順・コード・データ範囲・期間条件・外枠版・公開定義をまとめた承認対象の識別。状態・通知時刻は含めない |
| `approved_by`・承認日時 | 利用者承認を行ったユーザーへのFK、手順・データ・コード承認の日時。サーバーの本人情報から設定 |
| `status`・`state_revision` | 管理者承認待ち／正式／却下／置換済み、競合検出用の版 |
| `reviewed_by`・`reviewed_at`・`rejection_reason` | 管理者へのFK、確認日時、管理者入力の却下理由。入力内容の扱いは§5.3参照 |
| `replacement_id` | 訂正版への自己FK。置換元を削除・上書きせず、循環や別系統への誤リンクを拒否 |
| `created_at`・`updated_at` | プロジェクト規約どおりJST・naive。サーバーで`datetime.now()`から取得 |

ユーザーFKはSET_NULL、置換参照・通知履歴からテンプレートへのFKはPROTECTを候補とする。ユーザー削除後も版・承認日時を残し、「削除済みユーザー」と表示する。ユーザー名・メールアドレスの控えを新設しない。FK削除方針も承認対象である。

一意制約の候補は`(family_id, version)`と`(source_plan_id, source_plan_revision)`。後者は分析案由来の保存だけに使い、管理者訂正版の識別方法は実装案で明示する。一覧用索引の候補は`(status, updated_at, id)`・`(approved_by, created_at, id)`。版を訂正する際の採番はDBトランザクションと一意制約で競合を防ぎ、衝突を自動的な別内容の保存で隠さない。

#### 実行履歴のテンプレート列との対応（P2-2）

現行コード`pm_backend/apps/ai/models.py`の`AIAnalysisRun`を読み取り確認した。`template_id`は`PositiveBigIntegerField`、`template_version`は`PositiveIntegerField`で、いずれもNULL可。`template_id`はForeignKeyではない。実DBの列・既存の値は確認していない。

この設計案の推奨する対応は、**履歴の`template_id`＝実際に使用したテンプレート行の`id`、`template_version`＝その行の`version`** とする。`family_id`はテンプレートを系統としてまとめるUUIDで、履歴の数値ID列へ入れない。採用はBOSS承認待ちであり、既存列の意味を実装で変更したわけではない。

| 識別方法の案 | 利点 | 欠点・既存列との関係 |
|---|---|---|
| 行ID＋その行の版（推奨） | 使用した一つの原本を直接特定でき、既存数値列を使える。版とコードハッシュを実行時点の控えとして照合できる | 行IDから版は求められるため一部冗長。書込み時に同じ行から両値を取り、ID・版・ハッシュの不一致を拒否する必要がある |
| 系統ID＋版 | 同じ分析の版を系統単位で検索しやすく、複合キーで原本を特定できる | 今の`family_id`はUUIDで、履歴の数値列に保存できない。列型変更／新規列、または数値系統を持つ別モデルの設計が必要。UUIDを切り詰めたりハッシュ数値に代替したりしない |
| 行IDだけ | 冗長性が少ない | 履歴単体で版が分からず、原本が参照できない場合に版を示せない。既存`template_version`を使わない理由と、履歴仕様の変更が必要 |

推奨案の冗長性は意図的な履歴情報である。原本を訂正する場合は新行・新版とし、過去履歴のID・版を最新へ書き換えない。新規分析では両列をNULLとし、テンプレート利用では同じ原本から両方を設定する。FKなしではDBが対応を保証しないため、保存・実行時のサービス照合が必要である。原本が削除された後も数値・版・ハッシュは残せるが、コード本文まで復元できるとは保証しない。

履歴へFKを張るかは未決定。現状のFKなし維持を推奨する理由は既存§5.5・列型・履歴の独立性を保てるためであり、FKによる参照整合性・削除保護を選ぶ利点もある。FK化する場合は削除方針・既存NULL／不整合値の扱い・既存履歴テーブル変更を別途判断する。テンプレート内の置換FK・通知FKの案と、履歴のFKの判断は別である。

### 3.3 `ai_analysis_template_notification`の列案

以下は通知方式(a)の候補であり、採用済みではない。列だけの簡素案(b)・通知を後続へ回す案(c)との比較は§10.3に示す。

| 列候補 | 内容 |
|---|---|
| `id`・`template` | 主キー・対象のテンプレート版へのFK |
| `event_id`・`kind` | 保存／承認／却下／置換の確定イベントUUIDと通知種別。同じイベントの二重作成を防ぐ |
| `delivery_id`・`attempt_no` | 宛先・手段ごとの配送識別子と試行番号。明示再送でも前の記録を消さない |
| `recipient`・`channel` | 宛先ユーザーへのSET_NULL FK、メール／PM通知。アドレスそのものは保存しない |
| `status`・`reason` | 未送信／送信中／SMTP受付済みまたはPM通知作成済み／失敗／結果不明、固定理由コード。配送完了とSMTP受付を区別 |
| `requested_by`・`retry_of` | 操作者へのSET_NULL FK、再送元への参照 |
| `started_at`・`finished_at`・`created_at` | 試行日時。新たなタイムアウト値はこの案では決めない |
| `pm_notification` | 既存NotificationへのSET_NULL FK。既存通知が削除されても永続通知履歴を残す |

一意制約は`(delivery_id, attempt_no)`を候補とする。初回の配送IDは、確定イベント・宛先・手段から重複しないよう作り、DB側でも重複を拒否する。未送信一覧と版別履歴の索引は`(status, created_at, id)`・`(template, kind, created_at, id)`を候補とする。宛先なしの失敗はrecipient=NULLの診断記録にできるが、全員通知へ変換しない。

マイグレーションの範囲も通知方式と履歴FKの選択による。(a)と履歴FKなしなら、テンプレートと通知履歴の二つの新規テーブル・付随するFK／索引／一意制約の作成を想定する。(b)なら新規テンプレートテーブル内に通知状態列を含めるが、テンプレートを先に作成した後で選ぶ場合は列追加が必要になる。(c)の先行単位はテンプレートだけ、後続3-Cで(a)を選べば通知履歴テーブルを追加する。履歴FK化を選ぶ場合は既存履歴テーブルの変更が必要で、「新規テーブルだけ」とは言わない。既存Notificationと対象者中間テーブルへの行作成、既存実行履歴のID・版の設定はアプリ処理として必要。番号は現在の0026の後続となる見込みで、実装時に確認する。今回マイグレーションは作らない。

### 3.4 保存しないもの・計算方法

実データ行、集計結果、グラフ・報告書の結果、AIへ送った本文、AI応答の生本文、DB接続情報、SMTP認証情報、例外・DuckDB・launcherの生の説明文は保存しない。コード・目的・条件・管理者入力には識別情報を含められるため、「明細を保存しない」だけで個人情報ゼロを保証しない。保存確認で禁止対象を明示し、管理者も内容を確認する方針の承認を求める。

SQLのハッシュは既存`steps_text`と同じUTF-8の正規化JSONから、Pythonとコード全体は既存bundleと同じ本文から計算する。JSONのDB出力順やMySQL／PostgreSQLの表現に依存しない。追加のcontent/schemaハッシュも、対象キー・配列の意味・並びを定義したサーバー側の正規化JSONから計算する。SQL手順の順番を勝手に並べ替えず、日時の表記・NULLと空文字の区別を固定する。取得件数や分析計算の式を新設する案ではない。

## 4. 状態遷移と管理者訂正の案

| 現在 | 操作・成立条件 | 次の状態と効果 |
|---|---|---|
| Redisの承認済み案 | §3.1の照合後、利用者が保存 | 管理者承認待ち。確認依頼を記録。未承認警告付きで再利用候補にする |
| 管理者承認待ち | 管理者が対象版・内容ハッシュ・状態版を確認して承認 | 正式。承認者・日時を保存し、利用者へ通知する案 |
| 管理者承認待ち | 管理者が却下理由を入力して却下 | 却下。新しい再利用を拒否し、利用者へメール・PM通知 |
| 却下 | 管理者が訂正版を新規作成し、試行・コード承認等を満たす | 訂正版を新しい版で保存。元のコードは変えない |
| 却下＋利用可能な訂正版 | 管理者が置換を確定 | 元版を置換済み、置換先を記録し通知。元版は実行できない |

上表の通知は3-Cまで実装した場合の要件。通知後回しを選ぶ期間は、通知の未実装を明示し、通知が行われたとは記録しない。

管理者による訂正版は、推奨案ではいったん管理者承認待ちに置き、明示の承認操作で正式にする。同じ管理者が訂正と承認を行えるか、別の管理者を必要とするかはBOSS判断とする。訂正版を元利用者が承認したようには記録せず、実際に承認した人を記録する。新たに再利用する利用者は、訂正版の手順・データ・コードを確認する。

承認・却下・置換はDBトランザクションと期待する状態／版での条件付き更新を行い、競合した操作は成立させない。確定したイベントだけが通知対象となる。正式版の取り消し・追加訂正を同じフローへ含めるかは未決定で、自動で却下・訂正しない。

Redisへ複製した再利用案だけを信用せず、受付時とワーカー実行前に原本の状態・版・ハッシュ・公開定義を確認する案とする。却下直前に既に実行を開始したジョブの扱いは別の判断が必要である。「開始済みの処理も必ず止まる」とは保証せず、継続／結果不採用／明示中止のいずれかをBOSSが決める。DB・Redis・launcherを一つの原子操作にする設計ではない。

## 5. メール・PM通知の案（外部入出力）

### 5.1 宛先と送信者

- 管理者確認依頼の宛先は、PMのactiveなユーザーから実効`settings.ai/edit`を持つ人を抽出する案。SMTPの`is_admin`やstaffフラグを承認権限の代わりに使わない。宛先のメールアドレスは送信時にユーザーモデルのemailから取得する。
- 利用者への通知は、保存版に記録した承認利用者を対象とする。削除済み／非active／メール未登録なら、その手段は送れないと記録し、別ユーザーへ転送しない。誰に知らせるかの変更は再送でも明示する。
- 送信者はBOSSが指定した既存UserSmtpConfigの利用者／設定を一つ選ぶ案。設定の選択元を承認してから実装する。既存EmailServiceの既定管理者へのフォールバックをAI通知へ暗黙に採用しない。明示した設定だけを使える接続方法を設計し、確認できなければ送信しない。他の既存メール機能は変更しない。
- 外部入出力は、選択したSMTP設定のサーバーへ、指定宛先のメールを送信すること。AIモデルへの新規送信はこの段階に含めない。SMTPホスト・認証情報は既存設定からメモリで利用し、テンプレートや通知履歴へコピーしない。
- 権限・active・アドレスは送信直前にも確認する。判定できない対象に送らず、固定理由で記録する。宛先ゼロなら通知作成を失敗として可視化し、テンプレート保存自体は管理者承認待ちで残す案とする。

### 5.2 本文とリンク

メール本文・件名は「確認依頼／承認／却下／置換」の固定案内、テンプレートID・版・状態、PM内の確認リンクだけとする案。名称・目的・手順・コード・条件・期間・件数・却下理由・実データ・結果は載せない。実内容は権限と状態を照合したPM画面で確認する。HTMLや添付ファイルは使わず、他の宛先を露出しない宛先別送信にする。

リンクの基準URLはBOSS指定の信頼できるPM公開URL設定を取得元にする。今回調べた範囲ではAI通知用の確定した設定元を特定できていない。リクエストのOrigin・Refererからメール用URLを決める案は採用しない。URLが未設定なら送信を止め、localhost等へのフォールバックをしない。

### 5.3 成否・再送・PM通知

- DBの確定後に送信する。送信失敗で確定済みの保存／承認／却下を取り消さず、「保存成功・通知失敗」を分けて示す。
- SMTPへの受付成功は到達・既読の証明ではない。送信中の停止・応答消失は結果不明として、成功や未送信と断定しない。配送の厳密な一回性は保証しない。
- 初版は管理者の明示再送を候補とし、自動再送・別SMTPへの切替・新たな再送回数や間隔を設けない。再送は別の試行記録を作り、結果不明では重複配送の可能性を確認させる。手動送信の担当者・実行方法も実装承認時に決める。
- SMTPの生の戻り文・例外・アドレスをDBや画面へ保存／表示しない。固定理由へ変換する。管理者が入力する却下理由は、本人と承認管理者の画面だけで扱い、個人情報・秘密・実データを書かない案内を設ける。
- PM通知は既存Notificationの`target_users`に対象本人を指定し、作成と対象者設定を同一トランザクションにする。宛先なしでは作らない。SQL・却下理由等を載せず、固定案内・ID・版・リンクだけとする。通知履歴は通知本文を複製しない。
- 既存通知APIは対象者のサーバー絞込みがないため、対象外の利用者にも通知の存在・ID等が見える可能性がある。リンク先の本文はテンプレート権限で守るが、宛先指定だけで秘密保持を保証しない。**この最小通知でよいか、AI用の保護された通知取得・表示が必要かをBOSSが決める。後者は別途範囲を承認してから設計する。**
- 既存PM通知の削除・表示期限と、今回の永続通知履歴の保存期間を区別する。別業務の期限を流用せず、保存期間・削除はBOSS決定まで実装しない。

### 6.2 再利用の手順と外枠更新

1. サーバーが対象版を読み、保存内容のハッシュ、最新の状態・公開定義・権限・§6.1で承認した共有範囲を照合する。本文を閲覧できない利用者は再利用案を作れない。既存のサイズ・静的検査にも通す。
2. 今回の利用者を所有者にした新しいRedis案を作る。過去の承認、件数、明細、結果、外部送信確認、実行ジョブ情報は持ち込まない。テンプレートID・版と元の内容ハッシュは残す。
3. 目的・手順・SQL・Python・版・利用ビュー・今回の期間を提示し、手順・データ範囲承認、最新件数確認、SQL試行、コード承認を行う。既存の案キャッシュ期限を適用し、古い案を延命しない。
4. 管理者承認待ちなら「システム管理者未承認」を常時表示し、実行前にも対象版に結び付けた明示確認を要求する。確認を他の版へ転用しない。正式版のように表示しない。
5. 実行時は既存実行サービスに渡し、使用したテンプレートID・版を既存履歴の列へ設定する。実データ・結果はテンプレートへ書き戻さない。

外枠版が古い場合は、既存refreshと同じくAIを呼ばずSQL・Pythonのハッシュと新検査を照合し、新外枠での試行と利用者承認を取り直す。原本の保存コード・ハッシュ・管理者承認を自動で新外枠へ移さない。新外枠版の公開には新しいテンプレート版を保存して管理者承認待ちにする案であり、正式版の承認をそのまま流用してよいかはBOSS判断とする。新検査不合格は不合格として止め、AI再生成は本人が送信確認等を行った場合だけにする。

### 6.3 期間を変更する再利用の未決定点

生成済みSQLやPythonには、日付・月名が直接書かれていることがある。取得期間だけを変えても、そのSQL・Pythonが新期間を正しく扱うとは限らない。現在のSQL検査はパラメータも拒否しており、現行機能だけで安全な期間差替えが完成しているとは扱わない。文字列の一括置換や、知らないうちにAIを呼ぶ方式は提案しない。

- 案A：初版は保存した期間・条件だけで再利用し、同じ期間の最新データを再取得する。期間変更は利用者に不可と示す。実装範囲を小さくできるが、仕様書§5.3の「今回の期間条件」を狭めるためBOSSの仕様変更承認が必要。
- 案B：日付等の型付き入力と、SQL・Python両方で参照する固定の入力窓口を別の設計単位にする。利用者が承認した今回の入力だけを検査・束縛し、その組立て後のSQL・コードを既存guardへ通す。分析上の意味や月名まで正しく変わることを検証する。外枠・生成契約・静的検査への影響を先に承認し、外部AI送信の内容変更も別途確認する。

第3段階全体を現行仕様の期間変更まで満たすなら案Bの詳細設計が必要。BOSSが選ぶまでは、期間変更の再利用を実装可能・承認済みとは記載しない。

### 6.4 ビュー・列の変更

実行前に最新の公開定義と保存スナップショットを照合し、ビュー削除、承認列の削除／型変更、必要権限の変更、業務定義の版変更では再利用を拒否する案。未承認の列を追加取得して補わない。状態が正式でも整合が取れなければ実行不可とする。

同じ列名・型でビューの計算・結合・数値定義だけが変わった場合は、列比較では検出できない。取得元の候補は、承認した公開定義に明示する意味の版、またはDB別のビュー定義取得アダプターである。前者を推奨するが、更新責任者と変更手順をBOSSが決める必要がある。MySQL固有の定義取得SQLをここで追加せず、定義を確認できない場合を整合済みと扱わない。変更後のコード・範囲・試行・利用者承認・管理者承認を新しい版で取り直す案とする。

## 10. BOSSへの確認事項

判断は依存関係の順に分ける。まず§10.1の三つを決めればよく、全項目の一括承認は求めない。以下の推奨はCodexの意見であり、BOSSの決定ではない。未決定の項目を前提にした実装は始めない。

### 10.1 最初に決める：保存・共有・期間

1. **保存条件**：コード承認済みで保存するか、成功実行も必要か。推奨はコード承認まで。利用者承認後に登録する既存方針に沿い、成功した一実行だけでは分析の正しさを保証できないため。成功実行を要求する案は、実行時の形式不正を登録前に発見できる利点もあるが、開発実行基盤が使えない間は保存できない。
2. **管理者承認前の共有範囲**：§6.1の(a)全文を分析利用者全員に公開／(b)全文は作成者・管理者だけ、他の利用者へは名称・目的・状態のみ。推奨は審査前のコード・詳細条件の公開を狭める(b)。ただし他の利用者の未承認版再利用を制限する仕様変更の承認が必要で、名称・目的の機密性も別途確認する。既存の全員再利用を優先するなら(a)を選ぶ必要がある。警告だけで公開リスクが解消するとは扱わない。
