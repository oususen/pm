# 7アプリ構成仕様書 (v2)

## 目的
本システムを7つの業務ドメインに分割し、バックエンド・フロントエンドの構成を整理する。

## ドメイン一覧

| ドメイン | 日本語名 | バックエンド | フロントエンド | 備考 |
| --- | --- | --- | --- | --- |
| orders | 受注 | `pm_backend/apps/orders/` | `pm-ui/src/views/orders/` | 取込・一覧・ステージング管理 |
| production | 生産 | `pm_backend/apps/production/` | `pm-ui/src/views/production/` | 計画・進捗・在庫計算の中核 |
| purchase | 仕入 | `pm_backend/apps/purchase/` | `pm-ui/src/views/purchase/` | 画面・APIはプレースホルダ中心 |
| shipping | 出荷 | `pm_backend/apps/shipping/` | `pm-ui/src/views/shipping/` | 出荷指示書・集荷依頼書など |
| inventory | 在庫 | なし（生産に集約） | `pm-ui/src/views/inventory/` | 在庫計算ロジックは生産内 |
| quality | 品質 | `pm_backend/apps/quality/` | `pm-ui/src/views/quality/` | 画面・APIはプレースホルダ中心 |
| masters | マスタ | `pm_backend/apps/masters/` | `pm-ui/src/views/masters/` | 製品・得意先・容器・ルーティング |

## バックエンド構成 (Django)

### ルーティング
- 入口: `pm_backend/project/urls.py`
- 各アプリの `urls.py` を `/api/` 配下に集約
  - `masters`, `orders`, `production`, `shipping`, `purchase`, `quality`, `system_settings`

### アプリ配置
- `pm_backend/apps/` 配下にドメインごとのアプリを配置
- 代表的な役割:
  - `models.py`: DBモデル
  - `serializers.py`: RESTレスポンス
  - `views.py`: API View / ViewSet
  - `services/`: 集計・PDF生成・取込処理

### ドメイン別の特徴
- orders:
  - `core/` に受注モデル・インポート処理を集約
  - `core/services/` に客先別CSV取込サービス
  - `management/commands/` に一括処理系コマンド
- production:
  - 進捗・計画・在庫計算を担う
  - 在庫計算は `production/inventory/` に集約
  - 2026-08-23 時点で、在庫/進度再計算の開始日補正ロジックは `production/services/recalc_start_date.py` へ分離済み
  - 2026-08-23 時点で、レーザー系 API は `production/views_laser.py` に分離し、主要な業務処理は `production/services/laser_service.py` に分離済み
- shipping:
  - 出荷指示書・集荷依頼書PDF/Excel生成
  - 受注・マスタとの結合が多い
- masters:
  - `m_` 系テーブルの管理
  - ほぼ全ドメインから参照される基盤
- purchase / quality:
  - 現時点はプレースホルダ中心
- system_settings:
  - システム全体の汎用Key-Value設定を管理
  - 詳細は `システム設定仕様書.md` を参照

## フロントエンド構成 (Vue)

### 画面配置
- `pm-ui/src/views/` 配下にドメイン別フォルダ
  - `orders/`, `production/`, `purchase/`, `shipping/`, `masters/`
  - `inventory/`, `quality/` はメニュー/画面のプレースホルダ
- マスタ画面の主要例:
  - `BOMMaster.vue`（構成マスタ）
  - `RoutingMaster.vue`（ルーティングマスタ）

### ルーティング
- `pm-ui/src/router/` にドメイン別ルーターを配置
  - `orders.js`, `production.js`, `purchase.js`, `shipping.js`, `masters.js`
  - `inventory.js`, `quality.js`
- `masters.js` に `/masters/routing`（ルーティングマスタ）を定義

### メニュー・ナビゲーション
- グローバルメニュー: `pm-ui/src/components/GlobalNavigation.vue`
- サイドメニュー: `pm-ui/src/components/SideMenu.vue`

### マニュアル
- `pm-ui/public/manual/` にMarkdownを配置
- 目次定義: `pm-ui/src/manual/manualIndex.js`
- マニュアル表示: `pm-ui/src/views/manual/ManualPage.vue`

#### `?` ボタンからの導線作成方法

- 上部ナビゲーションの `?` ボタンは `pm-ui/src/components/GlobalNavigation.vue` の `openHelp()` から開く
- 通常は「現在の画面ルートに設定された `meta.manualPath`」を使って `/manual?path=...` へ遷移する
- そのため、新しい画面で `?` 導線を作るときは、まず対象ルートの `meta.manualPath` を設定する

例:

```js
{
  path: "/purchase/auto-order-send",
  name: "PurchaseAutoOrderSend",
  component: () => import("@/views/purchase/PurchaseAutoOrderSendSettings.vue"),
  meta: {
    pageTitle: "注文書自動送信設定",
    manualPath: "仕入れ/注文書自動送信.md",
    resource: "purchase.auto_delivery_list",
  },
}
```

#### 追加手順

1. `pm-ui/public/manual/` 配下に対象画面のMarkdownマニュアルを作成する
2. `pm-ui/src/manual/manualIndex.js` に目次項目を追加する
3. 対象ルート定義ファイル（例: `pm-ui/src/router/purchase.js`）で `meta.manualPath` にマニュアル相対パスを設定する
4. `?` ボタン押下時に `/manual?path=...` で対象マニュアルが開くことを確認する

#### パス記述ルール

- `manualPath` には `pm-ui/public/manual/` からの相対パスを入れる
- 区切りは `/` を使う
- 例:
  - `README.md`
  - `生産/工程作業入力_デスクトップ.md`
  - `仕入れ/注文書自動送信.md`

#### フォールバック対応

- 原則は全画面で `meta.manualPath` を設定する
- 既存画面との互換や一時対処で、`route.meta.manualPath` が拾えない画面だけ `GlobalNavigation.vue` の `manualPathFallbackMap` に個別追加してよい
- ただしフォールバックは例外対応であり、正式対応はルートの `meta.manualPath` 設定を優先する

#### 確認ポイント

- `?` ボタンでマニュアルトップではなく対象画面のマニュアルが開くこと
- `manualIndex.js` からも同じマニュアルを開けること
- ファイル名変更時は `manualPath` と `manualIndex.js` の両方を更新すること

## 命名規則
- マスタ: `m_` で開始（例: `m_product`）
- 取引/実績: `t_` で開始（例: `t_order_line`）
- ステージング: `stg_` で開始（例: `stg_order_raw`）

## 更新ルール
- 新しい業務ドメインを追加する場合は、必ず本書を更新する。
- プレースホルダ実装は備考欄に明記する。

## 現状構造レビュー（2026-08-23）

本章は、現行コードベースを確認したうえで、フロントエンド、API、バックエンド、分離の観点から見た構造課題を整理したものである。

### 総評

- ディレクトリ上は `orders` `production` `purchase` `shipping` などに分割されているが、実装上は `production` を中心に責務が集中している。
- 特にバックエンドの View 層と、フロントエンドの画面コンポーネント層に責務が集まりやすく、機能追加時の影響範囲が広い。
- 「ドメインで分かれているように見える構成」と「実際の依存関係」に差がある。

### フロントエンド観点

- `pm-ui/src/api/client.js` に API resource の import/export が集中しており、巨大な API シングルトンになっている。
- 多数の画面が `import api from '@/api/client'` を直接参照しており、画面が通信処理、レスポンス整形、エラーハンドリングを直接持ちやすい。
- 画面コンポーネントが大きくなりやすく、UI と業務ロジックの分離が弱い。
- 権限判定は `router/index.js` に共通関数がある一方で、各メニュー画面でも類似ロジックを個別実装しており、判定の重複が発生している。

#### 代表例

- API 集約: `pm-ui/src/api/client.js`
- 権限判定の共通化元: `pm-ui/src/router/index.js`
- 権限判定の重複実装:
  - `pm-ui/src/views/production/ProductionMenu.vue`
  - `pm-ui/src/views/purchase/PurchaseMenu.vue`
  - `pm-ui/src/views/orders/OrderMenu.vue`
  - `pm-ui/src/views/masters/MasterMenu.vue`
  - `pm-ui/src/views/shipping/ShippingMenu.vue`
  - `pm-ui/src/views/settings/SettingsMenu.vue`

### API観点

- `project/urls.py` では各アプリの URL をすべて `/api/` 直下に include しており、公開面の規則がアプリ単位で明確に分かれていない。
- `production/urls.py` では REST 風 endpoint と、実行系・帳票系・設定保存系の RPC 風 endpoint が同居している。
- resource 指向の API と command 指向の API が混在しているため、API 利用側から規則性を把握しづらい。

#### 代表例

- 入口: `pm_backend/project/urls.py`
- 混在例: `pm_backend/apps/production/urls.py`

### バックエンド観点

- `pm_backend/apps/production/views.py` が非常に大きく、生産計画、在庫、進度、レーザー、PDF、設定系 API まで同一ファイルに集約されている。
- View 層に業務ロジック補助関数が多く置かれており、HTTP 層と業務ロジック層の境界が弱い。
- `orders` や `purchase` が `production.views` の関数や ViewSet を直接参照しており、再利用の単位が service ではなく view になっている。

#### 代表例

- 巨大 View ファイル: `pm_backend/apps/production/views.py`
- アプリ横断の view 依存:
  - `pm_backend/apps/orders/views.py`
  - `pm_backend/apps/purchase/views.py`

### 分離の観点

- 現状は「ドメイン分割」よりも「機能追加のたびに既存の巨大ファイルへ追記」の傾向が強い。
- 再利用の中心が service 層ではなく、ViewSet・APIView・画面コンポーネントになっている。
- そのため、ある業務の改修が別業務の UI/API/計算ロジックへ波及しやすい。
- `inventory` はフロントでは独立メニューだが、バックエンドでは `production` に内包されており、境界の意味が UI とサーバで一致していない。

### 主な課題まとめ

| 観点 | 課題 | 影響 |
| --- | --- | --- |
| フロントエンド | 画面から API を直接呼び、権限判定も各画面で重複 | 画面ごとの差異混入、保守コスト増 |
| API | REST と RPC が混在し、公開ルールが曖昧 | 利用規約が読みにくく、拡張時に揺れやすい |
| バックエンド | `production` に責務集中、view に業務ロジック混在 | 変更影響範囲が大きい |
| 分離 | app 境界より実装都合の依存が優先 | ドメイン分割の効果が薄い |

### 改善優先度

1. バックエンドの `production` を中心に、view から service/usecase へ責務を分離する。
2. フロントエンドの権限判定を共通化し、メニューごとの重複実装をなくす。
3. フロントエンドで画面直結の API 呼び出しを減らし、ドメイン別の呼び出し窓口や composable を介す構成へ寄せる。
4. API を resource 系と command 系で整理し、命名と URL の規則を統一する。
5. `inventory` のような UI 上のドメインと、バックエンド上の責務境界を一致させるか、意図的に内包するならその方針を明文化する。
