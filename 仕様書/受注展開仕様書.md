# 受注展開仕様書

受注データ（Order/OrderLine）からライン別需要（LineDemand・LineBacklog）への展開ロジックをまとめる。

---

## 1. 全体フロー

```
CSVアップロード
     │
     ▼
StgOrderRaw / StgOrderRaw_Tiera / StgOrderRaw_Rieden / StgOrderRaw_Kubota
（PARSED ステータス）
     │
     ▼
StgOrderDaily
（CSVインポート時に自動生成）
     │
     ▼
create_orders_from_staging（CSVImportService）
     │
     ▼
Order / OrderLine（OPEN ステータス）
     │
     ├─── POST /api/line-demands/expand/
     │         （OrderExpansionService.expand_open_orders）
     │         │
     │         ├─ BOM倍率計算（再帰展開）
     │         ├─ ルーティング逆順で工程をたどる
     │         ├─ 営業日ベースで必要日を計算
     │         └─▼
     │        LineDemand（ライン×製品×日別需要）
     │
     └─── POST /api/line-backlogs/pickup/
               （LineBacklogViewSet.pickup）
               │
               ├─ 最終品: OrderLine から直接取得
               ├─ 中間品: 後工程のLineBacklogから逆伝播
               └─▼
              LineBacklog（ライン別生産計画）
```

## 2. ステージング → Order/OrderLine 生成

### 実装

- **ファイル**: `pm_backend/apps/orders/core/services/csv_import.py`
- **クラス**: `CSVImportService`
- **メソッド**: `create_orders_from_staging()`

### 対象レコード

ステータスが `PARSED` の StgOrderDaily のみを対象とする。

```python
query = StgOrderDaily.objects.filter(
    Q(raw__parse_status='PARSED') |
    Q(raw_kubota__parse_status='PARSED') |
    Q(raw_tiera__parse_status='PARSED') |
    Q(raw_rieden__parse_status='PARSED')
)
```

### グループ化単位

`（customer_id, order_type, version_no, source_file）` の組み合わせで1つの Order ヘッダを生成する。

### order_no 生成ルール

| 受注タイプ | 顧客 | フォーマット |
|-----------|------|------------|
| FORECAST | Kubota | `FC-{customer_code}-{calc_date}` |
| FORECAST | その他 | `FC-{customer_code}-{timestamp}` |
| FIRM | Kubota（特殊） | `FIRM-{customer_code}-{factory}-sp-{issue_date}` |
| FIRM | Kubota（通常） | `FIRM-{customer_code}-{factory}-{issue_date}` |
| FIRM | Rieden | `FIRM-{customer_code}-{order_date}` |
| FIRM | Tiera | `FIRM-{customer_code}-{delivery_no}` |
| FIRM | その他 | `FIRM-{customer_code}-{timestamp}` |

### order_no サフィックス付与ルール（Kubota FIRM のみ）

#### -tuika（発注番号ベース）
- **判定**: 同じ製品＋同じ納期の OPEN FIRM 行が既に存在し、かつ新しい発注番号が異なる場合
- **付与**: `{order_no}-tuika`
- **用途**: 同日同発注番号で追加の注文が来た場合

#### -tuika2（order_no 重複ベース）
- **判定**: 同じ `order_no` を持つファイルが複数存在し、かつこのデータが初回取込（同製品＋同納期の既存行がない）場合
- **付与**: `{order_no}-tuika2-{取込日}`
  - 取込日：ファイル名から抽出（最初の8文字 YYYYMMDD）
  - 例：`20260304取込済_RCV_JVAN - 47sakai.csv` → `-tuika2-20260304`
  - 日付の抽出に失敗した場合はタイムスタンプを使用
- **用途**: 同じ order_no で異なるタイミングに複数のファイルが到着した場合
- **ファイルごとにユニーク**: 3ファイル以上の場合も衝突しない

#### 優先度
1. 既存行がない ＋ order_no 重複 → **-tuika2** を付与
2. 既存行がある ＋ 発注番号が異なる → **-tuika** を付与
3. 既存行がある ＋ 発注番号が同じ → スキップ（重複取込）
4. factory が異なる（SAKAI vs HIRAKATA）→ order_no が異なるため分離される
5. その他 → 通常の order_no

### 置換戦略

| 受注タイプ | 戦略 |
|-----------|------|
| **FORECAST（内示）** | 部分置換：新データの最小納期以降の同製品の既存ラインを `SUPERSEDED` に変更し、新規作成 |
| **FIRM（確定）** | 原則新規追加。Special Kubota（`is_kubota_special=True`）のみ既存削除→新規作成 |

### クボタ内示の前処理（2026-02追加）

- 対象: `kubota_sakai_naiji_import.py` / `kubota_hirakata_naiji_import.py`
- ルール: 同一顧客・同一品番・同一納期にFIRMがある場合、FORECAST日次を `StgOrderDaily` に作成しない
- 参照条件: FIRMは `created_at` 直近90日分を対象
- 目的: 展開前に「同日同品番の確定/内示の重複」を抑制し、進度計算の意図しない二重計上を防ぐ

## 3. 受注展開 → LineDemand 生成

### 実装

- **ファイル**: `pm_backend/apps/production/services/order_expansion.py`
- **クラス**: `OrderExpansionService`
- **メソッド**: `expand_open_orders(clear_existing: bool = False)`
- **API**: `POST /api/line-demands/expand/`

### 展開対象の基本方針（2026-08更新）

- **FORECAST（内示）**: `OPEN` の `OrderLine` を毎回全件再集計し、`LineDemand.forecast_qty` をキー単位で置換する
- **FIRM（確定）**: `OPEN` かつ `is_expanded=False` の `OrderLine` のみを増分展開し、展開成功後に `OrderLine.is_expanded=True` を立てる
- **通常運用**: `LineDemand` 全削除・全再作成は行わない
- **保守運用**: `clear_existing=True` を指定した場合のみ、全件再構築を行う
- **過去/当日内示の無効化**: `FORECAST` は `due_date <= 今日` の時点で展開対象から除外する

### OrderLine の展開管理項目

`t_order_line` に以下を保持する。

| フィールド | 内容 |
|-----------|------|
| `is_expanded` | FIRM 明細の展開済みフラグ |
| `expanded_at` | 展開日時 |

### 展開戻しの保守運用（2026-08-25 追記）

- 保守UIでは、**完成品コード + 期間** を指定して対象の `OPEN FIRM` 受注明細を保守再処理できる。
- 保守UIは `受注 > 受注管理メニュー > ライン展開` から実行する。
- 操作は次の2段階に分かれる。
  1. **展開戻し**: 対象 `OrderLine` のうち `is_expanded=True` の明細について、既存 `LineDemand` から当該確定需要を差し戻す
  2. **再展開**: 対象期間の同一完成品 `OPEN FIRM` 明細のうち、未展開分だけを再展開する
- 目的は、誤展開・旧展開結果が残った特定完成品について、全件全消しではなく限定範囲で安全に戻しと再展開を行うこと。
- API としては「戻しだけ」「再展開だけ」「戻して再展開」をそれぞれ別に持つ。

#### 注意: `_is_empty_demand` と `actual_qty`

差し戻し時、`firm_qty=0` かつ `forecast_qty=0` になった `LineDemand` は空需要として削除される（`_is_empty_demand`）。
現在のこの判定は **`actual_qty` を見ていない**。
現時点（2026-08-26）では `actual_qty > 0` の `LineDemand` は0件のため実害はないが、
将来 `actual_qty` が使われ始めた場合は `_is_empty_demand` に `actual_qty > 0` の保護を追加すること。

### 処理ステップ

#### Step 1: 対象受注の取得

```python
order_lines = OrderLine.objects.filter(
    order__status='OPEN'
).select_related('order', 'product')
```

ステータス `OPEN` のみ対象。`SUPERSEDED` は除外。

通常運用ではここをさらに分ける。

- `FORECAST`: `order__status='OPEN' and order__order_type='FORECAST'`
- `FIRM`: `order__status='OPEN' and order__order_type='FIRM' and is_expanded=False`

#### Step 2: BOM 倍率計算（_get_bom_multiplier_maps）

BOM ツリーを再帰展開し、最終品1個あたりの各中間品の所要量を計算する。

```
最終品A（1個）
  ├─ 部品B（2個）
  │    └─ 部品C（1個）
  └─ 部品D（3個）

bom_multiplier = {A:1, B:2, C:2, D:3}
path_multiplier = {"1":2, "1.1":2, "2":3}
```

**連産品BOM（is_coproduct=True）は除外**する。

#### Step 3: ルーティング按分との補正

ルーティング上の工程倍率と BOM 倍率が異なる場合に補正係数を計算する。

```python
correction = bom_multiplier[pid] / routed_multiplier[pid]
```

ただし、**完成品自身を複数工程で同じ品番のまま流すルーティング**では、完成品数量を工程数で按分しない。完成品自身（受注明細の品番）に対する補正係数は常に `1` とする。

#### Step 4: 必要日の計算（営業日ベース）

ルーティングの `hierarchy_path` を親→子の順でたどり、工程ごとの必要日を再帰的に計算する。

```
受注納期(due_date)
  ↓ shift(-final_LT)
最終工程（hierarchy_path='final'）の必要日
  ↓ shift(-root_LT)
ルート工程の必要日
  ↓ shift(-child_LT)
子工程の必要日
  ↓ ...（再帰）
```

**hierarchy_path によるツリー構築**:

- `"final"` → 最終工程（出荷ステップ）
- `"1"`, `"2"` → ルート工程（finalの直下）
- `"1.1"`, `"1.2"` → `"1"` の子工程
- `"1.1.1"` → `"1.1"` の子工程（さらに深い階層）

親パスは `hierarchy_path.rsplit('.', 1)[0]` で決定する。

**中間工程の階層補正（orphan fix）**:

手動作成等で `hierarchy_path` が未設定（空）の中間工程（非final・加工後品目=ルーティング製品）がある場合、
自動的にツリーに組み込む:

1. 該当工程を仮想パスでルートに追加（step_no降順で連鎖）
2. `remark`（親製品コード）で子部品工程を正しい親に再配置

これにより、hierarchy_pathが空でも正しいLT連鎖計算が行われる。

**LT解決の統一ルール（`resolve_lead_days_for_step`）**：

全工程で共通の解決ルール（最終品/中間品の区別なし）:

| 優先度 | ソース | 備考 |
| --- | --- | --- |
| 1 | `RoutingStep.lead_time_days` | **0は有効値**（Noneのときのみ次へ） |
| 2 | `Line.lead_time_days` | step.lead_time_daysがNullの場合のフォールバック |
| 3 | `0` | いずれも未設定の場合 |

- `duration_min` はサイクルタイム専用であり、LT日数シフトには使用しない
- `time_unit`（MINUTE/DAY）はLT日数解決に影響しない
- 実装: `pm_backend/apps/production/inventory/lead_time_utils.py`

**営業日判定のカレンダ合成ルール**:

- 受注展開の必要日計算は **ラインカレンダ + 顧客カレンダ** で判定する
- 顧客にカレンダ設定がある場合、`顧客休み or ライン休み` の日は休みとして扱う
- したがって、`顧客カレンダもラインカレンダも稼働日` の日だけを営業日として採用する
- 顧客にカレンダ未設定の場合は、従来どおりラインカレンダのみで判定する

#### Step 5: ライン別に数量を集計

```python
# キー: (line_id, product_code, plan_date, process_id)
for step in reversed(steps):  # 後工程から前工程へ逆順処理
    qty = order_line.quantity × base_mult × correction
    is_shifted = (target_date != order_line.due_date)  # 前倒し判定
    if order_type == 'FIRM':
        aggregated[key].firm_qty += qty
    else:
        aggregated[key].forecast_qty += qty
    # 同一キーに複数明細が集約されるため、前倒しフラグはORで保持
    aggregated[key].is_shifted = aggregated[key].is_shifted or is_shifted
```

#### Step 6: LineDemand レコードを一括保存

通常運用（`clear_existing=False`、デフォルト）では差分更新（下記参照）。
`clear_existing=True` を指定した場合のみ全件削除・再作成する。

### 差分更新ルール（通常運用）

#### FORECAST

- `OPEN` の FORECAST `OrderLine` を毎回全件展開し、`line_id + product_code + plan_date + process_id` 単位で先に集計する
- ただし `due_date <= get_business_today()` の FORECAST は集計前にスキップする
- その集計結果で `LineDemand.forecast_qty` を**置換**する
- 前回存在したが今回存在しないキーは `forecast_qty=0` にする
- その結果 `firm_qty=0 and forecast_qty=0` になった行のみ削除する

#### FORECAST の当日以前無効化

- 判定単位は **LTシフト後の `plan_date` ではなく、元受注明細の `due_date`** とする
- `due_date <= 今日` の FORECAST は、最終品でも子部品でも一切 `LineDemand` に展開しない
- 目的は、過去や当日の古い内示が残留して加工内示へ展開されることを防ぐこと
- 特に、**クボタのように日次内示ファイルへ過去内示が残り続ける顧客運用への対策**として導入した
- `FIRM` は従来どおり展開する
- 「今日」は `get_business_today()` を使い、8:00 区切りの業務日付で判定する

#### FORECAST の除外判定キー（source demand key）

- FORECAST の展開前除外判定は、展開後の `LineDemand(line_id + product_code + plan_date)` では行わない
- 判定単位は元受注明細ベースの以下4項目とする
  - `customer_id`
  - `OrderLine.product_code`（完成品コード）
  - `ship_to_code`
  - `due_date`
- 同一 `source demand key` に `OPEN FIRM` が存在する場合、その FORECAST は展開対象から除外する
- さらに `due_date <= 今日` の FORECAST も、`source demand key` 判定より前に展開対象から除外する
- この `product_code` は **完成品コード** であり、展開後の子部品コードではない
- したがって、**別完成品** 由来の FORECAST と FIRM が、展開後に同じ子部品・同じ `plan_date` に落ちるケースでは、FORECAST は除外されず共存し得る

#### 取込時の内示/確定の扱い

- `FIRM` 取込時は、既存の FORECAST を `SUPERSEDED` にしない
- `FORECAST` 取込時のみ、置換対象の旧 FORECAST を `SUPERSEDED` にする
- そのため、取込時点では `FIRM` と `FORECAST` は別管理である
- 受注展開での二重計上抑止は、上記 `source demand key` 単位の除外判定で行う

#### FIRM

- `OPEN and is_expanded=False` の FIRM `OrderLine` のみ展開する
- 同じ `line_id + product_code + plan_date + process_id` が存在すれば `firm_qty` に**加算**する
- なければ新規作成する
- 成功後に対象 `OrderLine.is_expanded=True`、`expanded_at=now()` を更新する

#### 共用部品の扱い

- FORECAST は 1明細ごとに上書きせず、**全件集計後にキー単位で置換**する
- そのため、複数完成品から同一共用部品へ展開される数量は正しく合算される

### LineDemand の主要フィールド

| フィールド | 内容 |
|-----------|------|
| `line_id` | ライン |
| `routing_step_id` | ルーティング工程 |
| `process_id` | 工程。`routing_step.process` と同じ工程を保持し、後続の進度再計算・空行補完の正本として使用する |
| `product_id` / `product_code` | 製品 |
| `ship_to_code` | 納入先コード。`OrderLine.ship_to_code` を正規化（strip）して保存。BOM展開で中間品にも伝搬する |
| `plan_date` | 必要日（納期 - リードタイム） |
| `lead_time_days` | リードタイム（日） |
| `is_shifted` | 前倒し判定（`plan_date != due_date` の受注が1件でもあれば `True`） |
| `forecast_qty` | 内示数量 |
| `firm_qty` | 確定数量 |
| `plan_qty` | 計画数量（初期値 = forecast + firm） |
| `actual_qty` | 実績数量（初期値 0） |
| `order_numbers` | 紐付き受注番号（カンマ区切り、500字まで） |

### LineDemand の一意キー（2026-08-30更新）

- 旧1: `line_id + product_code + plan_date`
- 旧2: `line_id + product_code + plan_date + process_id`（2026-08-24）
- 現行: `line_id + product_code + plan_date + process_id + ship_to_code`
- 目的: 同一ライン・同一品番・同一日・同一工程でも、納入地が異なれば別需要として保持するため
- `ship_to_code` は `OrderLine.ship_to_code` から取得し、`.strip()` で正規化。未設定時は空文字 `''`
- BOM展開で中間品に展開する際も、親の `ship_to_code` がそのまま伝搬する
- 読取側（進度計算・在庫計算・画面表示）は当面、納入地別の表示をせず従来粒度で合算して使用する
- `pickup` / `pickup_purchase` は、`LineDemand` を納入地別行のまま読み、**行ごとに** `firm` / `forecast` 判定してから `LineBacklog` へ合算保存する
- 社内ライン `pickup` の最終品需要では
  - `order_qty` は各 `ship_to_code` 行の需要判定結果を合算する
  - `order_qty_actual` は各 `ship_to_code` 行の `firm_qty` のみを合算する
  - `demand_qty_plan` は合算後の `order_qty` を使用する
- 購買ライン `pickup_purchase` では、上記を基準にしつつ購買需要仕様書の `demand_qty_plan` 判定ルールを適用する

### 内示/確定の共存について

- `LineDemand` は `forecast_qty` と `firm_qty` を別列で保持する
- 同じ `line_id + product_code + plan_date + ship_to_code` に対して、内示と確定が同時に存在することがある
- 特に多親構成では、別親完成品由来の FORECAST と別親完成品由来の FIRM が同じ子部品需要へ合流し得る
- この場合も `LineDemand` 上は `forecast_qty` / `firm_qty` を共存保持する
- 後続画面・後続計算がどう採用するかは各仕様書に従う
- `LineDemand.routing_step.process` / `LineDemand.process` が未解決の需要は、進度再計算や進度表示用空行補完で補完せず異常扱いとする
- `LineDemand.process_id` は受注展開時に `RoutingStep.process_id` をそのまま保存し、後続計算は `routing_step` 経由ではなく `LineDemand.process_id` を正として参照する

## 4. LineBacklog 生成（pickup）

### 実装

- **ファイル**: `pm_backend/apps/production/views.py`
- **クラス**: `LineBacklogViewSet`
- **アクション**: `POST /api/line-backlogs/pickup/`

### 入力パラメータ

```json
{
  "line_id": 1,
  "start_date": "2025-01-01",
  "end_date": "2025-01-31"
}
```

### 最終品と中間品のリードタイム区別

pickup では製品を `is_final_product` で分類し、リードタイムの扱いが異なる。

| 区分 | LTの起点 | LT解決の優先順位 |
| --- | --- | --- |
| **最終品**（`is_final_product=True`） | 受注の `due_date` から遡る | Line.lead_time_days → 0（RoutingStep固有値は使わない） |
| **中間品**（上記以外） | 後ライン LineBacklog の `plan_date` から遡る | RoutingStep.lead_time_days → Line.lead_time_days → BOMItem.lead_time_days → 0 |

中間品は後工程のLTが先に確定している必要があるため、**後ライン → 前ライン の順**に pickup を実行すること。

### 最終品の需要取得

最終品（`is_final_product=True`）は **OrderLine** から直接取得する。

```python
for ol in order_lines:
    lead_days = resolve_lead_time_days(ol.product_id)
    # LT: Line.lead_time_days のみ使用（RoutingStep固有値は使わない）
    plan_date = shift_business_days(ol.due_date, lead_days)  # due_date から遡る
    if ol.order.order_type == 'FIRM':
        firm_map[(ol.product_id, plan_date)] += ol.quantity
    else:
        forecast_map[(ol.product_id, plan_date)] += ol.quantity
```

### 中間品の需要取得（後ライン逆伝播）

中間品は後工程の **LineBacklog** から BOM 個数を掛けて逆算する。
LTは `RoutingStep.lead_time_days → Line.lead_time_days → BOMItem.lead_time_days → 0` の順で解決する。

```text
現在ライン（例：A工程）: 中間品X を生産
後ライン（例：B工程）:   完成品Y を生産（BOM: Y → X × 2個）

→ B工程 LineBacklog(Y, plan_date=1/15, plan_qty=100) から
→ A工程のLT=2日を引いて plan_date=1/13 に展開
→ A工程 LineBacklog(X, plan_date=1/13, order_qty=200) に保存
```

### LineBacklog の sequence_no

| sequence_no | 意味 |
|-------------|------|
| `0` | 需要・在庫・実績などの基礎データ（自動削除なし） |
| `1以上` | ユーザー入力の生産計画（削除可能） |

### LineBacklog の主要フィールド

| フィールド | 内容 |
|-----------|------|
| `plan_date` | 生産予定日 |
| `order_qty` | pickup で設定した需要数 |
| `demand_qty_plan` | `order_qty` と同値（バックアップ） |
| `plan_qty` | ユーザー入力の計画数（初期値 0） |
| `actual_qty` | 実績数（ガントチャート等から更新） |
| `stock_qty` | 実在庫 |
| `planned_stock_qty` | 計画在庫 |
| `adjust_qty` | 手動調整数 |
| `scrap_qty` | 自工程仕損数 |
| `progress_qty` | 進度（顧客需要に対する実績の遅れ/先行） |
| `sequence_no` | 0=基本、1+=計画 |

## 5. 進度計算

### 需要ソース

**進度計算の需要は必ず LineDemand を使用する。**
LineBacklog の `order_qty` や `demand_qty_plan` をフォールバックに使ってはならない。

2026-08-24以降は、進度計算の工程需要解決も `LineDemand.process_id` を正とする。
工程需要が解決できない場合、製品需要へのフォールバックは行わず、進度再計算を失敗として中断する。

```python
# progress_calculator.py
if demand.is_shifted and (demand.firm_qty or 0) > 0 and (demand.forecast_qty or 0) > 0:
    qty = demand.firm_qty + demand.forecast_qty  # 前倒し衝突は合算
elif demand.firm_qty and demand.firm_qty > 0:
    qty = demand.firm_qty  # 通常は確定優先
elif demand.forecast_qty and demand.forecast_qty > 0:
    qty = demand.forecast_qty  # 確定なし時のみ内示
else:
    qty = 0
```

- 展開後の `LineDemand` は `firm_qty + forecast_qty` をそのまま需要として採用する。
- 同日・同品番でも工程別に `LineDemand(process)` を保持し、進度計算は工程単位の需要を合算して使う。
- ただし、`due_date <= 今日` の内示は受注展開時点で `LineDemand` に入らないため、進度計算では需要候補にならない。

### 工程需要未解決時の扱い

- `LineDemand` に製品需要があっても、対象工程の `process_id` 需要が解決できない場合は計算継続しない。
- API は `PROGRESS_STEP_DEMAND_MISSING` を返し、サーバーログ出力と管理者メール通知を行う。
- 目的は、工程未設定や `LineDemand.process_id` 欠落を「別数量でなんとなく計算する」形で隠さないためである。

### 需要0フォールバックの扱い

- `LineDemand` 自体が存在しない日は、進度計算では需要 `0` として計算継続する。
- これは本当に需要ゼロの日を止めないための運用上必要なフォールバックである。
- ただし無検知にはせず、`需要0フォールバック` として `production.log` に warning を残す。

## 6. 業務ルール

### 日替わり時刻（8:00）

「今日」の判定は 8:00 を区切りとする。

- 8:00 未満 → 前日扱い
- 8:00 以上 → 当日扱い

### 連産品（is_coproduct=True）の除外

受注展開（BOM倍率計算・在庫計算）では連産品BOMを除外する。

```python
BOM.objects.filter(is_coproduct=False, ...)  # 展開対象から除外
```

### 棚卸初期化と通常計算の分離

| 区分 | ファイル |
|------|---------|
| 通常計算（日次再計算） | `inventory_calculator.py` / `progress_calculator.py` |
| 棚卸専用初期化 | `stocktake_initializer.py` |

棚卸専用の在庫・進度再計算は `stocktake_initializer.py` 内の専用関数で行い、通常計算ファイルを流用しないこと。
