# 受注展開仕様書

受注データ（Order/OrderLine）からライン別需要（LineDemand・LineBacklog）への展開ロジックをまとめる。

---

## 1. 全体フロー

```
CSVアップロード
     │
     ▼
StgOrderRaw / StgOrderRaw_Tiera / StgOrderRaw_Rieden / StgOrderRaw_Kubota
（PARSED ステータス）
     │
     ▼
StgOrderDaily
（CSVインポート時に自動生成）
     │
     ▼
create_orders_from_staging（CSVImportService）
     │
     ▼
Order / OrderLine（OPEN ステータス）
     │
     ├─── POST /api/line-demands/expand/
     │         （OrderExpansionService.expand_open_orders）
     │         │
     │         ├─ BOM倍率計算（再帰展開）
     │         ├─ ルーティング逆順で工程をたどる
     │         ├─ 営業日ベースで必要日を計算
     │         └─▼
     │        LineDemand（ライン×製品×日別需要）
     │
     └─── POST /api/line-backlogs/pickup/
               （LineBacklogViewSet.pickup）
               │
               ├─ 最終品: OrderLine から直接取得
               ├─ 中間品: 後工程のLineBacklogから逆伝播
               └─▼
              LineBacklog（ライン別生産計画）
```

---

## 2. ステージング → Order/OrderLine 生成

### 実装

- **ファイル**: `pm_backend/apps/orders/core/services/csv_import.py`
- **クラス**: `CSVImportService`
- **メソッド**: `create_orders_from_staging()`

### 対象レコード

ステータスが `PARSED` の StgOrderDaily のみを対象とする。

```python
query = StgOrderDaily.objects.filter(
    Q(raw__parse_status='PARSED') |
    Q(raw_kubota__parse_status='PARSED') |
    Q(raw_tiera__parse_status='PARSED') |
    Q(raw_rieden__parse_status='PARSED')
)
```

### グループ化単位

`（customer_id, order_type, version_no, source_file）` の組み合わせで1つの Order ヘッダを生成する。

### order_no 生成ルール

| 受注タイプ | 顧客 | フォーマット |
|-----------|------|------------|
| FORECAST | Kubota | `FC-{customer_code}-{calc_date}` |
| FORECAST | その他 | `FC-{customer_code}-{timestamp}` |
| FIRM | Kubota（特殊） | `FIRM-{customer_code}-{factory}-sp-{issue_date}` |
| FIRM | Kubota（通常） | `FIRM-{customer_code}-{factory}-{issue_date}` |
| FIRM | Rieden | `FIRM-{customer_code}-{order_date}` |
| FIRM | Tiera | `FIRM-{customer_code}-{delivery_no}` |
| FIRM | その他 | `FIRM-{customer_code}-{timestamp}` |

### 置換戦略

| 受注タイプ | 戦略 |
|-----------|------|
| **FORECAST（内示）** | 部分置換：新データの最小納期以降の同製品の既存ラインを `SUPERSEDED` に変更し、新規作成 |
| **FIRM（確定）** | 原則新規追加。Special Kubota（`is_kubota_special=True`）のみ既存削除→新規作成 |

## 3. 受注展開 → LineDemand 生成

### 実装

- **ファイル**: `pm_backend/apps/production/services/order_expansion.py`
- **クラス**: `OrderExpansionService`
- **メソッド**: `expand_open_orders(clear_existing: bool = True)`
- **API**: `POST /api/line-demands/expand/`

### 処理ステップ

#### Step 1: 対象受注の取得

```python
order_lines = OrderLine.objects.filter(
    order__status='OPEN'
).select_related('order', 'product')
```

ステータス `OPEN` のみ対象。`SUPERSEDED` は除外。

#### Step 2: BOM 倍率計算（_get_bom_multiplier_maps）

BOM ツリーを再帰展開し、最終品1個あたりの各中間品の所要量を計算する。

```
最終品A（1個）
  ├─ 部品B（2個）
  │    └─ 部品C（1個）
  └─ 部品D（3個）

bom_multiplier = {A:1, B:2, C:2, D:3}
path_multiplier = {"1":2, "1.1":2, "2":3}
```

**連産品BOM（is_coproduct=True）は除外**する。

#### Step 3: ルーティング按分との補正

ルーティング上の工程倍率と BOM 倍率が異なる場合に補正係数を計算する。

```python
correction = bom_multiplier[pid] / routed_multiplier[pid]
```

#### Step 4: 必要日の計算（営業日ベース）

ルーティングの `hierarchy_path` を親→子の順でたどり、工程ごとの必要日を計算する。

```
最終工程（hierarchy_path='final'）の必要日 = 受注納期(due_date) - LT（営業日）
前工程の必要日  = 後工程の必要日 - 前工程のLT（営業日）
```

**LT解決の優先順位（OrderExpansionService._resolve_lead_time_days）**：

```text
1. RoutingStep.lead_time_days（工程固有、0より大の場合）
2. Line.lead_time_days（ライン共通）
3. 0（デフォルト）
```

※ time_unit='MINUTE'の工程はLT=0として扱い、duration_min（分）で計算する。

#### Step 5: ライン別に数量を集計

```python
# キー: (line_id, product_code, plan_date)
for step in reversed(steps):  # 後工程から前工程へ逆順処理
    qty = order_line.quantity × base_mult × correction
    if order_type == 'FIRM':
        aggregated[key].firm_qty += qty
    else:
        aggregated[key].forecast_qty += qty
```

#### Step 6: LineDemand レコードを一括保存

```python
with transaction.atomic():
    if clear_existing:
        LineDemand.objects.all().delete()  # 全件削除・再作成
    LineDemand.objects.bulk_create(objects_to_create)
```

`clear_existing=True`（デフォルト）の場合、**既存のLineDemand全件を削除**して再作成する（フル再計算）。

### LineDemand の主要フィールド

| フィールド | 内容 |
|-----------|------|
| `line_id` | ライン |
| `routing_step_id` | ルーティング工程 |
| `product_id` / `product_code` | 製品 |
| `plan_date` | 必要日（納期 - リードタイム） |
| `lead_time_days` | リードタイム（日） |
| `forecast_qty` | 内示数量 |
| `firm_qty` | 確定数量 |
| `plan_qty` | 計画数量（初期値 = forecast + firm） |
| `actual_qty` | 実績数量（初期値 0） |
| `order_numbers` | 紐付き受注番号（カンマ区切り、500字まで） |

## 4. LineBacklog 生成（pickup）

### 実装

- **ファイル**: `pm_backend/apps/production/views.py`
- **クラス**: `LineBacklogViewSet`
- **アクション**: `POST /api/line-backlogs/pickup/`

### 入力パラメータ

```json
{
  "line_id": 1,
  "start_date": "2025-01-01",
  "end_date": "2025-01-31"
}
```

### 最終品と中間品のリードタイム区別

pickup では製品を `is_final_product` で分類し、リードタイムの扱いが異なる。

| 区分 | LTの起点 | LT解決の優先順位 |
| --- | --- | --- |
| **最終品**（`is_final_product=True`） | 受注の `due_date` から遡る | RoutingStep.lead_time_days → Line.lead_time_days → 0 |
| **中間品**（上記以外） | 後ライン LineBacklog の `plan_date` から遡る | RoutingStep.lead_time_days → Line.lead_time_days → BOMItem.lead_time_days → 0 |

中間品は後工程のLTが先に確定している必要があるため、**後ライン → 前ライン の順**に pickup を実行すること。

### 最終品の需要取得

最終品（`is_final_product=True`）は **OrderLine** から直接取得する。

```python
for ol in order_lines:
    lead_days = resolve_lead_time_days(ol.product_id)
    # LT優先順位: RoutingStep.lead_time_days → Line.lead_time_days → 0
    plan_date = shift_business_days(ol.due_date, lead_days)  # due_date から遡る
    if ol.order.order_type == 'FIRM':
        firm_map[(ol.product_id, plan_date)] += ol.quantity
    else:
        forecast_map[(ol.product_id, plan_date)] += ol.quantity
```

### 中間品の需要取得（後ライン逆伝播）

中間品は後工程の **LineBacklog** から BOM 個数を掛けて逆算する。
LTは `RoutingStep.lead_time_days → Line.lead_time_days → BOMItem.lead_time_days → 0` の順で解決する。

```text
現在ライン（例：A工程）: 中間品X を生産
後ライン（例：B工程）:   完成品Y を生産（BOM: Y → X × 2個）

→ B工程 LineBacklog(Y, plan_date=1/15, plan_qty=100) から
→ A工程のLT=2日を引いて plan_date=1/13 に展開
→ A工程 LineBacklog(X, plan_date=1/13, order_qty=200) に保存
```

### LineBacklog の sequence_no

| sequence_no | 意味 |
|-------------|------|
| `0` | 需要・在庫・実績などの基礎データ（自動削除なし） |
| `1以上` | ユーザー入力の生産計画（削除可能） |

### LineBacklog の主要フィールド

| フィールド | 内容 |
|-----------|------|
| `plan_date` | 生産予定日 |
| `order_qty` | pickup で設定した需要数 |
| `demand_qty_plan` | `order_qty` と同値（バックアップ） |
| `plan_qty` | ユーザー入力の計画数（初期値 0） |
| `actual_qty` | 実績数（ガントチャート等から更新） |
| `stock_qty` | 実在庫 |
| `planned_stock_qty` | 計画在庫 |
| `adjust_qty` | 手動調整数 |
| `scrap_qty` | 自工程仕損数 |
| `progress_qty` | 進度（顧客需要に対する実績の遅れ/先行） |
| `sequence_no` | 0=基本、1+=計画 |

## 5. 進度計算

### 需要ソース

**進度計算の需要は必ず LineDemand を使用する。**
LineBacklog の `order_qty` や `demand_qty_plan` をフォールバックに使ってはならない。

```python
# progress_calculator.py
if demand.firm_qty and demand.firm_qty > 0:
    qty = demand.firm_qty   # 確定優先
elif demand.forecast_qty and demand.forecast_qty > 0:
    qty = demand.forecast_qty  # なければ内示
else:
    qty = 0
```

## 6. 業務ルール

### 日替わり時刻（8:00）

「今日」の判定は 8:00 を区切りとする。

- 8:00 未満 → 前日扱い
- 8:00 以上 → 当日扱い

### 連産品（is_coproduct=True）の除外

受注展開（BOM倍率計算・在庫計算）では連産品BOMを除外する。

```python
BOM.objects.filter(is_coproduct=False, ...)  # 展開対象から除外
```

### 棚卸初期化と通常計算の分離

| 区分 | ファイル |
|------|---------|
| 通常計算（日次再計算） | `inventory_calculator.py` / `progress_calculator.py` |
| 棚卸専用初期化 | `stocktake_initializer.py` |

棚卸専用の在庫・進度再計算は `stocktake_initializer.py` 内の専用関数で行い、通常計算ファイルを流用しないこと。
