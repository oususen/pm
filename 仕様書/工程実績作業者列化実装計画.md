## 状態（反映状況）

## 目的
一般の工程実績 `t_process_realtime_record` に、作業者のログインID（`auth_user.username`）を専用列 `operator_login_id` で保存し、AI分析・既存画面から扱いやすくする。仕損の作業者列化（`仕損作業者列化実装計画.md`）の前例を踏襲する。

## BOSS決定事項
1. 保存する値は `username`（例: 000175）。姓名は保存しない。`operator_name`（表示用）は従来どおり残す。
2. `ProcessRealtimeRecord.operator_login_id` = CharField(150, null=True, blank=True, db_index=True)。`ProcessWorkSession.operator_login_id` = CharField(150, null=True, blank=True)。NOT NULL 化はしない。補完を RunPython で行わない。
3. 親行（PRODUCTION / OPERATOR_ACTION / EQUIPMENT_STATE）はサーバーがログイン者の username を保存。クライアントの `operator_login_id`・`event_data.operator_login_id`・`event_data.operator_user_id` は通常入力では無視。認証されたユーザーがなければ400。
4. EQUIPMENT_STATE もログイン者（従来は作業者名が空）。工程作業記録の設備状態モードの作業者欄の初期値をログイン者の姓名にする。
5. SCRAP 行は NULL（仕損は `t_scrap_record` 側）。PURCHASE は対象外（NULL。認証必須の400を課さない）。
6. END/PAUSE で作る PRODUCTION 行と連産子行は親（OPERATOR_ACTION）行と同じ値。

## 単位1の内容

- `ProcessRealtimeCreateSerializer`: PRODUCTION / OPERATOR_ACTION / EQUIPMENT_STATE は未認証なら400、認証済みなら親行・END/PAUSE の PRODUCTION 行・連産子行へ `request.user.username` を保存。
- `expand_coproduct_children_production` に `operator_login_id`（既定 None）を追加。`rebuild_session_production_records` は `session_obj.operator_login_id` を引き継ぐ（単位1ではセッションが NULL のため NULL）。

- フロント `DesktopProcessInput.vue`（工程作業記録）: 設備状態モードの作業者欄の初期値をログイン者の姓名にし、設備状態の送信に `operator_name` を含める。
- LineBacklog・在庫・進度の計算式は変更しない。

## 単位2の内容（2人1設備・B治具）
- 画面の仕組み: `TwoPersonOneEquipmentInput.vue`（親画面）がA治具・B治具の2つの子画面（`DesktopProcessInput.vue`、iframe）を並べる。A治具の `operator_user_id` はログイン者の `auth_user.id`。B治具は、B作業者の社員番号入力から画面がユーザー一覧（`api.accounts.getUsers`）で探したユーザーの `auth_user.id`。子画面は記録保存時に `event_data` へ `two_person_same_equipment: true` と `operator_user_id`（文字列）を入れて送る。B作業者がいない運用ではB側の記録は作られない。
- サーバーの約束: 2人1設備の記録は「印 `event_data.two_person_same_equipment`（真）」と「作業者の `auth_user.id`（`event_data.operator_user_id`）」を送る。サーバーはその id で `auth_user` を引き、その `username` を `operator_login_id` に保存する。画面が id をどう見つけるか（一覧から探す／1人だけ問い合わせる等）には依存しない。実装は `serializers_process_realtime.py` の `resolve_record_login_id`（`validate` で作成前に呼ぶ）。
- 値の決め方: 親行（PRODUCTION / OPERATOR_ACTION / EQUIPMENT_STATE）のみ。印が真なら `operator_user_id` の username（ログイン者と同じ id ならログイン者、違えば別の作業者）。印が真でなければ `operator_user_id` は無視してログイン者（単位1どおり）。END/PAUSE で作る PRODUCTION 行・連産子行は OPERATOR_ACTION 行と同じ値。SCRAP / PURCHASE は NULL のまま。`event_data.operator_user_id` は削除せずそのまま保存する（既存画面が参照）。
- 異常時: 印が真で `operator_user_id` が無い・整数にできない・存在しない・`is_active=False` は400（エラーキー `event_data`）。作成前に検証するため、他の行・LineBacklog は1件も作られない。ログイン者へ落とすフォールバックは作らない。
- 将来の画面改善で変えてはならない点: ユーザー一覧を軽くしたり1人だけ問い合わせる形に直しても、送る `operator_user_id`（`auth_user.id`）と印 `two_person_same_equipment` は変えない。約束を変える場合はサーバーと画面（両vue）・テスト・本書を同時に直す。コメントを `serializers_process_realtime.py` / `DesktopProcessInput.vue` / `TwoPersonOneEquipmentInput.vue` に記載（vue はコメントのみ追加、動作変更なし）。
- 既知の範囲（BOSS確認 2026-10-14）: 2人1設備の画面（DesktopProcessInput.vue）の「数量を入力して登録」フォーム入力（生産記録・設備状態・仕損。送信は `DesktopProcessInput.vue` の submitRecord の else 側）は、2人1設備の印と `operator_user_id` を送らないため、B治具でも `operator_login_id` はログイン者になる。B治具ではこのフォーム入力を使わない運用で、「手入力する」リンク（計画にない品番を選ぶ機能）は計画員が現場で計画を追加する用途のため、画面の変更は行わない。B治具でフォーム入力を使う運用になった場合は、submitRecord の送信に印と `operator_user_id` を足す（サーバー側は対応済み）。
- テスト: `production/tests_process_realtime.py` の `ProcessRealtimeOperatorLoginIdTest`（B治具・3行同値・400と未作成・通常入力で無視・文字列/整数id・SCRAP）。
- LineBacklog・在庫・進度の計算は変更しない。
