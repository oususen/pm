## 目的
一般の工程実績 `t_process_realtime_record` に、作業者のログインID（`auth_user.username`）を専用列 `operator_login_id` で保存し、AI分析・既存画面から扱いやすくする。仕損の作業者列化（`仕損作業者列化実装計画.md`）の前例を踏襲する。

## BOSS決定事項
1. 保存する値は `username`（例: 000175）。姓名は保存しない。`operator_name`（表示用）は従来どおり残す。
2. `ProcessRealtimeRecord.operator_login_id` = CharField(150, null=True, blank=True, db_index=True)。`ProcessWorkSession.operator_login_id` = CharField(150, null=True, blank=True)。NOT NULL 化はしない。補完を RunPython で行わない。
3. 親行（PRODUCTION / OPERATOR_ACTION / EQUIPMENT_STATE）はサーバーがログイン者の username を保存。クライアントの `operator_login_id`・`event_data.operator_login_id`・`event_data.operator_user_id` は通常入力では無視。認証されたユーザーがなければ400。
4. EQUIPMENT_STATE もログイン者（従来は作業者名が空）。工程作業記録の設備状態モードの作業者欄の初期値をログイン者の姓名にする。
5. SCRAP 行は NULL（仕損は `t_scrap_record` 側）。PURCHASE は対象外（NULL。認証必須の400を課さない）。
6. END/PAUSE で作る PRODUCTION 行と連産子行は親（OPERATOR_ACTION）行と同じ値。

## 単位3a の内容（セッションと実績変更API。バックエンドのみ）
### BOSS決定
1. 作業者の名前と login_id は同じ出どころの組で取る。優先順は一覧の現行規則と同じ「終了記録→開始記録→セッション」。最初に名前が空でない出どころの名前と login_id を組で採用する（login_id が NULL でも名前があればその組を採用し、login_id は NULL のまま。推測で埋めない）。実装は `serializers_process_realtime.py` の `resolve_session_worker(session, refresh=False)`。一覧 Serializer の `operator_name`／`operator_login_id`、rebuild、変更履歴の「変更前」で共通に使う。どの出どころにも名前が無いときは、セッション自身の組（名前は空、セッションの login_id）を返す。
2. 既存の空欄（9月の16行など）の補完は単位4。今回は既存行を更新しない。
3. 変更履歴のスナップショットとラベルに `operator_login_id`（ラベル「ログインID」）を追加。login_id だけが変わった保存も履歴に残る。名前の「前」は `resolve_session_worker` の値。
4. 作業者ID（`auth_user.id`）の検証は共通ヘルパー `resolve_active_worker(raw_id)`（失敗は `WorkerLookupError`: 形式不正／存在しない・無効）。単位2の `resolve_record_login_id` と、セッションの処理の両方が使う。
5. 終了していないセッション（OPEN）の作業者も PATCH で変えられる（二勤で同じタブレットを2人が使い、ログインを忘れた場合の修正用）。
6. CANCEL で TEMP_END から再開するセッションの login_id は、取消を押した人（CANCEL の記録）の値。現行の動きは変えない。
7. 実績変更画面で変更するのは、リーダーによる記入漏れ・誤記入の修正と実績の追加。「ログイン者＝作業者」とは限らないため、画面が送る `operator_user_id` が login_id の正になる。

### 経路ごとの値の決め方
| 経路 | session.operator_login_id | session.operator_name |
|---|---|---|
| 通常 START / RESUME / PAUSE のセッション作成、RESUME・START欠落（END/TEMP_END/CANCEL）で作るセッション | その操作の記録の `operator_login_id`（ログイン者。2人1設備は `operator_user_id` の username） | 従来どおり（2人1設備のみ小文字名。通常は空） |
| CANCEL で TEMP_END から再開 | CANCEL の記録の値 | 従来どおり |
| END / PAUSE で既存セッションを閉じる | 変更しない（START の人のまま） | 変更しない |
| 手動 POST `/sessions/` | `operator_user_id` の username | サーバーが作る「姓 名」（(姓+' '+名)を trim、空なら username） |
| PATCH で作業者を変更 | 新しい username | 新しい「姓 名」 |
| PATCH で作業者を変えない | 変更しない | 変更しない |
| rebuild（PATCH／手動POST） | 書き換えない | 書き換えない。親 PRODUCTION 行・連産子行へ `resolve_session_worker`（記録をDBから取り直した値）の組を渡す |
| DELETE・連産子行の数量更新 | 対象外 | 対象外 |

### API
- 一覧 GET: 各行に `operator_login_id`（read_only。`resolve_session_worker` の login_id）。`operator_name` は従来と同じ値（同じ関数）。連産子の展開行は親の値を引き継ぐ。追加クエリなし（start/end 記録は select_related 済み）。
- 手動 POST `/sessions/`: `operator_user_id`（整数または数字文字列）が必須。検証はトランザクション前で、400のときどのテーブルにも書かない。なし／`operator_name` のみ（旧画面）→400「作業者が指定されていません。画面が古い場合は、アプリを閉じて開き直してください。」。整数でない・空・真偽値→400「作業者（operator_user_id）の形式が不正です。」。存在しない・無効・username 空→400「指定された作業者が存在しないか、無効なユーザーです。」。両方あるときは `operator_name` を無視。手動POSTは start/end の ProcessRealtimeRecord を作らない（従来どおり。セッションと rebuild の PRODUCTION 行・連産子行のみ）。
- PATCH `/sessions/<id>/`: `operator_user_id`・`operator_name` とも無し→作業者は変更しない（rebuild で名前が空にならない）。`operator_user_id` が有効→セッション・start/end 記録・rebuild の PRODUCTION 行／連産子行の名前と login_id を同時に更新。`operator_user_id` が空・null・形式不正・無効→400。`operator_name` のみ（空文字を含む）→400「画面が古いため作業者を保存できません。アプリを閉じて開き直してください。」。`operator_login_id` を送っても無視。検証は既存の `transaction.atomic()` の前。start/end 記録が隣のセッションと共有される場合は、現行どおり波及する。
- LineBacklog・在庫・進度の呼び出し（`adjust_backlog_actual_for_session` 等）は変更なし。

### コマンドと対象

- コマンド: `python manage.py backfill_process_realtime_operator_login_id`。既定は照合のみで更新しない。`--apply` を明示した場合だけ候補行を更新する。
- 対象: `t_process_realtime_record.operator_login_id IS NULL` かつ `record_type` が `PRODUCTION` / `OPERATOR_ACTION` / `EQUIPMENT_STATE` の行。空文字のログインID、`SCRAP`、`PURCHASE`、既に値がある行は対象外。
- 更新列: `ProcessRealtimeRecord.operator_login_id` のみ。`operator_name`、`event_data`、`ProcessWorkSession`、開始・終了記録は更新しない。
- `auth_user` は有効・無効を問わず照合する。退職者を削除せず `is_active=False` で保持する現在の運用では、無効ユーザーも過去実績の正しい照合元になるため。

### 候補の決め方

1. 名前が空の `PRODUCTION` かつ `event_data.source='MANUAL_RECORD_EDIT'` は、`event_data.work_session_id` のセッションを参照する。開始記録・終了記録の `operator_login_id` が両方非空で完全一致し、そのusernameが現在の `auth_user` に存在する場合だけ候補とする。
2. 名前がある行は、`operator_name` と `auth_user` の `(last_name + ' ' + first_name).strip()` が完全一致し、一人に決まる場合だけ候補とする。同名が複数いる場合は曖昧として補完しない。
3. 姓名が両方空のユーザーに限り、表示名となるusernameと `operator_name` が完全一致する場合に候補とする。本番で個別実行した `admin` の補完を、表示名規則に沿って一般化した段階である。
4. 空白除去、全半角変換、部分一致、姓だけ一致、前後作業からの推定、退職者名のパターン推定は行わない。候補にできない行は理由とともに一覧出力する。
5. 本番でBOSSが個別の画面確認・指示により確定した寺田2行、内山2行、行13284のID・usernameはコマンドへハードコードしない。他環境で同じ行が未補完なら、一般条件で確定できない限り未補完一覧に残す。

### 更新・出力・制限

- `--apply` ではトランザクション内で、行IDと `operator_login_id IS NULL` を再確認して条件付き更新する。再実行時は補完済み行が対象外となる。
- 標準出力には実行モード、補完前のNULL件数と記録種別内訳、根拠別候補件数、未補完理由内訳、更新件数を出す。補完後の実件数・種別内訳と、候補をすべて適用した場合の見込件数・種別内訳は別の行で明示する。
- 外部API・外部ファイルの入出力なし。件数・期間の上限なし。対象はPK順に `iterator()` で処理する。推測フォールバックなし。モデル変更・マイグレーションなし。
