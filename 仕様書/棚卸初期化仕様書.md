# 棚卸初期化仕様書

## 概要

設定メニューの「棚卸初期化」で使用する、棚卸データ取込と初期化計算の仕様を定義する。
本仕様は、通常の在庫再計算とは分離された**棚卸専用ロジック**を前提とする。

## 目的

- **棚卸の数値を正（TRUTH）** として、在庫・計画在庫・進度を再構築する
- 棚卸日を起点に、基準日以降のすべての値を棚卸値から連鎖計算で導出する
- リアルタイム再計算の保護ロジック（read-onlyゾーン等）に影響されず、棚卸基準で初期化する

## 大原則

1. **棚卸値が絶対の基準**: 棚卸で数えた物理在庫がすべての計算の起点
2. **棚卸日より前のデータは使わない**: 棚卸の目的は過去の数値を矯正すること
3. **通常計算コードを改変しない**: 棚卸専用ロジックは `stocktake_initializer.py` に閉じる

## 業務ルール

- 基準日（baseline_date）は常に `stocktake_date`（棚卸日）
- 棚卸初期化時は、棚卸日より前の日付を起点値として参照しない
- 棚卸日 `line_backlog(sequence_no=0)` が未存在なら自動作成する
- `line_backlog.stock_qty` は整数で保持するため、棚卸数量の小数は切り捨てで反映する
- 権限制御はフロントエンドUIで実施（`settings/edit` 権限）

### 初期化タイミング

- 棚卸日 + 最大LT + 1営業日 以降に実行するのが望ましい
- 例: 棚卸日=2/27、最大LT=7 → 3/12以降に実行
- 理由: 通常の日次再計算の `calc_start_date`（= today - (LT+1)BD）が棚卸日より後になり、棚卸初期化の値が日次再計算で上書きされない

### 計算終了日（end_date）

- 在庫・計画在庫・進度をこの日付まで再計算する。デフォルト: 昨日
- 手動設定（UIで入力）
- 目安: 棚卸日 + 最大LT + 1営業日
- 忘れて遅れて実行した場合（例: 3/11予定が3/13に）、end_dateを3/12に設定すれば不要な日の再計算を回避できる

## 対象画面

- `pm-ui/src/views/settings/StocktakeInit.vue`

画面フロー:
1. テンプレートDL
2. 棚卸Excel/CSV取込（在庫反映）
3. 初期化計算（在庫・計画在庫・進度）

## API仕様

### 1. テンプレートDL

- `GET /api/line-backlogs/download_stocktake_template/`
- 棚卸取込用テンプレート（xlsx）を返却する
- 列: `製品番号`, `製品名`, `数量`

### 2. 棚卸取込

- `POST /api/line-backlogs/import_stocktake_excel/`
- Content-Type: `multipart/form-data`

リクエスト:
- `file`（必須）: `.xlsx` or `.csv`
- `stocktake_date`（必須）: `YYYY-MM-DD`
- `location`（任意）: 既定 `MAIN`

テンプレート列仕様:
- `製品番号`（必須）: 製品コード
- `製品名`（任意）: 取込時は無視（バリデーションなし、NULLでもOK）
- `数量`（必須）: 棚卸数量（同一品番が複数行ある場合は合算）

処理:
1. ファイル読込、`製品番号` 単位で数量を集約
2. 未登録品番を検証（存在すればエラー）
3. `t_stock_allocation` を作成/更新
4. 基準日 `= stocktake_date` の `line_backlog(sequence_no=0)` を作成/更新
5. `is_stocktake_fix=True` を設定
6. ルーティング未設定品番を `unmapped_product_codes` で返却

レスポンス主要項目:
- `stocktake_date`
- `baseline_date`（= `stocktake_date`）
- `allocation_created`, `allocation_updated`
- `backlog_created`, `backlog_updated`
- `unmapped_product_codes`

### 3. 初期化計算

- `POST /api/line-backlogs/initialize_stocktake/`

リクエスト:
- `stocktake_date`（必須）: `YYYY-MM-DD`
- `end_date`（必須）: `YYYY-MM-DD`

処理:
1. `baseline_dt = stocktake_date`
2. `ensure_stocktake_backlogs(baseline_dt)` を実行
3. 対象ライン抽出（`plan_date` が `baseline_dt..end_date`）
4. 各ラインで在庫再計算（`_stocktake_recalc_stock`）
5. 各ラインで計画在庫再計算（`_stocktake_recalc_planned_stock`）
6. 進度初期化（`initialize_progress_from_stocktake`）

レスポンス主要項目:
- `stocktake_date`, `baseline_date`, `end_date`
- `line_count`
- `baseline_backlog_created`, `baseline_backlog_updated`
- `baseline_unmapped_product_codes`
- `updated_count`, `final_count`, `child_count`

エラー条件:
- 日付フォーマット不正
- `end_date < baseline_date`
- 計算対象期間に `line_backlog` が存在しない

## 棚卸専用ロジック

実装ファイル:
- `pm_backend/apps/production/inventory/stocktake_initializer.py`

主要関数:
- `ensure_stocktake_backlogs(stocktake_date, location='MAIN')`
- `recalculate_inventory_from_stocktake(line_id, baseline_date, end_date)`
- `_stocktake_recalc_stock(...)`
- `_stocktake_recalc_planned_stock(...)`
- `initialize_progress_from_stocktake(baseline_date)`

---

### 1. 在庫（stock_qty）

**最も単純**。棚卸値をそのままセットし、翌営業日から通常カスケード。

#### 基準日

```
stock_qty(基準日) = 棚卸値
```

#### 基準日+1BD以降（カスケード）

```
stock_qty(D) = prev_stock + actual_total - actual_shipment + scrap_adjust_total
```

- `actual_shipment`: 親の実績 + 親の仕損（同日、LTシフトなし）
- `scrap_adjust_total`: 子部品仕損のadjust_qty
- `is_stocktake_fix=True` の日はアンカー値としてカスケードを上書き

---

### 2. 計画在庫（planned_stock_qty）

**在庫と全く異なる**。計画在庫はLTシフトで親の消費を子の日付に引き戻すため、同じ日でも在庫と計画在庫は別の値になる。

#### 核心: LT前倒し集約

棚卸日より前のデータは使わない。しかしLT>=2の場合、親の生産が棚卸日より前の子日付にマッピングされる分がある。これを**基準日に前倒し集約**する。

##### 出庫のLTシフト（通常の仕組み）

```
子の日付D の出庫 = 親の生産(shift(D, +LT)) × BOM数量
```

例: 子のLT=2、子の日付=2/27 → 親の日付 = shift(2/27, +2BD) = 3/3

##### LT前倒しが必要な理由

逆方向で考える: 親が日付Pに生産 → 対応する子の日付 = P - LT(BD)

```
基準日=2/27(金), LT=2 の場合:
  親が3/2(月)に生産 → 子の日付 = 3/2 - 2BD = 2/26(木) ← 基準日より前！
  親が3/3(火)に生産 → 子の日付 = 3/3 - 2BD = 2/27(金) ← 基準日ON ✓
  親が3/4(水)に生産 → 子の日付 = 3/4 - 2BD = 3/2(月) ← 基準日後 ✓
```

LT=2だと、親の3/2生産分が基準日前（2/26）にマッピングされ、通常カスケードでは漏れる。

#### 基準日の計画在庫（LT前倒し集約）

```
planned_stock(基準日) = 棚卸値 - Σ(親生産(基準日 + i BD) × BOM数量)  i = 1 .. LT
```

**基準日後LT日間の親の消費を全て基準日に引く。**

##### 具体例

製品B（棚卸=200, LT=2で親Aに使われる, BOM数量=1）、基準日=2/27(金)

```
LT=1 の場合:
  planned_stock(2/27) = 200 - A生産(3/2)×1
                                ↑ i=1: shift(2/27,+1)=3/2

LT=2 の場合:
  planned_stock(2/27) = 200 - A生産(3/2)×1 - A生産(3/3)×1
                                ↑ i=1         ↑ i=2
  ※ A生産(3/2)分は本来child_date=2/26だが、基準日前なので基準日に前倒し

LT=3 の場合:
  planned_stock(2/27) = 200 - A生産(3/2)×1 - A生産(3/3)×1 - A生産(3/4)×1
                                ↑ i=1         ↑ i=2         ↑ i=3

一般化: LT=N → 親の生産を基準日+1BD〜基準日+N BD の N日分まとめて引く
```

##### 親が複数ある場合

製品Cが親A（LT=2, BOM=1）と親B（LT=3, BOM=2）に使われる場合:

```
planned_stock(基準日) = 棚卸値
  - Σ(A生産(基準日+i BD) × 1)  i=1..2
  - Σ(B生産(基準日+i BD) × 2)  i=1..3
```

各親のLTに応じて個別に前倒し範囲を決定する。

##### 出庫の時制分岐（基準日）

基準日は過去日であるため、親の出庫は**実績優先**で取得する:
- 親に実績(actual_qty)あり → 実績 + 仕損
- 親に実績なし → 計画(plan_qty)

#### 基準日+1BD以降（通常カスケード）

基準日以降は通常の計画在庫カスケードと同じ式:

```
過去（plan_date < today）:
  planned_stock(D) = prev_planned + actual_total - parent_shipment(shift(D, +LT))

今日以降（plan_date >= today）:
  planned_stock(D) = prev_planned + plan_total - parent_shipment(shift(D, +LT))
```

- 最終品: 出庫 = 顧客実需（将来は実需なければ計需）
- ライン最終品: 出庫 = order_qty
- 中間品: 出庫 = 親の実績or計画 × BOM数量（LTシフトあり）

---

### 3. 進度（progress_qty）

**最もややこしい**。BOMの全階層（親の親も含む）に関係する。

#### 計算順序: トポロジカルソート（上流→下流）

BOM階層を Kahn's algorithm でトポロジカルソートし、**最終品（上流）から順に計算**する。
親の進度が確定してから子の進度を計算するため、階層の深さに関係なく正しく伝播する。

#### 計算式

```
最終品:
  progress = stock_qty（棚卸値 = 在庫そのまま）

子部品:
  progress = stock_qty + Σ(親の進度 × BOM数量)
```

**注意: マイナスではなくプラス**。
子の在庫には親が既に消費した分が含まれていない。親の進度は「親がどれだけ消費したか」を表すため、子の本来の生産量 = 在庫 + 親が消費した分。

#### 具体例

```
A（最終品）: 在庫=100
└─ B（LT=1, BOM=1）: 在庫=200
   └─ C（LT=2, BOM=2）: 在庫=300

計算順序: A → B → C（上流から下流）

A: progress = 100（最終品 = 在庫そのまま）
B: progress = 200 + (Aの進度100 × BOM数量1) = 300
C: progress = 300 + (Bの進度300 × BOM数量2) = 900
```

Bの進度300は「在庫200 + 親Aが消費した100」= Bが実際に生産した総量。
Cの進度900は「在庫300 + 親Bが消費した600(=300×2)」= Cが実際に生産した総量。

## 補足

- `upper_bound_date` は表示用情報として返却するが、基準日の決定には使用しない
- 棚卸初期化は専用ロジックを使い、通常の在庫再計算ロジック（`inventory_calculator.py`）を直接呼ばない
- 通常の在庫再計算ファイルは棚卸のために変更してはならない
