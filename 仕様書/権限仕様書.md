# 権限仕様書（フロントエンドUIのみ）

## 概要

本システムの権限制御は主にフロントエンドUIで行う。  
バックエンドは権限判定ロジックを持たず、APIは認証のみ（または無制限）で動作する。  
画面上の非表示/非活性に加えて、`meta.resource` が設定された画面はルータガードで遷移を制御する。

## 権限データの取得元

ログイン後、`/api/auth/me/` の `user.effective_permissions` を参照する。  
形式は以下の通り。

```
[
  { "resource": "orders", "can_view": true, "can_edit": false },
  { "resource": "production", "can_view": true, "can_edit": true }
]
```

## 判定ルール

- `can_edit = true` の場合は閲覧も許可扱いとする。
- `can_view = false` かつ `can_edit = false` は非表示または押下不可とする。
- 下層ボタン用の権限が未設定の場合は、上位（例: `production`）の権限でフォールバック判定する。

### 2-1. 画面内ライン候補のグループ制御

- `生産計画入力` と `工程作業入力` のラインプルダウンは、ログインユーザーの `profile.unit`（組織階層の「グループ」）に紐づくライン設定がある場合、そのラインのみ表示する。
- 紐づくラインが複数ある場合、`初期ライン` 指定のものを初期選択する。初期ラインが未設定の場合は表示順先頭を初期選択する。
- グループにライン紐付が1件も無い場合は、従来どおり全候補から選択可能とする。
- この制御はUI表示上の絞り込みのみであり、バックエンドAPIでは権限制御しない。
- グループにライン紐付があるユーザーには、ラインプルダウン右横に「全」ボタンを表示する。押下するとグループ制限を一時解除し、タブ内の全ラインを選択可能にする。再度押下で元のグループ制限に戻る。グループ紐付が無いユーザーには「全」ボタンは表示しない。

### 2-2. 勤務管理（シフト）

| 画面/機能 | 既定の必要権限 |
| --- | --- |
| シフト確認（作業者用） | ログイン済みユーザー |
| シフト管理（配置・週間作成・基本設定） | `overtime.shift_management` / `can_view`（未設定時は `overtime` / `can_view`） |
| 個人別残業集計（社内AI） | `overtime.personal_summary` / `can_view`。親の `overtime` 権限へフォールバックしない |
| 社内AIチャット | `ai.chat` / `can_view`。親の `ai` 権限へフォールバックしない |
| 社内AI分析画面 | `ai.analysis` / `can_view`。分析案の承認、実行、テンプレート候補の保存は `can_edit`。親の `ai` 権限へフォールバックしない |
| AI設定 | `settings.ai` / `can_view`（設定変更は `can_edit`）。分析実行設定（キャッシュ有効期限、Python時間・メモリ・CPU上限）の閲覧は `can_view`、変更は `can_edit`。未設定時は `settings` 権限へフォールバックする |

- `シフト管理` はルーターの `meta.resource` でも同じ権限を判定するため、権限のないユーザーはURLを直接入力しても開けない。
- `個人別残業集計` は、個人別の合計時間・しきい値超過者を社内AIで照会する権限である。未許可の画面ではDeepSeekに個人別集計ツールを提示せず、グループ集計だけを利用可能とする。DeepSeekへ送る氏名は一時IDへ置換し、許可された画面で回答を表示するときだけ氏名を復元する。
- `ai.chat` と `overtime.personal_summary` は、フロントエンドの表示制御だけでなく、`POST /api/ai/chat/` 側でも実効権限を検証する（詳細は `仕様書/社内AI運用規約・AI用DB辞書.md` の2-2）。この2つは `accounts.models.UserPermission.RESOURCE_CHOICES` に未登録だった時期があり、その間は一般ユーザーに権限が一切反映されなかった（2026-09-30に追加・修正）。新しいAI関連の権限を追加するときは、フロントエンドの選択肢だけでなく `RESOURCE_CHOICES` にも必ず追加すること。
- `ai.analysis`を追加するときも、`accounts.models.UserPermission.RESOURCE_CHOICES`、部署・役職・個別権限の選択肢、ルートの`meta.resource`を同時に追加する。どれか一つでも漏れると実効権限に反映されない。
- `ai.analysis`を持つ利用者は、`管理者承認待ち`と`正式`のテンプレートを一覧・再利用できる。管理者承認待ちのテンプレートには「システム管理者未承認」と常に表示し、実行前に確認を求める。`却下`と`置換済み`は再利用候補に表示しない。作成者は自分のテンプレート履歴を確認でき、`settings.ai / can_edit`を持つシステム管理者は全履歴を確認できる。
- テンプレートの承認・却下・訂正・置換は`settings.ai / can_edit`だけに表示する。`ai.analysis / can_edit`は利用者による分析案の承認、実行、候補テンプレート保存までであり、管理者確認の操作はできない。

### 5. ユーザー一覧フィルタ（ユーザー管理 / ユーザー権限編集 共通）

ユーザー一覧には以下のフィルタを持つ。

- 事業部（部署と同値）
- 係
- 班
- グループ
- 役職
- 有効のみ
- 無効のみ

各セレクトには `すべて` に加えて `未設定` を持つ。  
件数は `（絞り込み後 / 全件）` で表示する。

補足:
- ユーザー管理/ユーザー権限編集の編集フォームでは `事業部` のみ入力し、保存時に `department` と `division` を同値で保存する。
- 既存データ移行時に `グループ(unit)` が0件の場合、班(team)配下へ同名のグループ(unit)を自動補完する（初期移行用）。
- ユーザー管理/ユーザー権限編集では、「担当班（複数）」を役割に関係なく設定できる。
- 役割が `リーダー` の場合は「担当グループ（複数）」を設定する。
- 役割が `係長` または `事業部長` の場合は、下位役職兼任用として「担当班（複数）」と「担当グループ（複数）」の両方を設定できる。
- `係長` は設定した担当班で `班長` として、`事業部長` は設定した担当班/担当グループ/係で下位役職として扱える。
- 「班」フィルタは、`所属班（profile.team）` または `班長担当班（profile.supervisor_teams）` のいずれか一致でヒットさせる。
- 「グループ」フィルタは、`所属グループ（profile.unit）` または `リーダー担当グループ（profile.leader_units）` のいずれか一致でヒットさせる。

補足:

### 9. 権限テンプレート画面の個別権限ユーザー一覧

- `権限テンプレート` 画面は、既存の `部署・役職` `部署` `役職` に加えて、4つ目のタブ `個別権限ユーザー一覧` を持つ。
- このタブでは、`/api/accounts/users/` の返却値をもとに、`permissions` を1件以上持つユーザーのみ表示する。

### 10. 権限テンプレート画面の設定済みテンプレ一覧

- `権限テンプレート` 画面は、5つ目のタブ `設定済みテンプレ一覧` を持つ。
- このタブでは、`部署・役職` `部署` `役職` の各テンプレートについて、権限が1件以上登録されている設定のみ一覧表示する。
- データ取得には既存の `/api/accounts/department-position-permissions/` `/api/accounts/department-permissions/` `/api/accounts/position-permissions/` を利用する。
- 一覧項目は `種別` `部署` `役割` `設定件数` `設定権限` とする。
- この一覧は監査・確認用途であり、編集操作は持たない。

## 設定方法

権限はテンプレートを基本とし、必要なユーザーのみ個別に上書きする。

1. テンプレート（部署・役職/部署/役職）で基本権限を設定  
2. ユーザー管理で個別権限を有効化し、例外のみ追加/変更  

テンプレートと個別権限の両方が設定されている場合、個別権限が優先される。
個別権限で未チェック（`can_view=false` かつ `can_edit=false`）の項目は保存・適用対象にせず、テンプレート判定へフォールバックする。

## 注意事項

- この仕様は主にフロントエンドUI制御であり、`meta.resource` が設定された画面はURL直打ちでも制限する。
- 権限の正当性・セキュリティはバックエンドで保証しない。
- バックエンドAPIでは権限チェックを行わないため、API呼び出し自体は制限しない。
