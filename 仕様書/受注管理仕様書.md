## 概要

本システムは、複数の得意先から**内示（FORECAST）**と**確定受注（FIRM）**を受け取り、優先順位を制御しながら生産計画を立てる受注管理システムです。

### 主な特徴

- **内示と確定の二元管理**: 予測情報（内示）と正式受注（確定）を区別して管理
- **自動優先順位制御**: 確定受注が来たら、対応する内示を自動的に無効化
- **内示の自動上書き**: 毎日更新される内示を最新版で置き換え
- **複数得意先・複数フォーマット対応**: 得意先ごとに異なるCSVフォーマットに対応
- **ステージングテーブル**: CSV取込時の生データを保持し、トラブルシューティングを容易に

## 受注タイプと優先順位

### 受注タイプ（order_type）

| order_type | 日本語 | 意味 | 更新頻度 | スケジューリング優先度 |
|-----------|--------|------|----------|----------------------|
| **FIRM** | 確定 | 正式な受注、必ず生産する | 適宜 | **最高**（必ず生産計画に含める） |
| **FORECAST** | 内示 | 予測情報、変更される可能性が高い | 毎日 | 低（確定がない場合のみ使用） |

### 受注ステータス（status）

| status | 日本語 | スケジューリング | 説明 |
|--------|--------|----------------|------|
| `OPEN` | オープン | ○ 対象 | 有効な受注 |
| `SUPERSEDED` | 無効 | × 除外 | 確定受注により無効化された内示 |
| `CLOSED` | クローズ | × 除外 | 完了した受注 |
| `CANCELED` | キャンセル | × 除外 | キャンセルされた受注 |

### 受注番号体系（order_no）

```
内示（FORECAST）:
  FC-{得意先コード}-{タイムスタンプ}
  例: FC-000001-20251204153000

確定（FIRM）:
  FIRM-{得意先コード}-{タイムスタンプ}
  例: FIRM-000001-20251204153000
```

## テーブル定義

### 1. t_order（受注ヘッダ）

受注の基本情報を管理するヘッダテーブル。内示（FORECAST）と確定（FIRM）を区別して管理。

#### テーブル構造

```sql
CREATE TABLE t_order (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    customer_id BIGINT NOT NULL,
    order_no VARCHAR(50) NOT NULL,
    order_type VARCHAR(20) NOT NULL,  -- 'FIRM' or 'FORECAST'
    version_no VARCHAR(20) DEFAULT 'v1',
    source_system VARCHAR(50),
    source_file VARCHAR(200),
    order_date DATE,
    freeze_from DATE,
    status VARCHAR(20) DEFAULT 'OPEN',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    UNIQUE KEY (customer_id, order_no, order_type, version_no),
    INDEX idx_status (status),
    FOREIGN KEY (customer_id) REFERENCES m_customer(id)
);
```

#### 主要フィールド

| フィールド名 | 型 | 説明 |
|------------|-----|------|
| `order_type` | VARCHAR(20) | 受注タイプ（FIRM/FORECAST） |
| `status` | VARCHAR(20) | ステータス（OPEN/SUPERSEDED/CLOSED/CANCELED） |
| `freeze_from` | DATE | 凍結開始日（この日以降の変更を禁止） |

### 2. t_order_line（受注明細）

受注の製品別・納期別の詳細情報を管理。**スケジューリングエンジンはこのテーブルを参照して生産計画を立てる。**

#### テーブル構造

```sql
CREATE TABLE t_order_line (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    order_id BIGINT NOT NULL,
    line_no INT NOT NULL,
    product_id BIGINT,
    product_code VARCHAR(50) NOT NULL,
    quantity DECIMAL(14,3) NOT NULL,
    due_date DATE NOT NULL,
    plant_code VARCHAR(20),
    ship_to_code VARCHAR(40),
    remark VARCHAR(200),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    UNIQUE KEY (order_id, line_no),
    INDEX idx_due_date (due_date),
    INDEX idx_product_code (product_code),
    FOREIGN KEY (order_id) REFERENCES t_order(id) ON DELETE CASCADE,
    FOREIGN KEY (product_id) REFERENCES m_product(id) ON DELETE SET NULL
);
```

#### 主要フィールド

| フィールド名 | 型 | 説明 |
|------------|-----|------|
| `due_date` | DATE | 納期（スケジューリングの基準日） |
| `quantity` | DECIMAL(14,3) | 数量 |
| `product_code` | VARCHAR(50) | 製品コード |

CSVファイルから取り込んだ生データをそのまま保存。解析前の状態を保持し、トラブルシューティングに使用。

    error_message VARCHAR(200),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    INDEX idx_customer_code (customer_code),
    INDEX idx_parse_status (parse_status)

#### 解析ステータス（parse_status）

| parse_status | 説明 |
|-------------|------|
| `PENDING` | 未処理 |
| `PARSED` | 処理済 |
| `ERROR` | エラー |

## データフロー

### 全体フロー

```
┌──────────────┐
│ CSVファイル  │  ← 得意先からのCSV（内示 or 確定）
└──────┬───────┘
       │ アップロード
       ▼
┌──────────────┐
│ 1. 生データ  │  stg_order_raw
│    保存      │  ・CSVをそのまま保存（トラブルシューティング用）
└──────┬───────┘  ・エンコーディング、フォーマット情報を保持
       │ 解析・正規化
       ▼
┌──────────────┐
│ 2. 日別正規化│  stg_order_daily
│    データ    │  ・製品コード、納期、数量を抽出
└──────┬───────┘  ・得意先コード → customer_id 解決
       │         ・製品マスタ自動登録（存在しない場合）
       │ ユーザー承認・確定
       ▼
┌──────────────┐
│ 3. 正式受注  │  t_order + t_order_line
│    作成      │  ・スケジューリング対象データ
└──────┬───────┘  ・優先順位制御（内示の上書き、確定による無効化）
       │
       ▼
  スケジューリングエンジン
```

## 優先順位制御ロジック

### 1. 内示の自動上書き（毎日更新）

#### 課題
内示は毎日更新される予測データ。古い内示と新しい内示を併存させると混乱する。

#### 解決策
新しい内示CSVがインポートされると、**同じ得意先の既存内示を削除**し、新しい内示で完全に置き換える。

#### 処理フロー

```
1. 内示CSVアップロード
2. ステージングテーブルへ保存
3. ユーザーが「受注作成」実行
   ↓
4. 同じ得意先の既存内示を検索
   WHERE customer_id = ? AND order_type = 'FORECAST' AND status = 'OPEN'
   ↓
5. 既存内示を削除（CASCADE により t_order_line も削除）
   ↓
6. 新しい内示を作成
```

#### 実装コード

```python
# pm_backend/orders/services/csv_import.py:223-232
if order_type == 'FORECAST':
    order_no = f"FC-{customer.customer_code}-{timestamp}"

    # Delete existing forecast orders for this customer (overwrite)
    old_forecast_orders = Order.objects.filter(
        customer_id=customer_id,
        order_type='FORECAST',
        status='OPEN'
    )
    deleted_count = old_forecast_orders.count()
    old_forecast_orders.delete()  # CASCADE delete で OrderLine も削除
```

#### 結果
常に最新の内示のみがシステムに保持され、データの整合性が保たれる。

---

### 2. 確定受注による内示の自動無効化

#### 課題
確定受注が来たら、その製品・納期については内示は不要になる。しかし、削除すると履歴が失われる。

#### 解決策
確定受注CSVがインポートされると、**同じ製品・同じ納期の内示を自動的に無効化**（status='SUPERSEDED'）する。

#### 処理フロー

```
1. 確定CSVアップロード
2. ステージングテーブルへ保存
3. ユーザーが「受注作成」実行
   ↓
4. 確定受注を作成
   ↓
5. 重複する内示を検索
   WHERE customer_id = ?
     AND order_type = 'FORECAST'
     AND status = 'OPEN'
     AND lines.product_code IN (確定の製品コード)
     AND lines.due_date IN (確定の納期)
   ↓
6. 該当内示のstatusを'SUPERSEDED'に更新
```

#### 実装コード

```python
# pm_backend/orders/services/csv_import.py:269-288
if order_type == 'FIRM':
    # Get all due dates and products from this firm order
    firm_due_dates = [daily.due_date for daily in dailies]
    firm_product_codes = [daily.product_code for daily in dailies]

    # Find forecast orders with overlapping products and dates
    overlapping_forecast_orders = Order.objects.filter(
        customer_id=customer_id,
        order_type='FORECAST',
        status='OPEN',
        lines__product_code__in=firm_product_codes,
        lines__due_date__in=firm_due_dates
    ).distinct()

    superseded_count = overlapping_forecast_orders.update(status='SUPERSEDED')
```

#### 結果
- 確定受注が優先される
- 内示は無効化されるが履歴として残る
- スケジューリング時には無効化された内示は無視される

---

### 3. スケジューリング時の優先順位

#### 基本ルール

1. **status='OPEN'** の受注のみを使用
2. **確定（FIRM）を優先**
3. **確定がない製品・納期のみ、内示（FORECAST）を使用**

#### スケジューリング用データ取得

```python
from orders.services.csv_import import CSVImportService

# スケジューリング用の受注明細を取得
order_lines = CSVImportService.get_active_order_lines_for_scheduling(
    customer_id=1,
    start_date=date(2025, 12, 1),
    end_date=date(2025, 12, 31)
)

# 結果は due_date, order_type でソート済み
# スケジューリングエンジンは確定を優先して処理
for line in order_lines:
    if line.order.order_type == 'FIRM':
        # 確定受注 → 必ず生産計画に含める
        schedule_production(line)
    else:  # FORECAST
        # 内示 → 同じ製品・納期に確定がない場合のみ使用
        if not has_firm_order(line.product_code, line.due_date):
            schedule_tentative_production(line)
```

## CSVインポート仕様

### 対応得意先

| 得意先コード | 得意先名 | 内示 | 確定 | フォーマット識別 |
|------------|---------|------|------|----------------|
| 000001 | ティエラ | ○ | ○ | データ区分（B17/Y55） |
| 000196 | クボタ（堺・枚方） | ○ | ○ | ファイル名 + データNO/No. |
| 000018 | リーデン | - | ○ | 発注コード（509） |

### サービス指向アーキテクチャ

各得意先のCSVフォーマットに対応するため、サービスクラスを実装：

```
pm_backend/orders/services/
├── base_import.py          # 基本クラス（共通処理）
├── tiera_naiji_import.py   # ティエラ内示
├── tiera_kakutei_import.py # ティエラ確定
├── kubota_sakai_naiji_import.py
├── kubota_sakai_kakutei_import.py
├── kubota_hirakata_kakutei_import.py
└── rieden_kakutei_import.py
```

### インポート処理フロー

1. CSVファイルアップロード
2. 得意先コード + 受注タイプ + ファイル名で適切なサービスを自動選択
3. 複数エンコーディングで自動デコード（CP932, Shift-JIS, UTF-8）
4. CSV解析、データ抽出
5. `stg_order_raw` へ生データ保存
6. 解析・正規化して `stg_order_daily` へ保存
7. 製品マスタ自動登録（存在しない製品コードの場合）

### 製品マスタ自動登録

CSVに存在しない製品コードが含まれていた場合、自動的に製品マスタに登録：

## スケジューリング連携

### スケジューリングエンジンへの入力

スケジューリングエンジンは、以下のクエリで受注明細を取得：

```python
# status='OPEN' かつ 確定を優先
order_lines = OrderLine.objects.filter(
    order__status='OPEN'
).select_related('order', 'product').order_by(
    'due_date',
    'order__order_type'  # FIRM が FORECAST より先
)
```

### 生産計画への反映

1. **確定受注（FIRM）**: 必ず生産計画に含める
2. **内示（FORECAST）**: 確定がない製品・納期のみ参考として使用
3. **無効化された内示（SUPERSEDED）**: 完全に無視

### 数量集約（Aggregation）

#### 背景

実際のCSVデータ（例：ティエラ_確定.csv）では、**同じ製品コード + 同じ納期で複数行（10行以上）が存在**することがあります。これは、異なる注文番号で同じ製品・納期の受注が入るためです。

#### 要件

1. **個別情報の保持**: 各注文番号と明細情報は、後で参照する必要があるため、個別に保存
2. **スケジューリング用の集約**: 生産計画を立てる際は、製品コード + 納期で数量を合計して使用

#### 実装方法

`get_active_order_lines_for_scheduling()` メソッドは、`aggregate` パラメータで動作を切り替え：

##### 方法A: 集約モード（aggregate=True、デフォルト）

製品コード + 納期で数量を合計したデータを返す：

```python
from orders.services.csv_import import CSVImportService

# スケジューリング用：集約データ取得
aggregated = CSVImportService.get_active_order_lines_for_scheduling(
    customer_id=1,
    aggregate=True  # デフォルト
)

for item in aggregated:
    print(f"{item['product_code']}: {item['total_quantity']} ({item['line_count']}行を集約)")
    # 例: 24201-36010: 150.000 (12行を集約)
```

返却データ構造：

```python
{
    'customer_id': 1,
    'customer_code': '000001',
    'product_code': '24201-36010',
    'due_date': date(2025, 12, 10),
    'total_quantity': Decimal('150.000'),  # 合計数量
    'order_type': 'FIRM',
    'line_count': 12  # 集約した行数
}
```

##### 方法B: 個別モード（aggregate=False）

すべての注文明細を個別に返す（注文番号などの詳細情報を含む）：

```python
# 個別情報参照用：すべての明細取得
individual = CSVImportService.get_active_order_lines_for_scheduling(
    product_code='24201-36010',
    aggregate=False
)

for line in individual:
    print(f"Order: {line.order.order_no}, Line: {line.line_no}, Qty: {line.quantity}")
    # 例:
    # Order: FIRM-000001-20251204120000, Line: 1, Qty: 10.000
    # Order: FIRM-000001-20251204120000, Line: 2, Qty: 15.000
    # ...
```

## 注意事項

### 内示の削除について
- 内示の削除は **CASCADE** により、関連する `OrderLine` も自動削除されます
- 削除前に履歴を保存する必要がある場合は、別途アーカイブテーブルを検討してください

### 確定受注の無効化について
- 確定受注による内示の無効化は、**製品コードと納期が完全一致**する場合のみ行われます
- 部分一致や近似する納期は考慮されません

### スケジューリングエンジンの実装
- 現在は `get_active_order_lines_for_scheduling()` メソッドが基本的なフィルタリングのみ実装
- 実際のスケジューリングロジックは将来実装予定（`scheduling_logic_v3.md` 参照）
