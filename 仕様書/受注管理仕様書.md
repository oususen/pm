## 概要

本システムは、複数の得意先から**内示（FORECAST）**と**確定受注（FIRM）**を受け取り、優先順位を制御しながら生産計画を立てる受注管理システムです。

### 主な特徴

- **内示と確定の二元管理**: 予測情報（内示）と正式受注（確定）を区別して管理
- **自動優先順位制御**: 確定受注が来たら、対応する内示を自動的に無効化
- **内示の自動上書き**: 毎日更新される内示を最新版で置き換え
- **複数得意先・複数フォーマット対応**: 得意先ごとに異なるCSVフォーマットに対応
- **ステージングテーブル**: CSV取込時の生データを保持し、トラブルシューティングを容易に

## 受注タイプと優先順位

### 受注タイプ（order_type）

| order_type | 日本語 | 意味 | 更新頻度 | スケジューリング優先度 |
|-----------|--------|------|----------|----------------------|
| **FIRM** | 確定 | 正式な受注、必ず生産する | 適宜 | **最高**（必ず生産計画に含める） |
| **FORECAST** | 内示 | 予測情報、変更される可能性が高い | 毎日 | 低（確定がない場合のみ使用） |

### 受注ステータス（status）

| status | 日本語 | スケジューリング | 説明 |
|--------|--------|----------------|------|
| `OPEN` | オープン | ○ 対象 | 有効な受注 |
| `SUPERSEDED` | 無効 | × 除外 | 確定受注により無効化された内示 |
| `CLOSED` | クローズ | × 除外 | 完了した受注 |
| `CANCELED` | キャンセル | × 除外 | キャンセルされた受注 |

### 受注番号体系（order_no）

```
内示（FORECAST）:
  FC-{得意先コード}-{タイムスタンプ}
  例: FC-000001-20251204153000

確定（FIRM）:
  FIRM-{得意先コード}-{タイムスタンプ}
  例: FIRM-000001-20251204153000
```

### 1. t_order（受注ヘッダ）

受注の基本情報を管理するヘッダテーブル。内示（FORECAST）と確定（FIRM）を区別して管理。

```sql
    FOREIGN KEY (customer_id) REFERENCES m_customer(id)

```

#### 主要フィールド

| フィールド名 | 型 | 説明 |
|------------|-----|------|
| `order_type` | VARCHAR(20) | 受注タイプ（FIRM/FORECAST） |

## 優先順位制御ロジック

### 1. 内示の更新（製品ごとの部分置換方式）

#### 課題

内示は毎日更新される予測データだが、以下の特性がある：

- 内示CSVには「今日より先の計画」のみ含まれる（開始日は製品ごとに異なる）
- 内示の開始日より前の期間は、確定受注が入る予定の期間
- 新しい内示で古い内示を完全置換すると、確定待ちの期間のデータが消える

#### 解決策（製品ごとの部分置換）

新しい内示CSVがインポートされると、**製品ごとに、新しい内示の開始日以降のみ既存内示を無効化**する。

- 新しい内示がカバーする範囲：置き換え
- 新しい内示に含まれない近い未来：既存内示を残す（確定待ち）

#### 処理フロー

```
1. 内示CSVアップロード
2. ステージングテーブルへ保存
3. ユーザーが「受注作成」実行
   ↓
4. 製品ごとの最小納期（開始日）を記録
   例：製品A → 12/16、製品B → 12/20、製品C → 1/6
   ↓
5. 製品ごとに、開始日以降の既存OPEN内示を無効化（SUPERSEDED）
   例：製品Aは 12/16以降の既存内示を無効化
       → 12/15の内示は残る（確定待ち）
   ↓
6. 新しい内示オーダを作成し、全ての明細を追加
```

#### 実装コード

```python
# pm_backend/orders/services/csv_import.py:265-305
if order_type == 'FORECAST':
    # 製品ごとの最小納期を記録
    product_earliest_dates = {}
    for daily in dailies:
        current_earliest = product_earliest_dates.get(daily.product_code)
        if current_earliest is None or daily.due_date < current_earliest:
            product_earliest_dates[daily.product_code] = daily.due_date

    # 製品ごとに、開始日以降の既存内示を無効化
    for product_code, earliest_date in product_earliest_dates.items():
        Order.objects.filter(
            customer_id=customer_id,
            order_type='FORECAST',
            status='OPEN',
            lines__product_code=product_code,
            lines__due_date__gte=earliest_date  # 開始日以降のみ
        ).distinct().update(status='SUPERSEDED')

    # 新しい内示明細を全て作成
    for daily in dailies:
        OrderLine.objects.create(
            order=order,
            product_code=daily.product_code,
            quantity=daily.quantity,
            due_date=daily.due_date,
            ...
        )
```

#### 結果

- 新しい内示がカバーする範囲（開始日以降）のみ置き換え
- 近い未来（開始日より前）の内示は残る
- 確定受注が来たら、その時点で内示を無効化（次のセクション参照）

#### 実データ分析結果（ティエラ）

12月2日インポート時の実際のデータ：

| 製品コード | 内示開始日 | 確定受注範囲 | 動作 |
|-----------|----------|------------|------|
| 3114047 | 12/16～ | ～12/16（予定） | 12/16以降を置換、12/15は残る |
| 3016161314 | 1/6～ | ～1/5（予定） | 1/6以降を置換、それ以前は残る |
| 4388286 | 12/22～ | ～12/21（予定） | 12/22以降を置換、12/21以前は残る |

**規律**: 内示の開始日 ≒ 確定受注の最終日 + 1日

### 2. 確定受注による内示の無効化

#### 課題
確定受注が来たら、その製品・納期については内示は不要になる。しかし、削除すると履歴が失われる。

#### 解決策
確定受注CSVがインポートされると、**同じ製品・同じ納期の内示を自動的に無効化**（status='SUPERSEDED'）する。

#### 処理フロー

```
1. 確定CSVアップロード
2. ステージングテーブルへ保存
3. ユーザーが「受注作成」実行
   ↓
4. 確定受注を作成
   ↓
5. 内示を無効化（customer別ルール）
   - 得意先コード 000001/000196: 各製品の確定納期の「最遅日」までの内示を一括無効化
   - その他: 確定の製品コード×納期が一致する内示のみ無効化
```

#### 実装コード

```python
# pm_backend/orders/services/csv_import.py:269-307
if order_type == 'FIRM':
    # 000001/000196: 製品別に確定納期の最遅日までをSUPERSEDED
    for product_code, cutoff_date in product_cutoffs.items():
        Order.objects.filter(..., lines__product_code=product_code,
                             lines__due_date__lte=cutoff_date).update(status='SUPERSEDED')
    # その他: 製品コード×納期が一致する内示のみSUPERSEDED
```

#### 結果
- 確定受注が優先される
- 無効化の範囲は得意先ごとに異なる（000001/000196は「確定納期まで」無効化、それ以外は「完全一致」のみ）
- SUPERSEDEDになった内示は履歴として残り、スケジューリングでは無視される

---

### 3. スケジューリング時の優先順位

#### 基本ルール

1. **status='OPEN'** の受注のみを使用
2. **確定（FIRM）を優先**
3. **確定がない製品・納期のみ、内示（FORECAST）を使用**

#### スケジューリング用データ取得

```python
from orders.services.csv_import import CSVImportService

# スケジューリング用の受注明細を取得
order_lines = CSVImportService.get_active_order_lines_for_scheduling(
    customer_id=1,
    start_date=date(2025, 12, 1),
    end_date=date(2025, 12, 31)
)

# 結果は due_date, order_type でソート済み
# スケジューリングエンジンは確定を優先して処理
for line in order_lines:
    if line.order.order_type == 'FIRM':
        # 確定受注 → 必ず生産計画に含める
        schedule_production(line)
    else:  # FORECAST
        # 内示 → 同じ製品・納期に確定がない場合のみ使用
        if not has_firm_order(line.product_code, line.due_date):
            schedule_tentative_production(line)
```

## CSVインポート仕様

### 対応得意先

| 得意先コード | 得意先名 | 内示 | 確定 | フォーマット識別 |
|------------|---------|------|------|----------------|
| 000001 | ティエラ | ○ | ○ | データ区分（B17/Y55） |
| 000196 | クボタ（堺・枚方） | ○ | ○ | ファイル名 + データNO/No. |
| 000018 | リーデン | - | ○ | 発注コード（509） |

### サービス指向アーキテクチャ

各得意先のCSVフォーマットに対応するため、サービスクラスを実装：

```
pm_backend/orders/services/
├── base_import.py          # 基本クラス（共通処理）
├── tiera_naiji_import.py   # ティエラ内示
├── tiera_kakutei_import.py # ティエラ確定
├── kubota_sakai_naiji_import.py
├── kubota_sakai_kakutei_import.py
├── kubota_hirakata_kakutei_import.py
└── rieden_kakutei_import.py
```

### インポート処理フロー

1. CSVファイルアップロード
2. 得意先コード + 受注タイプ + ファイル名で適切なサービスを自動選択
3. 複数エンコーディングで自動デコード（CP932, Shift-JIS, UTF-8）
4. CSV解析、データ抽出
5. `stg_order_raw` へ生データ保存
6. 解析・正規化して `stg_order_daily` へ保存
7. 製品マスタ自動登録（存在しない製品コードの場合）

## スケジューリング連携

### スケジューリングエンジンへの入力

スケジューリングエンジンは、以下のクエリで受注明細を取得：

```python
# status='OPEN' かつ 確定を優先
order_lines = OrderLine.objects.filter(
    order__status='OPEN'
).select_related('order', 'product').order_by(
    'due_date',
    'order__order_type'  # FIRM が FORECAST より先
)
```

### 生産計画への反映

1. **確定受注（FIRM）**: 必ず生産計画に含める
2. **内示（FORECAST）**: 確定がない製品・納期のみ参考として使用
3. **無効化された内示（SUPERSEDED）**: 完全に無視

### 数量集約（Aggregation）

#### 背景

実際のCSVデータ（例：ティエラ_確定.csv）では、**同じ製品コード + 同じ納期で複数行（10行以上）が存在**することがあります。これは、異なる注文番号で同じ製品・納期の受注が入るためです。

#### 要件

1. **個別情報の保持**: 各注文番号と明細情報は、後で参照する必要があるため、個別に保存
2. **スケジューリング用の集約**: 生産計画を立てる際は、製品コード + 納期で数量を合計して使用

#### 実装方法

`get_active_order_lines_for_scheduling()` メソッドは、`aggregate` パラメータで動作を切り替え：

##### 方法A: 集約モード（aggregate=True、デフォルト）

製品コード + 納期で数量を合計したデータを返す：

```python
from orders.services.csv_import import CSVImportService

# スケジューリング用：集約データ取得
aggregated = CSVImportService.get_active_order_lines_for_scheduling(
    customer_id=1,
    aggregate=True  # デフォルト
)

for item in aggregated:
    print(f"{item['product_code']}: {item['total_quantity']} ({item['line_count']}行を集約)")
    # 例: 24201-36010: 150.000 (12行を集約)
```

返却データ構造：

```python
{
    'customer_id': 1,
    'customer_code': '000001',
    'product_code': '24201-36010',
    'due_date': date(2025, 12, 10),
    'total_quantity': Decimal('150.000'),  # 合計数量
    'order_type': 'FIRM',
    'line_count': 12  # 集約した行数
}
```

##### 方法B: 個別モード（aggregate=False）

すべての注文明細を個別に返す（注文番号などの詳細情報を含む）：

```python
# 個別情報参照用：すべての明細取得
individual = CSVImportService.get_active_order_lines_for_scheduling(
    product_code='24201-36010',
    aggregate=False
)

for line in individual:
    print(f"Order: {line.order.order_no}, Line: {line.line_no}, Qty: {line.quantity}")
    # 例:
    # Order: FIRM-000001-20251204120000, Line: 1, Qty: 10.000
    # Order: FIRM-000001-20251204120000, Line: 2, Qty: 15.000
    # ...
```

詳細は [scheduling_example.py](../pm_backend/orders/services/scheduling_example.py) を参照。

## 注意事項

### 内示の削除について
- 内示オーダ自体は自動削除しない。明細を新オーダへ付け替えるため、既存オーダに明細が残らなければ空オーダが残ることがある（必要ならクリーンアップ要）。

### 確定受注の無効化について
- 000001/000196 は「該当製品の確定納期の最遅日まで」をSUPERSEDED。その他は「製品コード×納期の一致」でSUPERSEDED。

### 製品マスタについて
- 取込時に製品マスタは自動登録しない。未登録品は product_id がNULLのまま受注明細に入る。

### スケジューリングエンジンの実装
- 現在は `get_active_order_lines_for_scheduling()` メソッドが基本的なフィルタリングのみ実装
- 実際のスケジューリングロジックは将来実装予定（`scheduling_logic_v3.md` 参照）
