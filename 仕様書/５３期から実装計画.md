# 工程作業入力「現在時刻のみ」高速化計画

作成日: 2026-05-26  
対象画面: `production/desktop-process-input`（必要に応じて `mobile-process-input` も同時確認）

## 1. 背景

- 現在、`現在時刻のみ` をONにした際の初期表示が遅いケースがある。
- 本来は `line_gantt_plans.processes_plan` から現在時刻スロット対象を即時表示できる。
- ただし現実装では、同一フロー内で追加の重い処理（backlog/pickup/BOM/画像等）も実行されるため、体感遅延が発生する。

## 2. 現状の主な遅延要因（Desktop）

- ガント取得後に以下処理を継続実行している。
1. `line_backlogs.getLineBacklogs` / `line_backlogs.pickup`
2. BOM展開（連産子判定・子品目展開）
3. 画像ロード
4. フロア表示マップ照合

## 3. 9月対応方針

- `現在時刻のみ` ON時は、初期表示を「ガント由来データ中心」に限定する。
- 重い処理は初期表示経路から切り離す（または後段へ移動）。
- UI挙動は `mobile-process-input` を正として、Desktopの時間スロット挙動を一致させる。

## 4. 実施範囲（9月）

1. `loadPlannedProducts()` の分岐整理
2. `filterCurrentTime=true` の高速経路を新設（早期return）
3. 低優先処理（BOM/画像/補助照合）の遅延実行化またはスキップ
4. Desktop/Mobileの挙動差分テスト追加（スロット移動・対象品番一致）
5. ログ計測追加（初期表示時間、API呼び出し回数）

## 5. 受け入れ基準（案）

1. `現在時刻のみ` ON時、初期表示が現行より明確に短縮されること
2. 同一ライン・同一工程・同一時刻で Desktop/Mobile の表示対象が一致すること
3. `« »` の時間スロット移動で、対象リスト更新が即時に近いこと
4. 通常表示（`現在時刻のみ` OFF）の既存挙動を壊さないこと

## 6. リスクと確認事項

- ガント側データ欠損時のフォールバック方針を要決定
- 連産・子品目・仕損入力時の対象判定差異が出ないか重点確認
- 既存運用で必要な補助情報（画像・補助実績）の表示タイミングを要調整

## 7. スケジュール（2026年9月）

1. 第1週: 詳細設計・影響調査
2. 第2週: 実装（高速経路・分岐整理）
3. 第3週: 結合テスト（Desktop/Mobile比較、実データ検証）
4. 第4週: 現場確認・微調整・本番反映判定

# クボタ内示/確定 仕様見直し（後日対応メモ）

作成日: 2026-06-02  
対象: クボタ（`customer_code=000196`）内示取込と出荷進度表示

## 1. 背景（現場課題）

- 遠い将来日の特定日に、補用（パーツセンター向け）で `FIRM` が1台だけ入るケースがある。
- 現行ロジックでは同一キーに `FIRM` があると内示が除外されるため、量産内示まで見えなくなる懸念がある。

## 2. 現行ロジック（確認済み）

1. クボタ堺内示取込（36番）時、同一「品番 + 納入先 + 納期」に `FIRM` があると当該 `FORECAST` を作成しない。
2. 内示再取込時は旧内示（OPEN）を `SUPERSEDED` 化して置換する（クボタは品番+納入先単位）。
3. 出荷進度照会画面は `FORECAST` を内示行、`FIRM`（または未設定）を確定行として集計表示する。

## 3. 検討論点（後日）

1. 「補用FIRMが存在しても量産内示は保持したい」という業務要件の正式化
2. 量産/補用の識別キー（データ上で何を根拠に分離するか）の確定
3. 内示除外条件の見直し方針
4. 進度・納期調整・便計画への波及影響

## 3-1. 補用FIRMの需要採用方針メモ（2026-06-03追記）

- 将来日の一部ケースでは、補用 `FIRM` と量産 `FORECAST` が同日に共存する。
- この場合、業務要件としては「`FIRM` で `FORECAST` を完全置換する」のではなく、`FORECAST + FIRM` で需要採用したい。
- 例: `FORECAST=111`、補用 `FIRM=2` の場合、需要は `113` として扱いたい。
- ただし現時点では、補用を安定して識別できる特徴量（注番規則、納入先、用途区分、ファイル種別、明細属性など）が未確定。
- そのため、現段階では実装しない。補用判定条件が確定した時点で、53期対応として実装方針を確定する。

## 3-2. G工程 / 外作候補の複数化メモ

### 経緯

- `pickup_purchase` 側で SUBCON 判定を行う際、現状は `RoutingStep` の工程情報を見て G工程 / 外作を拾っている。
- これまでは同一品番に対して、G工程 / 外作候補は実質1件前提で扱っていた。
- ただし今後のマスタ整備や工程追加により、同一品番に複数候補が発生する可能性がある。
- その場合、単純に先頭1件で決めると誤判定や需要漏れの原因になるため、事前に方針を残しておく。

### 対象箇所

- `pm_backend/apps/production/views.py`
  - `pickup_purchase()` 内の `RoutingStep.objects.filter(...)`
  - `subcon_product_process_map` を作成している判定部分
  - `child_process_id = subcon_product_process_map.get(child_id, process_id)` で工程を引き回す部分
- 参照元の工程判定
  - `process_code == 'G'`
  - `Process.is_outsource == True`

### 実装計画

1. 現状は単一候補前提のまま維持し、既存の需要計算・在庫計算への影響を最小化する。
2. 将来複数候補が確認された場合は、`RoutingStep` を複数件保持したうえで優先順を明示する。
3. 重複候補がある場合は、どの候補を採用したかをログまたは警告で追跡できるようにする。
4. 必要であれば、品番ごとの候補一覧を事前検証するチェック処理を追加する。
5. 53期実装時は、候補選定ルール（G工程優先、外作優先、手順番号優先など）を確定してからコード化する。

## 4. 方針候補（未決定）

1. 内示取込での `FIRM` 優先除外を弱め、内示データ自体は保持する
2. 需要採用時のみ `FIRM` 優先を維持する（表示/計算で使い分け）
3. 補用を識別できる場合のみ、補用FIRMを除外判定から外す
4. 補用を識別できる場合のみ、需要採用を `FORECAST + FIRM` に切り替える

## 5. 対応ステータス

- 本件は「特徴把握中」のため未実装
- 後日、実データ確認（対象品番・納期・納入先）後に設計確定して着手する
- 実装予定時期は 53期 とする

# ティエラ受注/リーデン 仕様見直し（後日対応メモ）

作成日: 2026-06-02  
対象: ティエラ（`customer_code=000001`）/ リーデン（`customer_code=000018`）

## 1. 背景

- クボタ同様に、将来日の `FIRM` と `FORECAST` の共存時の見え方・有効範囲を整理する必要がある。
- 特に内示再取込時の旧内示無効化（`SUPERSEDED`）が、業務意図どおりの単位で行われているかを確認する。

## 2. 現行ロジック（確認済み）

1. 内示再取込時は、旧 `FORECAST`（OPEN）を `SUPERSEDED` 化する。
2. クボタ以外（ティエラ/リーデン等）は、基本「品番単位」で `SUPERSEDED` 化対象を決める。
3. 確定取込時は、内示を `SUPERSEDED` 化しない（確定と内示は別管理）。
4. 需要採用ロジック上は `FIRM` 優先（同一品番・同一納期に `FIRM` があれば `FORECAST` は採用されにくい）。

## 3. 検討論点（後日）

1. ティエラ/リーデンで、`SUPERSEDED` の対象単位（品番のみで良いか、納入先/用途区分まで要るか）
2. 将来日の少量FIRM（補用・スポット）と量産内示をどう共存表示するか
3. 画面表示と計算採用の分離要否（表示は保持、採用はFIRM優先）
4. 得意先別に挙動を分けるべきか（共通化か個別ルールか）

## 3-1. 補用FIRMの需要採用方針メモ（2026-06-03追記）

- ティエラでも、将来日の補用 `FIRM` と量産 `FORECAST` が同日に共存するケースを確認した。
- このケースでは、業務要件としては `FIRM` 優先置換ではなく、`FORECAST + FIRM` で需要採用したい。
- ただし現時点では、補用を一意に識別する特徴が未確定のため、コード実装はまだ行わない。
- 補用の特徴が整理できた後に、ティエラ/リーデン向けの需要採用ロジックを53期で見直す。

## 4. 対応ステータス

- 本件は「特徴把握中」のため未実装
- 後日、対象得意先の実データでケース分類して設計確定する
- 実装予定時期は 53期 とする

# 受注ファイル自動取込（後日対応メモ）

作成日: 2026-06-02  
対象: クボタ / ティエラ / リーデンの受注取込自動化

## 1. 前提運用

1. 受注ファイルを指定フォルダへ配置する作業は人が行う
2. システムは指定フォルダを定期監視して自動取込する

## 2. 希望要件

1. 得意先種別の判定はファイル名ではなく、できるだけファイル中身で判定する
2. 異常時は通知を送る
3. 監視周期は1時間ごととする

## 3. 識別方針（案）

1. 取込種別判定はファイル名依存を避け、CSV内容のヘッダ/管理番号/列構成/得意先コード/レコード形式で判定する
2. 判定不能時のみエラー扱いとして通知し、手動確認へ回す
3. 将来的にファイル名規則が変わっても取込継続できるよう、内容判定を主軸にする

## 4. 再取込ポリシー（案）

`ポリシー` は、同じ内容または似た内容のファイルが再度フォルダに入ったときの扱いを指す。

1. 重複判断はファイル名で行う
2. 同一ファイル名は再取込しない
3. 同一得意先・同一対象期間で別ファイル名かつ中身差分がある場合は差し替え取込とみなす
4. 差し替え取込時は、既存の `SUPERSEDED` ルールを適用する
5. 部分失敗後の再実行でも二重取込にならないよう、取込履歴を持つ

## 5. 通知方針（案）

1. 取込成功時も通知する
2. 取込失敗時も通知する
3. 判定不能時は通知する
4. 重複ファイル検知時は通知する
5. 件数急減などの異常値は通知する

## 6. 実装イメージ（案）

1. 定時タスクで1時間ごとに監視フォルダを走査
2. 未処理ファイルを内容判定して既存取込サービスへ振り分け
3. 取込結果を履歴へ保存
4. 成功/失敗/重複を通知へ連携

## 7. 後日決定事項

1. 監視対象フォルダの実パス
2. 取込後ファイルの保管先（`processed` / `error` / `duplicate` など）
3. 内容判定に使うキーの正式定義
4. 異常通知の送信先ユーザー/グループ

## 8. Docker前提の補足

1. 本番環境は Docker 起動のため、監視対象フォルダはコンテナから見えるよう `volumes` で明示的にマウントする必要がある
2. 自動取込を定時タスクで実行する場合、`pm-backend` だけでなく `pm-scheduler` からも同じ監視フォルダを参照できる必要がある
3. 監視フォルダ候補は、ホスト側の専用ディレクトリを作成し、例として `./import/orders -> /app/import/orders` のように共有する
4. 人はホスト側フォルダへ受注ファイルを投入し、Docker 内の定時タスクが `/app/import/orders` を1時間ごとに監視する

# 社内通話の活用（後日対応メモ）

作成日: 2026-06-19  
対象: 社内通話データの業務活用

## 1. 検討項目

1. 1通話を録音できるようにする
2. 1通話を文字起こしできるようにする
3. 1通話を外国語から日本語へ翻訳できるようにする

## 2. 想定ユースケース

1. 社内通話内容の記録保全
2. 会話内容の確認・共有
3. 外国語通話の内容を日本語で確認

## 3. 要件メモ

1. 録音は通話開始時に自動開始する
2. 録音中であることを通話参加者全員に表示する
3. 録音データは半永久保存とする
4. 文字起こしは全通話を対象とする
5. 翻訳対象言語は、現在の `i18n` で対応している言語とする
6. 翻訳結果の閲覧対象は、話者本人とその上位者とする

## 4. 今後の確認事項

1. 通話データの取得元と保存方法
2. 録音データの保存容量とバックアップ方針
3. 文字起こし方式と精度要件
4. `i18n` 対応言語との連携方法
5. 上位者判定の基準と閲覧権限のUI制御方法
6. 個人情報・機密情報の取り扱い

## 5. 対応ステータス

- 本件は検討メモとして追加
- 詳細要件は後日整理してから実装計画を具体化する

## 6. 現在システム調査結果（2026-06-19）

1. 社内通話の既存基盤は実装済み
   - フロント: `pm-ui/src/views/notifications/NotificationCallCenter.vue`
   - API: `pm_backend/apps/notifications/views.py`
   - モデル: `pm_backend/apps/notifications/models.py`
   - 現在は `WebRTC` による 1対1 音声/ビデオ通話
2. 通話セッションには録音関連の保存先がまだ存在しない
   - 既存モデルは `CallSession` / `CallSignal` のみ
3. `notifications` API クライアントは既に通話系拡張を受けやすい構造
   - `pm-ui/src/api/resources/notifications.js` に通話APIが集約済み
4. 対応言語は既存 `i18n` で管理済み
   - `pm-ui/src/i18n.js`
   - 対応言語: `ja` / `pt` / `th` / `vi` / `id`
5. 上位者判定に使える組織情報は既存プロファイルに保持済み
   - `pm_backend/apps/accounts/models.py`
   - `division` / `group` / `team` / `unit`
   - `role`
   - `supervisor_teams`
   - `leader_units`
6. 各部署の長を取得する考え方は既にシリアライザに実装済み
   - `pm_backend/apps/accounts/serializers.py` の `DepartmentSerializer.get_head()`
7. 非同期処理の前例は既存システム内にある
   - `threading.Thread` を使う画面起点の非同期実行
   - `apscheduler` を使う定時処理基盤

## 7. 実装方針

1. 53期の初回実装は、通話中リアルタイム翻訳ではなく「通話終了後処理」を採用する
2. 録音は通話開始時にフロントエンドで自動開始する
3. 録音ファイルは通話終了後にバックエンドへアップロードして保存する
4. 文字起こしと翻訳は、録音保存後にバックエンドで非同期実行する
5. 翻訳対象言語は既存 `i18n` 対応言語を前提とし、表示先は日本語固定とする
6. 閲覧権限制御は既存ルールどおりフロントエンドUIで行う
7. ただし、APIでも最低限「通話参加者のみ取得可能」の条件は維持し、その上で翻訳結果の返却対象を話者本人と上位者に限定する

## 8. 実装計画

### 8-1. フェーズ1: データモデル拡張

1. `notifications` アプリに録音管理モデルを追加する
   - 例: `CallRecording`
   - 保持項目: `session`, `file`, `mime_type`, `file_size`, `recording_started_at`, `recording_ended_at`, `created_at`
2. `notifications` アプリに文字起こし/翻訳管理モデルを追加する
   - 例: `CallTranscript`
   - 保持項目: `session`, `source_language`, `transcript_text`, `translated_text_ja`, `status`, `error_message`, `created_at`, `updated_at`
3. 将来の再実行や分割対応を考え、`CallTranscript` は `CallSession` と 1対1 前提で始める
4. 録音データは半永久保存前提のため、物理保存先と容量監視方針を別途定義する

### 8-2. フェーズ2: API拡張

1. `CallSessionViewSet` に録音登録APIを追加する
   - `POST /api/call-sessions/{id}/recording/`
2. 録音情報取得APIを追加する
   - `GET /api/call-sessions/{id}/recording/`
3. 文字起こし・翻訳結果取得APIを追加する
   - `GET /api/call-sessions/{id}/transcript/`
4. 必要であれば再処理APIを管理者向けに別途追加する
5. シリアライザに録音状態・文字起こし状態・翻訳状態を返す項目を追加する

### 8-3. フェーズ3: フロントエンド通話画面改修

1. `NotificationCallCenter.vue` に録音自動開始処理を追加する
   - 通話接続準備時に `MediaRecorder` を開始
2. 参加者全員に録音中表示を追加する
   - バッジまたは固定ラベルで明示する
3. 通話終了時に録音を停止し、APIへアップロードする
4. 録音アップロード中、文字起こし中、翻訳済みの状態表示を追加する
5. 翻訳結果の表示エリアを通話履歴詳細または通話詳細パネルに追加する
6. 既存 `notifications.js` に録音/文字起こし取得APIを追加する

### 8-4. フェーズ4: 上位者判定ロジック

1. 話者本人は常に閲覧可能とする
2. 上位者判定は既存組織階層を使って実装する
3. 初回実装では以下を上位者候補とする
   - `unit` のリーダー
   - `team` の班長
   - `group` の係長
   - `division` の事業部長・課長
4. `supervisor_teams` と `leader_units` も判定対象に含める
5. 実装は `accounts` 側の既存階層情報を使う共通関数化を優先する

### 8-5. フェーズ5: 非同期文字起こし/翻訳処理

1. 録音保存後に非同期ジョブを起動する
2. 初回は既存実装に合わせて `threading.Thread` ベースでもよい
3. ただし再実行管理や失敗監視を考えると、将来的には専用ジョブ化を前提にする
4. 処理順は以下とする
   - 言語判定
   - 文字起こし
   - 日本語翻訳
   - 結果保存
5. `status` は `pending` / `processing` / `completed` / `failed` で管理する

### 8-6. フェーズ6: 権限とUI制御

1. 通話画面自体の表示権限は既存の `notifications / can_view` を維持する
2. 翻訳結果の表示可否はフロントエンドで判定する
3. 判定材料は `me` API と対象通話参加者の `profile` 情報を利用する
4. 録音中表示は権限に関係なく通話参加者全員へ表示する

### 8-7. フェーズ7: テスト

1. 通話開始時に録音状態へ遷移すること
2. 通話終了時に録音停止とアップロードが行われること
3. 文字起こし・翻訳状態が `pending` から `completed` へ遷移すること
4. 日本語以外の `i18n` 対応言語で翻訳結果が保存されること
5. 話者本人は閲覧できること
6. 上位者は閲覧できること
7. 上位者以外はUI上で翻訳結果が表示されないこと
8. 既存の音声通話・ビデオ通話機能を壊さないこと

## 9. 実装順序

1. モデル・マイグレーション追加
2. 録音アップロードAPI追加
3. 通話画面の自動録音と録音中表示追加
4. 通話終了時アップロード連携
5. 文字起こし/翻訳非同期処理追加
6. 結果取得API追加
7. 閲覧権限UI制御追加
8. 結合テスト

## 10. リスク

1. `MediaRecorder` の出力形式がブラウザ依存になる可能性がある
2. WebRTC の相手音声と自分音声の合成方法を統一しないと録音品質差が出る
3. 半永久保存は容量増加リスクが高い
4. 上位者判定は現場運用と完全一致しない可能性があるため、組織定義の確認が必要
5. フロントのみで権限制御する方針上、翻訳結果の秘匿要件が強い場合は追加検討が必要
