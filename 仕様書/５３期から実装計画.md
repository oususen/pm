# 生産計画画面 需要表示見直し（53期対応メモ）

作成日: 2026-07-16  
対象画面: `production/plan-input`

## 1. 背景

- 生産計画画面の「需要」列は、現状 `LineBacklog.order_qty` / `demand_qty_plan` をそのまま表示している。
- ただし業務上見たい値は、単純な需要値ではなく「在庫計算・計画在庫計算で実際に減算に使った出庫値」である。
- フロア配送のように後工程カレンダと前工程カレンダがずれる場合、`order_qty` 表示では現場感と一致しない。

## 2. 課題

1. `LineBacklog` には実在庫用の `actual_shipment_qty` はあるが、計画在庫用の出庫値列はない。
2. 計画在庫側の出庫値は、親品の複数候補、BOM数量、LT、営業日カレンダ、便判定を噛ませて都度計算している。
3. 一覧APIのレスポンス生成時に毎回その場計算すると、一ライン数百品番の画面で負荷が高い。

## 3. 53期の実装方針

1. 生産計画画面の「需要」列は、`order_qty` ではなく出庫基準値を表示する。
2. 過去日:
   - `actual_shipment_qty` を表示候補とする。
3. 当日以降:
   - 計画在庫計算で使用した出庫値を表示候補とする。
4. そのため、`LineBacklog` に計画在庫用の出庫値（例: `planned_shipment_qty`）を保持する案を第一候補とする。
5. 需要表示専用にAPI都度計算する案は、性能面から採用しない。

## 4. 実装論点

1. `planned_shipment_qty` の保存タイミング
   - `recalculate_planned_stock_qty()` 実行時に、その日の減算値を保存する。
2. 保存値の定義
   - 親製品複数対応
   - BOM数量反映
   - LT反映
   - フロア配送便判定
   - 営業日カレンダ反映
   をすべて含んだ「その日に減算した値」とする。
3. 画面表示ルール
   - 過去日: `actual_shipment_qty`
   - 当日以降: `planned_shipment_qty`
4. 既存の `ORDER_QTY使用` / `ACTUAL_OR_PLAN` 特例との整合を確認する。

## 5. ステータス

- 本件は方針メモのみ追加
- 2026-07-16 時点では未実装
- 53期で詳細設計・列追加要否・性能確認を行ってから着手する

# クボタ内示/確定 仕様見直し（後日対応メモ）

作成日: 2026-06-02  
対象: クボタ（`customer_code=000196`）内示取込と出荷進度表示

## 1. 背景（現場課題）

- 遠い将来日の特定日に、補用（パーツセンター向け）で `FIRM` が1台だけ入るケースがある。
- 現行ロジックでは同一キーに `FIRM` があると内示が除外されるため、量産内示まで見えなくなる懸念がある。

## 2. 現行ロジック（確認済み）

1. クボタ堺内示取込（36番）時、同一「品番 + 納入先 + 納期」に `FIRM` があると当該 `FORECAST` を作成しない。
2. 内示再取込時は旧内示（OPEN）を `SUPERSEDED` 化して置換する（クボタは品番+納入先単位）。
3. 出荷進度照会画面は `FORECAST` を内示行、`FIRM`（または未設定）を確定行として集計表示する。

## 3. 検討論点（後日）

1. 「補用FIRMが存在しても量産内示は保持したい」という業務要件の正式化
2. 量産/補用の識別キー（データ上で何を根拠に分離するか）の確定
3. 内示除外条件の見直し方針
4. 進度・納期調整・便計画への波及影響

## 3-1. 補用FIRMの需要採用方針メモ（2026-06-03追記）

- 将来日の一部ケースでは、補用 `FIRM` と量産 `FORECAST` が同日に共存する。
- この場合、業務要件としては「`FIRM` で `FORECAST` を完全置換する」のではなく、`FORECAST + FIRM` で需要採用したい。
- 例: `FORECAST=111`、補用 `FIRM=2` の場合、需要は `113` として扱いたい。
- ただし現時点では、補用を安定して識別できる特徴量（注番規則、納入先、用途区分、ファイル種別、明細属性など）が未確定。
- そのため、現段階では実装しない。補用判定条件が確定した時点で、53期対応として実装方針を確定する。

## 3-2. G工程 / 外作候補の複数化メモ

### 経緯

- `pickup_purchase` 側で SUBCON 判定を行う際、現状は `RoutingStep` の工程情報を見て G工程 / 外作を拾っている。
- これまでは同一品番に対して、G工程 / 外作候補は実質1件前提で扱っていた。
- ただし今後のマスタ整備や工程追加により、同一品番に複数候補が発生する可能性がある。
- その場合、単純に先頭1件で決めると誤判定や需要漏れの原因になるため、事前に方針を残しておく。

### 対象箇所

- `pm_backend/apps/production/views.py`
  - `pickup_purchase()` 内の `RoutingStep.objects.filter(...)`
  - `subcon_product_process_map` を作成している判定部分
  - `child_process_id = subcon_product_process_map.get(child_id, process_id)` で工程を引き回す部分
- 参照元の工程判定
  - `process_code == 'G'`
  - `Process.is_outsource == True`

### 実装計画

1. 現状は単一候補前提のまま維持し、既存の需要計算・在庫計算への影響を最小化する。
2. 将来複数候補が確認された場合は、`RoutingStep` を複数件保持したうえで優先順を明示する。
3. 重複候補がある場合は、どの候補を採用したかをログまたは警告で追跡できるようにする。
4. 必要であれば、品番ごとの候補一覧を事前検証するチェック処理を追加する。
5. 53期実装時は、候補選定ルール（G工程優先、外作優先、手順番号優先など）を確定してからコード化する。

## 4. 方針候補（未決定）

1. 内示取込での `FIRM` 優先除外を弱め、内示データ自体は保持する
2. 需要採用時のみ `FIRM` 優先を維持する（表示/計算で使い分け）
3. 補用を識別できる場合のみ、補用FIRMを除外判定から外す
4. 補用を識別できる場合のみ、需要採用を `FORECAST + FIRM` に切り替える

## 5. 対応ステータス

- 本件は「特徴把握中」のため未実装
- 後日、実データ確認（対象品番・納期・納入先）後に設計確定して着手する
- 実装予定時期は 53期 とする

- クボタ同様に、将来日の `FIRM` と `FORECAST` の共存時の見え方・有効範囲を整理する必要がある。

4. 得意先別に挙動を分けるべきか（共通化か個別ルールか）

# 受注ファイル自動取込（後日対応メモ）

作成日: 2026-06-02  
対象: クボタ / ティエラ / リーデンの受注取込自動化

## 1. 前提運用

1. 受注ファイルを指定フォルダへ配置する作業は人が行う
2. システムは指定フォルダを定期監視して自動取込する

## 2. 希望要件

1. 得意先種別の判定はファイル名ではなく、できるだけファイル中身で判定する
2. 異常時は通知を送る
3. 監視周期は1時間ごととする

## 3. 識別方針（案）

1. 取込種別判定はファイル名依存を避け、CSV内容のヘッダ/管理番号/列構成/得意先コード/レコード形式で判定する
2. 判定不能時のみエラー扱いとして通知し、手動確認へ回す
3. 将来的にファイル名規則が変わっても取込継続できるよう、内容判定を主軸にする

## 4. 再取込ポリシー（案）

`ポリシー` は、同じ内容または似た内容のファイルが再度フォルダに入ったときの扱いを指す。

1. 重複判断はファイル名で行う
2. 同一ファイル名は再取込しない
3. 同一得意先・同一対象期間で別ファイル名かつ中身差分がある場合は差し替え取込とみなす
4. 差し替え取込時は、既存の `SUPERSEDED` ルールを適用する
5. 部分失敗後の再実行でも二重取込にならないよう、取込履歴を持つ

## 5. 通知方針（案）

1. 取込成功時も通知する
2. 取込失敗時も通知する
3. 判定不能時は通知する
4. 重複ファイル検知時は通知する
5. 件数急減などの異常値は通知する

## 6. 実装イメージ（案）

1. 定時タスクで1時間ごとに監視フォルダを走査
2. 未処理ファイルを内容判定して既存取込サービスへ振り分け
3. 取込結果を履歴へ保存
4. 成功/失敗/重複を通知へ連携

## 7. 後日決定事項

1. 監視対象フォルダの実パス
2. 取込後ファイルの保管先（`processed` / `error` / `duplicate` など）
3. 内容判定に使うキーの正式定義
4. 異常通知の送信先ユーザー/グループ

## 8. Docker前提の補足

1. 本番環境は Docker 起動のため、監視対象フォルダはコンテナから見えるよう `volumes` で明示的にマウントする必要がある
2. 自動取込を定時タスクで実行する場合、`pm-backend` だけでなく `pm-scheduler` からも同じ監視フォルダを参照できる必要がある
3. 監視フォルダ候補は、ホスト側の専用ディレクトリを作成し、例として `./import/orders -> /app/import/orders` のように共有する
4. 人はホスト側フォルダへ受注ファイルを投入し、Docker 内の定時タスクが `/app/import/orders` を1時間ごとに監視する

### 8-3. フェーズ3: フロントエンド通話画面改修

1. `NotificationCallCenter.vue` に録音自動開始処理を追加する
   - 通話接続準備時に `MediaRecorder` を開始
2. 参加者全員に録音中表示を追加する
   - バッジまたは固定ラベルで明示する
3. 通話終了時に録音を停止し、APIへアップロードする
4. 録音アップロード中、文字起こし中、翻訳済みの状態表示を追加する
5. 翻訳結果の表示エリアを通話履歴詳細または通話詳細パネルに追加する
6. 既存 `notifications.js` に録音/文字起こし取得APIを追加する

### 8-4. フェーズ4: 上位者判定ロジック

1. 話者本人は常に閲覧可能とする
2. 上位者判定は既存組織階層を使って実装する
3. 初回実装では以下を上位者候補とする
   - `unit` のリーダー
   - `team` の班長
   - `group` の係長
   - `division` の事業部長・課長
4. `supervisor_teams` と `leader_units` も判定対象に含める
5. 実装は `accounts` 側の既存階層情報を使う共通関数化を優先する

### 8-5. フェーズ5: 非同期文字起こし/翻訳処理

1. 録音保存後に非同期ジョブを起動する
2. 初回は既存実装に合わせて `threading.Thread` ベースでもよい
3. ただし再実行管理や失敗監視を考えると、将来的には専用ジョブ化を前提にする
4. 処理順は以下とする
   - 言語判定
   - 文字起こし
   - 日本語翻訳
   - 結果保存
5. `status` は `pending` / `processing` / `completed` / `failed` で管理する

### 8-6. フェーズ6: 権限とUI制御

1. 通話画面自体の表示権限は既存の `notifications / can_view` を維持する
2. 翻訳結果の表示可否はフロントエンドで判定する
3. 判定材料は `me` API と対象通話参加者の `profile` 情報を利用する
4. 録音中表示は権限に関係なく通話参加者全員へ表示する

### 8-7. フェーズ7: テスト

1. 通話開始時に録音状態へ遷移すること
2. 通話終了時に録音停止とアップロードが行われること
3. 文字起こし・翻訳状態が `pending` から `completed` へ遷移すること
4. 日本語以外の `i18n` 対応言語で翻訳結果が保存されること
5. 話者本人は閲覧できること
6. 上位者は閲覧できること
7. 上位者以外はUI上で翻訳結果が表示されないこと
8. 既存の音声通話・ビデオ通話機能を壊さないこと

## 9. 実装順序

1. モデル・マイグレーション追加
2. 録音アップロードAPI追加
3. 通話画面の自動録音と録音中表示追加
4. 通話終了時アップロード連携
5. 文字起こし/翻訳非同期処理追加
6. 結果取得API追加
7. 閲覧権限UI制御追加
8. 結合テスト

## 10. リスク

1. `MediaRecorder` の出力形式がブラウザ依存になる可能性がある
2. WebRTC の相手音声と自分音声の合成方法を統一しないと録音品質差が出る
3. 半永久保存は容量増加リスクが高い
4. 上位者判定は現場運用と完全一致しない可能性があるため、組織定義の確認が必要
5. フロントのみで権限制御する方針上、翻訳結果の秘匿要件が強い場合は追加検討が必要

# LTマスタ保持対応（53期対応メモ）

作成日: 2026-07-19  
対象: 在庫計算 / 計画在庫計算 / 進度計算 / 定時タスク開始日決定 / LTマスタ管理

## 1. 背景

- 現状の在庫・進度再計算では、開始日決定時に製品ごとの `直LT` または `累積LT` をその場で取得している。
- 特に進度計算は `累積LT` が必要であり、対象製品数が多いタスクでは都度計算の負荷が大きい。
- 実測では、全製品総当たり時に `直LT` より `累積LT` の取得が大幅に重く、定時タスク全体時間にも影響する。
- また、開始日決定と実計算で別ロジック・別取得範囲を使うと、調整値や需要の取得範囲ずれが起きやすい。

## 2. 53期の方針

1. `LT計算` と `在庫/進度再計算` の責務を分離する。
2. `直LT` / `累積LT` は、実行時その場計算ではなくマスタ保持した値を参照する方式へ寄せる。
3. 在庫系は `直LT`、進度系は `累積LT` を使う方針自体は維持する。
4. 開始日決定に使うLT値と、実計算に必要な取得範囲は必ず同じ基準で統一する。
5. 53期では `LTをマスタに持たせる実装` を正式対応対象とする。

## 3. 実装イメージ

1. 製品単位、または `product × line/process` 単位で LT保持用マスタを持つ。
2. 保存候補値は少なくとも以下とする。
   - `direct_lt_days`
   - `cumulative_lt_days`
3. 既存マスタへの列追加か、専用LTマスタ新設かは53期で確定する。
4. BOM または Routing 更新時に、該当製品の LT再計算を行う。
5. 定時タスク・手動再計算・納入予定再計算は、保存済みLTを読むだけにする。
6. 実計算側では、開始日だけでなく以下の取得範囲も同じ LT基準にそろえる。
   - `LineBacklog`
   - `LineDemand`
   - 調整値

## 4. 実装計画

1. 現行の `直LT` / `累積LT` 参照箇所を棚卸しする。
2. LTを保持するマスタ構造を決める。
3. 既存 `m_product` 等への列追加か、専用LTマスタ新設かを比較して確定する。
4. BOM/Routing変更時の再集計トリガを決める。
5. 初回一括集計バッチを用意する。
6. 定時タスク・画面再計算の開始日決定を保存済みLT参照へ切り替える。
7. `取得範囲` と `計算範囲` が同一LT基準で同期していることをテストで保証する。

## 5. 期待効果

1. 進度再計算時の `累積LT` 都度計算を削減できる。
2. 大量製品を対象にした定時タスクの開始日決定が安定する。
3. `取得範囲` と `計算範囲` のずれによる不整合を減らせる。
4. 将来的な製品増加・ライン増加に対して性能劣化を抑えやすくなる。

## 6. 留意点

1. LTをマスタに保持する場合、BOM/Routing変更時の再集計漏れを防ぐ必要がある。
2. どの粒度で保存するか（製品単位か、ライン/工程込みか）は53期で詳細設計する。
3. 事前集計済みマスタへ移行しても、例外品番や未整備マスタのフォールバック方針は残しておく。

# バックエンド権限制御の段階導入（53期対応メモ）

作成日: 2026-07-23  
対象: `accounts` / `production` / `purchase` / `shipping` / `system_settings` の更新系API

## 1. 背景

- 現状の権限制御は、基本的にフロントエンドUIとルータの `meta.resource` による制御が中心である。
- このため、通常操作やURL直打ちはかなり抑止できている。
- ただしバックエンドAPI側は、多くの画面で `IsAuthenticated` のみ、または一部 `AllowAny` で動作している。
- そのため、ログイン済みユーザーが開発者ツールやAPIクライアントから直接リクエストした場合、権限外の更新・削除・実行が通る余地がある。

## 2. 53期の方針

1. バックエンド権限制御は、危険度の高い `POST` / `PUT` / `PATCH` / `DELETE` / 実行系APIから段階導入する。
2. 権限キーは、既存フロントエンドで使用している `resource` と `effective_permissions` をそのまま流用する。
3. フロントエンドの表示制御は維持しつつ、最終判定はバックエンドで行う構成へ寄せる。
4. 初回導入では閲覧系 `GET` を全面対象にせず、更新・削除・実行系を優先する。
5. 53期では「全面一括置換」ではなく、「優先対象を絞った段階導入」を正式方針とする。

## 3. 優先対象

1. `settings.users`
   - `/api/accounts/users/`
   - ユーザー作成・更新・有効無効変更を保護対象とする。
2. `settings.permission_templates`
   - `/api/accounts/department-permissions/`
   - `/api/accounts/position-permissions/`
   - `/api/accounts/department-position-permissions/`
   - テンプレート権限の更新系を保護対象とする。
3. `settings.user_permissions`
   - ユーザー個別権限の更新系を保護対象とする。
4. `settings.scheduled_tasks`
   - `/api/schedule-config/run-now/`
   - `/api/schedule-config/cancel/`
   - `/api/schedule-config/purchase-actual-reconcile/fix/`
   - `/api/schedule-config/production-actual-reconcile/fix/`
   - 手動実行・キャンセル・整合修正を保護対象とする。
5. `settings.purchase_order_approval`
   - `/api/purchase-order-approval-config/`
   - 発注承認経路の更新を保護対象とする。
6. `production.plan_input` / `production.progress`
   - `/api/line-plans/`
   - `/api/line-backlogs/`
   - `/api/line-demands/`
   - 生産計画・需要・進度基礎データの更新/削除を保護対象とする。
7. `production.orders` / `production.stock_allocations`
   - `/api/production-orders/`
   - `/api/stock-allocations/`
   - 製造指示・在庫引当の更新系を保護対象とする。
8. `purchase.actual_edit` / `purchase.progress`
   - `/api/purchase-actual/<id>/`
   - `/api/purchase-receiving/recalculate-progress/`
   - 納入実績編集・進度再計算を保護対象とする。
9. `shipping.progress_edit` / `shipping.actual`
   - `/api/shipping-progress/adjust/`
   - `/api/shipping-actual-edit/`
   - 出荷進度調整・出荷実績編集を保護対象とする。
10. `purchase.order_proposals` / `purchase.auto_delivery_list`
    - 発注承認・送信・自動送信即時実行系を保護対象とする。

## 4. 実装方針

1. `accounts` 配下に共通のバックエンド権限クラスまたは共通判定関数を用意する。
2. APIごとに必要な `resource` と `view/edit` レベルを明示する。
3. 既存 `effective_permissions` と同じ判定ルールをバックエンドでも採用する。
   - `can_edit=true` は閲覧可を含む
   - 下位権限未設定時は親権限フォールバックを許容する
4. まずは `APIView` / `ViewSet` の更新系メソッドに個別適用し、その後共通Mixin化を進める。
5. 既に個別実装済みの画面は、その実装方針に寄せて整理統合する。

## 5. 実装順序

1. 共通権限クラスまたは共通判定関数を追加する。
2. `settings.users` / `settings.permission_templates` / `settings.user_permissions` を先行保護する。
3. `settings.scheduled_tasks` / `settings.purchase_order_approval` を保護する。
4. `production` / `purchase` / `shipping` の更新・削除・実行系へ拡大する。
5. 影響確認後、必要に応じて機密性の高い `GET` 系APIへ適用範囲を広げる。

## 6. 受け入れ基準

1. 権限なしユーザーが対象更新系APIを直接呼び出しても `403` になること。
2. 権限ありユーザーの既存業務フローが維持されること。
3. フロントエンドUI制御とバックエンド判定で `resource` の意味が一致していること。
4. 手動実行・削除・承認などの高リスク操作が、対象 `resource` なしでは実行できないこと。

## 7. 留意点

1. 一気に全面適用すると既存運用への影響範囲が大きいため、53期は段階導入とする。
2. 既存APIには `IsAuthenticated` 前提の実装が多く、適用時は業務画面単位で影響確認が必要である。
3. `AllowAny` のAPIは、権限制御以前に認証要否そのものを再点検する。
4. フロントエンドのみの抑止は維持価値があるため、バックエンド導入後もUI制御は残す。
