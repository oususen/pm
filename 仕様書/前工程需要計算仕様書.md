# 前工程需要計算仕様書

## 概要

前工程（最終ライン以外のライン）の需要は、後工程ラインの計画数量から逆算して計算されます。
この処理は `pickup` API で実行されます。

## 需要計算フロー

```
最終ライン（完成品）
    ↑ LineDemand（受注データ）から需要取得

前工程ライン（中間品）
    ↑ 後工程ラインの計画数 × BOM個数
    ↑ リードタイムで日付をシフト
```

## pickup処理の詳細

### 処理ステップ

| ステップ | 処理内容 |
|---------|---------|
| 1 | このラインの製品を「最終品」「中間品」に分類 |
| 2 | **最終品**: LineDemand（受注）から `order_qty` を取得 |
| 3 | **中間品**: BOMで親製品を特定 |
| 4 | 親製品を出力する後工程ラインを特定（RoutingStep経由） |
| 5 | 後工程の計画数を取得 |
| 6 | **前工程需要 = 後工程計画数 × BOM個数** |
| 7 | リードタイムを考慮して日付をシフト |
| 8 | 結果を `LineBacklog.order_qty` に保存 |

### 例

```
後工程（組立ライン）: 製品A を 100個 計画
    ↓ BOMで製品Aは部品Bを2個使う
前工程（部品ライン）: 部品B の需要 = 100 × 2 = 200個
```

## 後工程ラインの特定（ステップ4）

### ロジック

1. BOMで現ラインの製品（中間品）の親製品を特定
2. `RoutingStep` で親製品を `output_product_id` として持つ工程を検索
3. その工程が属するラインが「後工程ライン」

### コード参照

```python
# views.py 880-886行目
downstream_steps = downstream_steps_by_product.get(parent_product.id, [])
for d_step in downstream_steps:
    downstream_line_id = d_step.line_id  # 後工程ラインID
```

## 後工程の計画数取得（ステップ5）

### 参照先の優先順位

| 優先順位 | 参照元 | 対象製品 |
|---------|--------|---------|
| **1** | LineGanttPlan | 親製品（直接使用する製品） |
| **2** | LineGanttPlan | ライン最終品（フォールバック） |
| **3** | LineBacklog | 親製品 |
| **4** | LineBacklog | ライン最終品（フォールバック） |

### フォールバックロジック

```
親製品（製品382）の計画あり → 製品382の plan_qty を使用
親製品の計画なし → ライン最終品（製品111）の plan_qty を使用
```

### コード参照

```python
# views.py 899-940行目
target_ids = [parent_product.id]  # 親製品
if routing_final_product and routing_final_product != parent_product:
    target_ids.append(routing_final_product.id)  # ライン最終品も追加

# 親製品優先、なければ最終品
qty = parent_map.get(plan_date)
if qty is None or qty <= 0:
    qty = final_map.get(plan_date)  # フォールバック
```

## 需要日の決定

### 基本ルール

```
前工程の需要日 = 後工程の計画日 − リードタイム（営業日）
```

### 後工程の計画日の取得元

| 優先順位 | 参照元 | 日付の取得方法 |
|---------|--------|---------------|
| **1** | LineGanttPlan | `start_datetime` から日付を取得 |
| **2** | LineBacklog | `plan_date` |

### 日替わり8時ルールの適用

LineGanttPlanの `start_datetime` から日付を取得する際、日替わり8時ルールを適用します。

```
日替わり8時ルール:
- 8時より前の時刻 → 前日として扱う
- 8時以降の時刻 → 当日として扱う
```

**例:**
```
start_datetime = 2026-01-27 00:55:00
    ↓ 0:55は8時より前なので前日扱い
業務上の日付 = 2026-01-26
```

### リードタイムの優先順位

| 優先順位 | 参照先 | 説明 |
|---------|--------|------|
| **1** | RoutingStep.lead_time_days | 現ラインの工程に設定されたLT（0も有効値として扱う） |
| **2** | BOMItem.lead_time_days | BOM明細に設定されたLT |
| **3** | 0 | 設定なし（同日） |

### 計算例

```
後工程（ライン11）:
  - LineGanttPlan.start_datetime = 2026-01-27 00:55:00
  - 日替わり8時ルール適用後 = 2026-01-26

前工程（ライン10）:
  - リードタイム = 1営業日
  - 需要日 = 2026-01-26 - 1営業日 = 2026-01-25（土日祝考慮）
```

## 今後対応予定

### pickup日付判定の品目別化（将来対応）

`start_datetime` ではなく `processes_plan` の `output_product_id` ごとの `start_time` を使って、
品目単位で需要日を判定する方式を検討中。

- 背景: 同一 `plan_id` に8時前開始のサブ工程と8時以降開始の親工程が混在するケースで、品目ごとに期待日付が異なる。
- 現状: 本対応は未完了のため、現在の仕様は `start_datetime` 基準（8時境界）を採用。
- 方針: 将来の改修で、pickup日付判定を品目別ロジックへ切替する。

## 関連テーブル

| テーブル | 用途 |
|---------|------|
| LineBacklog | 工程単位の計画・需要・実績・在庫を管理 |
| LineGanttPlan | ガントチャートの計画（start_datetime含む） |
| LinePlan | ライン計画（ユーザー入力） |
| BOM / BOMItem | 部品構成（親子関係、個数、LT） |
| RoutingStep | 工程定義（ライン、製品、LT） |
| LineDemand | 受注展開データ（最終ラインの需要） |

## 関連API

| エンドポイント | 用途 |
|---------------|------|
| `POST /line-backlogs/pickup` | 需要取得・計算 |
| `POST /line-plans/save` | ライン計画保存 |
| `POST /line-backlogs/expand_processes` | 計画を工程レベルに展開 |
| `POST /line-backlogs/recalculate_inventory` | 在庫・計画在庫を再計算（進度は在庫再計算で実施） |
| `POST /line-gantt-plans/generate` | ガントを再生成 |

## 保存フロー

```
1. 画面で「保存」
2. POST /line-plans/save → LinePlanに保存
3. POST /line-backlogs/expand_processes → 同一ライン内の工程に展開してLineBacklog.plan_qtyを更新
4. POST /line-backlogs/recalculate_inventory → 在庫・計画在庫を再計算（進度は在庫再計算で実施）
5. POST /line-gantt-plans/generate → ガントを再生成
```

**注意**: 前ライン（他ライン）への需要反映は保存時ではなく、pickup（取り込み）で行う運用です。

## 共用部品の処理

### 問題点

異なる完成品（A製品、B製品）が同一ライン内で同じ部品を使用する場合、
工程展開時に同じキー（出力品ID, 工程ID, 日付, 順序）が複数回発生します。

### 解決策

スキップではなく**加算方式**を採用:

```python
# 同じキーの場合、plan_qtyを加算
entry['plan_qty'] += Decimal(qty_value or 0)
```

### 計画変更時の対応

影響範囲（変更された計画に対応するライン内工程）を**削除してから再作成**:

```python
# 影響範囲のレコードを削除
LineBacklog.objects.filter(q_filter).delete()

# 集計結果で再作成
for key, entry in aggregated.items():
    LineBacklog.objects.update_or_create(...)
```

## 計画削除時の連動削除

### 問題点

`LinePlan` を削除しても、展開先の `LineBacklog` が残る問題がありました。
（展開先の製品IDは元の製品IDと異なる場合があるため）

### 解決策

`plan_id` で `LineBacklog` を削除:

```python
# 削除前にplan_idを取得
existing_plan_ids = list(LinePlan.objects.filter(...).values_list('plan_id', flat=True))

# LinePlanを削除
LinePlan.objects.filter(...).delete()

# plan_idでLineBacklogを削除
LineBacklog.objects.filter(plan_id__in=existing_plan_ids, sequence_no__gt=0).delete()
```
