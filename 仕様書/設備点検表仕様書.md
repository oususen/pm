# 設備点検表仕様書

## 1. 目的

紙運用している設備点検表を、PMアプリ上で以下の3段階で運用できる状態にする。

1. 点検項目と帳票版の作成・確認・承認
2. 承認済みテンプレートを使った日次/定期実測の実施入力
3. 実施結果に対する週間リーダ確認、月間班長確認

加えて、各確認項目に対して「どこをどう見るか」を示す付表を持てるようにし、写真・確認ポイント・OK例/NG例を実施画面から参照できるようにする。

対象ファイル:
- `板金3連定置SPOT 設備点検表（20250411).xlsx`
- 初期対象シート: `SM-009`

## 2. 画面構成

配置:
- `品質` → `設備点検表` → `点検項目作成`
- `品質` → `設備点検表` → `点検実施`
- `品質` → `設備点検表` → `月間確認`
- `通知` → `タスク受信箱`
- `マスタ` → `設備マスタ`

画面:
- `点検項目作成`（`/quality/equipment-inspection/master`）
  - テンプレート一覧
  - テンプレート編集（ヘッダ + 点検項目）
  - 項目ごとの付表編集
  - ワークフロー操作
  - ワークフロー履歴
- `点検実施`（`/quality/equipment-inspection/operation`）
  - 承認済みテンプレート選択
  - 点検日/区分（日次点検・定期実測）指定
  - 実施結果入力
  - 項目付表参照
- `月間確認`（`/quality/equipment-inspection/monthly-review`）
  - 月度・設備単位の実績一覧
  - 週間リーダ確認
  - 月間班長確認
- `タスク受信箱`（`/tasks`）
  - `業務` と `類別` で購買タスクと品質タスクを類別表示
  - 品質タスクは `設備点検表` 類別で表示
  - `班長確認 / 係長承認 / 部長承認` を一覧化
- `設備マスタ`（`/masters/equipment`）
  - 設備コード/設備名/ライン/工程/表示順/有効/備考の管理

## 3. データモデル

### 3.0 設備マスタ

テーブル: `m_equipment`

主要項目:
- `equipment_code`（設備コード, 一意）
- `equipment_name`（設備名）
- `line`（`m_line` FK, 任意）
- `process`（`m_process` FK, 任意）
- `display_order`
- `is_active`
- `notes`

### 3.1 設備点検表テンプレート

テーブル: `quality_equipment_inspection_template`

主要項目:
- `sheet_code`（例: `SM-009`）
- `sheet_name`
- `title`
- `source_sheet_name`
- `revision_date`
- `revision_notes`
- `effective_from`
- `version`
- `status`
- `created_by`, `reviewer_user`, `chief_user`, `approver_user`
- `reviewed_by`, `reviewed_at`, `chief_reviewed_by`, `chief_reviewed_at`, `approved_by`, `approved_at`
- `rejection_comment`
- `is_active`

ステータス:
- `DRAFT`
- `SUPERVISOR_PENDING`
- `CHIEF_PENDING`
- `MANAGER_PENDING`
- `APPROVED`
- `REJECTED`

補足:
- 同一 `sheet_code` で複数版を持てる
- 承認時に同一 `sheet_code` の旧有効版を無効化する

- `item_name`
- `standard`
- `frequency`
- `method`

- `unit`
- `criteria`
- `is_required`
- `is_active`

### 3.3 項目付表

テーブル: `quality_equipment_inspection_item_attachment`

主要項目:
- `item`（FK）
- `display_order`
- `title`
- `description`
- `check_point`
- `ok_example`
- `ng_example`

用途:
- 点検箇所写真

### 3.4 設備点検実施ヘッダ

テーブル: `quality_equipment_inspection_record`

主要項目:
- `template`（FK, 実施時点のテンプレート参照）
- `sheet_code`
- `sheet_name`
- `template_title`
- `template_version`
- `operation_date`
- `section_type`（`DAILY` / `QUARTERLY`）
- `operator`
- `status`（`DRAFT` / `COMPLETED`）
- `overall_result`（`OK` / `NG`）
- `memo`
- `completed_at`

制約:
- 一意キーは `sheet_code + operation_date + section_type`

補足:
- 月中でテンプレート版が切り替わっても月度集計できるよう、実施は `sheet_code` 基準で管理する
- 実施時の帳票タイトル・版数はスナップショットとして保持する

### 3.5 設備点検実施明細

テーブル: `quality_equipment_inspection_result`

主要項目:
- `record`（FK）
- `item`（元点検項目 FK, 任意）
- `display_order`
- `inspection_no`
- `item_name`
- `standard`
- `frequency`
- `method`
- `record_type`
- `unit`
- `criteria`
- `is_required`
- `numeric_value`
- `photo_url`
- `text_value`
- `judgement`（`OK` / `NG`）
- `comment`
- `measured_at`

補足:
- 実施時点の項目文言をスナップショット保持する
- `CHECK` は判定のみ、`NUMERIC` / `TEXT` は値 + 判定、`PHOTO_NUMERIC` は写真+数値+判定、`PHOTO` は写真+判定を保持する

### 3.6 週次/月次確認

テーブル: `quality_equipment_inspection_confirmation`

主要項目:
- `sheet_code`
- `sheet_name`
- `target_month`（対象月の1日）
- `confirm_type`（`WEEKLY_LEADER` / `MONTHLY_CHIEF`）
- `week_index`
  - 週間リーダ確認: `1..n`
  - 月間班長確認: `0`
- `confirmed_by`
- `comment`
- `confirmed_at`

補足:
- 対象月内の週間区切りは `月曜始まり、日曜終わり`
- `MONTHLY_CHIEF` 登録後、その月の実施結果はロックする

### 3.7 テンプレート承認タスク

テーブル: `quality_equipment_inspection_task`

主要項目:
- `template`（FK）
- `task_type`（`SUPERVISOR_REVIEW` / `CHIEF_REVIEW` / `MANAGER_APPROVE`）
- `assigned_to`
- `status`（`PENDING` / `DONE` / `SKIPPED`）
- `due_date`
- `created_at`
- `done_at`

補足:
- タスク受信箱では `module=QUALITY`、`task_category=EQUIPMENT_INSPECTION` として類別する
- 確認/承認遷移時に次段のタスクを新規作成する
- 差戻し時は未完了タスクを `SKIPPED` に更新する

### 3.8 ワークフロー履歴

テーブル: `quality_equipment_inspection_workflow_log`

主要項目:

- `from_status`
- `to_status`
- `actor`
- `comment`
- `created_at`

## 4. 業務フロー

### 4.1 テンプレート作成フロー

1. 作成者が下書き保存
2. 作成者が確認依頼
3. 班長担当へ `班長確認` タスクを送る
4. 班長が確認完了
5. 係長担当へ `係長承認` タスクを送る
6. 係長が承認
7. 部長担当へ `部長承認` タスクを送る
8. 部長が承認
9. 承認済みテンプレートが実施対象になる

差戻し:
- 班長確認待ち / 係長承認待ち / 部長承認待ちから差戻し可能
- 差戻し後は `REJECTED`

### 4.2 実施フロー

1. 作業者が承認済みテンプレートを選択
2. 点検日と区分（日次点検 / 定期実測）を指定
3. 点検結果を入力
4. 必要時、項目付表を参照して確認箇所を確認
5. 下書き保存または点検完了

完了時ルール:
- 必須項目は入力必須
- 値を入力した項目は判定入力必須
- 1件でも `NG` があれば総合判定は `NG`
- `NUMERIC` 項目で判定基準または規格から数値条件を解釈できる場合、基準外の測定値では `OK` を選択不可
- `点検完了` 時に `NG` を含む場合、実施者の所属グループを担当するリーダーへ通知する

### 4.3 週間リーダ確認 / 月間班長確認

1. 月度一覧で日次点検実績を確認
2. 各週単位でリーダが確認登録
3. 月度締めで班長が月間確認登録
4. 月間班長確認後、その月の実施データは更新不可

## 5. 自動判定ルール（テンプレート承認ルート）

作成者の `profile.department` / `profile.role` を基準に判定する。

- 班長担当:
  - まず、作成者の所属班を `supervisor_teams` で担当している班長（`supervisor`）を優先
  - 該当者がいない場合は、同事業部の班長から採用

- 係長担当:
  - まず、作成者と同じ `profile.group` の係長（`chief`）を優先
  - 該当者がいない場合は、同事業部の係長から採用

- 部長担当:
  - 同事業部の部長（`manager`）を採用

補足:
- 確認依頼時に部長担当が判定できない場合は確認依頼不可
- 班長担当または係長担当が不在の場合は、存在する次段へスキップしてタスク送信する

## 6. API

### 6.1 テンプレート

ベース:
- `/api/equipment-inspection-templates/`

主なエンドポイント:
- `GET /` 一覧
- `POST /` 作成
- `GET /{id}/` 詳細
- `PUT /{id}/` 更新
- `DELETE /{id}/` 削除
- `POST /{id}/submit_for_review/`
- `POST /{id}/review/`
- `POST /{id}/approve/`
- `POST /{id}/reject/`
- `GET /{id}/workflow_logs/`
- `POST /upload_attachment_image/`
  - 項目付表画像アップロード
- `GET /api/equipment-inspection-tasks/`
  - タスク受信箱用
  - `assigned_to_me`, `status`, `task_type` で絞り込み

補足:
- `GET /?for_operation=true`
  - 承認済みかつ有効なテンプレートのみ取得

### 6.2 実施

ベース:
- `/api/equipment-inspection-records/`

主なエンドポイント:
- `GET /` 実施一覧
  - `sheet_code`, `operation_date`, `month`, `section_type`, `status` で絞り込み
- `POST /` 実施新規保存
- `GET /{id}/` 実施詳細
- `PUT /{id}/` 実施更新
- `GET /prepare/?sheet_code=...&operation_date=...&section_type=...`
  - 既存実施があれば返す
  - なければ承認済みテンプレートから初期明細を返す
- `GET /monthly_overview/?sheet_code=...&month=YYYY-MM`
  - 月間実績、週間/月間確認、週区切り情報を返す

### 6.3 週間/月間確認

ベース:
- `/api/equipment-inspection-confirmations/`

主なエンドポイント:
- `GET /` 一覧
  - `sheet_code`, `month`, `confirm_type` で絞り込み
- `POST /upsert/`
  - 週間リーダ確認、月間班長確認の作成/更新

### 6.4 設備マスタ

- `/api/equipments/`
- 一覧/作成/更新/削除（標準CRUD）

## 7. 権限制御

本機能も既存ルールに従い、権限制御はフロントエンドUIのみで行う。

- 閲覧: `quality` の `can_view` 以上
- 編集/実施/確認操作: `quality` の `can_edit`

バックエンド側では権限制御を行わず、認証のみ必須とする。
