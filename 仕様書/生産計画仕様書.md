# 生産計画機能仕様書

## 概要

ライン別に製品の生産計画を立案・管理する機能。
1日に複数ロット（順序）の計画を登録可能で、後工程需要を取り込み、工程展開と在庫計算を自動実行する。

## 関連テーブル

### LinePlan（ライン別生産計画）

ユーザーが入力した生産計画を保持するテーブル。

| フィールド名 | 型 | 説明 |
|------------|-----|------|
| plan_date | DATE | 計画日 |
| process | FK | 工程 |
| product | FK | 製品 |
| line | FK | ライン |
| plan_qty | INT | 計画生産数 |
| sequence_no | INT | 順序番号（同日内のロット順序） |
| plan_id | VARCHAR | 計画ID（自動生成） |
| created_at | DATETIME | 作成日時 |
| updated_at | DATETIME | 更新日時 |

#### 制約

- `unique_together`: `(plan_date, line, sequence_no)`
  - 同じライン・同じ日・同じ順序番号は重複不可
- `indexes`: `(plan_date, line)`
  - 日付・ライン検索の高速化

### LineBacklog（ライン別バックログ）

生産計画と在庫情報を保持するメインテーブル（LinePlanから展開される）。

| フィールド名 | 型 | 説明 |
|------------|-----|------|
| plan_date | DATE | 計画日 |
| process | FK | 工程 |
| product | FK | 製品 |
| line | FK | ライン |
| order_qty | INT | 後工程需要（内示/計画） |
| plan_qty | INT | 計画生産数 |
| actual_qty | INT | 実績生産数 |
| stock_qty | INT | 実在庫 |
| planned_stock_qty | INT | 計画在庫 |
| adjust_qty | INT | 調整数 |
| scrap_qty | INT | 仕損数 |
| actual_shipment_qty | INT | 実績出庫数 |
| sequence_no | INT | 順序番号 |
| plan_id | VARCHAR | 計画ID |
| demand_qty_plan | INT | 需要数量（pickupで計算したorder_qtyと同値を保存。需要行の表示判定に使用） |

## 計画ID（plan_id）の生成ルール

計画を一意に識別するためのID。

### 生成形式

```
{product_code}_{YYYYMMDD}_{qty_label}_{sequence_no}
```

### 構成要素

- `product_code`: 製品コード
- `YYYYMMDD`: 計画日（8桁）
- `qty_label`: 計画数量のラベル
  - 小数点がある場合は `.` を `p` に置換（例: `10.5` → `10p5`）
  - 末尾の `0` と `.` は削除（例: `10.0` → `10`）
- `sequence_no`: 順序番号

### 例

| 製品コード | 計画日 | 計画数量 | 順序番号 | 生成されるplan_id |
|----------|--------|---------|---------|-----------------|
| ABC123 | 2025-01-15 | 100 | 1 | ABC123_20250115_100_1 |
| ABC123 | 2025-01-15 | 50 | 2 | ABC123_20250115_50_2 |
| XYZ789 | 2025-01-16 | 10.5 | 1 | XYZ789_20250116_10p5_1 |

## 主要な機能

### 1. 生産計画の取り込み（pickup）

後工程の計画情報をLineBacklogに反映。

**補足（demand_qty_plan）**:
- `demand_qty_plan` は **LineDemand ではない**。
- `pickup` で計算した **`order_qty` と同値**を保存し、需要行の表示判定に使用する。
  - 最終品: OrderLine（内示/確定）から算出
  - 中間品: 後工程の plan_qty × BOM で算出

#### 処理フロー

1. `LineBacklog.pickup()` APIを呼び出し
   - 後工程のLinePlanから前工程への需要を計算
   - LineBacklogに`order_qty`として反映
2. 在庫再計算APIを実行
   - 実在庫・計画在庫を更新（進度は在庫再計算で実施）

#### ガント計画とfallbackの重複排除

後工程需要の算出では、ガント計画（`t_line_gantt_plan`）を優先しつつ、
ガントが不足する場合は後工程の`LineBacklog.plan_qty`をfallbackとして使用する。

同一計画の二重計上を防ぐため、**plan_idが一致する場合はfallback側を除外**する。

- ガント計画の`plan_id`と、後工程LineBacklogの`plan_id`が一致する場合は、fallbackから除外
- これにより、ガント由来の計画とLineBacklog由来の計画が同じ`plan_id`で重複加算されない

#### 前工程需要の需要日判定

- `pickup` で後工程ガントを参照する際、需要日の判定は `LineGanttPlan.start_datetime` を使用する。
- 日替わり8時ルールを適用し、`08:00` より前の開始時刻は前日として扱う。

#### LineDemand展開におけるリードタイム換算ルール

- 展開はルーティングの `hierarchy_path` を親子関係として辿り、系統ごとに日付を計算する。
- 展開対象の品番は **`routing_step.output_product` を優先**（未設定の場合は受注明細の品番）。
- **DAY工程**: `lead_time_days` を営業日換算で遡る。
- **MINUTE工程**: `duration_min` を累積し、営業日換算で日数に加算する。
  - 換算基準: 480分 = 1日
  - 切り捨て方式: `floor(累積分 / 480)`（480分未満は0日）
  - 例: 1日 + 20分 + 20分 → 1.166...日 → **1日**扱い

#### LineDemand展開の数量換算（BOM倍率）

- 合計数量はBOMで決定する。最終品1個あたりのBOM倍率（有効BOMを再帰展開して算出）が需要の合計となる。
- 同一品番が複数のルーティングステップに出現する場合、BOMパス倍率で按分し補正係数で合計をBOM倍率に一致させる。
- 連産品BOM（`is_coproduct=True`）は倍率計算から除外する。連産品の子は同時生産される出力品であり、材料入力ではないため。
- 例: 品番Xが2箇所（qty=2, qty=2）に出現 → BOM合計倍率=4 → 2ステップに按分（各2） → 合計需要 = 注文数 × 4

#### APIエンドポイント

```
POST /api/line-backlogs/pickup/
```

**リクエスト**:
```json
{
  "line_id": 8,
  "start_date": "2025-01-01",
  "end_date": "2025-01-31"
}
```

**レスポンス**:
```json
{
  "detail": "Pickup completed successfully"
}
```

### 2. 生産計画の保存（save）

ユーザー入力した計画データをLinePlanに保存。

#### 処理フロー

1. フロントエンドから計画データを送信
   - ライン別・製品別・日別・ロット別のデータ
2. バックエンドでバリデーション
   - product_id, process_id, plan_date, sequence_noが必須
   - plan_qty ≤ 0の場合は削除処理
   - sequence_no重複チェック（同日・同ライン内）
3. LinePlanにupsert（作成または更新）
4. 工程展開（expand_processes）を実行
5. 在庫・計画在庫を再計算
6. 工程ガント計画（LineGanttPlan）を再生成

#### APIエンドポイント

```
POST /api/line-plans/save/
```

**リクエスト**:
```json
{
  "line_id": 8,
  "items": [
    {
      "product_id": 123,
      "process_id": 5,
      "plan_date": "2025-01-15",
      "plan_qty": 100,
      "sequence_no": 1
    },
    {
      "product_id": 123,
      "process_id": 5,
      "plan_date": "2025-01-15",
      "plan_qty": 50,
      "sequence_no": 2
    }
  ]
}
```

**レスポンス**:
```json
{
  "created": 2,
  "updated": 0,
  "deleted": 0,
  "skipped": []
}
```

#### バリデーションルール

1. **必須フィールド**
   - `product_id`, `process_id`, `plan_date`, `sequence_no`

2. **数量チェック**
   - `plan_qty ≤ 0`: 該当レコードを削除
   - `plan_qty > 0`: 作成または更新

3. **順序番号重複チェック**
   - 同じライン・同じ日に同じsequence_noが存在する場合はエラー
   - ただし、同じproduct_id + process_idの組み合わせは更新可能

4. **製品存在チェック**
   - product_idが存在しない場合はスキップ

### 3. 工程展開（expand_processes）

LinePlanのライン最終品計画を、BOMに従って前工程に展開。

#### 処理フロー

1. ライン最終品（`is_line_final_product = true`）のLinePlanを取得
2. BOMを参照して前工程製品と必要数量を計算
3. LineBacklogに展開結果を保存
   - `plan_qty`, `plan_id`, `sequence_no`を設定

#### 連産品（コプロダクト）の展開

連産品BOMの場合、子製品の計画から親（仮想セット品番）への展開を行う。

**連産品代表品（is_coproduct_driver）の役割**:

- 連産品BOMの構成品目のうち1つを「代表品」（`is_coproduct_driver=TRUE`）として指定
- **代表品のみ**が親への計画展開のトリガーとなる
- 代表品以外の子製品は、計画展開に使用されない

**共有部品問題の解決**:

```
例：9733476S（共有部品）が複数の連産品に使われている場合

連産品A（SET-A）の子:
  - 製品X（is_coproduct_driver=TRUE）← 代表品
  - 9733476S（共有部品）

連産品B（SET-B）の子:
  - 製品Y（is_coproduct_driver=TRUE）← 代表品
  - 9733476S（共有部品）

→ 製品Xの計画 → SET-Aへ展開
→ 製品Yの計画 → SET-Bへ展開
→ 9733476Sの計画 → 展開されない（代表品ではないため）
```

**実装箇所**: `pm_backend/apps/production/views.py` の `expand_processes` メソッド

```python
# 連産品マップ構築（代表品のみ）
copro_child_map = {}
for bom in BOM.objects.filter(is_coproduct=True, is_active=True):
    for item in bom.items.filter(is_active=True):
        if item.is_coproduct_driver:  # 代表品のみ
            copro_child_map[item.child_product_id] = {
                'parent_id': bom.parent_product_id,
                'qty_per': item.quantity,
            }
```

#### APIエンドポイント

```
POST /api/line-backlogs/expand_processes/
```

**リクエスト**:
```json
{
  "line_id": 8,
  "start_date": "2025-01-01",
  "end_date": "2025-01-31",
  "read_only": false,
  "include_coproduct_children": true
}
```

**レスポンス**:
```json
{
  "detail": "Processes expanded successfully"
}
```

### 6. 日別スケジュール設定（LineDailyScheduleSetting）

ライン・日別に最終工程開始時刻を設定し、ガント計画生成時に使用する機能。

#### 機能概要

- 生産計画入力画面の各日付列に時刻入力ボックスを表示
- 日別に最終工程開始時刻を設定可能
- 設定した時刻は工程ガント計画生成時に使用される
- 優先順位: 日別設定 > デフォルト設定（ツールバー） > 8:00（フォールバック）

#### 関連テーブル: LineDailyScheduleSetting

| フィールド名 | 型 | 説明 |
|------------|-----|------|
| id | BigAutoField | 主キー |
| line | FK | ライン |
| plan_date | DATE | 計画日 |
| final_process_start_time | TIME | 最終工程開始時刻（NULL可） |
| adjust_to_break_end | BOOLEAN | 休憩時間終了に調整（デフォルト: true） |
| created_at | DATETIME | 作成日時 |
| updated_at | DATETIME | 更新日時 |

**制約**:
- `unique_together`: `(line, plan_date)`
- `index`: `(line, plan_date)`

#### APIエンドポイント

##### 一覧取得

**クエリパラメータ**:
- `line`: ラインID
- `plan_date`: 計画日（完全一致）
- `plan_date__gte`: 計画日（以上）
- `plan_date__lte`: 計画日（以下）

**レスポンス**:

#### ガント計画生成への統合

工程ガント計画生成時に日別設定を使用する優先順位:

1. **日別設定（最優先）**: `LineDailyScheduleSetting`に該当日の設定がある場合
2. **デフォルト設定**: ツールバーの「デフォルト開始時刻」
3. **フォールバック**: 8:00（設定がない場合）

**実装箇所**: `pm_backend/apps/production/services/gantt_planning.py`

```python
# 日別設定を事前ロード
daily_settings_qs = LineDailyScheduleSetting.objects.filter(
    line_id=line_id,
    plan_date__gte=start_date,
    plan_date__lte=end_date,
)
daily_settings_map = {}
for setting in daily_settings_qs:
    daily_settings_map[setting.plan_date] = {
        'final_process_start_time': setting.final_process_start_time,
        'adjust_to_break_end': setting.adjust_to_break_end,
    }

# 各計画日の処理時に日別設定を使用
for obj in line_backlog_with_plan:
    daily_setting = daily_settings_map.get(obj.plan_date)
    if daily_setting and daily_setting['final_process_start_time']:
        day_target_time_obj = daily_setting['final_process_start_time']
        day_adjust_to_break_end = daily_setting['adjust_to_break_end']
    else:
        day_target_time_obj = target_time_obj  # デフォルト設定
        day_adjust_to_break_end = adjust_to_break_end
```

## フロントエンド仕様

### 生産計画入力画面（ProductionPlanInput.vue）

#### 画面構成

1. **ツールバー**
   - 処理区分: 生産計画 / 実績
   - ライン選択
   - 表示開始日
   - 期間: 30日 / 60日 / 90日
   - 検索（品番/品名）
   - デフォルト開始時刻: 日別設定がない場合に使用される最終工程開始時刻

2. **グリッド表示**
   - 固定列: No / 品番 / 品名
   - 日別列（各日6列）:
     - ヘッダー部:
       - 日付ラベル（例: 1/15(水)）
       - 時刻入力ボックス（最終工程開始時刻の日別設定）
     - データ行:
       - 需要: 後工程需要
       - 実績: 実績生産数
       - 在庫: 実在庫
       - 計画: 計画生産数（入力可能）
       - 順序: 順序番号（入力可能）
       - 計画在庫: 計画在庫

3. **ボタン**
   - クリア: 全行削除
   - 計画変更: ロック期間を超えた計画変更時に変更理由を入力するダイアログを表示
   - 保存: 計画データをサーバーに保存
   - 取り込み: 後工程需要を取り込み
   - 工程ガント表示: 工程ガント計画を表示/非表示
   - 工程負荷表示: 工程別負荷を表示/非表示

4. **ツールバー設定項目**
   - デフォルト開始時刻: 日別設定がない場合の最終工程開始時刻（プレースホルダー: `00:00`）
   - 休憩明けに補正: チェックボックス（`adjust_to_break_end`）

5. **フッターショートカットキー**
   - F1: 終了
   - F3: クリア
   - F5: 備考
   - F10: 印刷（エクスポートダイアログを表示）
   - F12: 更新

#### グリッド操作

##### セル移動

- **Enter**: 下セルに移動（Shift+Enterで上セルに移動）
- **矢印キー**: 上下左右のセルに移動
- **Tab**: 次のフィールド（計画→順序）に移動

##### 複数ロット入力

1. 計画セル内の「+」ボタンをクリック
2. 追加ロットの入力欄が表示される
3. ロットごとに計画数量と順序番号を入力
4. 「x」ボタンでロットを削除

**注意**:
- 最初の行は常にメインロット
- 追加ロットは2番目以降のロット
- 順序番号は昇順で採番推奨

##### 行の並び替え

- No列の「↑」「↓」ボタンで行を移動
- 並び順は製品の表示順序のみに影響（保存データには影響なし）

##### タンクライン（L2200）の固定表示順

- ラインコードが **L2200 - タンクライン** のとき、品番表示順を固定する  
  `YD60003386 → YD60011305 → YD60000441 → YD60008491 → YD60009848 → YD60014764`  
- 上記に含まれない品番は従来の並び順で末尾に表示する  
- 固定順は画面表示のみで、`sequence_no` など保存データには影響しない

#### 表示ルール

##### 数値表示

- **0値**: 空白表示
- **プラス値**: 通常表示（カンマ区切り）
- **マイナス値**: 赤背景、赤文字、太字で強調

##### 在庫表示の特殊ルール

LineBacklogが存在しない日（`has_row = false`）は、直前の在庫値を引き継いで表示。

**例**:
| 日付 | has_row | 在庫（DBの値） | 画面表示 |
|------|---------|--------------|---------|
| 1/10 | true | 100 | 100 |
| 1/11 | false | 0 | 100（1/10の値を引き継ぎ） |
| 1/12 | false | 0 | 100（1/10の値を引き継ぎ） |
| 1/13 | true | 120 | 120 |

#### 取り込み処理の流れ

1. **pickup API**呼び出し
   - 後工程計画からorder_qtyを算出してLineBacklogに反映

2. **recalculateInventory API**呼び出し
   - 在庫・計画在庫を再計算（進度は在庫再計算で実施）

3. **LineBacklogとLinePlanを取得**
   - `line-backlogs`: 需要、実績、在庫データ
   - `line-plans`: 計画数量、順序番号

4. **グリッドデータの組み立て**
   - 通常ライン: ライン最終品（`is_line_final_product = true`）のみを対象
   - `L2201`（タンクセル）: 連産品の表示は「親品番 + 代表部番（`is_coproduct_driver=true`）」に限定し、連産品の非代表子は表示対象外。非連産品は従来どおり表示対象に含める
   - `L2201`（タンクセル）: 連産親（`ST...`）を直接計画した場合、工程ガント/工程作業入力では子品番へ展開せず、親品番1件として扱う
   - `L2201`（タンクセル）: 工程展開/工程ガント生成では、計画対象品番を親に持つルーティングのみ使用する。他品番ルーティングの `output_product` 一致だけでは展開しない
   - 製品ごとに1行を作成
   - 日別に需要・実績・在庫・計画・順序を設定
   - 複数ロット（sequence_no順）を展開

5. **画面表示**
   - グリッドにデータを反映
   - 0値は空白表示

#### 保存処理の流れ

1. **バリデーション**
   - ラインが選択されているか確認
   - product_idとprocess_idが存在するか確認

2. **保存データの作成**
   - 各行の日別データをループ
   - メインロットと追加ロット（extraLots）を配列に変換
   - plan_qtyとsequence_noがnullの行はスキップ

3. **save API**呼び出し
   - LinePlanに保存
   - 作成/更新/削除件数を返却

   - **recalculateInventory**: 在庫・計画在庫再計算（include_progress=false）

##### 時刻入力の正規化

入力された時刻は以下のように正規化されます:

```javascript
function normalizeTimeInput(value) {
  if (!value || value.trim() === '') return null
  // "08:30" → "08:30"
  // "8:30" → "08:30"
  // "830" → "08:30"
  const cleaned = value.replace(/[^\d:]/g, '')
  if (cleaned.includes(':')) {
    const [h, m] = cleaned.split(':')
    if (h && m) {
      return `${h.padStart(2, '0')}:${m.padStart(2, '0')}`
    }
  } else if (cleaned.length >= 3) {
    const h = cleaned.slice(0, -2)
    const m = cleaned.slice(-2)
    return `${h.padStart(2, '0')}:${m.padStart(2, '0')}`
  }
  return null
}
```

## 在庫一覧画面との連携

### 順序番号を考慮した表示ロジック

在庫一覧画面（ProductionInventory.vue）では、LineBacklogに複数の順序番号（ロット）が存在する場合、適切に集約して表示します。

#### 需要行と計画行の区別

LineBacklogのレコードは以下のように区別されます：

- **需要行（isDemandRow）**: `order_qty > 0` または `demand_qty_plan > 0` かつ `plan_qty = 0`
  - 後工程からの需要を表す
  - 内示（forecast）と確定（firm）を表示

- **計画行**: `plan_qty > 0`
  - 生産計画を表す
  - 複数ロット（sequence_no）が存在する可能性

#### 内示・確定の表示ルール

複数の順序番号がある場合、最小のsequence_noを持つ需要行を優先表示：

```javascript
// 順序番号が最小の需要行を採用
if (c.demand_seq === undefined || seqVal < c.demand_seq) {
  c.demand_seq = seqVal;
  c.forecast = forecastVal;  // 内示
  c.firm = firmVal;           // 確定
}
// 同じ順序番号の場合は最大値を採用
else if (seqVal === c.demand_seq) {
  c.forecast = Math.max(c.forecast, forecastVal);
  c.firm = Math.max(c.firm, firmVal);
}
```

#### 計画・在庫の表示ルール

計画数量、在庫、計画在庫は全ての順序番号（ロット）を合算して表示：

- **計画**: 全ロットの`plan_qty`を合計
- **実績**: 全ロットの`actual_qty`を合計
- **調整**: 全ロットの`adjust_qty`を合計
- **仕損**: 全ロットの`scrap_qty`を合計
- **在庫**: 順序番号が最小の行の`stock_qty`を表示
- **計画在庫**: 順序番号が最小の行の`planned_stock_qty`を表示

#### 表示例

| 日付 | sequence_no | order_qty | plan_qty | stock_qty | 画面表示 |
| ---- | ----------- | --------- | -------- | --------- | -------- |
| 1/15 | 0 | 100 | 0 | 50 | 内示:100, 計画:150, 在庫:50 |
| 1/15 | 1 | 0 | 100 | 0 | （合算される） |
| 1/15 | 2 | 0 | 50 | 0 | （合算される） |

→ 画面では1行に集約表示：内示100、計画150（100+50）、在庫50

## 注意事項

### 順序番号の管理

- **同日・同ライン内で重複不可**
- **推奨**: 1, 2, 3, ...の連番
- **重複時**: エラーメッセージが表示され、保存失敗

### 計画数量の扱い

- **0以下の入力**: 該当計画を削除
- **空白入力**: 0として扱われ、削除される
- **小数入力**: 許可（plan_idに反映）

### 工程展開の前提

- **LinePlan**: ライン最終品のみ登録
- **LineBacklog**: 全工程に展開される
- **BOM**: 正しく設定されている必要がある

### パフォーマンス

- **推奨期間**: 30日（デフォルト）
- **最大期間**: 90日
- **大量データ**: ライン・期間を絞り込み

3. **`LineBacklog.plan_qty` への同期を追加**
   - 対象レコード: `line_id + process_id + product_id + plan_id` が一致する計画行
   - 同期値: 編集後の数量（`LineBacklog.plan_qty` は整数のため整数化して保存）

4. **非同期範囲を明確化**
   - `LinePlan` は更新しない
   - 在庫・進度の再計算は自動実行しない

5. **数量変更履歴の記録を追加**
   - 数量が実際に変化した場合のみ `ProductionPlanChangeLog` を作成
   - 記録内容: `plan_date, line, process, product, sequence_no, plan_id, before_qty, after_qty, changed_by`
   - 記録理由: `reason=工程ガント数量編集`

- `pm-ui/src/views/production/ProcessGanttView.vue`
- `pm_backend/apps/production/views.py`

### 2026-01-20: pickup API パフォーマンス改善

#### 1. 目的

pickup API（取り込み機能）の実行時間を短縮する。

**改善前**: 約10秒（322件の処理で9.6秒）
**改善後**: 約0.5秒以下（見込み）

**原因**: `update_or_create` をループで322回実行していたため、毎回DBアクセスが発生していた。

#### 2. リスク分析

**リスクがない理由**:

| 観点 | 説明 |
|------|------|
| 対象レコード | `sequence_no=0` の基礎データレコードのみ（変更なし） |
| 更新フィールド | `order_qty` と `demand_qty_plan` のみ（仕様通り） |
| plan_qty | 更新しない（仕様書に「需要展開時は order_qty と demand_qty_plan のみ更新」と明記） |
| 検索キー | `plan_date, process_id, product_id, line_id, sequence_no=0`（変更なし） |
| データ整合性 | 本番DBで `sequence_no=0 AND plan_qty > 0` のレコードが0件であることを確認済み |

**潜在的リスク**:

| リスク | 可能性 | 対策 |
|--------|--------|------|
| bulk_update の部分失敗 | 低（Django標準機能） | トランザクション内で実行される |
| 大量データ時のメモリ使用 | 低（322件程度） | 必要に応じてバッチサイズ指定可能 |

#### 3. 編集箇所

**ファイル**: `pm_backend/apps/production/views.py`

**変更内容**: `pickup` メソッド内の LineBacklog 保存処理

**変更前** (1007-1033行目付近):
```python

upsert_start = time.perf_counter()
for (product_id, plan_date), order_qty in demand_map.items():
```

**変更後**:
```python
# 4. LineBacklogに保存（order_qtyのみ更新、他の数量は維持）- bulk操作で高速化
upserted_items = []
upsert_start = time.perf_counter()

# 対象キーを収集
target_keys = []
for (product_id, plan_date), order_qty in demand_map.items():
    process_id = product_process_map.get(product_id)
    if not process_id:
        continue
    target_keys.append((product_id, plan_date, process_id, order_qty))

if target_keys:
    # 既存レコードを一括取得
    from django.db.models import Q
    q_filter = Q()
    for product_id, plan_date, process_id, _ in target_keys:
        q_filter |= Q(
            plan_date=plan_date,
            process_id=process_id,
            product_id=product_id,
            line_id=line_id,
            sequence_no=0,
        )
    existing_records = {
        (r.product_id, r.plan_date, r.process_id): r
        for r in LineBacklog.objects.filter(q_filter)
    }

    to_create = []
    to_update = []
    for product_id, plan_date, process_id, order_qty in target_keys:
        key = (product_id, plan_date, process_id)
        if key in existing_records:
            obj = existing_records[key]
            obj.order_qty = order_qty
            obj.demand_qty_plan = order_qty
            to_update.append(obj)
        else:
            to_create.append(LineBacklog(
                plan_date=plan_date,
                process_id=process_id,
                product_id=product_id,
                line_id=line_id,
                sequence_no=0,
                order_qty=order_qty,
                demand_qty_plan=order_qty,
                plan_qty=0,
            ))

    # bulk_create と bulk_update を実行
    if to_create:
        LineBacklog.objects.bulk_create(to_create)
    if to_update:
        LineBacklog.objects.bulk_update(to_update, ['order_qty', 'demand_qty_plan'])

    upserted_items = to_create + to_update
```

**改善のポイント**:
- 322回のDB往復 → 3回（SELECT + bulk_create + bulk_update）に削減
- `plan_qty` を更新対象から除外（仕様準拠）

## 補足（生産計画と購買計画の運用差）

- 本仕様は生産計画向けであり、`sequence_no=0` は基礎データ行として扱う（計画入力には使用しない）。
- 購買計画は同日複数ロットを扱わないため、`sequence_no=0` 行に `plan_qty` を入力する運用とする。
- 需要取り込み（`pickup` / `pickup_purchase`）は共通で `order_qty` と `demand_qty_plan` のみ更新し、`plan_qty` は更新しない。
