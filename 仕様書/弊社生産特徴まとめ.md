# 弊社生産特徴まとめ

## 概要

本システムは、段階BOM・セル工程・時間運用・ライン/購買LT対応の生産管理システムです。
複数の得意先から内示（FORECAST）と確定受注（FIRM）を受け、優先順位を制御しながら生産計画を立てます。

---

## 1. 受注管理の特徴

### 1.1 内示と確定の二元管理

弊社では、得意先から以下2種類の受注情報を受け取ります：

| 受注タイプ | 日本語 | 性質 | 更新頻度 | スケジューリング優先度 |
|-----------|--------|------|----------|----------------------|
| **FORECAST** | 内示 | 予測情報、変更される可能性が高い | 毎日 | 低（確定がない場合のみ使用） |
| **FIRM** | 確定 | 正式な受注、必ず生産する | 適宜 | 最高（必ず生産計画に含める） |

### 1.2 複数得意先・複数フォーマット対応

#### 対応得意先

| 得意先コード | 得意先名 | 内示 | 確定 | フォーマット識別 |
|------------|---------|------|------|----------------|
| 000001 | ティエラ | ○ | ○ | データ区分（B17/Y55） |
| 000196 | クボタ（堺・枚方） | ○ | ○ | ファイル名 + データNO/No. |
| 000018 | リーデン | - | ○ | 発注コード（509） |

#### CSVフォーマット対応

各得意先のCSVフォーマットに対応するため、**サービス指向アーキテクチャ**を採用：

```
pm_backend/orders/services/
├── base_import.py          # 基本クラス（共通処理）
├── tiera_naiji_import.py   # ティエラ内示
├── tiera_kakutei_import.py # ティエラ確定
├── kubota_sakai_naiji_import.py
├── kubota_sakai_kakutei_import.py
├── kubota_hirakata_kakutei_import.py
└── rieden_kakutei_import.py
```

- 得意先コード + 受注タイプ + ファイル名で自動的にサービスを選択
- 複数エンコーディング対応（CP932, Shift-JIS, UTF-8）
- カラム位置指定による柔軟なフォーマット対応

## 2. 受注データフロー

### 2.1 CSVインポートから受注確定まで

```
┌──────────────┐
│ CSVファイル  │  ← 得意先からのCSV（内示 or 確定）
└──────┬───────┘
       │ アップロード
       ▼
┌──────────────┐
│ 1. 生データ  │  stg_order_raw
│    保存      │  ・CSVをそのまま保存（トラブルシューティング用）
└──────┬───────┘  ・エンコーディング、フォーマット情報を保持
       │ 解析・正規化
       ▼
┌──────────────┐
│ 2. 日別正規化│  stg_order_daily
│    データ    │  ・製品コード、納期、数量を抽出
└──────┬───────┘  ・得意先コード → customer_id 解決
       │         ・製品マスタ自動登録（存在しない場合）
       │ ユーザー承認・確定
       ▼
┌──────────────┐
│ 3. 正式受注  │  t_order + t_order_line
│    作成      │  ・スケジューリング対象データ
└──────┬───────┘  ・優先順位制御（内示の上書き、確定による無効化）
       │
       ▼
  スケジューリングエンジン
```

### 2.2 内示の自動上書き（毎日更新）

**課題**:
内示は毎日更新される予測データ。古い内示と新しい内示を併存させると混乱する。

**解決策**:
新しい内示CSVがインポートされると、**同じ得意先の既存内示を削除**し、新しい内示で完全に置き換える。

```
【処理フロー】
1. 内示CSVアップロード
2. ステージングテーブルへ保存
3. ユーザーが「受注作成」実行
   ↓
4. 同じ得意先の既存内示を検索
   WHERE customer_id = ? AND order_type = 'FORECAST' AND status = 'OPEN'
   ↓
5. 既存内示を削除（CASCADE により t_order_line も削除）
   ↓
6. 新しい内示を作成
```

**結果**:
常に最新の内示のみがシステムに保持され、データの整合性が保たれる。

### 2.3 確定受注による内示の自動無効化

**課題**:
確定受注が来たら、その製品・納期については内示は不要になる。しかし、削除すると履歴が失われる。

**解決策**:
確定受注CSVがインポートされると、**同じ製品・同じ納期の内示を自動的に無効化**（status='SUPERSEDED'）する。

```
【処理フロー】
1. 確定CSVアップロード
2. ステージングテーブルへ保存
3. ユーザーが「受注作成」実行
   ↓
4. 確定受注を作成
   ↓
5. 重複する内示を検索
   WHERE customer_id = ?
     AND order_type = 'FORECAST'
     AND status = 'OPEN'
     AND lines.product_code IN (確定の製品コード)
     AND lines.due_date IN (確定の納期)
   ↓
6. 該当内示のstatusを'SUPERSEDED'に更新
```

**結果**:
- 確定受注が優先される
- 内示は無効化されるが履歴として残る
- スケジューリング時には無効化された内示は無視される

## 3. スケジューリングにおける優先順位制御

### 3.1 基本ルール

1. **status='OPEN'** の受注のみを使用
2. **確定（FIRM）を優先**
3. **確定がない製品・納期のみ、内示（FORECAST）を使用**

### 3.2 スケジューリングロジック

```python
# スケジューリング用の受注明細を取得
order_lines = OrderLine.objects.filter(
    order__status='OPEN'
).select_related('order', 'product').order_by(
    'due_date',
    'order__order_type'  # FIRM が FORECAST より先
)

# スケジューリングエンジンで処理
for line in order_lines:
    if line.order.order_type == 'FIRM':
        # 確定受注 → 必ず生産計画に含める
        schedule_production(line)
    else:  # FORECAST
        # 内示 → 同じ製品・納期に確定がない場合のみ使用
        if not has_firm_order(line.product_code, line.due_date):
            schedule_tentative_production(line)
```

### 3.3 受注ステータスの意味

| status | 日本語 | スケジューリング | 説明 |
|--------|--------|----------------|------|
| `OPEN` | オープン | ○ 対象 | 有効な受注 |
| `SUPERSEDED` | 無効 | × 除外 | 確定受注により無効化された内示 |
| `CLOSED` | クローズ | × 除外 | 完了した受注 |
| `CANCELED` | キャンセル | × 除外 | キャンセルされた受注 |

## 4. 生産構造の特徴

### 4.1 段階BOM

製品は複数階層の部品で構成される。

```
製品A (FINISHED)
├── 中間品B (SEMI_FINISHED)
│   ├── 原材料C (RAW_MATERIAL)
│   └── 原材料D (RAW_MATERIAL)
└── 購入品E (PURCHASED)
```

- 各階層ごとにBOMを定義
- `m_bom` (BOMヘッダ) と `m_bom_item` (BOM明細) で管理
- 展開時に全階層を再帰的に処理

### 4.2 セル工程（ルーティング）

製品ごとに工程順序と所要時間を定義。

```
製品A のルーティング:
1. プレス工程 (PRESS) - 10分/個
2. 溶接工程 (WELD) - 15分/個
3. 塗装工程 (PAINT) - 20分/個
4. 検査工程 (INSPECTION) - 5分/個
```

- `m_routing` (ルーティングヘッダ) と `m_routing_step` (工程明細) で管理
- 各工程には以下を定義：
  - 工程タイプ（製造 / 検査 / 移送）
  - 作業時間（分単位 or 日単位）
  - 段取時間、バッファ時間
  - 使用ライン

### 4.3 時間運用

#### 時間単位の混在

- **製造工程**: 分単位（10分/個、15分/個 など）
- **購買リードタイム**: 日単位（7日、14日 など）
- **移送時間**: 日単位（1日、2日 など）

`m_routing_step.time_unit` で `DAY` or `MINUTE` を指定。

#### スケジューリング計算

- 納期から逆算（バックワードスケジューリング）
- 工程ごとに所要時間を積算
- カレンダマスタで稼働日・非稼働日を考慮
- 日跨ぎ計算（分単位の作業が営業日をまたぐ場合）

### 4.4 ライン / 購買LT対応

#### 製造工程

- 各工程に使用ラインを指定（`m_routing_step.line_id`）
- ライン別に負荷を計算し、キャパシティを超えないように調整

#### 購買部品

- BOM明細で `procurement_type='PURCHASE'` を指定
- 購買リードタイム（`m_bom_item.purchase_lead_time_days`）を考慮
- 購買計画（発注日、納入日）を自動計算
- 製品で使う購買品は、その製品の得意先（受注先）から調達する想定とし、仕入先コードは得意先コードを流用してよい
- 得意先を直接仕入先として使えない場合は、その製品専用の擬似仕入先コードを作成して運用してもよい

#### レーザ切断 → ブレーキ曲げ（単品のまま流すパターン）

- レーザ切断工程のWIP品番: `YD40000680-16L`（LT=1日）
- ブレーキ曲げ工程のWIP品番: `YD40000608-16B`（LT=1日）
- 両工程とも単品のまま流す。中間在庫を持たない場合は同一親品番のルーティング工程で管理し、中間在庫が必要な場合のみ上記WIP品番をBOM/ルートで受け渡す。

### 4.5 ライン最終品の概念

#### ライン最終品とは

**ライン最終品**: 各ラインの最終工程で加工される製品のこと。必ずしも出荷品（最終製品）ではない。

```
【例：タンクライン】
  Step 17: 最終組立 → YD60000441S（中間品）
  Step 18: タンク組立 → YD60000441（出荷品） ← ライン最終品

【例：ブレーキライン】
  Step 1: レーザ加工 → YD40000608-10L（中間品）
  Step 2: ブレーキ加工 → YD40000608-10B（中間品） ← ライン最終品
  ※この後、タンクラインに投入される

【例：レーザーライン】
  Step 1: レーザ加工 → YD40000608-06（中間品） ← ライン最終品
  ※この後、ブレーキラインに投入される
```

#### ライン最終品の自動判定

システムは、`m_routing_step`から**ライン最終品を自動判定**します：

```python
# 各ルーティングについて、そのラインの最終工程を特定
for routing_id in routing_ids:
    last_step_on_line = RoutingStep.objects.filter(
        routing_id=routing_id,
        line_id=line_id
    ).order_by('-step_no').first()

    # 最終工程のoutput_product = ライン最終品
    line_final_product = last_step_on_line.output_product
```

**利点**:
- マスタ入力不要（ルーティングから自動判定）
- ルーティング変更時も自動追従
- 各ラインの計画対象製品が明確

#### 出荷品フラグとの違い

| フラグ | 意味 | 例 |
|--------|------|-----|
| `m_product.is_final_product` | **出荷品フラグ**<br>得意先に出荷する製品 | YD60000441, YD60003386 |
| （自動判定） | **ライン最終品**<br>そのラインの最終工程で加工される製品 | YD40000608-10B（ブレーキライン）<br>YD60000441（タンクライン） |

**重要**: ライン最終品は中間品を含むが、出荷品は必ず最終製品のみ。

## 6. 長期生産計画（LineBacklog）

### 6.1 長期生産計画の役割

**LineBacklog**テーブルは、各ラインの日別生産計画を管理します：

```
line_backlog テーブル:
- plan_date: 計画日
- line_id: 対象ライン
- product_id: 製品
- process_id: 工程
- demand_qty_plan: 需要数量（後工程からの要求）
- plan_qty: 計画数量（ユーザー入力）
- actual_qty: 実績数量
- stock_qty: 在庫数量
- planned_stock_qty: 計画在庫
```

### 6.2 需要展開の考え方：「後工程 = お客さん」

#### 基本概念

弊社の需要展開は、**「後工程 = お客さん」**という考え方で行います：

```
最終ライン（タンクライン）:
  お客さん = 得意先（ティエラ、クボタ等）
  需要 = 受注データ（LineDemand）

前工程ライン（ブレーキライン）:
  お客さん = 後工程（タンクライン）
  需要 = タンクラインのLineBacklog.plan_qty × BOM個数

前工程ライン（レーザーライン）:
  お客さん = 後工程（ブレーキライン）
  需要 = ブレーキラインのLineBacklog.plan_qty × BOM個数
```

#### 重要な原則

1. **需要展開は逆順（最終ライン → 前工程）でライン一つずつ行う**
2. **受注から全ラインの需要を一括計算するのではない**
3. **各ラインは「後工程の計画」を見て自ラインの需要を決める**

### 6.3 生産計画の自動生成（pickup）

#### 処理フロー

生産計画入力画面で各ラインごとに以下の操作を行います：

##### 【最終ラインの場合（例：タンクライン）】

```
1. ライン選択: タンクライン
2. 取り込みボタン押下
   ↓
3. システム処理:
   - LineDemand（受注展開データ）から需要を取得
   - ライン最終品のみを対象
   - order_qty に保存（需要数量）
   ↓
4. 画面表示:
   - 日別マトリックスに「需要」列が表示される
   ↓
5. ユーザー操作:
   - 「計画」列に計画数量を入力
   ↓
6. 保存ボタン押下:
   - plan_qty に保存（計画数量）
```

**データフロー（最終ライン）**:
```
LineDemand.plan_qty
  ↓ pickup()
LineBacklog.order_qty（需要）
  ↓ ユーザー入力
LineBacklog.plan_qty（計画）
```

##### 【前工程ラインの場合（例：ブレーキライン）】

```
1. ライン選択: ブレーキライン
2. 取り込みボタン押下
   ↓
3. システム処理:
   - 後工程（タンクライン）のLineBacklog.plan_qtyを取得
   - BOM個数を掛けて必要数を計算
   - リードタイムを考慮して日付を遡る
   - order_qty に保存（需要数量）
   ↓
4. 画面表示:
   - 日別マトリックスに「需要」列が表示される
   ↓
5. ユーザー操作:
   - 「計画」列に計画数量を入力
   ↓
6. 保存ボタン押下:
   - plan_qty に保存（計画数量）
```

**データフロー（前工程ライン）**:
```
後工程のLineBacklog.plan_qty × BOM個数
  ↓ pickup()
LineBacklog.order_qty（需要）
  ↓ ユーザー入力
LineBacklog.plan_qty（計画）
```

#### 実装ロジック（pickup）

```python
# orders/views.py - LineBacklogViewSet.pickup()

1. ライン最終品の特定（RoutingStepから自動判定）
   ↓
2. 需要の計算：
   【最終ラインの場合】
   - LineDemandから需要を取得
   - ライン最終品のみを対象
   - order_qty = LineDemand.plan_qty

   【前工程ラインの場合】
   - 後工程（次ライン）のLineBacklogから需要を取得
   - BOM個数を掛けて必要数を計算
   - リードタイムを考慮して日付を遡る
   - order_qty = 後工程のplan_qty × BOM個数
   ↓
3. LineBacklog.order_qtyに保存
   ↓
4. 画面に日別マトリックスで表示
```

#### ライン別の計画生成例

**タンクライン（最終ライン）の場合**:
```
LineDemand（受注展開データ）
  YD60000441: 12個（2025-12-19）
  YD60003386: 8個（2025-12-19）
    ↓ pickup()実行
LineBacklog（タンクライン）
  YD60000441: 需要12個、計画12個（2025-12-19）
  YD60003386: 需要8個、計画8個（2025-12-19）
```

**ブレーキライン（前工程）の場合**:
```
LineBacklog（タンクライン）← 後工程の計画
  YD60000441: 計画12個（2025-12-19）
    ↓ BOM展開
    YD40000608-10B × 1個/製品
    ↓ リードタイム1日を遡る
LineBacklog（ブレーキライン）
  YD40000608-10B: 需要12個、計画12個（2025-12-18）
```

### 6.3 ライン最終品のみを対象とする理由

各ラインの計画は、**そのラインの最終品のみ**を対象とします。

**理由**:
1. **重複計算の防止**: 中間工程の製品も全て含めると、同じ製品が複数回計画される
2. **計画の明確化**: 各ラインで「何を何個作るか」が明確
3. **前工程への展開**: ライン最終品から前工程の需要を自動計算できる

**例**:
```
タンクラインの場合:
  Step 4-11: 中間品（YD40000607, 9733476S等）← 計画対象外
  Step 18: YD60000441（ライン最終品）← 計画対象✅

→ タンクラインの計画はYD60000441のみ
→ 中間工程の製品は、YD60000441の生産に自動的に含まれる
```

### 6.4 UI操作フロー

#### 生産計画入力画面

1. **ライン選択**: タンクライン、ブレーキライン等を選択
2. **期間設定**: 表示開始日、期間（60日/30日/14日）を設定
3. **取り込み**: 「取り込み」ボタンで需要を自動計算
4. **計画入力**: 日別マトリックスで計画数量を入力・調整
5. **保存**: 「保存」ボタンで計画を確定

#### 画面表示（日別マトリックス）

```
┌──────┬─────────┬──────┬──────┬──────┬──────┬─────────┐
│ 品番  │ 品名     │12/16 │12/17 │12/18 │12/19 │12/20... │
│      │         ├──┬─┬─┼──┼──┼──┼──┤
│      │         │需│実│在│計│計在│... │
├──────┼─────────┼──┼─┼─┼──┼──┼──┼──┤
│YD60..│タンク組立│12│0│0│12│0  │... │
│YD60..│タンク組立│ 8│0│0│ 8│0  │... │
└──────┴─────────┴──┴─┴─┴──┴──┴──┴──┘
```

- **需要**: 後工程からの要求数（自動計算）
- **実績**: 実際の生産数
- **在庫**: 現在在庫
- **計画**: ユーザー入力（調整可能）
- **計画在庫**: 見込み在庫

## 7. スケジューリングロジック概要

### 6.1 逆算ロジック（バックワード）

```
納期（due_date）
  ↓ 逆算
最終工程（検査）終了時刻
  ↓ 逆算（検査時間）
最終工程（検査）開始時刻
  ↓ 逆算（バッファ）
前工程（塗装）終了時刻
  ↓ 逆算（塗装時間）
前工程（塗装）開始時刻
  ...
  ↓
部品発注日（購買リードタイム考慮）
```

### 6.2 日跨ぎ計算

- 分単位の作業時間が営業日をまたぐ場合の処理
- カレンダマスタで稼働日を判定
- 非稼働日をスキップ

### 6.3 移送バッチ・バッファ制御

- 工程間の移送時間を考慮
- バッファ時間で余裕を持たせる
- ロットサイズによる移送バッチを設定

## 7. データベース設計のポイント

### 7.1 製品カテゴリENUM化

`m_product.category` を ENUM 型で定義し、データの整合性を保証。

### 7.2 時間単位の明示化

`m_routing_step.time_unit` で `DAY` / `MINUTE` を明示し、計算ミスを防止。

### 7.3 調達整合性CHECK制約

`m_bom_item` に CHECK 制約を設定：

```sql
CHECK (
  (procurement_type = 'MAKE' AND line_id IS NOT NULL) OR
  (procurement_type = 'PURCHASE' AND purchase_lead_time_days IS NOT NULL)
)
```

製造品にはライン、購買品にはリードタイムを必須とする。

## 2. ラインと工程 (補足)
- 工程マスタはライン直下に紐づけておく（ルーティングがなくても工程の所属ラインを決められる）。
- ラインのLTはルーティング工程(m_routing_step)にぶら下げ、ライン既定LTは m_line_default、製品別例外は m_line_product_lt を使用。
- スケジュール展開は m_routing_step で行うが、工程-ラインの紐づけはマスタで先に定義しておく。

- ラインマスタにリードタイム(日)を保持し、ライン配下の工程は工程マスタでラインIDを直接持たせる。
