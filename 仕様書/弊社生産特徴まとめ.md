# 弊社生産特徴まとめ

## 概要

本システムは、段階BOM・セル工程・時間運用・ライン/購買LT対応の生産管理システムです。
複数の得意先から内示（FORECAST）と確定受注（FIRM）を受け、優先順位を制御しながら生産計画を立てます。

---

## 1. 受注管理の特徴

### 1.1 内示と確定の二元管理

弊社では、得意先から以下2種類の受注情報を受け取ります：

| 受注タイプ | 日本語 | 性質 | 更新頻度 | スケジューリング優先度 |
|-----------|--------|------|----------|----------------------|
| **FORECAST** | 内示 | 予測情報、変更される可能性が高い | 毎日 | 低（確定がない場合のみ使用） |
| **FIRM** | 確定 | 正式な受注、必ず生産する | 適宜 | 最高（必ず生産計画に含める） |

### 1.2 複数得意先・複数フォーマット対応

#### 対応得意先

| 得意先コード | 得意先名 | 内示 | 確定 | フォーマット識別 |
|------------|---------|------|------|----------------|
| 000001 | ティエラ | ○ | ○ | データ区分（B17/Y55） |
| 000196 | クボタ（堺・枚方） | ○ | ○ | ファイル名 + データNO/No. |
| 000018 | リーデン | - | ○ | 発注コード（509） |

#### CSVフォーマット対応

各得意先のCSVフォーマットに対応するため、**サービス指向アーキテクチャ**を採用：

```
pm_backend/apps/orders/core/services/
├── base_import.py          # 基本クラス（共通処理）
├── tiera_naiji_import.py   # ティエラ内示
├── tiera_kakutei_import.py # ティエラ確定
├── kubota_sakai_naiji_import.py
├── kubota_sakai_kakutei_import.py
├── kubota_hirakata_kakutei_import.py
└── rieden_kakutei_import.py
```

- 得意先コード + 受注タイプ + ファイル名で自動的にサービスを選択
- 複数エンコーディング対応（CP932, Shift-JIS, UTF-8）
- カラム位置指定による柔軟なフォーマット対応

## 2. 受注管理の業務要件

### 2.1 内示の自動上書き（毎日更新）

**ビジネス要件**:
内示は毎日更新される予測データ。古い内示と新しい内示を併存させると混乱する。

**システム要求**:
新しい内示CSVがインポートされたら、**同じ得意先の既存内示を完全に置き換える**こと。

**期待される結果**:
常に最新の内示のみがシステムに保持され、データの整合性が保たれる。

### 2.2 確定受注による内示の自動無効化

**ビジネス要件**:
確定受注が来たら、その製品・納期については内示は不要になる。しかし、削除すると履歴が失われる。

**システム要求**:
確定受注CSVがインポートされたら、**同じ製品・同じ納期の内示を自動的に無効化**すること。
履歴として残すが、生産計画には使用しない。

**期待される結果**:

- 確定受注が優先される
- 内示は無効化されるが履歴として残る
- スケジューリング時には無効化された内示は無視される

## 3. 優先順位制御の要件

### 3.1 基本ルール

1. **status='OPEN'** の受注のみを使用
2. **確定（FIRM）を優先**
3. **確定がない製品・納期のみ、内示（FORECAST）を使用**

### 3.2 受注ステータスの意味

| status | 日本語 | スケジューリング | 説明 |
| ------ | ------ | ---------------- | ---- |
| `OPEN` | オープン | ○ 対象 | 有効な受注 |
| `SUPERSEDED` | 無効 | × 除外 | 確定受注により無効化された内示 |
| `CLOSED` | クローズ | × 除外 | 完了した受注 |
| `CANCELED` | キャンセル | × 除外 | キャンセルされた受注 |

**実装の詳細は [受注管理仕様書](受注管理仕様書.md) を参照してください。**

## 4. 生産構造の特徴

### 4.1 段階BOM

製品は複数階層の部品で構成される。

```
製品A (FINISHED)
├── 中間品B (SEMI_FINISHED)
│   ├── 原材料C (RAW_MATERIAL)
│   └── 原材料D (RAW_MATERIAL)
└── 購入品E (PURCHASED)
```

- 各階層ごとにBOMを定義
- `m_bom` (BOMヘッダ) と `m_bom_item` (BOM明細) で管理
- 展開時に全階層を再帰的に処理

### 4.2 セル工程（ルーティング）

製品ごとに工程順序と所要時間を定義。

```
製品A のルーティング:
1. プレス工程 (PRESS) - 10分/個
2. 溶接工程 (WELD) - 15分/個
3. 塗装工程 (PAINT) - 20分/個
4. 検査工程 (INSPECTION) - 5分/個
```

- `m_routing` (ルーティングヘッダ) と `m_routing_step` (工程明細) で管理
- 各工程には以下を定義：
  - 工程タイプ（製造 / 検査 / 移送）
  - 作業時間（分単位 or 日単位）
  - 段取時間、バッファ時間
  - 使用ライン

### 4.3 時間運用

#### 時間単位の混在

- **製造工程**: 分単位（10分/個、15分/個 など）
- **購買リードタイム**: 日単位（7日、14日 など）
- **移送時間**: 日単位（1日、2日 など）

`m_routing_step.time_unit` で `DAY` or `MINUTE` を指定。

#### スケジューリング計算

- 納期から逆算（バックワードスケジューリング）
- 工程ごとに所要時間を積算
- カレンダマスタで稼働日・非稼働日を考慮
- 日跨ぎ計算（分単位の作業が営業日をまたぐ場合）

### 4.4 ライン / 購買LT対応

#### 製造工程

- 各工程に使用ラインを指定（`m_routing_step.line_id`）
- ライン別に負荷を計算し、キャパシティを超えないように調整

#### 購買部品

- BOM明細で `procurement_type='PURCHASE'` を指定
- 購買リードタイム（`m_bom_item.purchase_lead_time_days`）を考慮
- 購買計画（発注日、納入日）を自動計算
- 製品で使う購買品は、その製品の得意先（受注先）から調達する想定とし、仕入先コードは得意先コードを流用してよい
- 得意先を直接仕入先として使えない場合は、その製品専用の擬似仕入先コードを作成して運用してもよい

#### レーザ切断 → ブレーキ曲げ（単品のまま流すパターン）

- レーザ切断工程のWIP品番: `YD40000680-16`（LT=1日）
- ブレーキ曲げ工程のWIP品番: `YD40000608-16B`（LT=1日）
- 両工程とも単品のまま流す。中間在庫を持たない場合は同一親品番のルーティング工程で管理し、中間在庫が必要な場合のみ上記WIP品番をBOM/ルートで受け渡す。

### 4.5 ライン最終品の概念

#### ライン最終品とは

**ライン最終品**: 各ラインの最終工程で加工される製品のこと。必ずしも出荷品（最終製品）ではない。

```
【例：タンクライン】
  Step 17: 最終組立 → YD60000441S（中間品）
  Step 18: タンク組立 → YD60000441（出荷品） ← ライン最終品

【例：ブレーキライン】
  Step 1: レーザ加工 → YD40000608-10（中間品）
  Step 2: ブレーキ加工 → YD40000608-10B（中間品） ← ライン最終品
  ※この後、タンクラインに投入される

【例：レーザーライン】
  Step 1: レーザ加工 → YD40000608-06（中間品） ← ライン最終品
  ※この後、ブレーキラインに投入される
```

#### ライン最終品の自動判定

システムは、`m_routing_step`から**ライン最終品を自動判定**します：

```python
# 各ルーティングについて、そのラインの最終工程を特定
for routing_id in routing_ids:
    last_step_on_line = RoutingStep.objects.filter(
        routing_id=routing_id,
        line_id=line_id
    ).order_by('-step_no').first()

    # 最終工程のoutput_product = ライン最終品
    line_final_product = last_step_on_line.output_product
```

**利点**:
- マスタ入力不要（ルーティングから自動判定）
- ルーティング変更時も自動追従
- 各ラインの計画対象製品が明確

#### 出荷品フラグとの違い

| フラグ | 意味 | 例 |
|--------|------|-----|
| `m_product.is_final_product` | **出荷品フラグ**<br>得意先に出荷する製品 | YD60000441, YD60003386 |
| （自動判定） | **ライン最終品**<br>そのラインの最終工程で加工される製品 | YD40000608-10B（ブレーキライン）<br>YD60000441（タンクライン） |

**重要**: ライン最終品は中間品を含むが、出荷品は必ず最終製品のみ。

### 4.6 連産品（コプロダクト）の概念

#### 4.6.1 概念

**連産品**: 1つの工程で複数の製品が同時に完成する生産方式。  
出力比率は固定で、**BOMの数量が「セットあたりの数量」**を表す。

- 親は**仮想セット品番**（在庫を持たない代表品番）
- 子品番が**実際の製品**（在庫・出荷対象）
- 歩留まり・副産物は現仕様では考慮しない（固定比率）

#### 4.6.2 作成し方（マスタ登録）

1. **仮想セット品番を作成**  
   `m_product.is_virtual_set = true` を設定（例: `SET-ABCD`）
2. **連産品BOMを作成**  
   `m_bom.is_coproduct = true`、親製品に仮想セット品番を指定
3. **BOM明細で子品番を登録**（セットあたり数量）
4. **ルーティング・工程時間は仮想セット品番に紐づける**

**例（1セットでA/B/Cを同時生産）**:
```
親: SET-ABCD（仮想セット品番）
  子: 製品A x1
  子: 製品B x1
  子: 製品C x2
```

#### 4.6.3 使い方（計画・在庫・実績）

**計画（需要→セット数変換）**:
- 需要は子品番で発生する
- 計画は仮想セット品番で立てる
- 必要セット数は**最大要求に合わせる**

```
必要セット数 = MAX( ceil(製品A需要/1), ceil(製品B需要/1), ceil(製品C需要/2) )
```

**在庫**:
- 仮想セット品番の在庫は持たない
- 実在庫は子品番で管理する

**実績**:
- 実績入力は仮想セット品番のセット数で記録
- システムが子品番の実績数量を自動展開（セット数×BOM数量）

**運用上の注意**:
- 連産品は**必ずしもライン最終品ではない**ため、計画対象は「連産品BOMの親（仮想セット品番）」に統一し、二重計画を避ける
- 子品番の過不足は在庫で吸収する

## 6. 生産計画管理（LinePlanとLineBacklog）

### 6.1 二層構造の生産計画

弊社の生産計画は**二層構造**で管理されます：

#### LinePlan（ユーザー入力層）

ユーザーが直接入力する生産計画：

```
line_plan テーブル:
- plan_date: 計画日
- line_id: 対象ライン
- product_id: 製品（ライン最終品）
- process_id: 工程
- plan_qty: 計画数量
- sequence_no: 順序番号（同日複数ロット対応）
- plan_id: 計画ID（自動生成、一意識別子）
```

**特徴**:
- ライン最終品のみを登録
- 1日に複数ロット（順序番号）を登録可能
- 計画IDで計画を一意に識別（例: `ABC123_20250115_100_1`）

#### LineBacklog（展開・在庫管理層）

LinePlanから工程展開され、在庫計算が行われるテーブル：

```
line_backlog テーブル:
- plan_date: 計画日
- line_id: 対象ライン
- product_id: 製品（全工程の製品）
- process_id: 工程
- order_qty: 後工程需要
- plan_qty: 計画数量（LinePlanから展開）
- actual_qty: 実績数量
- stock_qty: 実在庫
- planned_stock_qty: 計画在庫
- adjust_qty: 調整数
- scrap_qty: 仕損数
- actual_shipment_qty: 実績出庫数
- sequence_no: 順序番号
- plan_id: 計画ID
```

**特徴**:
- LinePlanから自動展開（全工程の製品を含む）
- 在庫計算機能を持つ
- 需要展開結果を保持

### 6.2 データフロー

```
[ユーザー入力]
    ↓
LinePlan（ライン最終品のみ、複数ロット）
    ↓ 工程展開（expand_processes）
LineBacklog（全工程、plan_qty・plan_id・sequence_no）
    ↓ 在庫計算（recalculate_inventory）
LineBacklog（stock_qty・planned_stock_qty更新）
    ↓ 工程ガント生成（generate）
LineGanttPlan（時間軸計画）
```

**詳細は [生産計画仕様書](生産計画仕様書.md) と [在庫計算仕様書](在庫計算仕様書.md) を参照してください。**

### 6.3 需要展開の考え方：「後工程 = お客さん」

弊社の需要展開は、**「後工程 = お客さん」**という考え方で行います：

```
最終ライン（タンクライン）:
  お客さん = 得意先（ティエラ、クボタ等）
  需要 = 受注データ

前工程ライン（ブレーキライン）:
  お客さん = 後工程（タンクライン）
  需要 = タンクラインの計画 × BOM個数

前工程ライン（レーザーライン）:
  お客さん = 後工程（ブレーキライン）
  需要 = ブレーキラインの計画 × BOM個数
```

**重要な原則**:

1. 需要展開は逆順（最終ライン → 前工程）でライン一つずつ行う
2. 受注から全ラインの需要を一括計算するのではない
3. 各ラインは「後工程の計画」を見て自ラインの需要を決める

### 6.4 ライン最終品のみを対象とする理由

各ラインの計画は、**そのラインの最終品のみ**を対象とします。

**理由**:

1. **重複計算の防止**: 中間工程の製品も全て含めると、同じ製品が複数回計画される
2. **計画の明確化**: 各ラインで「何を何個作るか」が明確
3. **前工程への展開**: ライン最終品から前工程の需要を自動計算できる

**実装の詳細は [生産計画仕様書](生産計画仕様書.md) を参照してください。**

## 7. スケジューリングロジック概要

### 6.1 逆算ロジック（バックワード）

```
納期（due_date）
  ↓ 逆算
最終工程（検査）終了時刻
  ↓ 逆算（検査時間）
最終工程（検査）開始時刻
  ↓ 逆算（バッファ）
前工程（塗装）終了時刻
  ↓ 逆算（塗装時間）
前工程（塗装）開始時刻
  ...
  ↓
部品発注日（購買リードタイム考慮）
```

### 6.2 日跨ぎ計算

- 分単位の作業時間が営業日をまたぐ場合の処理
- カレンダマスタで稼働日を判定
- 非稼働日をスキップ

### 6.3 移送バッチ・バッファ制御

- 工程間の移送時間を考慮
- バッファ時間で余裕を持たせる
- ロットサイズによる移送バッチを設定

## 7. データベース設計のポイント

### 7.1 製品カテゴリENUM化

`m_product.category` を ENUM 型で定義し、データの整合性を保証。

### 7.2 時間単位の明示化

`m_routing_step.time_unit` で `DAY` / `MINUTE` を明示し、計算ミスを防止。

### 7.3 調達整合性CHECK制約

`m_bom_item` に CHECK 制約を設定：

```sql
CHECK (
  (procurement_type = 'MAKE' AND line_id IS NOT NULL) OR
  (procurement_type = 'PURCHASE' AND purchase_lead_time_days IS NOT NULL)
)
```

製造品にはライン、購買品にはリードタイムを必須とする。

## 2. ラインと工程 (補足)
- 工程マスタはライン直下に紐づけておく（ルーティングがなくても工程の所属ラインを決められる）。
- ラインのLTはルーティング工程(m_routing_step)にぶら下げ、ライン既定LTは m_line_default、製品別例外は m_line_product_lt を使用。
- スケジュール展開は m_routing_step で行うが、工程-ラインの紐づけはマスタで先に定義しておく。

- ラインマスタにリードタイム(日)を保持し、ライン配下の工程は工程マスタでラインIDを直接持たせる。
