順番の比較と推奨

前提(確認済み・BOSS指示): 本番PC入替は2026年11月末ごろ。現行の本番PCはメモリ8GB、ディスク228GB(空き57GB)。Docker Desktop、共通MySQLコンテナ、バックエンド(gunicorn 3)、nginxが動作。分析実行は1件最大2GBで、8GBではMySQLとPGの併走や分析実行に余裕がありません。
A: 現行PCで先にPGB: 新PC入替を先、その後PG 推奨C: 新PC入替と同時にPG
リスク高 作業が2回。8GB機でリハーサル・pgloader・検証の負荷低〜中 変更が1つずつ。PG切替が12月以降にずれる高 PC・OS・Docker基盤・DBエンジンが同時に変わり、切り分け不能
戻し方旧MySQLのダンプで戻せる。切替後の入力データは逆変換が必要旧PC・旧MySQLを残せば即戻せる。PG切替も新PC上のMySQLを残して戻せる旧PC・旧MySQLで戻せる。原因がPC側かPG側か判別できない
メモリ不足の恐れ(併存が必要になり得る)新PC上で併存できる(§9)新PC。検証中の余裕はスペック次第
日程10月中に切替とPC入替の準備が重なる11月末はPC入替のみ。PGは12月〜で余裕あり11月末に集中。リハーサルが遅れると全体が遅れる
分析実行の有効化8GB機では余裕なし新PC+PG切替後(12月以降)新PC+PG稼働後

Bを推奨する理由

  • 変更を1つずつにでき、不具合の原因を切り分けられる
  • 戻し方が単純(旧PC・旧MySQLを残すだけ)
  • 8GB機でPG移行作業を行わずに済む
  • 11月末の期限をPC入替だけに絞れ、PG側の遅れが入替日程に影響しない

代償: PGへの切替と、分析実行の本番有効化が12月以降になります。

Cへ切り替えてよい条件: リハーサルが11月上旬までに「突合の合格」「migrate/スキーマ作成方式の確定」「計算結果の一致」を満たし、新PCの納入・セットアップに余裕があること。満たさなければBのままです。Aは、新PCの納入が大幅に遅れ、かつMySQLに性能・安定性の緊急問題が出た場合のみ再検討します。

データ移行と突合

コピー方式

方式内容長所短所
Pスキーマ=Django migrate、データ=pgloader(data only)Djangoのスキーマと一致するmigrateが通らない恐れ(§6)
Qpgloaderでスキーマ込みmigrateに依存しない。管理対象外3テーブルも作られるDjangoの制約・型とずれる恐れ。migrate --fake で履歴を合わせる必要
Rdumpdata / loaddataスキーマ作成はDjango遅い。巨大テーブルに不向き。型の扱いに注意

まずPの前提(空のPGでmigrate)を試験し、結果で決めます。pgloaderがWindowsで動かない場合は、WSL2内またはDockerイメージで実行します。方式の切替(P→Q→R)は、そのつどBOSSへ報告して承認を得ます。

コピー元MySQLの読み取りユーザーと接続経路 追加

  • コピー元は、新規作成するSELECT専用ユーザーで読み、作業終了後にそのユーザーを削除します(MySQL側の権限変更にあたるため、BOSS承認事項)
  • MySQLはWindows上、リハーサルのコンテナはWSL2のDocker内です。接続には「WSLから見たWindowsのIPアドレスの指定」「MySQL側での接続元の許可」「Windowsファイアウォールの設定」が必要です。ユーザーの作成とセットで承認を得ます

突合の手順

  • 件数: 全テーブルの COUNT(*) をMySQLとPGで比較(管理対象外3テーブルを含む)
  • 代表値: 主要テーブル(LineBacklog / LineDemand / LinePlan / Order / OrderLine / 在庫・進度関連)で、日付・数量・ステータス列の合計、最小・最大、NULL件数を比較。抜き取り行は主キー指定で全列を比較
  • 計算結果の一致: 同一入力で、在庫・計画在庫・進度の再計算結果を比較。差分が出たら、まずDBの実データで原因を切り分ける(生成ロジックの修正は最後)
  • 性能比較 追加: データ投入後に ANALYZE を実行し、インデックスを確認。在庫計算の速度と、主要画面の応答時間をMySQL版と比較します。移行の目的が速度の改善であるためです

骨子のみです。停止時間・件数・容量の数値は、リハーサルと会社での確認の後に確定します。ここに推測の数値は書きません。

P5: PC入替(MySQLのまま)

  1. 新PCにWSL2 + Docker Engineを構築(旧PCは稼働継続)
  2. 本番のダンプを取得し、新PCのMySQLへ復元。件数突合
  3. 新PCでアプリを起動し、IP(10.0.1.232)と証明書(pm-ui/certs/pm-prod.crt)の扱いを確認(§10)
  4. 引き継ぎ項目の確認 追加: 本番ComposeのRedis(AI分析)と AI_ANALYSIS_REDIS_URL、.env の項目(AI用DBユーザー、外部AIのAPIキー、SMTP、FCMなど)を安全に引き継ぐ方法。バックアップの取得方法(MySQLの mysqldump)
  5. 切替: 旧PCを停止 → 最終差分を反映 → IPを新PCへ → 動作確認
  6. 旧PC・旧MySQLは停止状態で残す(戻し先)

  • 突合で重大な不一致(件数不一致、計算結果の不一致)が解消できない
  • 主要業務フロー(受注展開、ガント、在庫・進度)が動かない

確認用SQL(MySQL、読み取りのみ)

-- DB別容量(GB)とテーブル数
SELECT table_schema,
       ROUND(SUM(data_length + index_length) / 1024 / 1024 / 1024, 2) AS gb,
       COUNT(*) AS tables
FROM information_schema.tables
GROUP BY table_schema;

-- テーブル別容量の上位(巨大テーブルの特定)
SELECT table_name, table_rows,
       ROUND((data_length + index_length) / 1024 / 1024, 1) AS mb
FROM information_schema.tables
WHERE table_schema = 'pm_db'
ORDER BY (data_length + index_length) DESC
LIMIT 30;
-- 他システムの利用状況(接続中のユーザー・接続元・DB)
SELECT user, host, db, COUNT(*) AS conns
FROM information_schema.processlist
GROUP BY user, host, db;

-- 共通MySQL上のDB一覧とアカウント
SHOW DATABASES;
SELECT user, host FROM mysql.user;

-- 不正な日付(0000-00-00)の有無: 日付列ごとに実行(列・表名は要確認)
-- SELECT COUNT(*) FROM <表> WHERE <列> = '0000-00-00';

processlist は実行時点の接続のみです。他システムの利用有無は、数日間の取得または担当者への確認が必要です。

リスクと代案

リスク影響対応・代案
migrateが通らないスキーマ作成が遅れる案Y(pgloaderでスキーマ込み)へ切替。BOSS承認
管理対象外テーブルのDDL取得元が不明PGに作れない実DBから取得。確定できなければBOSSへ報告
挙動差(大文字小文字、整数割り算、NULL順、照合順序)在庫・進度の数値ずれ突合で検出。ずれた箇所を実データで切り分けてから修正
リハーサルの遅れ11月末に間に合わないB案ならPC入替に影響しない。PG切替を12月以降に延期
新PCの納入が遅れる入替の遅れ旧PCでMySQL継続。PGは新PC後
共通MySQLを他システムが使用MySQL全体を止められない / PG化の影響§10-4で確認。使用していれば、PM専用DBを分離して移行する案を別途提案
PG切替後の戻し(データ逆変換)運用開始後の戻しが困難運用開始前に戻す原則。逆変換の手順は別途用意
8GB機で分析実行メモリ不足本番の分析実行は新PC+PG後。それまで無効
本書の数値の多くが未確認計画の精度§10の実測後に改訂
