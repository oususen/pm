# クボタ堺出荷便計画 依頼書

## 背景・目的

クボタ堺向け出荷の便振り分け・計画立案を行うため、以下の業務を支援する機能を構築する。

- クボタ堺向け製品は**内示と確定の乖離**が大きく、内示ベースで前工程を動かすとムダ/欠品リスクが高い
- 現在は便ごとの積載制約（荷台サイズ）が未考慮
- 便の出発時刻から逆算して**前工程の需要日**を決定する仕組みが必要（フロア配送の考え方を前工程にも適用）

## スコープ

- **対象**: クボタ**堺向け**のみ（他納入先は対象外）
- **積載計算精度**: 面積占有率方式（厳密な3D bin packingは不要）
- **振り分け方式**: **業務員が手動**で便選択（自動アルゴリズムは実装しない）
- **便マスタの所在**: 現在 `kubota_db.truck_master`（別DB）にあるものを `pm_db` へ**移植**し、`kubota_db` は捨てる

## 業務フロー

```
①受注取込
   OrderLine（元納期）
     ↓
②納期調整【新ステップ・営業担当】
   - 前倒し/後ろ倒しを営業が判断
   - 顧客調整・承認取得（口頭承認）
   - 調整後納期・数量を確定（分割可）
     ↓
③便割付【業務/物流担当】
   - 調整後納期をもとに便を選択
   - 積載占有率を見ながら手動で便に割付
   - 分割積載可
     ↓
④前工程需要日逆算
   便出発前日 → LineDemand / LinePlan へ反映
```

②と③は**完全に別画面・別ステップ**。

## データモデル（新規）

### 1. `KubotaSakaiTruck`（便マスタ）
配置: `apps/masters/`

| フィールド | 型 | 用途 |
|---|---|---|
| name | str | 便名（例: NO_2_10T） |
| width | int | 荷台幅(mm) |
| depth | int | 荷台奥行(mm) |
| height | int | 荷台高さ(mm) |
| max_weight | int | 最大積載重量(kg) |
| departure_time | time | 出発時刻 |
| arrival_time | time | 到着時刻 |
| arrival_day_offset | int | 到着日オフセット（0=当日着, 1=翌日着） |
| default_use | bool | 常用便フラグ |
| active | bool | 有効フラグ |

**データ移植元**: `kubota_db.truck_master` の現行4件
- NO_2_10T: 2400×9740×2400, max 10000kg, 11:00出発→15:15着, offset=0
- NO_3_10T: 2400×9500×2400, max 10000kg, 18:00出発→10:00着, offset=1
- NO_4_10T: 2400×9000×2400, max 10000kg, 10:00出発→12:00着, offset=0
- NO_5_10T: 2400×6100×2400, max 4000kg, 18:00出発→10:00着, offset=1

### 2. `KubotaSakaiDueAdjustment`（納期調整）
配置: `apps/shipping/` もしくは `apps/orders/`（要検討）

| フィールド | 型 | 用途 |
|---|---|---|
| order_line | FK(OrderLine) | 受注明細 |
| split_no | int | 分割連番（1,2,3...） |
| adjusted_due_date | date | 調整後納期 |
| adjusted_qty | int | 調整後数量 |
| remaining_qty | int | 残量（調整行単位） |
| adjustment_type | choice | just / forward / backward |
| customer_approved | bool | 後ろ倒し時の顧客口頭承認フラグ |
| adjusted_by | FK(User) | 営業担当 |
| adjusted_at | datetime | 調整日時 |
| note | text | 任意メモ |

**制約**:
- `unique_together = [('order_line', 'split_no')]`
- `Σ(adjusted_qty where order_line=X) == OrderLine.quantity`（過不足禁止）
- 分割しない場合は `split_no=1` の1行のみ
- **未操作の明細は自動ジャストとみなす**（レコード無しでも便計画画面に表示される）

### 3. `KubotaSakaiTripAssignment`（便割付）
配置: `apps/shipping/`

| フィールド | 型 | 用途 |
|---|---|---|
| order_line | FK(OrderLine) | 受注明細 |
| truck | FK(KubotaSakaiTruck) | 便 |
| departure_date | date | 便の出発日 |
| qty | int | 割付数量（分割対応） |
| created_by | FK(User) | 業務員 |
| created_at | datetime | |
| updated_at | datetime | |

**制約**:
- `Σ(qty where order_line=X) ≤ 調整後納期の総数量`
- 同一便の占有率 ≤ 100%（計算サービスで検証）
- **前倒し/後ろ倒しフラグはここには持たない**（納期調整ステップで処理済みのため）

### 4. `KubotaSakaiConfig`（設定）
配置: `apps/shipping/`

| フィールド | 型 | 用途 |
|---|---|---|
| assignment_deadline_days | int | 調整後納期の何営業日前までに便割付必須か |

- 設定画面から変更可能
- 期限超過で未割付の明細は便計画画面で**赤警告**表示

## 既存テーブル活用

- **容器マスタ**: pm_db 既存（`容器名`、`容器コード`、`サイズ(W×D×H)`、`最大重量`、`混載可否`、`積み重ね可否`）
- **製品マスタ**: 既存の `使用容器`（FK）と `容器入り数` を利用

→ 製品↔容器の紐付けテーブルは**新設不要**

## 積載計算ロジック（面積占有率方式）

```
# トラック床面積 = truck.width × truck.depth
# 容器床面積 = container.width × container.depth
# 段数 = container.積み重ね可 ? (truck.height // container.height) : 1
# 実効床面積 = 容器床面積 / 段数
# 占有率 = Σ(実効床面積 × 容器数) / トラック床面積
# 重量チェック = Σ(製品重量 × 数量) ≤ truck.max_weight
```

**追加ルール**:
- `混載不可` の容器 → その容器だけで1区画を占有（他容器と床面積共有不可）
- 占有率 > 100% でエラー
- 重量 > max_weight でエラー

配置: `apps/shipping/services/truck_load_calculator.py`（新設）

**配置**: 出荷管理メニュー配下

**UIパターン**: **生産計画画面を完全踏襲**（`ProductionPlanInput.vue` を参考）

```
┌──────────────────────────────────────────────────────────┐
│ 開始日:[4/15] 期間:[30日] 検索:[___]    [保存][表示のみ]│
├──────────────────────────────────────────────────────────┤
│                    │ 4/14(火)             │ 4/15(水)             │総残量│
│ No 品番    品名    │ 受注  納入  残量     │ 受注  納入  残量     │      │
├──────────────────────────────────────────────────────────┤
│ 1  3016... フレーム│ 100  [100]       │                  │  0   │
│ 2  3018... カバー  │      [ 80]       │ 200  [120]       │  0   │
│ 3  3020... ベース  │ 50   [ 50]       │                  │  0   │
└──────────────────────────────────────────────────────────┘
```

**サブ列構成（1日付あたり）**:
| サブ列 | 意味 | 編集可否 |
|---|---|---|
| 受注 | 元々の受注数量（`OrderLine.quantity` を元納期日付に表示） | 読み取り専用 |
| 納入 | 調整後に実際に出す数量（営業が入力） | 編集可 |
| 残量 | 当日日付の残量（`受注 - 納入`） | 読み取り専用 |

**残量列**:
- 日付サブ列: 各日付に `残量` 列を表示
- 行末列: 総残量列（`Σ受注 − Σ納入`）も併用

**動作ルール**:
- 元納期日の「受注」セルに元数量を表示（基準線）
- 営業は任意日付の「納入」セルに数量を入力
- 別日付への入力 = 前倒し/後ろ倒し（日付差から自動判定）
- 複数日に納入数量を入れれば自動的に分割扱い（専用ボタン不要）
- 後ろ倒し（納入日付 > 元納期）入力時に「顧客承認済みですか？」モーダル表示
- 保存時、総残量 ≠ 0 の行はエラー
- 保存時、納入セル入力を `KubotaSakaiDueAdjustment` レコードにマッピング（`remaining_qty` も保存）

**フィルタ**: 開始日・期間・品番/品名検索（生産計画画面と同一）

**配置**: 出荷管理メニュー配下

**表示対象**: `KubotaSakaiDueAdjustment` の調整後納期（レコード無し=元納期を自動ジャスト扱い）

├─────────────────────────────────────────────────────────┤

│ 4/15  3016... フレーム  50  17U  [NO_2▼]  2.76m²       │

**動作**:
- 行ごとに便をドロップダウンで選択 → `KubotaSakaiTripAssignment` に保存
- 上部に各便の占有率リアルタイム表示
- 分割積載: 同一明細の行を分割可能（数量を分けて別便へ）
- 未割付のまま `assignment_deadline_days` を超過した明細は**赤警告**
- 割付は 100% 超過するとエラー

## 前工程需要日ロジック

**基本ルール**: 便出発日の**前日**（1営業日前）が前工程の完了必要日

```python
def get_kubota_sakai_demand_date(order_line):
    assignment = KubotaSakaiTripAssignment.get(order_line)
    if not assignment:
        return None  # 未割付は警告対象
    return subtract_business_days(assignment.departure_date, 1)
```

**実装方針**:
- フロア配送の pickup ロジック（`floor_shipping` 関連）を参考に拡張

## 業務ルール確認事項（決定済み）

- **前倒し**: 上限ルール無し、営業判断で自由
- **後ろ倒し**: 顧客口頭承認ありで許可、厳密な承認記録は不要（フラグのみ）
- **分割積載**: 1つのOrderLineを複数便に分けて積載可能
- **未割付**: 基本NG、`assignment_deadline_days` 営業日前までに割付必須
- **前倒し/後ろ倒しの判断主体**: **営業**（納期調整ステップで実施）
- **便振り分けの判断主体**: **業務/物流**（便計画ステップで実施）
- **容器と製品の紐付け**: 既存の製品マスタ `使用容器` + `容器入り数` を使用
