# 在庫計算機能仕様書

## 概要

生産計画と実績に基づいて、在庫・計画在庫を自動計算する機能。
仕損数の集計、実績出庫数の計算、時制を考慮した在庫推移計算を行う。

## リードタイム対応

### 設計方針

工程間のリードタイム（LT）を考慮し、前工程への需要を適切な日付に積む。

| 区分 | 項目 | リードタイム考慮 | 説明 |
|------|------|------------------|------|
| **計画系** | order_qty（需要） | ✅ 遡る | 後工程計画日からLT分前に需要を立てる |
| **計画系** | 計画出庫 | ✅ 遡る | 後工程の計画日からLT分前が出庫日 |
| **実績系** | actual_shipment_qty | ❌ 同日 | 後工程実績と同日に出庫計上 |
| **実績系** | stock_qty（実在庫） | ❌ 同日 | 消費日に出庫、実態を反映 |
| **実績系** | progress_qty（進度） | ✅ 遡る | 後工程実績をLT遡りで出庫計上 |

### リードタイムの取得優先順位

1. **RoutingStep.lead_time_days**（工程ステップごと）
2. **Line.lead_time_days**（ラインのデフォルト）
3. **BOMItem.lead_time_days**（BOM明細ごと）
4. 0（デフォルト）

### 実績出庫を同日とする理由

1. **実績は「事実」を記録するもの**
   - 後工程で実績入力された日に部品が消費された事実を記録
   - 過去に遡って記録すると実在庫の整合性が崩れる

2. **リードタイムが必要なのは「計画」側**
   - 「いつまでに何個作るべきか」を計算するのに必要
   - 実績は後追いなので、リードタイム逆算は不要

3. **実在庫の整合性**
   - 実在庫は「今、物理的に何個あるか」を表す
   - 消費された日に出庫計上するのが自然

### 進度と在庫の違い

| 項目 | 需要/出庫の元データ | 用途 |
|------|---------------------|------|
| **stock_qty（在庫）** | 後工程実績（BOM経由、同日） | 今物理的に何個あるか |
| **progress_qty（進度）** | LineDemand（Routing展開済み） | 顧客需要に対する遅れ/先行 |

#### 計算式

```
在庫 = 前日在庫 + 実績 - 出庫（同日） + 調整 - 仕損
進度 = 前日進度 + 実績 - 需要（LineDemandから取得） + 調整 - 仕損
```

- プラス → 先行（余裕あり）
- マイナス → 遅れ（後工程に影響の可能性）

#### 進度の需要取得ロジック

進度は**ラインの計画とは無関係**。顧客需要に対する実績の遅れ/先行を表す。

需要は**LineDemand**（受注からRoutingでLT遡りして展開済み）から取得：

| 優先順位 | 条件 | 使用する値 |
|----------|------|------------|
| 1 | 確定（firm_qty）> 0 | firm_qty |
| 2 | 確定なし、内示（forecast_qty）> 0 | forecast_qty |
| 3 | どちらもなし | 0 |

### 具体例

**前提**: 顧客需要が1/17に10個確定。bライン（加工）のLT=2日。

```
顧客需要: 1/17に確定10個
  ↓ Routing展開でLT2日遡る
LineDemand: bラインの1/15に需要10個として展開される

■ 在庫計算（BOM経由、同日）
  後工程で1/17に10個実績 → bラインの1/17の在庫が減る

■ 進度計算（LineDemandから需要取得）
  bラインの1/15のLineDemandから需要10個を取得
  1/15時点で実績が0個 → 進度 = -10（10個遅れ）
  1/15時点で実績が15個 → 進度 = +5（5個先行）
```

進度なら「1/15までに作っておくべきだった」ことが見えるので、遅れの把握がしやすい。

## 計算ロジック

### 1. 仕損数の集計 (aggregate_scrap_to_backlog)

#### 処理フロー

1. 対象期間のLineBacklog.scrap_qtyをゼロリセット
2. 自工程仕損を集計
   - ScrapRecordから`disposition_status = 'REJECTED'`のレコードを抽出
   - plan_date, product, line, processが一致するLineBacklogに加算
3. 後工程仕損の展開分を集計
   - ScrapRecordDetailから仕損確定レコードを抽出
   - plan_date, product, line_id, process_idが一致するLineBacklogに加算

#### SQL イメージ

```python
# 自工程仕損
LineBacklog.objects.filter(
    plan_date=scrap.plan_date,
    product=scrap.product,
    line=scrap.line,
    process=scrap.process
).update(scrap_qty=F('scrap_qty') + scrap.qty)

# 後工程仕損展開
LineBacklog.objects.filter(
    plan_date=detail.scrap_record.plan_date,
    product=detail.product,
    line_id=detail.line_id,
    process_id=detail.process_id
).update(scrap_qty=F('scrap_qty') + detail.deduct_qty)
```

### 2. 実績出庫数の計算 (calculate_actual_shipment)

後工程の実績生産数からBOMを使って逆算。

**注意**: 本ロジックは最終品以外（BOM上に親が存在する製品）の出庫算出に使用する。  
最終品（`product.is_final_product = true`）は顧客確定を出庫として扱う（実在庫の計算を参照）。

#### 処理フロー

1. 対象製品を子製品として使用しているBOMItemを検索
2. 各BOMの親製品（後工程製品）のLineBacklogを検索
3. 後工程の実績生産数 × BOM数量 = 実績出庫数
4. 複数の後工程がある場合は合計

#### 計算式

```
実績出庫数 = Σ(後工程i.actual_qty × BOMi.quantity)
```

#### コード例

```python
parent_bom_items = BOMItem.objects.filter(
    child_product=backlog.product,
    bom__is_active=True
)

for bom_item in parent_bom_items:
    downstream_backlogs = LineBacklog.objects.filter(
        product=bom_item.bom.parent_product,
        plan_date=backlog.plan_date
    )
    for downstream in downstream_backlogs:
        if downstream.actual_qty > 0:
            shipment = downstream.actual_qty * bom_item.quantity
            total_shipment += shipment
```

### 3. 実在庫の計算 (recalculate_stock_qty)

日次で実在庫を再計算。

#### 計算式

```
当日実在庫 = 前営業日実在庫 + 実績生産 - 出庫 + 調整 - 仕損
```

#### 処理フロー

1. 製品・ライン・期間でLineBacklogを日付順に取得
2. 各日について：
   - 前営業日在庫を取得（カレンダが無い場合は暦日）
   - 出庫の扱いは「最終品 / 最終品以外」で分岐  
     （実在庫は過去〜今日までを対象とし、内示・計画は出庫に使わない）
     - 最終品（`product.is_final_product = true`）
       - plan_date <= 今日: 出庫 = 顧客確定（firm）
       - plan_date > 今日: 出庫 = 0（内示・計画は計上しない）
     - 最終品以外
       - plan_date <= 今日: 出庫 = Σ(親製品の実績 × BOM使用数)
       - plan_date > 今日: 出庫 = 0（内示・計画は計上しない）
     - 親が複数ある場合は合算
   - 実在庫を計算して保存
3. 前営業日のLineBacklogが無い場合は直前に計算した値を保持（0に戻さない）

#### コード例

```python
backlog.stock_qty = (
    prev_stock
    + (backlog.actual_qty or 0)
    - actual_shipment
    + (backlog.adjust_qty or 0)
    - (backlog.scrap_qty or 0)
)
```

### 4. 計画在庫の計算 (recalculate_planned_stock_qty)

時制を考慮して計画在庫を再計算。

#### 出庫の定義（計画在庫）

計画在庫は「計画ベース」の値なので、出庫も**計画値（内示）**を使用する。
これは実在庫（後工程の実績を使用）との重要な違い。

- 最終品（親なし）
  - 過去/今日（plan_date <= 今日）: 出庫 = 顧客確定（内示は使用しない）
  - 将来（plan_date > 今日）: 出庫 = 顧客確定。確定がない場合は内示を使用
- **最終品以外はBOM上の親製品すべての合算**
  - **全日付共通: 出庫 = Σ(親製品の計画値 × BOM使用数)**
  - 計画在庫は「計画どおり進んだ場合の在庫」なので、実績ではなく計画値（内示）で出庫計算

| 項目 | 出庫の計算 |
|------|------------|
| 実在庫（stock_qty） | 後工程の**実績**（actual_qty）× BOM使用数 |
| 計画在庫（planned_stock_qty） | 後工程の**計画値**（plan_qty）× BOM使用数 |

#### 時制による分岐

##### 過去（plan_date < 今日）

実績ベースで計算。出庫は後工程の**計画値**を使用。

```
計画在庫 = 前営業日計画在庫 + 実績生産 - 計画出庫 + 調整 - 仕損
```

##### 今日以降（plan_date >= 今日）

計画ベースで計算。出庫は後工程の**計画値**を使用。

```
計画在庫 = 前営業日計画在庫 + 計画生産 - 計画出庫 + 調整 - 仕損
```

#### コード例

```python
today = get_business_today()

# 出庫は常に後工程の計画値（内示）を使用
planned_shipment = _calculate_parent_planned_shipment(sample, today, shift_working_days)

if backlog.plan_date < today:
    # 過去: 生産は実績、出庫は計画値（内示）
    backlog.planned_stock_qty = (
        prev_planned
        + (backlog.actual_qty or 0)
        - planned_shipment
        + (backlog.adjust_qty or 0)
        - (backlog.scrap_qty or 0)
    )
else:
    # 今日以降: 生産は計画、出庫は計画値（内示）
    backlog.planned_stock_qty = (
        prev_planned
        + (backlog.plan_qty or 0)
        - planned_shipment
        + (backlog.adjust_qty or 0)
        - (backlog.scrap_qty or 0)
    )
```

### 5. ライン全体の在庫再計算 (recalculate_inventory_for_line)

指定ラインの全製品について在庫を再計算。

#### 処理フロー

1. 仕損数を集計（aggregate_scrap_to_backlog）
2. ライン・期間内の全製品IDを取得
3. 各製品について：
   - 実在庫を計算（recalculate_stock_qty）
   - 計画在庫を計算（recalculate_planned_stock_qty）

### 6. 進度計算の起点

進度も在庫と同様に**前々日を初期値**として使用し、**前日以降のみ再計算**する。

- 前々日以前: 既存の進度値をそのまま使用（更新しない）
- 前日以降: 前々日の進度を起点に再計算

## LineDemand展開とリードタイム換算

### リードタイムの取り扱い

- 展開はルーティングの `hierarchy_path` を親子関係として辿り、系統ごとに日付を計算する。
- 展開対象の品番は **`routing_step.output_product` を優先**（未設定の場合は受注明細の品番）。
- **DAY工程**: `lead_time_days` を営業日換算で遡る。
- **MINUTE工程**: `duration_min` を累積し、営業日換算で日数に加算する。
  - 換算基準: 480分 = 1日
  - 切り上げ方式: `ceil(累積分 / 480)`
  - 例: 1日 + 20分 + 20分 → 1.166...日 → **2日**扱い

#### 在庫再計算ボタン

1. 確認ダイアログを表示
2. 表示中の全ラインIDを取得
3. 各ラインに対して`recalculateInventory` APIを呼び出し
4. 完了後、データを再読み込み

```javascript
const recalculateInventory = async () => {
  if (!confirm('在庫と計画在庫を再計算しますか？\n※全ラインの在庫データが更新されます。')) {
    return;
  }

  const start = columns.value[0];
  const end = columns.value[columns.value.length - 1];
  const lines = [...new Set(demands.value.map(d => d.line).filter(Boolean))];

  for (const lineId of lines) {
    await api.lineBacklogs.recalculateInventory({
      line_id: lineId,
      start_date: start,
      end_date: end
    });
  }

  await load();
};
```

#### 内示（order_qty）の更新

在庫一覧の読み込み時に、表示中のラインに対して`line-backlogs/pickup`を呼び出し、
後工程計画から`order_qty`を再計算して反映する。

## 使用例

### シナリオ1: 過去で実績なしの場合

**前提条件**:
- 12/24（過去日）
- order_qty = 6（後工程需要あり）
- plan_qty = 0
- actual_qty = 0（生産しなかった）
- 前日計画在庫 = 0

**計算結果**:
```
計画在庫 = 0 + 0 - 6 + 0 - 0 = -6
```

→ 生産しなかったが需要があったため、在庫不足（-6）

### シナリオ2: 過去で実績ありの場合

**前提条件**:
- 12/24（過去日）
- order_qty = 6
- plan_qty = 10
- actual_qty = 8（実績入力済み）
- 前日計画在庫 = 0
- 実績出庫 = 6（後工程で実際に使用）

**計算結果**:
```
計画在庫 = 0 + 8 - 6 + 0 - 0 = 2
```

→ 8個生産、6個出庫、2個在庫

### シナリオ3: 仕損発生の場合

**前提条件**:
- 12/25（過去日）
- actual_qty = 10
- 実績出庫 = 5
- scrap_qty = 2（仕損発生）
- 前日計画在庫 = 2

**計算結果**:
```
計画在庫 = 2 + 10 - 5 + 0 - 2 = 5
```

→ 仕損分を差し引いた在庫

## 運用フロー

### 日次運用

1. **生産実績入力**
   - 各ラインで実績数量（actual_qty）を入力
   - 仕損発生時はScrapRecordに記録

2. **在庫再計算**
   - 在庫一覧画面で「在庫再計算」ボタンをクリック
   - 全ラインの在庫・計画在庫が自動更新

3. **在庫確認**
   - マイナス在庫（赤字表示）をチェック
   - 必要に応じて調整数（adjust_qty）を手入力

### 月次運用

1. **棚卸**
   - 実在庫とシステム在庫を比較
   - 差異をadjust_qtyに入力

2. **在庫再計算**
   - 調整後の在庫を再計算

## 注意事項

### 計算順序

1. 仕損数の集計
2. 実在庫の計算（製品ごと、日付順）
3. 計画在庫の計算（製品ごと、日付順）

**重要**: 日付順に計算する必要がある（前日在庫を参照するため）

### 前日参照の定義

- 前日は「カレンダの前営業日」を使用する
- ラインにカレンダが無い場合は`tiera_muke`を使用
- カレンダが無い場合は暦日で前日を扱う
- 前営業日のLineBacklogが無い場合は直前に計算した値を保持する

### 後工程実績の考慮

- 実績出庫数は後工程の実績から自動計算（最終品以外）
- 後工程に複数のラインがある場合は合算
- 最終品（`product.is_final_product = true`）の出庫は顧客確定を使用
- 実在庫の出庫は過去〜今日のみ計上し、内示・計画は使用しない

### 時制判定

- 今日の日付は**日替わり時刻（8時）を考慮**して取得
  - `get_business_today()`を使用
  - 8時より前なら前日扱い（例: 1/20 7:59 → 1/19として扱う）
- 工程作業入力（工程実時間記録）の計画日も8時区切りで判定する
  - 8時より前の入力は前日扱いで `plan_date` を決定する
- 過去: `plan_date < today`
- 未来: `plan_date >= today`

### 日替わり時刻と在庫計算の関係

弊社では日替わり時刻を8:00としているため、在庫計算でも8時区切りを考慮する。

#### 問題となるケース

```
例：1月20日 8:01に在庫計算を実行する場合

- 7:59に実績入力 → これは「1月19日」の実績として扱われる
- しかし、1月19日の在庫はまだ7:59の実績が反映されていない可能性がある
- 単純に「前日の在庫」を起点にすると、最新の実績が反映されない
```

#### 解決策

- 在庫計算の起点を**前々日の在庫**とする
- 前々日の在庫は確定しているので、そこから前日・今日を再計算すれば正しい値になる
- **前々日以前の在庫は更新しない**（過去の事実は変更しない）

#### 計算ロジック

| 日付 | 処理 |
|------|------|
| 前々日以前 | 既存の在庫値をそのまま使用（更新しない） |
| 前日 | 前々日の在庫を起点に再計算 |
| 今日以降 | 前日の在庫を起点に再計算 |

#### コード例

