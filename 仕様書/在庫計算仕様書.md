# 在庫計算機能仕様書

## 概要

生産計画と実績に基づいて、在庫・計画在庫を自動計算する機能。
仕損数の集計、実績出庫数の計算、時制を考慮した在庫推移計算を行う。

## リードタイム対応

### 設計方針

工程間のリードタイム（LT）を考慮し、前工程への需要を適切な日付に積む。

| 区分 | 項目 | リードタイム考慮 | 説明 |
|------|------|------------------|------|
| **計画系** | order_qty（需要） | ✅ 遡る | 後工程計画日からLT分前に需要を立てる |
| **計画系** | 計画出庫 | ✅ 遡る | 後工程の計画日からLT分前が出庫日 |
| **実績系** | actual_shipment_qty | ❌ 同日 | 後工程実績と同日に出庫計上 |
| **実績系** | stock_qty（実在庫） | ❌ 同日 | 消費日に出庫、実態を反映 |
| **実績系** | progress_qty（進度） | ✅ 遡る | 後工程実績をLT遡りで出庫計上 |

### リードタイムの取得優先順位

1. **RoutingStep.lead_time_days**（工程ステップごと）
2. **Line.lead_time_days**（ラインのデフォルト）
3. **BOMItem.lead_time_days**（BOM明細ごと）
4. 0（デフォルト）

### 実績出庫を同日とする理由

1. **実績は「事実」を記録するもの**
   - 後工程で実績入力された日に部品が消費された事実を記録
   - 過去に遡って記録すると実在庫の整合性が崩れる

2. **リードタイムが必要なのは「計画」側**
   - 「いつまでに何個作るべきか」を計算するのに必要
   - 実績は後追いなので、リードタイム逆算は不要

3. **実在庫の整合性**
   - 実在庫は「今、物理的に何個あるか」を表す
   - 消費された日に出庫計上するのが自然

### 休日当日の再計算ルール（2026-04-05 反映）

- 目的: 休日に登録された実績が、再計算時に除外される不整合を防ぐ。
- 変更内容:
  - 在庫/計画在庫の再計算では、以下を分離して扱う。
  - `calc_today`（再計算開始日の算出用）: 非稼働日の場合は前営業日に丸める。
  - `business_today`（実績反映判定用）: 当日の日付をそのまま使う。
  - 進度/計画進度の再計算は、非稼働日でも当日の実績を計算に含める（在庫系と同じ方針）。
  - 進度の累積は「前営業日」ではなく「前日（暦日）」を参照して引き継ぐ。
- 効果:
  - 休日（例: 2026/04/04）に入力した実績も、当日分として `actual_shipment_qty` / 在庫 / 計画在庫 / 進度へ反映される。
  - 既存どおり、営業日ベースの計算開始日（LT窓）は維持される。
- 例外: 完成品（is_final）の計画出庫(`planned_shipment`)判定のみ `calc_today`（営業日調整済）を使用する。
  - 理由: 休日当日で firm_qty が無い場合に、顧客カレンダ由来の `order_qty` への
    フォールバック（`firm_qty if firm_qty > 0 else order_total`）を維持するため。
  - これにより、ライン非稼働日でも顧客が受け取る注文分の計画出庫が欠落しない。

### 進度と在庫の違い

| 項目 | 需要/出庫の元データ | 用途 |
|------|---------------------|------|
| **stock_qty（在庫）** | 後工程実績（BOM経由、同日） | 今物理的に何個あるか |
| **progress_qty（進度）** | LineDemand（Routing展開済み） | 顧客需要に対する遅れ/先行 |

#### 計算式

```
在庫 = 前日在庫 + 実績 - 出庫（親の実績+仕損）
進度 = 前日進度 + 実績 - 需要（LineDemandから取得） + 調整
```

**在庫計算**: 調整（adjust_qty）は使用しない
- 出庫 = 親の実績 + 親の仕損（全て）
- 仕損による子部品消費は、親製品の仕損が出庫に含まれるため自動的に反映される

**進度計算**: 調整（adjust_qty）を使用する
- 出庫 = 顧客需要（LineDemand）
- 仕損による子部品消費は顧客需要に含まれないため、adjust_qty で調整する必要がある

- プラス → 先行（余裕あり）
- マイナス → 遅れ（後工程に影響の可能性）

#### 進度の需要取得ロジック

進度は**ラインの計画とは無関係**。顧客需要に対する実績の遅れ/先行を表す。

需要は**LineDemand**（受注からRoutingでLT遡りして展開済み）から取得：

| 優先順位 | 条件 | 使用する値 |
|----------|------|------------|
| 1 | 実需（firm_qty）> 0 | firm_qty |
| 2 | 実需なし、計需（forecast_qty）> 0 | forecast_qty |
| 3 | どちらもなし | 0 |

### 具体例

**前提**: 顧客実需が1/17に10個。bライン（加工）のLT=2日。

```
顧客実需: 1/17に10個
  ↓ Routing展開でLT2日遡る
LineDemand: bラインの1/15に需要10個として展開される

■ 在庫計算（BOM経由、同日）
  後工程で1/17に10個実績 → bラインの1/17の在庫が減る

■ 進度計算（LineDemandから需要取得）
  bラインの1/15のLineDemandから需要10個を取得
  1/15時点で実績が0個 → 進度 = -10（10個遅れ）
  1/15時点で実績が15個 → 進度 = +5（5個先行）
```

進度なら「1/15までに作っておくべきだった」ことが見えるので、遅れの把握がしやすい。

## 計算ロジック

### 1. 仕損数の集計 (aggregate_scrap_to_backlog)

#### 処理フロー

1. 対象期間のLineBacklog.scrap_qty, adjust_qtyをゼロリセット
2. 自製品仕損を集計
   - ScrapRecordから仕損確定レコードを抽出
   - plan_date, product, line, processが一致するLineBacklogの**scrap_qty**に加算
   - **常にscrap_qtyに保存**（is_production_recordedに関わらず）
3. 子部品仕損（BOM展開分）を集計
   - ScrapRecordDetailから仕損確定レコードを抽出
   - plan_date, product, line_id, process_idが一致するLineBacklogの**adjust_qty**に**負の値として**保存

#### 仕損の保存先

| 対象 | 保存先フィールド | 値 | 用途 |
|------|------------------|-----|------|
| 自製品 | scrap_qty | 正の値 | 親製品の出庫計算で使用（親の実績+仕損） |
| 子部品（BOM展開） | adjust_qty | 負の値 | 在庫・進度計算で調整として減算 |

#### is_production_recorded による処理分岐

| is_production_recorded | 対象 | 処理 |
|------------------------|------|------|
| True（入力済み） | 自製品 | scrap_qtyに保存 + actual_qtyから減算 |
| True（入力済み） | 子部品 | adjust_qtyに負の値で保存（在庫減算は不要、出庫済み） |
| False（未入力） | 自製品 | scrap_qtyに保存のみ |
| False（未入力） | 子部品 | adjust_qtyに負の値で保存 + 在庫から即時減算 |

**注意**: 入力済みの場合、子部品は既に生産実績入力時に出庫として消費済みのため、在庫減算は不要。

#### SQL イメージ

```python
# 自製品仕損（常にscrap_qtyに保存）
LineBacklog.objects.filter(
    plan_date=scrap.plan_date,
    product=scrap.product,
    line=scrap.line,
    process=scrap.process
).update(scrap_qty=F('scrap_qty') + scrap.qty)

# 子部品仕損展開（adjust_qtyに負の値で保存）
LineBacklog.objects.filter(
    plan_date=detail.scrap_record.plan_date,
    product=detail.product,
    line_id=detail.line_id,
    process_id=detail.process_id
).update(adjust_qty=F('adjust_qty') - detail.deduct_qty)
```

### 2. 実績出庫数の計算 (calculate_actual_shipment)

後工程の実績生産数からBOMを使って逆算。

**注意**: 本ロジックは最終品以外（BOM上に親が存在する製品）の出庫算出に使用する。  
最終品（`product.is_final_product = true`）は顧客実需を出庫として扱う（実在庫の計算を参照）。

#### 処理フロー

1. 対象製品を子製品として使用しているBOMItemを検索
2. 各BOMの親製品（後工程製品）のLineBacklogを検索
3. 後工程の実績生産数 × BOM数量 = 実績出庫数
4. 複数の後工程がある場合は合計

#### 計算式

```
実績出庫数 = Σ(後工程i.actual_qty × BOMi.quantity)
```

#### コード例

```python
parent_bom_items = BOMItem.objects.filter(
    child_product=backlog.product,
    bom__is_active=True
)

for bom_item in parent_bom_items:
    downstream_backlogs = LineBacklog.objects.filter(
        product=bom_item.bom.parent_product,
        plan_date=backlog.plan_date
    )
    for downstream in downstream_backlogs:
        if downstream.actual_qty > 0:
            shipment = downstream.actual_qty * bom_item.quantity
            total_shipment += shipment
```

### 3. 実在庫の計算 (recalculate_stock_qty)

日次で実在庫を再計算。

#### 計算式

```
当日実在庫 = 前営業日実在庫 + 実績生産 - 出庫（親の実績+仕損） + 調整
```

**注意**: 仕損は直接減算しません。
- **自製品の仕損**: is_production_recorded=Trueの場合、actual_qty減算で対応済み
- **親製品の仕損**: 出庫計算で「親の実績 + 親の仕損」として反映される
- **子部品の仕損**: adjust_qtyに負の値として保存され、上記式の「調整」で反映される

#### 処理フロー

1. 製品・ライン・期間でLineBacklogを日付順に取得
2. 各日について：
   - 前営業日在庫を取得（カレンダが無い場合は暦日）
   - 出庫の扱いは「最終品 / 最終品以外」で分岐  
     （実在庫は過去〜今日までを対象とし、計需・計画は出庫に使わない）
     - 最終品（`product.is_final_product = true`）
       - plan_date <= 今日: 出庫 = 顧客実需（firm）
       - plan_date > 今日: 出庫 = 0（計需・計画は計上しない）
     - 最終品以外
       - plan_date <= 今日: 出庫 = Σ(親製品の実績 × BOM使用数)
       - plan_date > 今日: 出庫 = 0（計需・計画は計上しない）
     - 親が複数ある場合は合算
   - 実在庫を計算して保存
3. 前営業日のLineBacklogが無い場合は直前に計算した値を保持（0に戻さない）

#### コード例

```python
# 出庫 = 親製品の実績 + 親製品の仕損
actual_shipment = _calculate_parent_actual_shipment(backlog)
# ※ _calculate_parent_actual_shipment は親の actual_qty + scrap_qty を合算

backlog.stock_qty = (
    prev_stock
    + (backlog.actual_qty or 0)
    - actual_shipment  # 親の実績+仕損が反映済み
    + (backlog.adjust_qty or 0)  # 子部品仕損は負の値で含まれる
)
```

### 4. 計画在庫の計算 (recalculate_planned_stock_qty)

時制を考慮して計画在庫を再計算。

#### 出庫の定義（計画在庫）

計画在庫は「計画ベース」の値だが、**過去は実績ベース**で整合を取る。
これは実在庫（後工程の実績を使用）との違いを意識した運用。

- 最終品（親なし）
  - 過去/今日（plan_date <= 今日）: 出庫 = 顧客実需（計需は使用しない）
  - 将来（plan_date > 今日）: 出庫 = 顧客実需。実需がない場合は計需を使用
- ライン最終品（親あり・ライン終点）
  - 過去（plan_date < 今日）: 出庫 = Σ(親製品の**実績優先、なければ計画** × BOM使用数)【LTシフトあり】
    - 親参照が取得できない場合は `order_qty` を使用
  - 今日以降（plan_date >= 今日）: 出庫 = 需要（order_qty）
- **最終品以外（ライン最終品を除く）はBOM上の親製品すべての合算**
  - **過去（plan_date < 今日）**: 出庫 = Σ(親製品の**実績優先、なければ計画** × BOM使用数)【LTシフトあり】
  - **今日以降（plan_date >= 今日）**: 出庫 = Σ(親製品の計画値 × BOM使用数)【LTシフトあり】
  - 過去も今日以降も、出庫計算時に**BOMのLT分だけ日付をシフト**して親製品を参照する
  - 過去の出庫で、LTシフト後の親製品の日付が未来になる場合は計画値を使用

| 項目 | 出庫の計算 | LTシフト |
|------|------------|----------|
| 実在庫（stock_qty） | 後工程の**実績**（actual_qty）× BOM使用数 | なし（同日） |
| 計画在庫（planned_stock_qty） | 過去は後工程の**実績優先、なければ計画**、今日以降は**計画値** × BOM使用数 | あり（LT分シフト） |

#### 出庫のLTシフト（計画在庫）

計画在庫の出庫計算では、BOMのリードタイムを考慮して親製品の日付をシフトする。

```
例: 子製品Aの計画日が1月20日、親製品BへのLTが3日の場合
  → 子製品Aの1月20日の出庫 = 親製品Bの「1月23日」の実績/計画を参照
```

これにより、「子製品が出庫されるタイミング」と「親製品が製造されるタイミング」の関係が正しく反映される。

#### 時制による分岐

##### 過去（plan_date < 今日）

実績ベースで計算。出庫は**最終品以外（ライン最終品を除く）は後工程の実績+仕損**を使用。

```
計画在庫 = 前営業日計画在庫 + 実績生産 - 出庫（親の実績+仕損） + 調整
```

##### 今日以降（plan_date >= 今日）

計画ベースで計算。出庫は**最終品以外（ライン最終品を除く）は後工程の計画値**を使用。

```
計画在庫 = 前営業日計画在庫 + 計画生産 - 計画出庫 + 調整
```

**注意**: 仕損は直接減算しません（自製品はactual_qty減算、子部品はadjust_qtyで対応）。

#### コード例

```python
today = get_business_today()

if sample.product.is_final_product:
    # 出庫は実需優先。実需なしの場合のみ計需を使用
    planned_shipment = firm_qty if firm_qty > 0 else order_qty
elif sample.product.is_line_final_product:
    # ライン最終品は需要（order_qty）を出庫として扱う
    planned_shipment = order_qty
elif backlog.plan_date < today:
    # 出庫は過去=実績優先（なければ計画）。LTシフトを適用
    planned_shipment = _calculate_parent_actual_or_plan_shipment(sample, shift_working_days)
else:
    # 今日以降=計画値（計需）。LTシフトを適用
    planned_shipment = _calculate_parent_planned_shipment(sample, today, shift_working_days)

if backlog.plan_date < today:
    # 過去: 生産は実績、出庫は実績+仕損
    # planned_shipment には親の actual_qty + scrap_qty が含まれる
    backlog.planned_stock_qty = (
        prev_planned
        + (backlog.actual_qty or 0)
        - planned_shipment  # 親の実績+仕損が反映済み
        + (backlog.adjust_qty or 0)  # 子部品仕損は負の値で含まれる
    )
else:
    # 今日以降: 生産は計画、出庫は計画値（計需）
    backlog.planned_stock_qty = (
        prev_planned
        + (backlog.plan_qty or 0)
        - planned_shipment
        + (backlog.adjust_qty or 0)  # 子部品仕損は負の値で含まれる
    )
```

### 5. ライン全体の在庫再計算 (recalculate_inventory_for_line)

指定ラインの全製品について在庫を再計算。

#### パラメータ

| パラメータ | デフォルト | 説明 |
|-----------|-----------|------|
| progress_only | False | Trueの場合は進度のみ再計算し、在庫・計画在庫・仕損集計をスキップ |
| include_progress | True | 進度も再計算するか（progress_only=Trueのとき強制True） |
| line_final_only | False | ライン最終品のみ計算するか |
| product_ids | None | 対象製品ID配列（指定時はその製品のみ計算） |

#### 処理フロー

**通常モード（progress_only=False）:**
1. 仕損数を集計（aggregate_scrap_to_backlog）
2. 確定受注マップを作成
3. ライン・期間内の全製品IDを取得
4. 各製品について：
   - 実在庫を計算（recalculate_stock_qty）
   - 計画在庫を計算（recalculate_planned_stock_qty）
   - include_progress=Trueの場合は進度も計算（recalculate_progress_qty）

**進度専用モード（progress_only=True）:**
1. 仕損集計・確定受注マップ作成をスキップ
2. 各製品について進度のみ計算（recalculate_progress_qty）

### 6. 進度計算の起点

**計算開始日**: 今日 - (最大LT + 1)営業日（計画在庫と同じ）

進度は計画在庫と同様に**今日 - (最大LT + 1)営業日を初期値**として使用し、**それ以降のみ再計算**する。

- 最大LT = その製品の**完成品向け累積LTの最大値**（自分LTを含む）
- **理由**: 親製品の実績が変更されると、LT分遡った日の子製品の需要（LineDemand）に影響するため

- 計算開始日以前: 既存の進度値をそのまま使用（更新しない）
- 計算開始日より後: 計算開始日の進度を起点に再計算

### 7. 計画進度の計算 (planned_progress_qty)

計画在庫と同じ設計思想で、**時制を考慮**して計画進度を計算する。

#### 初期値

計画進度の初期値（計算開始日の値）は **`progress_qty`（実進度）** を使用する。
これは「計画在庫の初期値に実在庫を使う」のと同じ思想。

#### 生産数の時制切り替え

| 日付 | 使用する生産数 | 理由 |
|------|--------------|------|
| 過去（plan_date < 今日） | 実績（actual_total） | 過去は事実ベース |
| 今日以降（plan_date >= 今日） | 計画（plan_total） | 未来は計画ベース |

#### 計算式

```
計画進度 = 前日計画進度
         + 生産数（過去=実績 / 今日以降=計画）
         - 計画出荷
         + 調整合計
         + 仕損調整合計
         + 進度調整値
```

これにより、過去日の計画進度が実進度と一致するよう整合性が保たれる。

## LineDemand展開とリードタイム換算

### リードタイムの取り扱い

- 展開はルーティングの `hierarchy_path` を親子関係として辿り、系統ごとに日付を計算する。
- 展開対象の品番は **`routing_step.output_product` を優先**（未設定の場合は受注明細の品番）。
- **DAY工程**: `lead_time_days` を営業日換算で遡る。
- **MINUTE工程**: `duration_min` を累積し、営業日換算で日数に加算する。
  - 換算基準: 480分 = 1日
  - 切り捨て方式: `floor(累積分 / 480)`（480分未満は0日）
  - 例: 1日 + 20分 + 20分 → 1.166...日 → **1日**扱い

#### 画面操作フロー

1. **フィルター入力**: ライン、工程、品番のいずれか（または複数）を入力
2. **更新ボタン**: データ取得のみ（高速）
3. **表示ライン全品番再計算ボタン**: 表示中のラインに対して以下を実行
   - 需要再計算（pickup）
   - 仕損再計算（recalculate_scrap）
   - 在庫再計算（recalculate_inventory）
4. **表示品番だけ再計算ボタン**: フィルター後に表示されている品番だけに対して以下を実行
   - 生産在庫画面: `pickup_for_products` → `recalculate_scrap_for_products` → `recalculate_inventory_for_products`
   - 仕入れ在庫画面: `pickup_purchase_for_products` → `recalculate_scrap_for_products` → `recalculate_inventory_for_products`
   - 進度のみ画面: `recalculate_inventory_for_products(include_progress=true)` を表示品番だけに対して実行
5. 再計算完了後、最新データを自動再取得

#### 更新ボタン

データ取得のみを行う。画面を開いた時点では自動取得せず、フィルター入力後に明示的に実行する。

```javascript
const load = async () => {
  const res = await api.lineBacklogs.getLineBacklogs(getBacklogParams());
  applyDemands(res.data || []);
};
```

#### 表示ライン全品番再計算ボタン

表示中のライン（フィルター適用後）に対して、需要・仕損・在庫再計算を並列実行する。

```javascript
const recalculate = async () => {
  const lineIds = getDisplayedLineIds(); // 表示中のラインのみ

  // 1. 需要再計算（pickup）- 並列実行
  await Promise.all(lineIds.map(lineId => api.lineBacklogs.pickup({...})));

  // 2. 仕損再計算 - 並列実行
  await Promise.all(lineIds.map(lineId => api.lineBacklogs.recalculateScrap({...})));

  // 3. 在庫再計算 - 並列実行
  await Promise.all(lineIds.map(lineId => api.lineBacklogs.recalculateInventory({...})));

  // 4. 最新データを再取得
  await load();
};
```

#### 表示品番だけ再計算ボタン

- 既存の全件再計算ボタンとは別ボタンで実行する。
- 対象は「現在表示されているグループ」の `product_id` 一覧とする。
- 実行前に対象件数を確認表示する。
- バックエンドには `product_ids` を渡し、需要・仕損・調整反映・在庫/進度計算の全てを表示品番だけに限定する。
- `start_date` には画面の表示開始日を渡していても、バックエンド側ではこれを再計算開始日に使わない。
- 表示品番だけ再計算の開始日は、前々営業日と LT 起点の内部開始日から自動決定する。
- 進度のみ画面では既存仕様に合わせ、需要再計算は行わず `recalculate_inventory(include_progress=true)` の品番限定版だけを実行する。

**パフォーマンス改善**:

- 表示中のラインのみを対象（全ラインではない）
- 各処理を並列実行（直列ではない）

#### order_qty 作成タイミング

`order_qty/demand_qty_plan` は **pickup 実行時に作成/更新**される。  
在庫/残量一覧では「再計算」ボタンが pickup の実行タイミングとなる。

#### 需要再計算（pickup）の詳細

pickup API は「計需」と「実需」の両方を更新する。

| 対象 | 更新内容 | 更新フィールド |
|------|----------|---------------|
| **最終品** | 顧客の計需/実需を取得（実需優先） | `order_qty`, `demand_qty_plan`, `forecast_order_qty`, `firm_order_qty` |
| **中間品** | 後工程の計画数 × BOM数量 | `order_qty`, `demand_qty_plan` |

**注意**: 中間品の「実需」列（= 後工程の実績）は pickup では更新されない。在庫再計算（recalculate_inventory）で `actual_shipment_qty` として計算される。

#### 画面表示項目と更新タイミング

| **実需** | `firm_order_qty`（顧客実需） | `actual_shipment_qty`（後工程実績） | 最終品: 需要再計算、中間品: **在庫再計算** |
| **計画** | `plan_qty` | `plan_qty` | 生産計画入力で保存 |
| **実績** | `actual_qty` | `actual_qty` | 生産実績入力 |

| **在庫** | `stock_qty` | `stock_qty` | 在庫再計算 |
| **計画在庫** | `planned_stock_qty` | `planned_stock_qty` | 在庫再計算 |
| **進度** | `progress_qty` | `progress_qty` | 在庫再計算 |

## 使用例

### シナリオ1: 過去で実績なしの場合

**前提条件**:
- 12/24（過去日）
- order_qty = 6（後工程需要あり）
- plan_qty = 0
- actual_qty = 0（生産しなかった）
- 前日計画在庫 = 0

**計算結果**:
```
計画在庫 = 0 + 0 - 6 + 0 - 0 = -6
```

→ 生産しなかったが需要があったため、在庫不足（-6）

### シナリオ2: 過去で実績ありの場合

**前提条件**:
- 12/24（過去日）
- order_qty = 6
- plan_qty = 10
- actual_qty = 8（実績入力済み）
- 前日計画在庫 = 0
- 実績出庫 = 6（後工程で実際に使用）

**計算結果**:
```
計画在庫 = 0 + 8 - 6 + 0 - 0 = 2
```

→ 8個生産、6個出庫、2個在庫

### シナリオ3: 仕損発生の場合（生産実績入力済み）

**前提条件**:
- 12/25（過去日）
- actual_qty = 8（仕損2個分を減算済み。元は10個生産したが、仕損登録時に-2）
- 実績出庫 = 5（親製品の実績）
- scrap_qty = 2（自製品の仕損記録）
- 前日計画在庫 = 2
- is_production_recorded = True（生産実績入力済み）

**計算結果**:
```
計画在庫 = 2 + 8 - 5 + 0 = 5
```

→ 仕損はactual_qty減算（10→8）で反映済みのため、計算式からは直接引かない

### シナリオ4: 仕損発生で子部品に影響する場合

**前提条件**:
- 親製品Aで仕損2個発生
- 子部品Bの必要数 = 3個/親1個（BOM）
- 子部品Bのadjust_qty = -6（2個 × 3 = 6個分を負の値で保存）
- 子部品Bの前日在庫 = 20
- 子部品Bの実績 = 10
- 子部品Bの出庫 = 8（親の実績+仕損で計算済み）

**子部品Bの計算結果**:
```
在庫 = 20 + 10 - 8 + (-6) = 16
```

→ 子部品の仕損分はadjust_qty（-6）として反映される

## 注意事項

### 計算順序

1. 仕損数の集計
2. 実在庫の計算（製品ごと、日付順）
3. 計画在庫の計算（製品ごと、日付順）

**重要**: 日付順に計算する必要がある（前日在庫を参照するため）

### 前日参照の定義

- 前日は「カレンダの前営業日」を使用する
- ラインにカレンダが無い場合は`daiso`を使用
- カレンダが無い場合は暦日で前日を扱う
- 前営業日のLineBacklogが無い場合は直前に計算した値を保持する

### 後工程実績の考慮

- 実績出庫数は後工程の実績から自動計算（最終品以外）
- 後工程に複数のラインがある場合は合算
- 最終品（`product.is_final_product = true`）の出庫は顧客実需を使用
- 実在庫の出庫は過去〜今日のみ計上し、計需・計画は使用しない

### 時制判定

- 今日の日付は**日替わり時刻（8時）を考慮**して取得
  - `get_business_today()`を使用
  - 8時より前なら前日扱い（例: 1/20 7:59 → 1/19として扱う）
- 工程作業入力（工程実時間記録）の計画日も8時区切りで判定する
  - 8時より前の入力は前日扱いで `plan_date` を決定する
- 過去: `plan_date < today`
- 未来: `plan_date >= today`

### 日替わり時刻と在庫計算の関係

弊社では日替わり時刻を8:00としているため、在庫計算でも8時区切りを考慮する。

#### 問題となるケース

```
例：1月20日 8:01に在庫計算を実行する場合

- 7:59に実績入力 → これは「1月19日」の実績として扱われる
- しかし、1月19日の在庫はまだ7:59の実績が反映されていない可能性がある
- 単純に「前日の在庫」を起点にすると、最新の実績が反映されない
```

#### 解決策

**実在庫・計画在庫ともに `effective_start` を基準に再計算する**：

| 項目 | 計算開始日（effective_start） | 理由 |
| --- | --- | --- |
| 実在庫 | `min(start_date, calc_start_date)` | 計画在庫の初期値参照日まで stock_qty を最新化するため |
| 計画在庫 | `calc_start_date` = 今日 - (最大LT + 1)営業日 | 親製品の実績変更が子製品の出庫に正しく反映されるため |

> `calc_start_date = shift_working_days(today, -(max_lt + 1))`
> `effective_start = min(start_date, calc_start_date)`
> 通常は `effective_start == calc_start_date`（calc_start_date の方が古いため）

##### 実在庫の計算開始日

- 計算の起点を **`effective_start` より前の最新 stock_qty** とする
- `effective_start` = `min(start_date, calc_start_date)`
- **`effective_start` 以前の在庫は更新しない**（過去の事実は変更しない）
- **計画在庫は `calc_start_date` の `stock_qty` を初期値として参照する**ため、在庫も同じ日まで再計算することで整合を保つ

##### 計画在庫の計算開始日

- 計算の起点を**今日 - (最大LT + 1)営業日**とする
- 最大LT = その製品の**完成品向け累積LTの最大値**（自分LTを含む）
- **理由**: 親製品の実績が変更されると、LT分遡った日の子製品の出庫計算に影響するため
- 例: LT=5日の場合、今日から6営業日前まで遡って計画在庫を再計算

```
例: 今日が1月20日、子製品AのLTが5日の場合
- 親製品Bの1月20日の実績が入力される
- → 子製品Aの「1月15日」（5日前）の出庫に影響
- → 計算開始日を1月14日（LT+1=6日前）にすることで正しく反映
```

#### 計算ロジック

| 項目 | 日付 | 処理 |
|------|------|------|
| 実在庫 | 前々営業日以前 | 既存の在庫値をそのまま使用（更新しない） |
| 実在庫 | 前営業日以降 | 前々営業日の在庫を起点に再計算 |
| 計画在庫 | 計算開始日より前 | 既存の表示値を保持 |
| 計画在庫 | 初期値（計算開始日の前営業日） | `stock_qty - LT分の親実績合計` を初期値とする（後述） |
| 計画在庫 | 計算開始日以降 | 初期値を起点に再計算 |

補足:
- 在庫/計画在庫/進度の**定時タスク**でも同じ開始日補正を適用する。
- `INVENTORY_ONLY` は「前々営業日」と「今日 - (最大LT + 1)営業日」を見て、内部的に必要な日まで遡って再計算する。
- `PROGRESS_ONLY` は**製品ごとの**「今日 - (最大LT + 1)営業日」まで遡ってから進度を再計算する。
- 手動実行API（`/schedule-config/run-now/`）は、同一タスクが `RUNNING` の間は再実行を拒否する（10分タイムアウトによる強制リセットは行わない）。
- 中断が必要な場合は `POST /schedule-config/cancel/` でキャンセル要求を行い、定時タスクは安全な区切りで処理を中断する。

#### コード例（実在庫）

```python

    line_id=line_id,

    stock_qty__isnull=False
).order_by('-plan_date', 'sequence_no', 'id').first()

        existing_stock = row.stock_qty  # 既存値を保持
        continue

    # 前日以降は再計算
    # 注: shipmentには親の実績+仕損が含まれる、adjustには子部品仕損（負の値）が含まれる
    stock_qty = prev_stock + actual - shipment + adjust
```

#### 計画在庫の初期値とLT調整

実在庫（`stock_qty`）は**LTシフトなし**（同日）で計算されるが、計画在庫は**LTシフトあり**で計算される。
この差異により、初期値として `stock_qty` をそのまま使用すると計画在庫が乖離する。

**初期値の補正式:**

```text
初期値 = stock_qty(initial_date) - Σ(各親製品の実績[initial_date+1 ～ initial_date+LT])
```

- `initial_date` = calc_start_date の前営業日
- `initial_date + LT ≤ today - 1` が保証されるため、この期間の親実績は全て確定済み（再計算しても値が変わらない）

**具体例（LT=1、今日=3/20）:**

```text
calc_start_date = 3/18（今日 - (1+1)営業日）
initial_date    = 3/17
stock_qty at 3/17 = -110
親実績 at 3/18  = 22
初期値 = -110 - 22 = -132
```

#### コード例（計画在庫）

```python
today = get_business_today()
# 製品の完成品向け累積LT（自分LT含む）の最大値を取得し、LT+1日前から再計算
max_lt = _get_max_parent_bom_lead_time(product_id)
calc_start_date = shift_working_days(today, -(max_lt + 1))

# 計算開始日より前（initial_date）の実在庫を取得
initial_backlog = LineBacklog.objects.filter(
    line_id=line_id,
    product_id=product_id,
    plan_date__lt=calc_start_date,   # strictly less than（前営業日）
    stock_qty__isnull=False
).order_by('-plan_date', 'sequence_no', 'id').first()

# 初期値 = 実在庫 - LT分の親実績（実在庫はLTシフトなし、計画在庫はLTシフトありの乖離を補正）
# initial_date+LT ≤ today-1 のため、この期間の親実績は全て確定済みで値が安定する
lt_adjustment = _compute_planned_stock_lt_adjustment(
    product_id, initial_backlog.plan_date, max_lt, shift_working_days
)
last_planned = (initial_backlog.stock_qty or 0) - lt_adjustment

for plan_date in sorted(by_date.keys()):
    # 計算開始日より前は既存値を保持（更新しない）
    if plan_date < calc_start_date:
        continue

    # 計算開始日以降は再計算
    # 注: shipmentには親の実績+仕損が含まれる、adjustには子部品仕損（負の値）が含まれる
    planned_stock_qty = prev_planned + input - shipment + adjust
```

### パフォーマンス

- 製品ごとに個別計算（並列化可能）
- 大量データの場合は期間を分割して実行推奨

## 過去実績変更時の差分更新

### 機能概要

`/production/record-edit` 画面で過去の工程実績セッションを追加・変更・削除した場合、日次再計算タスクを待たずに即時で在庫・計画在庫・進度・計進・子製品実需を差分更新する。

実装箇所: `views_process_realtime.py` の `_apply_delta_to_inventory_and_progress(session, delta)`

### トリガー

| 操作 | delta |
|------|-------|
| セッション新規追加（後入力） | `+production_qty` |
| セッション数量変更（PATCH） | `新数量 - 旧数量` |
| セッション削除（DELETE） | `-旧数量` |

### 更新対象と範囲

#### 親製品（変更された製品）

対象: `LineBacklog` where `line_id=session.process.line_id`, `product_id=session.product_id`, `plan_date IN [session.plan_date, 今日]`, `sequence_no=0`

| フィールド              | 変更量      |
| ---------------------- | ----------- |
| `stock_qty`            | `+ delta`   |
| `planned_stock_qty`    | `+ delta`   |
| `progress_qty`         | `+ delta`   |
| `planned_progress_qty` | `+ delta`   |

在庫・進度は累積値のため、変更日から今日まで全行に加算する。

#### 子製品（BOM構成品）

対象: `BOM.parent_product_id = session.product_id` の全アクティブBOMの `BOMItem` を展開

`child_delta = int(delta × BOMItem.quantity)`

**在庫・計画在庫**（累積値のため変更日〜今日の範囲）:

対象: `LineBacklog` where `product_id=child_id`, `plan_date IN [session.plan_date, 今日]`, `sequence_no=0`

| フィールド           | 変更量           |
| -------------------- | ---------------- |
| `stock_qty`          | `- child_delta`  |
| `planned_stock_qty`  | `- child_delta`  |

親の実績が増えると子の消費が増えるため、子の在庫は減少する（逆符号）。

**actual_shipment_qty（実需表示用）**（日次実績のため変更日のみ）:

対象: `LineBacklog` where `product_id=child_id`, `plan_date=session.plan_date`, `sequence_no=0`

| フィールド               | 変更量           |
| ------------------------ | ---------------- |
| `actual_shipment_qty`    | `+ child_delta`  |

`ProductionInventory` 画面の「実需」行は中間品の場合 `actual_shipment_qty` を使用するため、親の実績変更に連動して更新する。

### 符号の例

親の実績が 24→2（delta = -22）、BOM使用数 = 1 の場合:

| 対象                   | フィールド                                                    | 変化            |
| ---------------------- | ------------------------------------------------------------- | --------------- |
| 親製品（変更日〜今日） | stock_qty, planned_stock_qty, progress_qty, planned_progress_qty | -22          |
| 子製品（変更日〜今日） | stock_qty, planned_stock_qty                                  | +22（消費減少） |
| 子製品（変更日のみ）   | actual_shipment_qty                                           | -22（出庫実績減少） |

### 前提条件

- `session.plan_date > today` の場合は何もしない（未来日は対象外）
- `sequence_no=0` 行のみ対象（需要/集計行）
- `IntegerField` にDB側のマイナス制約はなく、マイナス値も許容される
- ブレーキライン実績入力では、上部の表示日とは別に入力した「作業日」を `plan_date` として保存する。表示日を切り替えても保存対象日は変わらない。

### 子部品の再計算補正（record-edit実行時）

実績変更後、子部品は差分更新に加えて在庫/計画在庫の再計算を実行する。

- 対象: `BOM.parent_product_id = session.product_id` の子部品
- 目的: 変更日が通常再計算開始日より前でも、子部品の累積値を整合させる
- 基準日: `session.plan_date` を「today相当」として開始日を算出
  - 在庫開始日: `前々営業日(session.plan_date基準)`
  - 計画在庫開始日: `session.plan_date - (最大LT + 1)営業日`
- 再計算範囲: `開始日 ～ 実際のtoday`

この補正は `record-edit` の実績変更フロー内だけで実行し、通常の在庫再計算APIの既定動作は変更しない。

### 子部品の再計算補正（事後仕入れ実績入力時）

事後仕入れ実績入力でも、親品目の実績登録後に子部品の在庫/計画在庫を再計算する。

- 対象: 登録した仕入れ品を `BOM.parent_product` に持つ子部品
- トリガー: 登録ボタン押下後、対象日の `LineBacklog.actual_qty` 更新完了後
- 基準日: 画面で指定した納入日（`target_date`）を `parent_plan_date` として使用
- 再計算範囲:
  - 実在庫: `target_date` 基準の前々営業日 ～ 実際のtoday
  - 計画在庫: `target_date - (最大LT + 1)営業日` ～ 実際のtoday
- 凍結基準: `recalculate_stock_qty(..., reference_today=target_date)` / `recalculate_planned_stock_qty(..., reference_today=target_date)` を使用し、遡及入力時も凍結判定を納入日基準へずらす
- 子品目が存在しない場合はスキップする
- 例外発生時は warning ログに記録し、実績登録レスポンス自体は失敗させない

例:

```text
登録日: 2026/03/27
納入日(target_date): 2026/03/23

子部品再計算:
- reference_today = 2026/03/23
- 実在庫の凍結基準 = 2026/03/19 基準
- 2026/03/23, 2026/03/24 は凍結外として再計算される
```

これにより、遡及で仕入れ実績を登録した場合でも、子部品の `actual_shipment_qty`（実需表示用）が対象日基準で正しく再計算される。
