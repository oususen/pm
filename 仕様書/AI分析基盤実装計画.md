# PM社内AI分析基盤 実装計画

## 1. 目的

PMの業務データをAIで分析できるようにする。AIはPM本体テーブルを直接操作せず、AI用ビューと読み取り専用ユーザーを経由してデータを取得する。AIが作成するSQL・Python・グラフ・報告書は、利用者とシステム管理者の確認を経て再利用可能なテンプレートにする。

本計画の正式な機能仕様は、[AI分析基盤仕様書](AI分析基盤仕様書.md)に従う。

## 2. 決定事項

- 常設のAI専用DBは作成しない。`pm_db`内のAI用ビューを使用する。
- AI用ユーザーは`pm_ai_reader`とし、`v_ai_...`ビューへの`SELECT`だけを許可する。元テーブルへの権限は付与しない。
- AI生成Pythonは、AI用ビューを`SELECT`できる。一時DuckDB内では中間テーブルの作成・更新・削除を許可する。
- Python実行はDjango本体の`exec`では行わず、専用Docker実行コンテナで行う。生成PythonへMySQL接続情報を渡さず、読み取り専用ビュー操作だけを提供する。
- 一時DuckDBは分析処理ごとに作成し、正常終了・失敗終了のどちらでも削除する。
- 利用者が承認した分析はPM本体DBの`ai_analysis_template`へ保存し、システム管理者へメールで確認依頼を送る。
- 分析案キャッシュ有効期限、Python最大実行時間・メモリ・CPU上限は、`/settings/ai`の分析実行設定で管理する。初期値は60分、300秒、2048MB、1コアとし、編集可能範囲は順に5〜480分、30〜600秒、512〜4096MB、0.5〜2コアとする。取得行数の上限も同じ設定で管理し、初期値は100,000行とする。
- 利用者が承認したテンプレートは管理者承認待ちとして利用可能にする。却下時は管理者が正しいテンプレートを作成し、利用者へ通知する。
- 管理者承認待ちテンプレートを再利用する画面には、「システム管理者未承認」の警告を表示し、実行前に確認を求める。
- テンプレートの本番運用にGit操作や本番コンテナ内のソースコード変更は使わない。

### 第2段階：分析実行基盤

1. フル画面の社内AIに「検索」「分析」の2タブを追加する。既存AIチャットを検索タブとして継続利用し、ドロワーはそのまま検索専用とする。
2. AIが分析目的・手順を提示し、利用者が承認する操作を実装する。
3. AIが必要なビュー・フィールド・資料を提示し、利用者が承認する操作を実装する。
4. `pm_internal`だけに公開するRedisコンテナへ、分析案を有効期限付きで保持し、複数ワーカーでも承認・実行を継続できるようにする。Redisは外部ポート・永続ボリュームを持たない。有効期限はAI分析基盤仕様書§4.7の設定値による。
5. `analysis-runner`の専用Dockerコンテナを追加し、Djangoから内部HTTPで実行依頼する。`docker exec`やWindows上のPython直接実行は使用しない。
6. Djangoだけが`pm_ai_reader`で承認済みビューを取得し、runnerの一時DuckDBへ渡す。AI生成Pythonには、取得済みスナップショットを読む`load_view()`だけを提供する。
7. runnerのPython子プロセスを非rootで隔離し、PM本体DBの更新、外部ネットワーク、ホスト側の任意ファイル操作、MySQL・Redis・内部HTTPの接続情報へのアクセスを禁止する。時間・CPU・メモリの上限値はAI分析基盤仕様書§4.7の設定値による。
8. 一時DuckDBの終了時削除を実装する。

タブ、分析案作成、手順承認、期間付き必要データのCOUNT確認・承認、Redis共有状態管理を実装済み。開発DBのログイン・定義者修復・実DB件数確認は通過した。開発の共有状態管理はMemuraiを使用し、開発`.env`も設定済み（手順はAI分析基盤仕様書§4.5）。実Redisの期限・競合・別プロセス共有、実Qwenの出荷分析案から実DB件数確認・データ承認までDRFビュー経由で確認した。ブラウザではデータ承認後に「未実行」と表示され、実行ボタンが無効であることを確認した。実gunicorn複数ワーカーおよび分析実行・結果表示までの通し確認は未実施。分析案作成ではローカルQwen・DeepSeek・OpenRouterとモデルを選べる（初期選択は検索AIと同じ）。実際の外部AIでの所要時間・動作は未測定。追加条件・資料は未着手。初期検証でQwenの90秒タイムアウトがあったが、その後Qwen専用設定を追加したため、現在は第3-2段階に記載の設定値を使う。

### 第3段階：テンプレートと承認

1. AIアプリのマイグレーション`0022`は、分析実行設定`ai_analysis_execution_policy`と初期値1行の追加だけに使用する。`0023`はQwen専用の分析案作成タイムアウト列に使用する。テンプレート`ai_analysis_template`、通知履歴`ai_analysis_template_notification`、実行履歴`ai_analysis_run`は後続の`0024`以降で追加する（番号は実装時に確認する）。
2. 利用者承認後に、SQL・Python・利用ビュー・分析条件・利用者・状態・版を保存する。
3. システム管理者へ確認依頼メールを送信する。
4. 管理者の確認・却下・却下理由の保存と、利用者へのメール・PM通知を実装する。管理者の承認・却下・訂正・置換は`settings.ai`の`can_edit`に限定する。
5. 却下時は管理者が正しいテンプレートを作成し、置換関係を記録する。

### 第3-2段階：分析実行設定

1. `/settings/ai`へ、分析案キャッシュ有効期限、Python最大実行時間・メモリ・CPU上限・取得行数の上限を編集する「分析実行設定」を追加する。
2. 初期値を60分、300秒、2048MB、1コア、100,000行で作成する。
3. `settings.ai / can_edit`を持つ利用者だけに編集・保存操作を表示する。
4. 権限制御はフロントエンドUIだけで行う。APIは権限判定を追加せず、0、空欄、範囲外、指定単位に合わない値を拒否する範囲検証だけを行う。
5. 設定値を次のrunnerジョブへ渡し、実行時間・メモリ・CPU制限とDuckDB並列度へ適用する。

設定モデル・初期値・GET/PUT API・画面の5項目一括保存は実装済み。runnerへの適用は分析実行基盤の実装時に行う。

2026-10-03にBOSS承認で、ローカルQwenカードへ分析案作成タイムアウトを追加した。初期値180秒、30〜600秒の整数を専用ボタンで保存し、次のQwen分析案作成にだけ適用する。保存先は`ai_provider_config.analysis_plan_timeout_seconds`、列追加は`0023_aiproviderconfig_analysis_plan_timeout`。検索AI・社外API・Python最大実行時間は変更しない。詳細はAI分析基盤仕様書§4.7に従う。

実装時の検証はバックエンド40件・フロント9件の自動テスト、フロント全体のビルド検証（ファイル出力なし）、Djangoシステムチェック、AIモデルの追加マイグレーション差分なしを通過。開発DBでは`0023`適用済みと既存のモデル・有効状態が維持されていることを確認した。開発Djangoを再起動し、ブラウザのQwenカードで240秒の保存、実DBと分析案作成用取得関数での再取得、180秒への復帰・保存を確認した。画面記録は`output/qwen-analysis-timeout-settings-20261003.jpg`。実AIを呼んで180秒まで待つ測定は行っていない。その後のpush範囲`2097ec3e..0546df0d`には、このQwen設定変更とマイグレーション`0023`も含まれた。本番の起動時にはmigrateが実行される構成だが、実際の適用・正常稼働は未確認。本番の分析sandboxが起動しないことと、push全体が本番へ影響しないことは区別する。

### 第4段階：AI用ビューの拡張

生産実績、確定仕損、入荷実績、出荷実績、残業を優先候補とする。ビューごとの対象テーブル、結合条件、数値定義、公開フィールド、個人情報の扱いを別計画で確定してから実装する。

初期の分析画面は、既存の`v_ai_purchase_receipt`と`v_ai_shipment`だけを対象にする。生産実績、仕損、中断、残業の分析は、対応するビューの作成・検証後に有効化する。

## 4. 完成条件

- AIは元テーブルを直接読めず、AI用ビューだけを`SELECT`できる。
- AI生成Pythonは、一時DuckDBを自由に加工できるが、PM本体DBを更新できない。
- 分析のSQL・Python・利用条件・承認状態は`ai_analysis_template`で永続管理される。
- 管理者が却下したテンプレートは利用停止され、却下理由と置換テンプレートを利用者へ通知できる。
- `ai.analysis`の権限とテンプレートの閲覧・利用・管理範囲が権限仕様書へ定義されている。

- 開発／本番、手動DDL／マイグレーション、単一コミット／push範囲全体を区別する。本番の適用・稼働を確認できなければ「未確認」と明記する。
- 古い現在状況を残して矛盾させない。過去の検証は実施時点の記録と分かるようにし、最新の進捗を§3の進捗一覧へ反映する。
- 計画書の更新は、未承認の実装・DB変更・上限変更・commit／push・本番有効化の承認を兼ねない。
