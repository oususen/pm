# AI二画面実装計画（フル画面内の検索・分析タブ）

## 1. 目的

既存のAIドロワーは検索専用として維持する。フル画面の社内AIに「検索」「分析」の2タブを設け、検索タブに現在のチャット機能、分析タブに承認付きのSQL・Python分析を配置する。文書名の「二画面」は検索・分析の二つの機能領域を指し、フル画面を別々の画面へ分離する意味ではない。

本計画は[AI分析基盤仕様書](AI分析基盤仕様書.md)および[社内AIチャット仕様書](社内AIチャット仕様書.md)に従う。

## 2. 現状

- フル画面の検索・分析タブ枠、個別の権限制御、タブ切替時の状態保持、質問文と起点画面の引継ぎを実装した。分析タブにはAI（ローカルQwen・DeepSeek・OpenRouter）の選択と分析案作成、手順承認、期間付き必要データのCOUNT確認・承認を追加した。DuckDB・runner・SQL／Python実行・テンプレート保存は未実装である。
- `/settings/ai`の分析実行設定（5項目の取得・一括保存）は実装済み。分析ジョブへの適用は実行基盤の実装時に行う。

- 全画面チャットは`/ai/chat`、`pm-ui/src/views/ai/AIChat.vue`、ルート名`AIChat`で提供している。
- 通常画面では`AIChatDrawer.vue`から同じチャット機能を開く。
- バックエンドは`POST /api/ai/chat/`、会話履歴、音声入力を提供している。
- 現在のチャットは、生産・品質・勤務・受注・仕入・出荷の照会、読み取り専用SQL、簡易チャート・報告書を扱う。
- AI生成Python、一時DuckDB、`ai_analysis_template`、利用者承認と管理者確認は未実装である。

## 3. 二画面の責務

| 区分 | 調査・検索画面 | 分析画面 |
|---|---|---|
| 画面 | フル画面`/ai/chat`内の「検索」タブ、既存AIドロワー | 同じフル画面内の「分析」タブ |
| 主目的 | 業務データの照会、質問応答、集計、簡易チャート | 分析案、承認、SQL・Python、複数指標の分析、報告書 |
| データ利用 | 既存の読み取り専用ツール・AI用DB辞書SQL | `v_ai_...`ビューを`pm_ai_reader`で`SELECT` |
| 実行方式 | 現在のAIチャット処理 | AI生成Pythonと一時DuckDB |
| 承認 | 既存の横断参照に対する質問単位の承認 | 分析案、必要ビュー・フィールド・資料、テンプレート保存の承認 |
| 保存 | `ai_conversation` | `ai_analysis_template`（利用者承認後） |
| AIの更新権限 | なし | PM本体DBはなし。一時DuckDBだけ編集可 |

既存チャットの簡易チャート・報告書は調査・検索画面に残す。AI生成Pythonによる自由な加工、複数段階の分析、テンプレート化は分析画面だけで行う。

## 4. 画面実装計画

### 4.1 調査・検索画面の変更

1. 既存の`/ai/chat`のフル画面は「社内AI」とし、その中へ「検索」「分析」の2タブを配置する。
2. `AIChatDrawer.vue`は現在の検索専用ドロワーとして維持し、分析タブを追加しない。
3. フル画面の検索タブに「分析する」導線を追加する。押下時は同じフル画面の分析タブへ切り替え、質問文・起点画面・利用者が選択した条件だけを渡す。チャットの集計結果・明細・会話履歴は自動で渡さない。
4. AI生成Pythonの実行、DuckDB、一時分析データ、テンプレート登録のUIは調査・検索画面へ追加しない。
5. 既存の会話履歴API、音声入力、横断参照承認、AI設定は互換性を維持する。

### 4.2 分析画面の新設

`pm-ui/src/views/ai/AIAnalysis.vue`を分析タブの内容として追加する。フル画面の共通コンテナが既存検索コンポーネントと分析コンポーネントを切り替える。分析専用の独立画面`/ai/analysis`は新設しない。

フル画面の入口は検索・分析のどちらかの閲覧権限で開けるようにし、検索タブは`ai.chat`、分析タブは`ai.analysis`で個別に表示を制御する。片方の権限しかない利用者は、そのタブだけを利用できる。タブ切替時も各タブの入力・表示状態を保持し、実行中の分析をタブ切替だけで取消しない。権限のないタブのコンポーネントやAPIは起動しない。

画面は次の順序で表示する。

1. 利用者が分析目的を入力する。
2. AIが分析案、分析手順、必要ビュー、フィールド、資料、出力案を提示する。
3. 利用者が分析案を承認する。
4. 利用者が必要なデータを承認する。
5. AIがSQL・Python・グラフ・報告書を作成して実行する。
6. 利用者が結果を確認し、テンプレートとして保存するか選ぶ。
7. 保存後、管理者確認待ち・正式・却下・置換済みの状態を表示する。

分析画面には、次の情報を常に表示する。

- 利用する`v_ai_...`ビュー
- 利用フィールドと分析条件
- 対象期間
- 生成したSQLとPython
- 実行日時、成功・失敗、根拠データ
- テンプレートの状態と却下理由
- 管理者承認待ちテンプレートには「システム管理者未承認」の警告

## 5. バックエンド実装計画

### 5.1 APIの分離

既存の`/api/ai/chat/`は調査・検索専用として維持する。分析画面には`/api/ai/analysis/`配下のAPIを追加する。

| API | 用途 |
|---|---|
| `GET /api/ai/analysis/options/` | 分析案作成に選べるAI（ローカルQwen・DeepSeek・OpenRouter）、モデル、利用可否と理由、初期選択を取得する |
| `POST /api/ai/analysis/plans/` | 分析目的から分析案・必要データを生成する |
| `GET /api/ai/analysis/plans/{id}/` | 自分の未保存分析案の最新状態を取得する |
| `POST /api/ai/analysis/plans/{id}/approve/` | 利用者が分析案・必要データを承認する |
| `POST /api/ai/analysis/plans/{id}/data-preview/` | 手順承認後、必要データの対象行数を確認する |
| `POST /api/ai/analysis/plans/{id}/execute/` | 承認済みの分析を実行する |
| `GET /api/ai/analysis/templates/` | 利用可能なテンプレートを一覧する |
| `POST /api/ai/analysis/templates/` | 利用者承認済みのSQL・Pythonを保存する |
| `PATCH /api/ai/analysis/templates/{id}/` | システム管理者が確認・却下・置換関係を更新する |

分析案の一時状態は、テンプレートとして保存するまでPM本体DBへ保存しない。複数のgunicornワーカーで承認・実行を継続できるよう、`pm_internal`内だけに公開するRedisコンテナへ分析案ID単位で有効期限付き保存する。Redisは外部ポート・永続ボリュームを持たない。有効期限はAI分析基盤仕様書§4.7の設定値による。

#### 現在の実装範囲（分析案・承認）

- 作成APIはJSONの`purpose`、`date_from`、`date_to`だけを受け付ける。期間は必須の`YYYY-MM-DD`で、開始日は終了日以前とする。期間の日数上限を新設せず、チャットの期間上限を流用しない。
- 初期の対象条件は指定期間の全登録行だけとする。必要ビュー・フィールドは既存辞書の入荷・出荷ビューに限定し、未公開・重複フィールドや追加SQL・条件を拒否する。追加条件・資料を必要とする案は対応前として失敗させる。
- 分析案の作成は、検索AIと同じく、ローカルQwen・DeepSeek・OpenRouterとそのモデルを選べる。初期選択は検索AIと同じ`openrouter`（選べない場合は、選べる先頭のAI）で、既定モデルは管理設定（`ai_provider_config`）の値とする。`POST /api/ai/analysis/plans/`は、`provider`・`model`を任意で受け取り、省略時は`qwen`として扱う。
- 選択できるのは、管理設定で有効なプロバイダ、検索AIと同じモデル許可リスト（`DEEPSEEK_MODELS`・`OPENROUTER_MODELS`）、APIキー設定済み、外部AIへの送信の全体許可（`allow_aggregated_external_transfer`）がオンの場合に限る。ローカルQwenは、Qwenが有効で既定モデルが`OLLAMA_MODEL`と一致する場合だけ利用できる。条件を満たさない選択は、AIを呼ぶ前に拒否する。
- 外部AIへ送るのは、システム指示（公開ビューの列・意味の説明）、分析目的、対象期間だけである。DBの明細行・件数・チャット履歴・検索結果・利用者ID・氏名は渡さない。送信前に、既存の`ExternalDataRedactor`で、PMに登録済みのユーザー名・作業者名・得意先名・仕入先名を一時IDへ置換し、メールアドレスを除去する。応答の一時IDは、検証済みの分析案（名称・手順・出力案）の文字列に限り、元の名称へ戻す。保存する分析目的は元の文のままとする。登録されていない人名・社名や自由記述の機密は置換されないため、画面に注意を表示する。伏字化の対象を取得できない場合は、外部へ送らずに失敗とする。
- 外部AIの呼出しは、検索AIの処理を変更せず、分析専用の`analysis_llm.py`で行う（DeepSeekとOpenRouterは同じOpenAI互換の経路で、思考の指定などのパラメータだけを切り替える）。タイムアウトは既存の分析案作成と同じ90秒、生成上限は`AGENT_MAX_TOKENS`を使い、外部AIでの所要時間を実測してからBOSSが確定する。分析案には、使ったプロバイダ・モデルを記録する。
- 有料モデル（DeepSeek、OpenRouterの有料枠）は、検索AIと同じく選択時に確認する。OpenRouterの無料枠は、提供元が入力を記録・学習に使う場合があるため、利用条件の確認が必要である。
- 伏字化の識別子は、既存の検索AIと同じ読み取り接続（`ai_reader`）から取得する。分析用接続をビュー限定へ分離する際は、伏字用データの取得元を別途確定する。
- Redis未設定・接続失敗時は503で止める。ローカルメモリ・PM本体DBへ代替保存せず、接続確認前にAIを呼ばない。Composeの`analysis-redis`は`pm_internal`のみに接続し、RDB/AOFを無効化、`/data`はtmpfsとする。開発環境は`AI_ANALYSIS_REDIS_URL`を明示設定する。
- 状態は`awaiting_method`→`awaiting_data`→`data_approved`。承認APIは`revision`と`stage`（`method`または`data`）を必須とする。対象件数APIは`revision`だけを受け付ける。承認内容を要求本文で書き換えるAPIは設けない。
- 手順承認後にDjangoの固定COUNTと束縛した期間で、`pm_ai_reader`接続から対象行数を取得する。件数はビューごとと合計を表示し、数量合計と区別する。未確認・上限超過ではデータ承認できない。データ承認時に最新の取得行数設定も照合する。
- RedisのWATCH/MULTI/EXECで版の競合を拒否する。承認・件数確認ではTTLを延長せず、COUNT中に期限切れ・更新があれば古い件数を採用しない。他人の分析案は404、期限切れは410、版・承認順序の不一致は409とする。認証・所有者照合を行うが、新たなバックエンドのresource権限判定は設けない。
- データ承認は実行ではない。実行API・生成SQL／Python・明細取得・DuckDB・保存は未実装。実行ボタンは無効表示とし、今後の実行時には同一スナップショットでCOUNT・全行取得・一意キー照合を改めて行う。
- モックを使った状態遷移・境界・SQL検証（31件）は通過。開発DBのログイン自体は正常で、ビューの存在しない定義者`root`@`%`が参照失敗の原因だった。開発限定でログイン不能の`pm_ai_view_owner`@`localhost`を作成し、必要列のSELECTを付与、両ビューの定義者だけを修復した。PMと同じTLS接続で2026-09-01〜2026-09-30の固定COUNTを確認済み（入荷863行、出荷226行、合計1,089行。数量合計ではない）。既存チャット共用reader権限・業務データ・本番は変更していない。
- 開発用Memuraiの実接続で別Pythonプロセスからの状態共有、WATCHによる更新競合409、所有者不一致404、自然な期限切れ410、更新時のTTL維持を確認済み。保存しないテスト利用者を認証済みとしてDRFビューを呼び、実Qwenによる出荷分析案作成201→手順承認200→実DB件数確認200（226行）→データ承認200まで通過した。入荷・出荷の両ビューの承認確認はAI生成ではない検証用案でも実施した。検証用Redisキーだけを終了後に削除し、PM本体DBへ分析案やテスト利用者は保存していない。
- 入荷・出荷の両方を求めた実Qwen呼出しでは既存90秒のタイムアウトが1回発生し、出荷のみの案は正常完了した。タイムアウト・生成上限・モデル設定は変更していない。ブラウザ操作によるUI通し確認、実gunicorn複数ワーカーでの検証、本番反映は未実施。

### 5.2 サービス分割

`pm_backend/apps/ai/services/`に次の責務を分離して追加する。

| サービス | 役割 |
|---|---|
| `analysis_planning_service.py` | 分析案・必要ビュー・フィールド・資料の生成と承認内容の検証 |
| `analysis_data_service.py` | 承認済みビュー・フィールド・条件を検証し、実行コンテナへ渡すデータ取得指示を作成 |
| `analysis_execution_service.py` | 専用Docker実行コンテナへの実行依頼、結果・グラフ・報告書の返却、一時DuckDBの削除 |
| `analysis_template_service.py` | テンプレート保存、状態遷移、置換関係、管理者通知 |

HTTP処理は`ai/views.py`に置き、分析ロジックはViewへ置かない。

### 5.3 実行コンテナの実装単位

- Docker Composeへ`redis`と`analysis-runner`を追加する。どちらも`pm_internal`だけに接続し、外部ポートを公開しない。
- Djangoは`analysis_execution_service.py`から`analysis-runner`へ内部HTTPでジョブを送る。`docker exec`は使用しない。
- `analysis_data_service.py`が、承認済みの`v_ai_...`だけを`pm_ai_reader`で取得する。取得結果はジョブ単位で`analysis-runner`へ渡し、runnerが一時DuckDBへ投入する。
- 生成Pythonの`load_view()`は、runner内の一時DuckDBに投入済みのビュー・スナップショットだけを読む。MySQLへの直接接続ではない。
- runnerの生成Python子プロセスには、MySQL・Redis・内部HTTPの接続情報を渡さない。PMソースコード、ホストの任意フォルダ、Dockerソケットをマウントしない。
- Windows開発ではDockerを使用しない。分析案・承認の共有キャッシュは開発専用Memuraiを使用する（導入手順・現在の状態はAI分析基盤仕様書§4.5）。生成Pythonの隔離実行環境は別途確定する。DjangoやWindows上で生成Pythonを直接実行する経路は作らない。
- 実行時間・CPU・メモリの上限値は、AI分析基盤仕様書§4.7の設定値による。

### 5.4 分析実行設定画面

- 既存の`/settings/ai`へ「分析実行設定」を追加する。保存先は新規モデル`AIAnalysisExecutionPolicy`、テーブル名は`ai_analysis_execution_policy`とする。
- 編集項目は、分析案キャッシュ有効期限（分）、Python最大実行時間（秒）、Python最大メモリ（MB）、Python CPU上限（コア数）、取得行数の上限（行）とする。
- 初期値は、60分、300秒、2048MB、1コア、100,000行とする。
- 保存可能範囲と入力単位は、有効期限5〜480分（1分単位）、最大実行時間30〜600秒（1秒単位）、最大メモリ512〜4096MB（128MB単位）、CPU上限0.5〜2コア（0.5コア単位）、取得行数の上限1,000〜100,000行（1,000行単位）とする。範囲外・0・空欄は設定API側でも必ずエラーにして保存しない。
- `settings.ai / can_edit`を持つ利用者だけに編集・保存ボタンを表示する。閲覧だけは`settings.ai / can_view`で可能とする。設定APIへ新たな権限判定は追加しない（既存のフロントエンドUI方針）。
- 設定APIは`GET /api/ai/settings/analysis-execution-policy/`と`PUT /api/ai/settings/analysis-execution-policy/`とする。PUTでは5項目すべてを必須とし、不正な項目があれば全項目を保存せず400を返す。
- 保存した設定は、次に開始するジョブの実行依頼へ含める。実行中のジョブは設定変更の影響を受けない。
- runnerは受領した設定値を実行時間・メモリ・CPU制限およびDuckDB並列度へ反映する。Docker Compose側の実行可能上限を超える値は、ジョブ実行時にエラー表示し、実行しない。

### 5.5 データと権限

- 分析用の読み取り接続は`AI_DB_NAME=pm_db`、`AI_DB_USER=pm_ai_reader`を使用する。
- `pm_ai_reader`には`v_ai_...`ビューの`SELECT`だけを付与し、元テーブルへの権限は付与しない。
- AI生成Pythonは、実行コンテナが提供する読み取り専用操作を通じて、AI用ビューを`SELECT`できる。一時DuckDBでは`CREATE`、`INSERT`、`UPDATE`、`DELETE`、`DROP`を許可する。
- 実行コンテナはDjango本体と分離し、生成PythonへMySQL接続情報を渡さない。PM本体テーブルの更新、元テーブルへの接続、外部ネットワーク、ホスト側のソースコード・任意ファイルの読書込みを行えない構成にする。
- 一時DuckDBは処理ごとに作成し、成功・失敗・中断時に削除する。
- 外部AIへは、ビュー定義、公開フィールド、分析目的、集計結果だけを自動送信する。明細行の送信は、伏字化と利用者承認がある場合だけ許可する。
- 初期リリースで分析対象にできるのは、既存の`v_ai_purchase_receipt`と`v_ai_shipment`だけとする。生産・仕損・中断・残業は、対応するAI用ビューを作成・検証後に有効化する。

## 6. テンプレートと通知

新規モデル`AIAnalysisTemplate`（テーブル`ai_analysis_template`）を追加する。保存する主な内容は、テンプレート名、SQL、Python、利用ビュー、分析条件、利用者、管理者、状態、版、却下理由、置換先、各日時である。

状態遷移は次のとおりとする。

```text
下書き
  ↓ 利用者承認
管理者承認待ち（利用可能）
  ↓ 管理者承認
正式

管理者却下
  ↓
却下（利用停止）
  ↓ システム管理者が正しいテンプレートを作成
置換済み
```

利用者が承認して保存した時点で、システム管理者へメールを送信する。管理者承認待ちのテンプレートは利用できるが、再利用者へ「システム管理者未承認」と常に表示し、実行前に確認を求める。却下時は、却下理由と正しいテンプレートを利用者へメールおよびPM通知で連絡する。本番コンテナのソースコードやGitへテンプレートを保存しない。

### 6.1 分析画面の権限

- `ai.analysis`を新設する。`can_view`で分析画面・利用可能テンプレートの一覧・実行結果を閲覧できる。`can_edit`で分析案の承認、実行、テンプレート候補の保存をできる。
- `管理者承認待ち`と`正式`のテンプレートは、`ai.analysis`を持つ利用者へ一覧・再利用を許可する。`却下`と`置換済み`は通常利用者へ再利用候補として表示しない。作成者は自分の履歴を確認でき、システム管理者は全履歴を確認できる。
- 管理者によるテンプレートの承認・却下・訂正・置換は`settings.ai`の`can_edit`を必要とする。
- `ai.analysis`は`ai`親権限へフォールバックしない。`UserPermission.RESOURCE_CHOICES`、部署・役職・個別権限の全選択肢へ同時に追加する。

## 7. 実装順序

1. 既存のAI用ビューを正常化し、`pm_ai_reader`のビュー限定権限を確認する。
2. `AIAnalysisExecutionPolicy`と初期値1行をAIアプリのマイグレーション`0022`で追加し、分析実行設定API・画面を実装する。`AIAnalysisTemplate`・通知履歴`ai_analysis_template_notification`・実行履歴`AIAnalysisRun`は後続の`0023`で追加し、テンプレートAPIと管理者通知を実装する。`ai.analysis`権限は追加済み。
3. `pm_internal`限定のRedis共有キャッシュと、内部HTTPで呼び出す`analysis-runner`コンテナを追加する。一時DuckDBの削除処理をテストする。
4. 分析APIを追加し、承認前・期限切れの分析案は実行できないことをテストする。
5. `AIAnalysis.vue`とフル画面の検索・分析タブを追加し、タブごとの権限と状態保持を実装する。
6. フル画面の検索タブへ分析タブへの導線を追加する。既存`AIChatDrawer.vue`は検索専用のまま維持する。
7. 既存チャットの照会、会話履歴、横断参照、音声入力、簡易チャートの回帰試験を実施する。
8. 分析画面の承認、実行、却下、置換、通知、一時DuckDB削除の試験を実施する。

## 8. 完成条件

- フル画面の検索・分析が2タブで利用でき、検索と分析のAPIは分離されている。
- AIドロワーは現在の検索機能を維持し、分析タブを持たない。
- 既存の`/ai/chat`とAIドロワーの照会機能が維持される。
- 分析画面は、利用者の分析案・データ承認前にSQL・Pythonを実行しない。
- AI生成PythonはAI用ビューだけを読め、一時DuckDBだけを編集できる。
- 利用者承認済みテンプレートはPM本体DBへ保存され、管理者確認と却下通知を追跡できる。管理者承認待ちであることは、再利用者へ警告表示される。
