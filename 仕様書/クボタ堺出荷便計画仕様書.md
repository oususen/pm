# クボタ堺出荷便計画 仕様書

## 概要

クボタ堺向け出荷の納期調整・便割付・前工程需要日反映を行う機能。

### 背景

- クボタ堺向け製品は**内示と確定の乖離**が大きく、内示ベースで前工程を動かすとムダ/欠品リスクが高い
- 便ごとの積載制約（荷台サイズ）を考慮した割付が必要
- 便の出発日から逆算して**前工程の需要日**を決定する仕組みが必要（フロア配送の考え方を前工程にも適用）

### スコープ

- **対象**: クボタ**堺向け**のみ（`customer_code='000196'` かつ `ship_to_code='ZGHC'` かつ `status='OPEN'` の受注。`order_type` は FIRM / FORECAST 両方を対象）
- **積載計算精度**: 面積占有率方式（厳密な3D bin packingは行わない）
- **振り分け方式**: 業務員が**手動**で便選択（自動アルゴリズムなし）

## 業務フロー

```
①受注取込
   OrderLine（元納期）
     ↓
②納期調整【営業担当】
   - 前倒し/後ろ倒し/分割を営業が判断
   - 顧客調整・承認取得（口頭承認）
   - 調整後納期・数量を確定
     ↓
③便割付【業務/物流担当】
   - 調整後納期をもとに便を選択
   - 積載占有率を見ながら手動で便に割付
   - 分割積載可
     ↓
④前工程需要日反映
   便出発日 → クボタ配送ラインの LineBacklog 同期
   → 既存 pickup カスケードにより前工程ラインへ伝播
```

②と③は完全に別画面・別ステップ。

### 2. KubotaSakaiDueAdjustment（納期調整）

配置: [pm_backend/apps/orders/core/models.py](../pm_backend/apps/orders/core/models.py)
DBテーブル: `t_kubota_sakai_due_adjustment`

| フィールド | 型 | 用途 |
|---|---|---|
| order_line | FK(OrderLine) | 受注明細 |
| split_no | PositiveInt | 分割連番（1,2,3...） |
| adjusted_due_date | date | 調整後納期 |
| adjusted_qty | decimal(14,3) | 調整後数量 |
| remaining_qty | decimal(14,3) | 残量（調整行単位、デフォルト0） |
| adjustment_type | choice | just / forward / backward |
| customer_approved | bool | 後ろ倒し時の顧客口頭承認フラグ |
| adjusted_by | FK(User, SET_NULL) | 営業担当 |
| adjusted_at | datetime | 調整日時 |
| note | text | 任意メモ |

**制約**:
- `unique_together = [('order_line', 'split_no')]`
- 保存時に `Σ(adjusted_qty) == OrderLine.quantity`（過不足禁止）をバリデーション
- 後ろ倒し（`adjusted_due_date > order_line.due_date`）は `customer_approved=True` 必須
- 分割しない場合は `split_no=1` の1行のみ
- **未操作の明細は自動ジャストとみなす**（レコード無しでも便計画画面に表示）

配置: [pm_backend/apps/orders/core/models.py](../pm_backend/apps/orders/core/models.py)

| フィールド | 型 | 用途 |
|---|---|---|
| order_line | FK(OrderLine) | 受注明細 |
| truck | FK(KubotaSakaiTruck) | 便 |

**インデックス**: `(departure_date, truck)`, `(order_line)`

**制約**:
- `Σ(qty where order_line=X) ≤` 対象日の調整後納期数量
- 同一便の占有率 ≤ 100%（`truck_load_calculator` で検証）
- 前倒し/後ろ倒しフラグは持たない（納期調整ステップで処理済み）

## 既存テーブル活用

- **容器マスタ** (`Container`): `width`, `depth`, `height`, `max_weight`, `can_mix`, `stackable`, `max_stack`, `capacity`
- **製品マスタ** (`Product`): `used_container` (FK), `capacity`（容器入り数）, `specific_gravity`, `size_length/width/thickness`（重量算出用）

→ 製品↔容器の紐付けテーブルは新設不要

## 積載計算ロジック

配置: [pm_backend/apps/shipping/services/truck_load_calculator.py](../pm_backend/apps/shipping/services/truck_load_calculator.py)

```
トラック床面積 = truck.width × truck.depth
容器床面積 = container.width × container.depth
段数 = stackable ? min(truck.height // container.height, container.max_stack) : 1
実効床面積 = 容器床面積 / 段数
容器数 = qty / container.capacity
占有率 = Σ(実効床面積 × 容器数) / トラック床面積
重量 = Σ(unit_weight × qty) ここで unit_weight = 比重 × 長さ × 幅 × 厚さ / 1,000,000
```

**エラー条件**:
- 占有率 > 100%
- 重量 > `truck.max_weight`
- **混載不可容器** を含みつつ複数品番が同一便にある → `mixed_blocked=True`

**戻り値**: `{occupancy_ratio, occupancy_percent, total_weight, mixed_blocked, errors[]}`

## API

### 便マスタ CRUD
- `GET/POST/PUT/DELETE /api/kubota-sakai-trucks/`

### 納期調整
- `GET /api/kubota-sakai-due-adjustments/grid/` — 生産計画パターンのグリッドデータ取得
  - クエリ: `start_date`, `horizon_days`, `keyword`
  - 戻り: `{start_date, end_date, horizon_days, rows: [{order_key, order_line_ids, product_code, product_name, due_date, quantity, adjustments: [...]}]}`
- `POST /api/kubota-sakai-due-adjustments/bulk_save/` — まとめ保存
  - 入力: `{rows: [{order_key, order_line_ids, adjustments: [{adjusted_due_date, adjusted_qty, remaining_qty, customer_approved, note}]}]}`
  - バリデーション: 対象受注確認、数量合計一致、後ろ倒しの顧客承認、明細への配分

### 便割付
- `GET /api/kubota-sakai-trip-assignments/grid/` — 指定日の割付状況取得
  - クエリ: `target_date`, `keyword`
  - 戻り: `{target_date, assignment_deadline_days, rows, trucks, truck_summaries}`
- `POST /api/kubota-sakai-trip-assignments/bulk_save/` — 指定日の割付をまとめ保存
  - 入力: `{target_date, rows: [{order_line_id, allocations: [{truck_id, qty}]}]}`
  - 保存後、`_sync_kubota_delivery_backlog_for_date` で `LineBacklog` へ同期

すべて `customer_code='000196'` かつ `order_no` に `SAKAI` を含む `order_type='FIRM'` `status='OPEN'` で絞り込み。

**サブ列（1日付あたり）**:
| サブ列 | 意味 | 編集可否 |
|---|---|---|
| 受注 | 元の受注数量（`OrderLine.quantity` を元納期日付に表示） | 読取専用 |
| 納入 | 調整後に実際に出す数量 | 編集可 |
| 残量 | `受注 − 納入` | 読取専用 |

**動作**:
- グループキー: `(product_code, due_date)` — 同品番同元納期は1行に集約
- 元納期日の「受注」セルに元数量を表示（基準線）
- 任意日付の「納入」セルに数量を入力。複数日に入れれば自動的に分割扱い
- 後ろ倒し（納入日付 > 元納期）入力時に「顧客承認済みですか？」モーダル表示
- 保存時、総残量 ≠ 0 の行はエラー
- 品番検索: 部分一致、大文字小文字無視、品名も対象
- 保存時、バックエンドで受注明細に割付（複数明細グループなら数量按分）

- 保存時、占有率100%超 or 重量超 or 混載不可衝突はエラー

## 前工程需要日反映ロジック

### 運用方針

- `LineDemand` は顧客確定/内示の元データとして保持し、**便割付結果で更新しない**
- 便割付結果は `LineBacklog` の **クボタ配送ライン**（`sequence_no > 0` の plan 行）へ反映する
- 前工程需要日（便出発日の前日）は、クボタ配送ライン LineBacklog → 既存 pickup カスケードの routing lead_time によって自動的に算出される

### 同期処理

配置: [pm_backend/apps/shipping/views_kubota_sakai_trip_assignment.py](../pm_backend/apps/shipping/views_kubota_sakai_trip_assignment.py) の `_sync_kubota_delivery_backlog_for_date`

**トリガー**: `POST /api/kubota-sakai-trip-assignments/bulk_save/` 実行時、積載検証OK後に同期

**処理内容**:
1. クボタ配送ライン/工程を解決（`line_code='L3102'` またはプロセス名に「クボタ配送」を含む、無ければ `KUBOTA_DELIVERY` で自動生成）
2. 対象日の `LineBacklog` 既存 plan 行（`sequence_no > 0`）を全削除
3. 対象日の `KubotaSakaiTripAssignment` をループし、1割付 = 1 LineBacklog plan 行として作成
   - `plan_date = 出発日`
   - `sequence_no = 品番ごとの連番`
   - `plan_qty = 割付数量`（整数丸め）
   - `order_qty = 0`, `demand_qty_plan = 0`
4. クボタ配送ラインから上流工程への需要伝播は既存 pickup ロジックが担当（routing の `lead_time_days` 経由で前工程需要日が自動算出）

### `LineBacklog_sequence_no` 規約

- `sequence_no = 0`: 需要専用行。`plan_qty = 0` 必須
- `sequence_no > 0`: 計画値専用行。実績値は入れない

詳細は [LineBacklog_sequence_no仕様.md](LineBacklog_sequence_no仕様.md) 参照。

## 業務ルール（決定済み）

- **前倒し**: 上限ルール無し、営業判断で自由
- **後ろ倒し**: 顧客口頭承認ありで許可、厳密な承認記録は不要（フラグのみ）
- **分割積載**: 1つの OrderLine を複数便に分けて積載可能
- **未割付**: 基本NG、`assignment_deadline_days` 営業日前までに割付必須
- **前倒し/後ろ倒し判断主体**: 営業（納期調整ステップ）
- **便振り分け判断主体**: 業務/物流（便計画ステップ）
- **容器と製品の紐付け**: 既存の製品マスタ `used_container` + `capacity` を使用

## 未確定事項（後日検討）

1. **内示の扱い**: 前工程は「確定のみ」で引くルールか、「確定＋内示の一部」か
