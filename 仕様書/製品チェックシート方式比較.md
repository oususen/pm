# 製品チェックシート 方式比較

## 現状の課題

現在の紙チェックシートは、製品ごとに複数工程のチェックを紙帳票で管理している。デジタル化にあたり、2つの方式を検討する。

---

## A案: 台紙方式（現行実装済み）

既存の紙チェックシートをそのまま台紙画像として取り込み、画像上にフィールドを配置する方式。

### 仕組み

- 紙帳票のPDF/画像を台紙として登録
- 台紙画像の上に入力フィールド（テキスト、チェックボックス等）を座標配置
- 製品×工程ごとに1テンプレートを作成

### メリット

- 現在の紙帳票のレイアウトをそのまま再現できる
- 現場の作業者が紙と同じ見た目で違和感なく使える
- 紙→デジタルの移行コストが低い

### デメリット

- チェック項目の追加・変更には台紙画像の再作成が必要
- 工程ごとにテンプレートが分かれるため、1製品の品質状況を横断的に把握しにくい
- 工程間の順序制御がなく、前工程の未チェックに気づかないリスクがある
- 製品に5工程あれば5バッチ発行され、管理が煩雑になる

---

## B案: 工程一体方式（新規提案）

チェック項目をアプリ内で定義し、1製品1帳票に全工程のチェックブロックをまとめる方式。台紙画像も参考資料として併用可能。

### 仕組み

- チェック項目はアプリ上で作成・管理（設備始業点検表と同様の方式）
- 1つの帳票内に工程ごとのブロック（セクション）を設ける
- 台紙画像は参考資料として表示可能（項目定義はアプリ側で管理）
- 製品で1バッチを発行し、全工程が同じバッチを共有

### メリット

| 観点 | 効果 |
|------|------|
| **一覧性** | 1製品の全工程チェック状況を1画面で把握できる |
| **工程順序制御** | 先頭工程の完了前に次工程のチェック不可（台目単位） → 抜け漏れ防止 |
| **項目管理** | チェック項目の追加・変更がアプリ上で即時反映（台紙再作成不要） |
| **バッチ管理** | 1製品1バッチで管理がシンプル |
| **台紙併用** | 紙帳票の見た目も台紙として参照可能（A案の良さを維持） |
| **トレーサビリティ** | 工程の完了順序がシステムで記録され、品質問題発生時の追跡が容易 |

### デメリット

- チェック項目をアプリに入力する必要がある（その代わりフィールド座標配置は不要）
- 既存の紙帳票レイアウトと完全一致はしない（項目定義はアプリ管理のため）

## 構造の違い

### A案: 台紙方式

```
製品 YD60000441（5工程）

  テンプレートA（タンクサブー工程）→ バッチ1 → 台目1, 台目2, ...
  テンプレートB（箱組工程）      → バッチ2 → 台目1, 台目2, ...
  テンプレートC（タンクコンプ工程）→ バッチ3 → 台目1, 台目2, ...
  テンプレートD（水没洗浄工程）  → バッチ4 → 台目1, 台目2, ...
  テンプレートE（タンク小組工程） → バッチ5 → 台目1, 台目2, ...

  ※ 各バッチは独立、工程間の順序制御なし
```

### B案: 工程一体方式

```
製品 YD60000441（5工程）

  帳票テンプレート（1つ）
    ├─ 工程1: タンクサブー ─┐
    ├─ 工程2: 箱組        ─┤
    ├─ 工程3: タンクコンプ ─┼→ バッチ1 → 台目1, 台目2, ...
    ├─ 工程4: 水没洗浄    ─┤
    └─ 工程5: タンク小組  ─┘

  ※ 台目単位で工程1→2→3→4→5の順序を強制
  ※ 台目1の工程3がチェック可能になるのは、台目1の工程2が完了してから
```

## 紙チェックシートの形式（現場で使用予定）

現場で使用中の紙チェックシートは**マトリクス形式**である。

```
┌──────────────────────────────────────────────────────────┐
│ NO │ 点検項目         │ 規格         │ 頻度  │ 方法            │ 1 │ 2 │ 3 │ ... │ 21 │
├────┼─────────────────┼─────────────┼──────┼────────────────┼───┼───┼───┼─────┼────┤
│  1 │ パイプ傾き倒れ無き事 │ -           │ 全数 │ 目視確認          │ ✓ │ ✓ │ ✓ │     │    │
│  2 │ 子部品欠品無き事「ブラケット×2.Pクランプ×2」 │ - │ 全数 │ 目視確認 │ ✓ │ ✓ │   │     │    │
│  3 │ 内側にM10ナット取り付け、溶接忘れ無き事 │ -   │ 全数 │ 目視確認 │ ✓ │   │   │     │    │
│  4 │ ボトムプレート浮き・穴ずれ無き事 │ -      │ 全数 │ 目視確認 │ ✓ │   │   │     │    │
└──────────────────────────────────────────────────────────┘
  ↑ 縦軸: チェック項目                                       ↑ 横軸: 台目（1ロット分）
```

- **1ロット = 1枚**の帳票
- 横軸の台目数はロットの計画数量に応じて変動する

### A案でこの形式を再現できるか？

製品＋工程ごとに1台紙として、横軸に台目を並べたマトリクス台紙を作る案は考えられるが、以下の運用上の問題が残る。

**1. フィールド配置の作業量**

チェック項目5項目あるなら、5項目 × 台目30列（余裕を持たせた場合） = **150個のフィールドを1枚の台紙に手配置**する必要がある。さらにこれが工程ごとに必要なため、5工程なら**750個のフィールド配置**が初期作業となる。

**2. チェック項目の変更に弱い**

項目の追加・削除・順番変更のたびに、台紙画像を作り直し、フィールドを再配置する必要がある。アプリ上で項目を編集して即反映、ということができない。

**3. 台紙サイズとタブレット表示の問題**

30列分のマトリクスを1枚の台紙に収めると、画像が非常に横長になる。タブレット端末では拡大・スクロールが必要で、現場での操作性が悪化する。

**4. 台目上限を超えた場合のリスク**

多めに設定しても（例: 30列）、それを超えるロットが来た場合にテンプレートの作り直しが必要。上限値の管理が運用負荷になる。

**5. 未使用列の見た目**

21台のロットに30列テンプレートを使うと、9列分が空欄のまま残り、紙帳票のような整然とした見た目にならない。

**6. チェックデータの活用ができない**

A案では台紙画像上のフィールドに入力するが、そのフィールドが「何のチェック項目か」はシステム上で管理されていない。入力データはフィールド座標に紐づくだけで、項目名・規格・判定基準との関連がない。つまり：

- 「この製品の不良率が高い項目はどれか？」→ **分析不可**
- 「この工程で規格外が多発している傾向は？」→ **集計不可**
- 「過去3ヶ月で同じ項目がNG連発しているか？」→ **追跡不可**

※ 現状運用では、NGは製品チェックシートに記入していない（実質的にOK確認中心）。このため、現時点の分析用途は限定的である。  
それでも、せっかくデジタル化するなら将来の運用変更（NG記録を残す運用）に備えて、**項目を構造化して持てる設計**の方が拡張しやすい。B案は項目がアプリで定義されているため、項目別・工程別・期間別の集計・分析・傾向把握に発展させやすい。

**7. 品質記録の原則: 1台=1チェックシート**

製品チェックシートは「この1台が品質基準を満たしているか」を保証する記録である。1ロットに1枚のマトリクスでまとめてしまうと、**個体ごとの品質保証記録として成立しない**。品質問題が発生した際、「この台目のチェック結果はどこか？」→ ロット帳票の中の1列を探す必要があり、トレーサビリティとして不十分。B案は1台=1チェックシート（全工程分）として個体単位の品質記録が自然に残る。

**8. 紙の手書きとデジタル入力の根本的な違い**

現場の紙チェックシートは**手書き**で運用されている。狭いセルでも人間は柔軟に書き込める。しかし台紙方式でデジタル化する場合、紙と同じセルサイズにフィールドを配置しても、タブレットでの**タップ→入力**操作は手書きのようにはいかない。フィールドが小さすぎて押しにくい、入力欄が見えにくいなど、**「紙の見た目を再現すること」と「デジタルで使いやすいこと」は両立しない**。紙のレイアウトを忠実に再現するほど、現場の操作性は悪化する。

### B案ならどうか？

**自然に実現可能。** チェック項目はアプリで定義するため、台数に応じたマトリクスグリッドを自動生成できる。台数が21でも26でも同じテンプレートで対応する。

## 現場運用での違い（例: 計画数21台）

### A案の場合

1. 生産計画に21台を入力
2. 5工程で5バッチに分かれて発行（ロット/枚）
3. 工程ごとに個別画面を開いてチェック入力
4. 各工程の作業者がそれぞれのバッチから入力
5. 工程間の進捗は別画面で確認が必要

### B案の場合

1. 生産計画に21台を入力 → この時点でバッチが生成される
2. **1バッチ21台分**が発行（各台目に5工程分のチェック欄）
3. **紙と同じマトリクス表示**で一覧チェック可能（横軸=台目、縦軸=項目）
4. 台目ごとに工程1から順にチェック → 前工程が終わっていなければ次工程はロック
5. 1画面で台目ごとの全工程進捗を確認可能

---

## 結論

**A案とB案は排他ではなく、併用可能。**

- A案は既に実装済みであり、紙帳票のデジタル化として即運用可能
- B案は工程間連携・一覧性・項目管理の面で優れ、中長期的な運用効率が高い（現時点で実装済み）
- A案の台紙併用という良さはB案にも取り入れ済み（B案でも台紙画像を参照表示可能）

**提案: 両方式をシステムに用意し、製品・現場の特性に応じて選択可能とする。**

---

## B案の訴求ポイント（意思決定向け）

「どちらが実装可能か」だけでなく、「どちらが現場運用を継続的に改善しやすいか」という観点で見ると、B案には以下の強みがある。

### 1. 現場にとっての価値（毎日の作業が軽くなる）

- 工程別ロックにより、前工程漏れをその場で防止できる
- 1バッチで全工程を追えるため、探す・開く・切り替える操作が減る
- 台目の前後移動、工程単位保存、工程単位状態表示により連続入力が速い
- 台数可変（21台/26台/30台超）でもテンプレートを作り直さない

### 2. 品質保証にとっての価値（説明可能性が上がる）

- 1台単位で「どの工程で」「誰が」「いつ」入力したかが残る
- 不良発生時に、工程横断で当該台目の履歴を即追跡できる
- 項目定義が構造化されているため、将来的にNG記録を開始した場合も項目別・工程別の傾向分析へ拡張しやすい
- 監査時に、記録に加えて経緯を説明しやすくなる

### 3. 管理者にとっての価値（運用コストが下がる）

- 項目追加・修正がアプリ設定で完結し、台紙再作成待ちが不要
- 工程追加・順序変更にもテンプレート1本で追従できる
- 担当者（班長/係長/部長）補完や承認フローと連携しやすい

### 4. IT運用にとっての価値（保守負債が増えにくい）

- 座標依存のフィールド大量配置を避けられ、UI改修時のリスクを抑えられる
- 画面・データ構造が一貫しており、改修時の影響範囲が読みやすい
- 将来の集計・アラート・自動判定などの機能拡張を追加しやすい

---

## A案とB案の本質的な違い（再整理）

- A案は「紙面の再現」に強い
- B案は「品質データ運用」に強い

製品チェックシートの目的を「紙の見た目維持」だけでなく「品質保証の実効性」まで含める場合、B案を主軸候補として検討しやすい。

---

## B案導入の現実的な進め方（段階導入）

### フェーズ1（短期）

- 早期運用するなら、A案を先行して実用
- 同時にB案を整備する

### フェーズ2（中期）

- ライン最終品への全適用
- 運用によりデータ収集

### フェーズ3（定着）

- B案を標準、A案を例外運用（特殊帳票）へ整理
- 品質改善活動（再発防止、工程能力改善）にデータ活用を接続

## よくある質問（Q&A）

### Q1. 「紙と同じ見た目でないと現場が混乱しませんか？」

A. B案でも台紙画像を参照表示できる。入力は紙の再現度とタブレット操作性のバランスを取ることで、運用を安定させやすい。

### Q2. 「新規作成コストが高いのでは？」

A. 初期の項目入力は必要だが、フィールド座標配置は不要。項目変更・工程変更のたびに発生する再レイアウト工数を継続的に削減できる。中長期では総保有コスト（TCO）を下げられる可能性がある。

### Q3. 「A案で今すぐ回るなら、それで十分では？」

A. A案は短期の立ち上げには有効。ただし工程横断管理・分析・監査説明まで求める場合は、追加の工夫が必要になる。「今すぐ回すA案」と「継続改善するB案」は役割が違う。

---

## 最終提案（B案を主軸に据える）

- 運用の即効性: A案を補助的に活用
- 品質保証の実効性: B案を標準方式として採用
- システム戦略: B案中心で機能拡張し、A案は特殊要件対応に限定

運用開始のしやすさと中長期の改善性を両立する観点では、**短期は併用しつつ、標準化の着地点としてB案を育てる**方針が適切である。
