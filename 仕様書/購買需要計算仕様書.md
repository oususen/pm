# 購買需要計算機能仕様書

## 概要

仕入れ計画画面において、後ラインや後工程の計画数量から購買部品の需要を自動計算する機能。
BOM展開を使用して親製品の計画数量から子部品（購買部品）の必要数量を逆算し、リードタイムを考慮した日付で需要を算出する。
ここでいう需要は、**その仕入先ラインから出庫すべき数量**を意味する。

## 目的

- 後ラインや後工程の生産計画から、購買部品の需要を自動的に算出
- 手動で需要を入力する手間を削減
- BOM個数とリードタイムを考慮した正確な需要計算
- 仕入れ計画の精度向上
- 同一仕入先ライン・同一製品に対して需要行を一意に保つ

## 計算ロジック

### 1. 購買需要の取り込み (pickup_purchase)

後工程の計画数量から購買部品の需要を計算し、LineBacklogに保存する。

#### 処理フロー

1. **仕入先ラインの解決**
   - 仕入先IDから購買ライン（`line_code = supplier_code`）を取得または作成
   - 仕入先マスタ新規作成・更新時にも、同じコード・同じ名称の購買ラインを自動同期する
   - 仕入先ラインは `line_type='PURCHASE'` の管理ラインとして扱う
   - 工程は固定しない。`BUY` は `PURCHASE`、`SUBCON` は `G` または `is_outsource=True` の工程を使う
   - **同一仕入先ライン・同一製品の工程は一意** とする
   - `PURCHASE` と `G` のような別工程の需要行を同じ製品・同じ日付に共存させてはならない

#### 仕入先と購買ラインの同期ルール

- 仕入先新規作成時
  - `supplier_code` は未登録であること
  - 同じ `line_code` の `PURCHASE` ラインが存在しないこと
  - 保存後に `line_code = supplier_code`、`line_name = supplier_name`、`line_type='PURCHASE'` のラインを同時作成する
- 仕入先更新時
  - `supplier_code` 変更時は、対応する `PURCHASE` ラインの `line_code` も同時更新する
  - `supplier_name` 変更時は、対応する `PURCHASE` ラインの `line_name` も同時同期する
- 購買ライン更新時
  - 仕入先と紐づく `PURCHASE` ラインの `line_code` は単独変更禁止
  - 仕入先と紐づく `PURCHASE` ラインの `line_type` は変更禁止
- 購買ライン削除時
  - 仕入先と紐づく `PURCHASE` ラインの手動削除は禁止

2. **対象BOMの取得**
   - `sourcing_type IN ('BUY', 'SUBCON')`
   - `supplier_id = 指定仕入先`
   - `is_active = True`

3. **対象ルーティング工程の取得（互換基準）**
- `RoutingStep.supplier_id = 指定仕入先` **または** `RoutingStep.line_id = 仕入先コード対応ライン`
- 有効ルーティング期間（`build_effective_routing_range_q`）に一致
- `output_product` を需要対象品目として採用
- BOM未設定の「丸ごと外作」でも需要計算対象に含める
- SUBCONのLineBacklogは、RoutingStep.process が process_code='G' または Process.is_outsource=True の工程を使用する。

#### 工程解決ルール

- 仕入先ラインは共通で `line_type='PURCHASE'` を使用する
- `BUY` は `PURCHASE` 工程を使用する
- `SUBCON` は以下の順で工程を決定する
  - BOMItem.process
  - RoutingStep.process（`process_code='G'` または `is_outsource=True`）
  - 外作工程（`process_code='G'` または `is_outsource=True`）
- 画面表示・検収・承認保存・需要展開は同じ工程解決ルールを使用し、`PURCHASE` への一律フォールバックはしない
- 同一 `line_id + product_id` に対して複数工程候補が出た場合は、需要を分割せず **マスタ矛盾または解決エラー** として扱う

#### 計需の意味

- `pickup_purchase` が作る `order_qty` / `demand_qty_plan` は、**その仕入先ラインから出庫すべき数量** を表す
- したがって、同一仕入先ライン・同一製品・同一日付の需要は業務上1つである
- `process_id` はその需要行の所属工程属性であり、同一需要を二重化するためのキーではない

4. **親製品と子部品の紐付け**
   - BOMItemから親製品IDと子部品ID、使用数量、リードタイムを抽出
   - `parent_to_children`: 親製品 → [(子部品ID, 使用数量, リードタイム)]のマップを作成
   - BOMが無い場合のみ、ルーティング工程を **擬似BOM** として扱う
   - ルーティング工程は `routing.product -> routing_step.output_product` を紐付け、数量は1固定で扱う
   - **親が最終品かつ子が非最終品** のルーティング直結は、最終品 `LineDemand` を非最終品の計需源にしてしまうため、購買需要計算では採用しない

5. **親製品の計画数量取得**
   - 親製品IDリストに対して数量を取得する
   - 通常品: `LineBacklog.plan_qty`（`plan_qty > 0`）
   - `OUTSOURCE` ライン: `LineBacklog.order_qty`（`order_qty > 0`）
   - **最終品（`is_final_product=True`）は `LineDemand` を使用し、数量は社内ライン最終品pickupと同じ式で決定する**
   - ただし、この最終品 `LineDemand` 起点は **最終品自身** または **最終品BOM/通常親計画経由で展開される対象** に限る。**非最終品をルーティング直結だけで最終品 `LineDemand` にぶら下げて需要化してはならない**
   - 数量決定式:
     - `is_shifted=true` かつ `firm_qty>0` かつ `forecast_qty>0` の場合: `firm_qty + forecast_qty`
     - それ以外: `firm_qty` 優先、`firm_qty=0` の場合は `forecast_qty`
     - split未設定時のみ互換で `plan_qty` を参照
   - 対象期間: `start_date` ～ `end_date`

6. **計需取得先の優先順位**
   - `pickup_purchase` の計需取得先は、社内生産 `pickup` と同じく「後ろの需要から当該ラインの出庫需要を1回だけ作る」思想で統一する
   - 取得先は次の優先順位で評価し、**同一製品・同一日付に複数ソースを重ねて加算しない**
   - 第1優先: **BOM展開**
     - 親製品需要を子部品へ展開する通常経路
   - 第2優先: **ルーティング擬似BOM**
     - BOMなしで `RoutingStep.supplier` または仕入先ラインに紐づく丸外作・外作加工品
     - 数量は1固定
   - 第3優先: **仕入先ライン自身の `LineDemand`**
     - BOM展開でも routing 擬似BOM でも需要が作られない品目だけに使う
     - 対象は仕入先ラインで直接必要となる品目
   - `BOM > routing擬似BOM > LineDemand` の優先順位で1つの需要に確定する
   - **BOM展開対象品（`child_ids` に含まれる品目）は、日付に関わらず `LineDemand` フォールバック対象外** とし、需要ソースをBOM展開値に統一する
   - **routing 擬似BOMで需要化した品目も `LineDemand` を重ねない**
   - 用途: BOM親子だけでは拾えない購買ライン直結品（例: 直接管理品、BOM未紐付け品、丸外作）を仕入れ計画で需要表示する

7. **親製品の計画日決定**
   - `LineBacklog.plan_date` をそのまま使用する
   - **将来改善**: 本来は `LineGanttPlan.start_datetime` に日替わり8時ルールを適用して正確な計画日を決定すべきだが、中間品→最終品のガント検索や複数ラインにまたがるケースの処理が複雑なため、現時点では `plan_date` を直接使用している

8. **需要計算**
   - 各親製品の計画日・計画数量について:
     ```
     子部品の需要 = 親製品のplan_qty × BOM使用数量
     ```
   - リードタイムを考慮して日付をシフト:
     ```
     子部品の必要日 = 親製品のplan_date - リードタイム（営業日）
     ```
   - 算出した需要は **出庫需要** として扱い、同一仕入先ライン・同一製品・同一日付で1行に集約する

9. **LineBacklogへの保存**
   - 子部品ごとに日付別の需要を集計
   - `update_or_create`で以下を保存:
     - `order_qty`: 需要数量（フロントエンドで「需要」列に表示）
     - `demand_qty_plan`: 計画需要数
   - `process_id` は購買固定ではなく、上記の工程解決ルールに従って品目ごとに決定する
   - 業務上の需要行は **`line_id + product_id + plan_date + sequence_no(=0)` で一意** と考える
   - 別工程の既存行が存在する場合は「別需要」ではなく誤行として補正対象にする
   - 既存の `plan_qty`（購買画面で入力した計画発注数）は **更新しない**

#### 計算式

```python
# 親製品の計画数量を取得（plan_qty > 0のもののみ）
parent_orders = LineBacklog.objects.filter(
    product_id__in=parent_ids,
    plan_date__gte=start_date,
    plan_date__lte=end_date,
    plan_qty__gt=0
).values('product_id', 'plan_date', 'plan_qty')

# 需要計算
demand_map = defaultdict(Decimal)
for row in parent_orders:
    parent_id = row['product_id']
    plan_date = row['plan_date']
    plan_qty = Decimal(str(row['plan_qty'] or 0))

    # plan_qtyが0または未入力の場合はスキップ（order_qtyにはフォールバックしない）
    if plan_qty == 0:
        continue

    for child_id, qty, lead_time_days in parent_to_children.get(parent_id, []):
        # リードタイムを考慮した日付シフト
        target_date = shift_business_days(plan_date, lead_time_days)

        # 需要 = 親の計画数量 × BOM個数
        demand_map[(child_id, target_date)] += plan_qty * qty
```

#### リードタイムの日付シフト

```python
def shift_business_days(target_date, days):
    """
    稼働日で日付をシフトする。
    days > 0 なら過去方向へ、days < 0 なら未来方向へ。
    カレンダが無い場合は暦日でシフト。
    """
    if not days:
        return target_date

    # カレンダが無い場合は暦日でシフト
    if not calendar_id:
        return target_date + timedelta(days=-days)

    # 稼働日ベースでシフト
    step = -1 if days > 0 else 1  # 正:過去へ、負:未来へ
    remaining = abs(int(days))
    current = target_date

    while remaining > 0:
        current = current + timedelta(days=step)
        cal = CalendarDay.objects.filter(
            calendar_id=calendar_id,
            target_date=current
        ).first()
        is_work = cal.is_working_day if cal is not None else True
        if is_work:
            remaining -= 1

    return current
```

### 2. 既存レコードのゼロクリア

需要がなくなった製品・日付のレコードは`order_qty = 0`に更新する。

```python
# 需要計算後に残った既存レコードをゼロクリア
for obj in existing_map.values():
    if (obj.order_qty or 0) != 0 or (obj.demand_qty_plan or 0) != 0:
        obj.order_qty = 0
        obj.demand_qty_plan = 0
        obj.save(update_fields=['order_qty', 'demand_qty_plan', 'updated_at'])
```

### 3. 購買計画（plan_qty）との関係

- 購買計画画面では、`sequence_no=1` の行に `plan_qty` を保存する（1ロット固定）。`sequence_no=0` には `plan_qty` を保存しない。
- `pickup_purchase` は需要再計算APIであり、`plan_qty` を初期化・上書きしてはならない。
- `pickup_purchase` 実行時の更新対象は `order_qty` と `demand_qty_plan` のみ。

## API仕様

### POST /api/line-backlogs/pickup_purchase/

指定仕入先の購買需要を計算してLineBacklogに保存する。

#### リクエスト

```json
{
  "supplier_id": 1,
  "start_date": "2026-01-02",
  "end_date": "2026-03-02"
}
```

**パラメータ**:
- `supplier_id` または `line_id` (required): 仕入先ID、または仕入先ラインID
- `start_date` (optional): 開始日（YYYY-MM-DD）
- `end_date` (optional): 終了日（YYYY-MM-DD）

#### レスポンス

```json
{
  "created": 15,
  "updated": 8,
  "items": 23,
  "line_id": 100,
  "process_id": 50
}
```

**フィールド説明**:
- `created`: 新規作成レコード数
- `updated`: 更新レコード数
- `items`: 需要が計算された(子部品, 日付)組み合わせ数
- `line_id`: 購買ライン（仕入先コード） のID
- `process_id`: 代表工程ID。BUY品がある場合は `PURCHASE` を返すが、実際の保存工程は品目ごとに解決される

#### エラーレスポンス

```json
{
  "detail": "supplier_id is required"
}
```

**HTTPステータス**: 400 Bad Request

#### 品番別 process_id の解決（fetchAndApplyData）

同一仕入先ラインに `外作工程(G)` と `購買(PURCHASE)` の2つの工程が混在する場合、LineBacklog の取得結果には複数工程の `sequence_no=1` 行が含まれ得る。後から処理された行が先の行を上書きし、計画値が消える不具合を防ぐため、以下の2パス方式でデータを読み込む。

**1パス目**: `sequence_no=0`（需要行）を走査し、品番ごとに正しい `process_id` を確定する。`pickup_purchase` が BOM の `sourcing_type`（BUY/SUBCON）に基づき品番ごとに正しい工程を付与しているため、需要行の `process_id` が正となる。

**2パス目**: 全 backlog を走査し、`sequence_no=1`（計画行）については、1パス目で確定した `process_id` と異なる工程の行をスキップする。これにより、別工程の `plan_qty=0` 行が正規の計画値を上書きすることを防ぐ。

この品番別 `process_id` は `row.process_id` に保持され、計画の保存・削除時にも品番ごとに正しい工程で送信される。

**対象となる仕入先**: `外作工程` と `購買` の両工程を持つ品番がある仕入先（例: 三原金属工業、北東工業、大豊製作所、SIAM DAISO）。単一工程のみの仕入先では1パス目の結果が全品番同一になるため、動作に変化はない。

#### 日別計画削除（clearDayPlan）の対象品番限定

日別計画の×ボタンで削除する際、`plan_base`（DB保存済み計画値）が 0 でない品番のみを対象とする。これにより:
- `save` で不要な `plan_qty=0` の送信を削減
- `recalculateInventory` に `product_ids` を渡し、削除対象品番のみ在庫・進度を再計算（全品番再計算の回避）

#### データフロー

```
1. ユーザーが仕入先を選択
2. 「取り込み」ボタンをクリック
3. pickup_purchase API呼び出し
   → 後工程のplan_qtyから需要を計算
   → LineBacklogにorder_qtyとして保存（工程は品番ごとにBUY→購買、SUBCON→外作工程）
4. LineBacklog取得
   → 1パス目: seq=0から品番ごとのprocess_idを確定
   → 2パス目: 確定したprocess_idに一致するseq=1の計画値のみ採用
   → order_qtyを「需要」列に表示
5. 必要に応じて「在庫再計算」ボタンを実行
   → stock_qty / planned_stock_qty / progress_qty を再計算
6. ユーザーが「計画」列に発注計画を入力
7. 「保存」ボタンで計画をLineBacklogに保存（品番ごとの正しいprocess_idを使用）
```

#### 関連画面: 仕入れ在庫 / 残量一覧（`/purchase/inventory`）

- 仕入先選択時（または「更新」実行時）は `pickup_purchase` と `recalculate_scrap` のみ実行する。
- `recalculate_inventory` は自動実行しない。
- 在庫・計画在庫・進度の再計算は「在庫再計算」ボタン実行時のみ行う。
- 「在庫再計算」実行後の再表示は、`pickup_purchase` を再実行せずに最新 `LineBacklog` 再取得で反映する。
- 表示対象品番は `RoutingStep.supplier = 選択仕入先` または `RoutingStep.line.line_code = supplier_code` の工程出力品目（互換条件）を採用する。

#### 関連画面: 仕入れ進度のみ（`/purchase/progress-only`）

- 「更新」実行時は、対象期間・フィルタに一致する `LineDemand` を起点に、表示用の `LineBacklog` 空行（`sequence_no=0`, `order_qty=0`, `demand_qty_plan=0`）を不足分だけ補完する。
- この補完は進度画面の表示トリガーを目的とし、需要値（`order_qty` / `demand_qty_plan`）は設定しない。
- 補完後に `LineBacklog` / `LineDemand` を再取得し、内示・確定は従来どおり `LineDemand` を表示する。
- 多親構成の子品番では、別親品番由来の FORECAST と別親品番由来の FIRM が同じ子品番・同じ `plan_date` に共存し得る。この場合も、画面では `LineDemand.forecast_qty` / `firm_qty` をそのまま表示する。
- 同一親需要の二重計上防止ルールと `source demand key` の定義は、[受注展開仕様書.md](受注展開仕様書.md) に従う。子品番へ集約した後の `LineDemand` キーでは判定しない。
- 仕入モードでは、ライン（仕入先コード）に対して `RoutingStep.supplier一致` または `line_code = supplier_code` で取得した工程出力品目のみを表示対象とする。
- 画面の「削除」ボタンは、誤ったルーティング作成や誤展開で残った `LineBacklog(sequence_no=0)` の基礎データを、表示期間単位で削除する保守用途として使用する。需要ソースの `LineDemand` 自体は削除しない。

## 事後仕入れ実績入力

### 登録時の反映

事後仕入れ実績入力で納入実績を登録した場合、登録対象日の `LineBacklog.actual_qty` を更新する。

- `target_date` が当日以外でも、その納入日に対して実績を加算する
- 子品目を持つ仕入れ品は、登録後に子部品の在庫/計画在庫を追加で再計算する
- 子部品再計算時の凍結基準は実行日ではなく `target_date` を使う
- これにより、遡及入力でも子部品の `actual_shipment_qty` が対象日基準で更新される
- 子品目が存在しない場合は子部品再計算を行わない
- 子部品再計算で例外が発生した場合は warning ログに記録し、登録レスポンス自体は成功のままとする
- 登録後は、対象仕入先ラインの進度も自動再計算する
- 進度再計算の対象品番は、今回登録した製品のみとする（仕入先配下の全製品は再計算しない）
- 進度再計算期間は `PurchaseAutoDeliveryListConfig.progress_days_back / progress_days_forward` を使用する
- 上記設定が未作成の仕入先は、既定値として `7営業日前 ～ 30日後` を使用する
- 進度再計算で例外が発生した場合も warning ログに記録し、登録レスポンス自体は成功のままとする

### デプロイ影響

- 本対応にマイグレーションは不要
- 本番反映はバックエンド再起動のみ

## 使用例

### シナリオ1: 単一親製品からの需要展開

**前提条件**:
- 仕入先: A社
- 親製品: ブレーキアッセンブリ（製品ID=100）
- 子部品: ブレーキパッド（製品ID=200）
- BOM個数: 2個/組
- リードタイム: 3営業日
- 親製品の計画:
  - 2026/01/10: plan_qty = 10
  - 2026/01/15: plan_qty = 20

**計算結果**:

| 子部品 | 必要日 | 需要計算 | 需要数量 |
|--------|--------|---------|---------|
| ブレーキパッド | 2026/01/07 | 10 × 2 | 20 |
| ブレーキパッド | 2026/01/10 | 20 × 2 | 40 |

※ 必要日 = 親の計画日 - 3営業日

### シナリオ2: 複数親製品からの需要集約

**前提条件**:
- 子部品: ボルト（製品ID=300、共通部品）
- 親製品A: ブレーキ（BOM個数=4）
  - 2026/01/10: plan_qty = 10
- 親製品B: サスペンション（BOM個数=6）
  - 2026/01/10: plan_qty = 5
- リードタイム: 2営業日（共通）

**計算結果**:

```
必要日: 2026/01/08

需要数量 = (10 × 4) + (5 × 6) = 40 + 30 = 70
```

→ 複数の親製品から使用される共通部品は、需要が合算される

### シナリオ3: 需要がゼロになった場合

**前提条件**:
- 前回の取り込み時: ブレーキパッドの需要 = 20（2026/01/07）
- 今回の取り込み時: 親製品の計画が削除された（plan_qty = 0）

**計算結果**:

```python
# 前回のLineBacklogレコードが存在
existing = LineBacklog.objects.filter(
    product_id=200,
    plan_date='2026-01-07'
).first()

# 今回の需要計算でdemand_mapに含まれない
# → 既存レコードをゼロクリア
existing.order_qty = 0
existing.demand_qty_plan = 0
existing.save()
```

→ フロントエンドの「需要」列は空白表示

## 重要な設計判断

### 1. なぜ `plan_qty` を使用するのか？

**理由**:
- `order_qty`は「後工程からの需要」であり、循環参照になる
- `plan_qty`は「このラインで実際に作る計画数」なので、それを基に部品を手配すべき
- 生産計画が確定した段階で、必要な部品数が決まる

**例**:
```
溶接ライン:
  - 製品A（中間品）
  - order_qty = 100（さらに後工程からの需要）
  - plan_qty = 120（実際の生産計画、ロットサイズで切り上げ）

購買部品（ボルト）:
  - 溶接ラインのplan_qty=120を使用
  - 需要 = 120 × 4個 = 480個 ← 正しい

  もし order_qty=100 を使用すると:
  - 需要 = 100 × 4個 = 400個 ← 80個不足！
```

### 2. `order_qty` と `demand_qty_plan` の使い分け

| フィールド | 用途 | 購買需要計算での扱い |
|-----------|------|-------------------|
| order_qty | 画面表示用の需要 | 計算結果を保存 |
| demand_qty_plan | 計画需要（将来用） | 同じ値を保存 |
| plan_qty | 計画数量 | ユーザーが入力（後工程では自動計算） |

### 3. リードタイムの考慮

- 親製品の計画日から**過去方向**に日付をシフト
- 営業日ベースで計算（非稼働日をスキップ）
- カレンダがない場合は暦日で計算

**例**:
```
親製品計画日: 2026/01/15（水）
リードタイム: 3営業日

カレンダ:
  1/13（月）: 稼働日
  1/14（火）: 祝日（非稼働）
  1/15（水）: 稼働日

計算:
  1/15 → 1/13（-1営業日）→ 1/10（-2営業日）→ 1/09（-3営業日）

必要日: 2026/01/09（木）
```

## 運用フロー

### 日次運用

1. **生産計画の入力**
   - 各生産ラインで計画数量（plan_qty）を入力

2. **購買需要の取り込み**
   - 仕入れ計画画面で仕入先を選択
   - 「取り込み」ボタンをクリック
   - 需要列に後工程からの需要が自動表示

3. **発注計画の入力**
   - 需要を確認しながら「計画」列に発注数を入力
   - リードタイムや在庫を考慮して調整

4. **保存**
   - 「保存」ボタンで計画をLineBacklogに保存

### 週次運用

1. **需要の再計算**
   - 生産計画変更後、「取り込み」を再実行
   - 変更された需要を確認

2. **発注計画の調整**
   - 需要増減に応じて発注計画を修正

## 注意事項

### ⚠️ 購買ラインの is_active について

購買ライン（`line_type='PURCHASE'`）は `is_active=True` で作成されます。

| 項目 | 説明 |
|------|------|
| is_active | `True`（通常のラインと同様に有効状態で作成） |
| 自動生成 | BOMの仕入先から `supplier_code` をそのまま使用して自動作成 |
| 削除可否 | **削除禁止** - ルーティング等から参照されている可能性あり |

**削除前の確認クエリ**:
```sql
SELECT l.id, l.line_code, l.line_name,
       (SELECT COUNT(*) FROM m_product WHERE line_id = l.id) as product_count,
       (SELECT COUNT(*) FROM m_routing_step WHERE line_id = l.id) as routing_count
FROM m_line l
WHERE l.line_type = 'PURCHASE';
```

`routing_count > 0` または `product_count > 0` のラインは使用中のため削除不可。

### データの整合性

1. **BOMの精度**
   - BOM個数が正確でないと需要計算がずれる
   - 定期的なBOMメンテナンスが必要

2. **仕入先の設定**
   - BOMItemに正しい仕入先が設定されていることを確認
   - sourcing_type（BUY/SUBCON）の設定も必要

3. **リードタイムの設定**
   - BOMItemのlead_time_daysが未設定の場合は0日扱い
   - 実態に合わせた設定が必要

### 計算タイミング

1. **plan_qty変更時**
   - 後工程のplan_qtyを変更したら、購買需要を再計算する必要がある
   - 自動連携はされないため、手動で「取り込み」を実行

2. **BOM変更時**
   - BOM個数や仕入先を変更した場合も再計算が必要

### パフォーマンス

1. **大量データの処理**
   - 期間を長くしすぎると処理時間がかかる
   - 推奨: 2～3ヶ月程度

2. **仕入先ごとの処理**
   - 仕入先を選択することで対象データを絞り込む
   - 全仕入先一括処理は避ける

## トラブルシューティング

### 需要が表示されない

**確認項目**:
1. 後工程のplan_qtyが入力されているか？
2. BOMItemが存在し、is_active=Trueか？
3. sourcing_type が BUY または SUBCON か？
4. 仕入先が正しく設定されているか？
5. 期間設定は正しいか？（リードタイムを考慮）
6. BOM外品の場合、対象購買ラインに `LineDemand.plan_qty` が存在するか？

### 需要が想定より多い/少ない

**確認項目**:
1. BOM個数は正しいか？
2. 複数のBOMが存在していないか？
3. 親製品のplan_qtyは正しいか？
4. リードタイムによる日付ズレはないか？
5. 同一仕入先ライン・同一製品で工程が複数に分かれていないか？ 分かれている場合はマスタ矛盾または誤展開を疑う

### 需要がゼロにならない

**原因**:
- 別の親製品からの需要が残っている
- 複数ラインで同じ製品を使用している

**対処**:
- 全ての親製品の計画を確認
- 必要に応じて手動でゼロクリア
