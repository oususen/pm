# ルーティング変更在庫移行機能 仕様書

## 概要

BOM変更に伴いルーティングを削除・再作成した際に、旧ラインのLineBacklogに残存した在庫（孤立在庫）を新ラインへ移行する機能。

### 背景・課題

BOM変更で品番の製造ライン・工程が変わる場合、以下の手順を踏む：

1. 旧ルーティングを削除
2. 新BOMから新ルーティングを自動生成

このとき旧ルーティングのRouting Stepが削除されると、LineBacklogの `source_routing_step` が NULL になるが、**LineBacklogレコード自体は削除されない**（`on_delete=SET_NULL`）。

この「孤立したLineBacklog」には実績・在庫・調整数などの重要データが含まれるため、削除せず移行する仕組みが必要。

---

## 業務フロー

```
BOM変更
  ↓
旧ルーティング削除（Django管理画面）
  ↓
新ルーティング自動生成（BOMMasterから）
  ↓
【本機能】ルーティングマスタ画面で在庫移行
  ↓
生産計画画面でピックアップ＋在庫計算
```

---

## 機能詳細

### 1. 孤立在庫検出（detect）

**エンドポイント**: `POST /api/stock-migration/detect/`

**処理内容**:

1. 指定ライン（`line_id`）に属する品番を、**有効なルーティング**（`routing__is_active=True`）から取得
2. 取得した品番のLineBacklogを全ラインから検索
3. 以下の条件をすべて満たすレコードを「移行候補」として返す:
   - `source_routing_step` が NULL（旧ルーティング削除済み）
   - `stock_qty > 0`（在庫がある）
   - `sequence_no = 0`（需要行）
   - `line_id` が指定ラインと**異なる**（新ラインとは別のラインに孤立）
4. 品番ごとに最新日付の1件のみ返す

**レスポンス例**:
```json
[
  {
    "product_id": 123,
    "product_code": "YD60009874",
    "product_name": "タンクエオイル(品番)",
    "old_line_id": 5,
    "old_line_code": "L2200",
    "old_line_name": "タンクライン",
    "old_process_id": 42,
    "old_process_code": "4007",
    "old_process_name": "タンク組",
    "stock_qty": 50,
    "new_line_id": 6,
    "new_line_code": "L2201",
    "new_line_name": "タンクセル",
    "new_process_id": 45,
    "new_process_code": "4221",
    "new_process_name": "タンクセル組"
  }
]
```

---

### 2. 在庫移行実行（execute）

**エンドポイント**: `POST /api/stock-migration/execute/`

**リクエスト例**:
```json
{
  "migration_date": "2026-03-11",
  "items": [
    {
      "product_id": 123,
      "old_line_id": 5,
      "old_process_id": 42,
      "new_line_id": 6,
      "new_process_id": 45,
      "migrate_qty": 50
    }
  ]
}
```

**処理内容（品番ごと）**:

1. **旧ライン側** に `LineBacklogAdjustment` を作成/更新
   - `adjust_type = 'STOCK'`
   - `adjust_qty -= migrate_qty`（マイナス調整）
   - `reason = 'ルーティング変更による在庫移行（移行元）'`

2. **新ライン側** に `LineBacklogAdjustment` を作成/更新
   - `adjust_type = 'STOCK'`
   - `adjust_qty += migrate_qty`（プラス調整）
   - `reason = 'ルーティング変更による在庫移行（移行先）'`

3. **RoutingMigrationLog** に移行記録を保存

> 実績（actual_qty）は旧ラインに残す。移行対象は在庫（stock_qty）のみ。

## データモデル

### RoutingMigrationLog（新規）

**テーブル名**: `production_routing_migration_log`

| フィールド | 型 | 説明 |
|-----------|-----|------|
| id | BigAutoField | PK |
| migrated_at | DateTimeField | 移行実行日時（自動） |
| product | FK → Product | 対象製品 |
| old_line | FK → Line | 旧ライン（SET_NULL） |
| old_process | FK → Process | 旧工程（SET_NULL） |
| new_line | FK → Line | 新ライン（SET_NULL） |
| new_process | FK → Process | 新工程（SET_NULL） |
| migrated_qty | IntegerField | 移行数量 |
| migration_date | DateField | 移行基準日 |
| migrated_by | FK → User | 実行者（SET_NULL） |

## 業務ルール

- **実績は移行しない**: 旧ラインの `actual_qty` はそのまま残す（過去の生産事実を変更しないため）
- **移行はadjust_qty経由**: 在庫計算（recalculateInventory）実行後に反映される
- **二重移行の防止**: `LineBacklogAdjustment` は `(line, product, process, plan_date, adjust_type)` でユニーク制約。同一条件で再実行すると既存レコードに加算されるため、実行前に確認すること
- **移行基準日**: 当日日付がデフォルト。任意の日付に変更可能

---

## 移行後の注意

移行実行後、以下を行うこと：

1. **生産計画画面でピックアップ＋在庫計算を実行**
   → adjust_qty が在庫計算に反映される

2. **旧ラインの生産計画画面で在庫が0になっていることを確認**

3. **新ラインの生産計画画面で在庫が引き継がれていることを確認**
