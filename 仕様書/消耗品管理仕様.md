# 消耗品管理仕様書

作成日：2026-10-06

## 1. 目的・対象範囲

旧消耗品管理システム（syomohin）の機能をPMへ取り込み、ログイン、ユーザー・組織、画面権限、注文書承認、通知、SMTPを共通化する。消耗品マスタ、専用購入先、在庫、入出庫履歴、注文依頼、発注準備、注文書、PDF、メール、安全在庫割れの自動依頼を対象とする。

本書は2026-10-06時点の現行ソースを基に作成した。業務ルールの新設・コード変更は行っていない。データ移行・本番確認の進捗は [消耗品管理_移行計画.md](消耗品管理_移行計画.md)、権限の共通仕様は [権限仕様書.md](権限仕様書.md) を参照する。

## 2. データモデル

消耗品購入先は生産系の `m_supplier` と統合せず、専用テーブルで管理する。作業者・依頼者はPMのユーザー（`auth_user`、`UserProfile`）を使用し、消耗品専用社員マスタは作らない。

| モデル | テーブル | 主な保存内容・関係 |
|---|---|---|
| ConsumableSupplier | `t_consumable_supplier` | 購入先名（ユニーク）、担当者、電話、メール、住所、備考、有効フラグ |
| Consumable | `t_consumable` | コード（ユニーク）、発注コード、品名、カテゴリ、単位、保管場所、在庫数、安全在庫、発注単位、単価、購入先、画像、備考、有効フラグ |
| ConsumableOrderEmailConfig | `t_consumable_order_email_config` | 購入先と1対1。メール本文とCCユーザー（Userへの多対多） |
| ConsumableRequest | `t_consumable_request` | 消耗品、数量、単価、金額、納期、依頼者・氏名・組織スナップショット、依頼種別、状態、備考、依頼／発注／完了日時、登録者 |
| ConsumableDispatchOrder | `t_consumable_dispatch_order` | 注文書番号（ユニーク）、業務日、同一購入先の当日回数、購入先・名称、明細数、合計金額、状態、ApprovalRequest（1対1）、PDF、送信先・送信／入庫日時、作成者 |
| ConsumableDispatchOrderItem | `t_consumable_dispatch_order_item` | 注文書、消耗品、元依頼、コード・発注コード・品名・数量・単位・単価・金額・納期・備考のスナップショット |
| ConsumableStockMovement | `t_consumable_stock_movement` | 消耗品、入出庫／調整区分、入庫種別、対象依頼、数量、処理後在庫、作業者・氏名・組織スナップショット、使用ライン、単価、金額、備考、処理日時、登録者 |

- 在庫数・安全在庫は整数。発注単位・依頼数量・明細数量・履歴数量は正整数型で管理する。入出庫・依頼の登録APIは数量1以上を要求する。
- 単価は小数2桁、金額は小数2桁のDecimal型。依頼の金額は登録時のマスタ単価×数量とし、数量編集時も依頼に保存された単価で再計算する。
- 組織は `division_name`＝事業部、`group_name`＝係、`team_name`＝班、`unit_name`＝グループを別々に保存する。各階層はUserProfileの該当フィールドから独立して取得し、班から係をたどらない。
- 作業者・依頼者は指定された有効ユーザー。未指定ならログインユーザー。ユーザー削除後も氏名・組織のスナップショットを保持する。
- 注文書明細は作成時点の値を保存する。後日のマスタ編集で過去明細は書き換えない。
- 画像保存先は `MEDIA_ROOT/consumables/images/`、PDF保存先は `MEDIA_ROOT/consumables/purchase_orders/`。

### 削除・在庫編集

- 注文書で使用中の購入先は削除不可。有効フラグを無効にする。
- 依頼・入出庫履歴のある消耗品は削除不可。消耗品と注文書明細の参照もモデルのPROTECTで保持する。
- マスタの在庫数は新規登録時のみ設定可能。既存マスタの通常編集で在庫数を変えるとエラーとなる。在庫の変更は入庫・出庫・在庫調整で行う。

## 3. 在庫と履歴

### 在庫一覧

- 欠品判定は **在庫数 <= 安全在庫**。`is_shortage` はAPIで導出し、独立した欠品状態を保存しない。
- 注文状態は未完了依頼から導出する。優先順位は `ordered`（発注済）＞`preparing`（発注準備）＞`requested`（依頼中）。該当依頼がなければ未発注。
- カードAPIは各品目に未完了依頼（依頼者名・数量・日時等）と直近2件の入庫履歴を付けて返す。入庫履歴は処理日時・IDの降順で抽出する。

### 出庫・手動入庫

処理は `transaction.atomic` 内で消耗品行を `select_for_update` によりロックし、在庫更新と履歴作成をまとめて行う。

| 操作 | 在庫更新 | 履歴 |
|---|---|---|
| 出庫 | 現在庫－数量。不足時はエラー | `movement_type=outbound`。数量、処理後在庫、作業者、組織、使用ライン、マスタ単価×数量等を記録 |
| 手動入庫 | 現在庫＋数量 | `movement_type=inbound`、`inbound_type=manual`。作業者・組織・処理後在庫等を記録 |
| 在庫調整 | 現在庫＋符号付き調整数。0は禁止、調整後の負在庫は禁止 | `movement_type=adjustment`。作業者はログインユーザー。`quantity` は調整数の**絶対値**、`stock_after` は調整後在庫。API応答の `adjustment` は符号付き |

在庫調整の履歴には符号専用フィールドがない。既定の備考は `在庫調整: +N`／`在庫調整: -N`。任意の備考を指定した場合はその内容が保存される。調整履歴の単価・金額はモデル既定の0で、通常入出庫のような金額計算は行わない。履歴の数量だけを符号付き在庫増減と解釈しない。

### 履歴の検索・集計

- 期間、入出庫区分、入庫種別、品目、作業者、コード・品名・氏名・備考、組織名で検索・絞り込みを行う。
- 組織階層は `division`／`group`／`team`／`unit`。集計の初期値は `team`（班）、空の組織名は「（未設定）」と表示する。
- 部署別集計は、組織名と `movement_type` ごとの履歴件数・保存数量合計・保存金額合計。異なる単位の品目の数量も合算されるため、品目別の在庫残高を示すものではない。在庫調整の数量合計は絶対値の合計になる。
- 業務日の範囲は開始日8:00以上、終了日の翌日8:00未満。履歴の現在の所属ではなく、記録時点の組織スナップショットを使う。

## 4. 注文依頼・発注準備

### 状態

| 保存値 | 表示 | 未完了扱い |
|---|---|---|
| requested | 依頼中 | 対象 |
| preparing | 発注準備 | 対象 |
| ordered | 発注済 | 対象 |
| received | 入庫済 | 対象外 |
| rejected | 却下 | 対象外 |
| cancelled | キャンセル | 対象外 |

- 通常の手動登録は `requested`。`direct=true` または `direct=1` は発注担当の直接追加で `preparing`。依頼種別はいずれも `manual`。
- 納期は `最短`／`通常`／`余裕あり` または厳密な `YYYY-MM-DD`。手動APIで未指定の場合は「最短」、自動依頼は「通常」。モデルの既定値は「通常」。
- 編集できるのは、注文書に未掲載の `requested`／`preparing` の依頼。数量、納期、備考を変更し、金額を再計算する。
- 手動状態変更は `requested → preparing/rejected/cancelled`、`preparing → requested/rejected/cancelled`、`rejected/cancelled → requested`。注文書に載っている依頼は変更不可。
- `ordered` と `received` は注文書の送信・入庫処理で更新する。手動の状態変更APIからは指定できない。
- 注文書に掲載済み、または発注済・入庫済の依頼は削除不可。

## 5. 注文書・承認・一括入庫

### 作成

1. 有効な `item_key=consumable_dispatch_order` のApprovalRouteConfigが必要。設定 > 承認設定で「消耗品注文書」を登録する。
2. 作成者は承認設定で解決されるcreatorと代理ユーザーを確認する。スーパーユーザーは作成可能。ルート未登録は400、作成対象外は403。
3. `supplier` と `request_ids` を指定する。同一購入先の発注準備状態で、まだ注文書に載っていない依頼だけを対象とする。不一致があれば作成を拒否する。
4. 対象依頼をロックし、注文書・明細・承認申請を作成、PDFを保存する。作成時点で依頼は発注準備のまま。

- 注文書番号は `PO-YYYYMMDD-NNN`。日付は8時区切りの業務日で、連番はその業務日の注文書全体を対象とする。同時採番による重複時は最大3回試行する。
- `daily_count` は同一購入先・業務日の既存注文書数＋1。
- 明細数は依頼件数、合計金額は依頼の保存金額の合計。明細は品目コード順に作成する。

### 注文書状態と承認状態の分離

注文書の保存状態は **`unsent`（未送信）→`sent`（送信済）→`received`（入庫済）**。承認状況は共通ApprovalRequestの状態・現在段階で別に管理する。「承認済」を注文書のstatusに保存しない。

- 作成時のApprovalRequestは `status=created`、`current_stage=creator`。contextに `dispatch_order_id`／`order_number`／`supplier_name` を保存する。
- 確認依頼・確認・承認・却下はPM共通承認APIを使用する。受信箱の「注文書へ」は `/consumables/dispatch-orders?id=<ID>` に遷移する。
- 画面の確認・承認・却下ボタンはログインユーザーに割り当てられた未処理タスクで表示する。確認依頼は未送信かつ承認状態created/rejectedで、作成者またはスーパーユーザーに表示する。
- 未送信の注文書は削除可能。PDF・注文書・承認申請を削除する。依頼は削除せず、作成時から保持している発注準備の状態で再利用できる。

### メール送信

- 未送信かつApprovalRequestが `approved` の場合のみ送信可能。送信先はAPIで指定した `email`、未指定なら購入先マスタのメール。
- 最新の承認欄を反映したPDFを生成してから送信する。メール成功時に注文書をsent、承認申請をsent、対象依頼をorderedにし、送信／発注日時を記録する。失敗時はこれらの状態を進めない。
- メール送信と、その後のDB状態更新は別処理。外部送信とDB更新全体が単一トランザクションであるとは扱わない。

### 注文書単位の一括入庫

- 送信済み注文書だけが対象。注文書をロックし、処理時にもsentであることを確認して二重入庫を防ぐ。
- 全明細の数量を各消耗品の在庫へ加算し、入庫種別dispatchの履歴を作成する。単価・金額は明細の保存値を使用する。
- 対象依頼のうちorderedをreceivedにし、完了日時を記録。注文書もreceivedにし入庫日時を記録する。
- 個別の分納数量を指定するAPIではなく、全明細の一括入庫。処理は注文書・品目の行ロックとatomicでまとめる。

## 6. PDF・メール設定

- PDFはA4縦、日本語フォントは共通の `overtime.pdf_generator.register_japanese_fonts()` を使用。商品名・備考を折り返し、明細表は複数ページに分割し見出しを繰り返す。
- 承認欄は左から承認、確認②（設定有効時）、確認、作成。姓と日付を表示し、姓未登録時はユーザー名を使用する。最後の却下以前の承認記録は表示に使わない。
- 作成、承認操作の連携、送信前にPDFを生成・更新する。PDF取得時も保存PDFがなければ生成する。
- PDF名は `YYYYMMDD_購入先名_合計金額整数部_注文書_当日回数.pdf`。
- 送信は共通EmailServiceを使用し、`user_id=request.user.id`（送信操作ユーザー）のSMTP設定を使用する。
- 購入先別の本文・CCユーザーは設定 > 注文書メール設定の「消耗品注文書」で管理する。CCは設定ユーザーのメールがあるものを使用する。
- 本文の `{created_by_name}`／`{created_by_email}` は**注文書作成者**の氏名・メールへ置換する。SMTPの送信操作ユーザーと区別する。
- 件名は `【注文書送付】注文書番号 - 購入先名`。購入先別本文設定がない場合は既定本文を使う。設定詳細GETは、購入先が存在して設定がないときに既定本文で設定レコードを作成する。

## 7. 安全在庫割れ自動依頼

タスク名は `CONSUMABLE_AUTO_REQUEST`。ScheduleConfigの初期値は無効、7:00。定時タスク設定とスケジューラーへ登録されている。

- 対象は有効な消耗品で `stock_quantity <= safety_stock`、かつ未完了依頼（requested/preparing/ordered）がないもの。
- 発注単位は整数化し、最低1として計算する。数量は旧syomohinの式を維持する。

```text
数量 = max(発注単位,
           int((安全在庫 × 2 − 在庫数) / 発注単位 + 1) × 発注単位)
```

- 割り切れる場合も1単位多くなる既存挙動を維持する。
- 登録内容は `request_type=auto`、`status=requested`、`deadline=通常`、依頼者名「システム自動」、依頼者FKなし、備考「自動発注依頼（在庫: X, 安全在庫: Y）」。
- マスタ単価で金額計算し、`datetime.now()`で依頼日時を記録する。既存の未完了依頼によって次回実行時の重複を除外する。この処理を同時起動に対する一意制約保証と同一視しない。
- 実行時はScheduleConfigにRUNNINGを記録し、結果はSUCCESS/FAILED、所要時間、メッセージと共通実行ログに保存する。注文書の作成・承認・送信は自動依頼タスクの対象外。

## 8. CSV取込・画像・QR

### CSV

- multipart/form-dataの `file` を受け取り、UTF-8 BOM付き／UTF-8、CP932の順に読み取る。空行は除外し、既知の列名だけを使用する。
- 購入先はname／名称／購入先名／購入先を名称に対応付ける。名称必須、同名は更新、なければ追加。
- 消耗品はコードと品名が必須。同コードは更新、なければ追加。購入先名で紐付けるため、購入先CSVを先に取り込む。未登録購入先の行はエラーとしてスキップ。
- 対応列はcode／コード／品目コード、order_code／注文コード／発注コード、name／品名、category／カテゴリ、unit／単位、stock_quantity／在庫数、safety_stock／安全在庫、unit_price／単価、order_unit／発注単位、supplier／supplier_name／仕入先／購入先、storage_location／保管場所、note／備考、image_path／画像パス／画像URL／画像ファイル。
- 数値のカンマを除去し、整数項目はDecimalから整数化する。発注単位は最低1。既存品の在庫数はCSVに含まれていても更新しない。
- 消耗品の更新は記載された属性だけの差分更新ではなく、コードで特定して組み立てた既定値を含めて上書きする。省略列による空値・既定値の更新に注意する。
- 画像列はパスの末尾ファイル名を取得して `consumables/images/<file>` に紐付ける。画像ファイル自体のコピーはCSV取込では行わない。画像列が空なら既存画像を変更しない。
- 応答は `created`／`updated`／`errors`。想定する入力エラーの行をスキップして有効行を保存するため、errorsがあることだけで全行ロールバックされたとは判断しない。

### QR・品名検索

- カメラ画像は `QrScanner.vue` のjsQRでブラウザ側でデコードする。サーバー側OpenCVによる画像デコードはこの機能では使用しない。
- 「管理番号：コード 品名…」「code=コードname=…」、先頭に不要文字があるラベルを正規化する。
- 有効品目を対象に、大文字小文字を無視したコード完全一致→ハイフン・空白を除く一致→コード前方一致→品名部分一致の順で照合する。
- 1件なら品目を返す。前方／品名一致で複数候補がある場合は `multiple=true` とresultsを返す。既存の候補取得は各最大20件。該当なしは404、QR空は400。

## 9. API一覧

基点は `/api/consumables/`。一般APIはIsAuthenticatedによるログイン認証を使用する。画面資源権限の追加チェックは行わない。承認設定のcreator照合と承認状態・在庫・依頼状態等の業務条件は別に検証する。

| 相対URL | メソッド | 内容・主な入力 |
|---|---|---|
| `suppliers/`、`suppliers/{id}/` | GET/POST、GET/PUT/PATCH/DELETE | 購入先CRUD |
| `suppliers/import-csv/` | POST | 購入先CSV、file |
| `items/`、`items/{id}/` | GET/POST、GET/PUT/PATCH/DELETE | 消耗品CRUD |
| `items/import-csv/` | POST | 消耗品CSV、file |
| `items/{id}/upload-image/` | POST | 画像、image |
| `items/lookup/` | GET | qrによる照合 |
| `items/cards/` | GET | 在庫カードと依頼・直近入庫 |
| `items/filter-options/` | GET | 有効品目のカテゴリ・保管場所の候補 |
| `movements/`、`movements/{id}/` | GET | 履歴一覧・詳細 |
| `movements/inbound/`、`movements/outbound/` | POST | consumable、quantity、worker（省略可）、usage_line、note |
| `movements/adjustment/` | POST | consumable、符号付きquantity、note。stock_after／adjustment／movement_idを返す |
| `movements/workers/` | GET | 有効ユーザー・係・班・グループ・有効PRODライン。group／team／unitでユーザー絞り込み |

| `dispatch-orders/`、`dispatch-orders/{id}/` | GET、GET/DELETE | 注文書一覧・詳細・未送信削除 |
| `dispatch-orders/route-status/` | GET | route_configured／can_create |

| `dispatch-orders/{id}/pdf/` | GET | PDF。download=1は添付、それ以外はinline |

| `order-email-configs/` | GET | 保存済みメール設定一覧 |
| `order-email-configs/{supplier_id}/` | GET/PUT | 購入先別の本文・CC設定 |

主な絞り込み：品目はis_active／supplier／category／storage_location／shortage=1／order_status（noneは未発注）／search、依頼はstatus／statuses（カンマ区切り）／request_type／consumable／supplier／undispatched=1／search、注文書はstatus／supplier／search、履歴はdate_from／date_to／org_level／org_name等。標準の一覧はPM共通ページング、cards・summary・workers・設定一覧は独自応答。画面側の一覧取得には既存のpage_size=0指定がある。

## 10. 画面・権限

グローバルナビ「消耗品」は `GlobalNavigation.vue` で表示し、タイルとルーターの `meta.resource` で画面遷移を制御する。親／子資源の扱い、can_editが閲覧を含む判定は共通権限仕様に従う。

| 画面 | URL | resource |
|---|---|---|
| 消耗品メニュー | `/consumables` | consumables（allowChildResources=true） |
| 在庫一覧 | `/consumables/inventory` | consumables.inventory |
| 入出庫・注文依頼・在庫調整 | `/consumables/operations` | consumables.operations |
| 発注準備 | `/consumables/requests` | consumables.dispatch |

| 入出庫履歴 | `/consumables/history` | consumables.history |
| 消耗品・購入先マスタ | `/consumables/masters` | consumables.masters |

- 発注準備の編集操作、注文書の送信・削除は `consumables.dispatch / can_edit` を使用する。

- マスタ画面の編集操作は `consumables.masters / can_edit` を使用する。
- 共通画面権限と、承認ルートで解決される作成者・確認者・承認者の判定を区別する。未処理承認タスクは応答の `my_pending_task_types` で画面表示へ連携する。
