## 1. 順番の比較と推奨

### 前提(確認済み・BOSS指示)

- 新PCは **2026年10月19日週ごろに納入予定**（正確な納入日は未確定）。PGへの切替日はBOSSが別途決める方針
- 現行の本番PC: メモリ8GB、ディスク228GB(空き57GB)。Docker Desktop + 共通MySQLコンテナ + バックエンド(gunicorn 3) + nginx
- 新PCの商品表示上の仕様: AMD Ryzen 5 5500、メモリ32GB DDR4-3200、NVMe SSD 1TB、Windows 11 Home、GPUなし（受入時の確認事項は§5）
- 分析実行は1件最大2GB。8GBではMySQLとPGの併走や分析実行に余裕がない

### 案

| | A: 現行PCで先にPG | B: 新PC入替を先、その後PG | C: 新PC入替と同時にPG |
|---|---|---|---|
| 概要 | 現行8GB機でMySQL→PGへ切替。その後PC入替 | 新PCへMySQLのまま移し、安定後にPGへ切替 | 新PCの初稼働と同時にPG版へ切替 |
| リスク | **高**。作業が2回(現行機で1回、PC入替で1回)。8GB機でPG移行リハ・pgloader・検証を行う負荷 | **低〜中**。変更を1つずつ検証できる。ただしPG切替は別工程となる | **高**。PC・OS・Docker基盤・DBエンジンの変更が同時で、不具合の切り分けができない |
| 戻し方 | PGで業務入力を開始する前は旧MySQLへ復帰。開始後は逆移行が必要 | PC入替: 新PCで業務入力する前は旧PCへ復帰。入力開始後は新PCの更新分を旧PCへ反映する手順が必要。PG切替後も同様に入力開始後の単純復帰は不可(§4-3) | 入力開始前は旧PCへ復帰。開始後は逆移行が必要で、原因がPC側かPG側かの切り分けも必要 |
| メモリ | **不足の恐れ**。切替の瞬間・移行中はMySQL+PG併存が必要になり得る(8GB) | 新PC上でMySQL+PG併存が可能(スペックは§5) | 新PC。併存の必要は少ないが、検証中の併走余裕は新PCのスペック次第 |
| 日程 | 現行機でのPG切替と新PC準備が重なる | 新PC到着後、MySQL移設とPG検証・切替を別工程にできる | 新PC受入・本番移設・PG切替が同時期に集中する |
| 分析実行の有効化 | PG移行後だが、8GB機では有効化の余裕なし | 新PC+PG切替後 | 新PC+PG稼働後 |

### 推奨: **B**

理由:
1. 変更を1つずつにでき、不具合の原因を切り分けられる。
2. 業務入力開始前の戻し先を保持できる。入力開始後は旧PC・旧MySQLを残すだけでは戻せないため、§4-3の条件に従う。
3. 8GB機でPG移行作業を行わずに済む。
4. 新PCの初回移設をMySQLのまま行うため、PG側の遅れがPC入替日程に影響しない。

代償: PGへの切替と分析実行の本番有効化は、新PC+MySQLの安定稼働確認後になる。

**C に切り替えてよい条件**: リハーサル(§2)で「突合の合格」「migrate/スキーマ作成方式の確定」「計算結果の一致」を満たし、新PCの納入・セットアップ日程に十分な余裕があること。満たさなければ B のまま。

A は、新PCの納入が大幅に遅れ、かつMySQL側に性能・安定性の緊急問題が出た場合のみ再検討する。

## 2. リハーサル環境の設計(開発PCまたは新PC)

### 2-1. 基本方針

- MySQL開発DBには**触れない**(コピー元として読み取りのみ)
- 本番の接続情報は一切入れない
- 名前に「wanoco」を使わない
- 新PCでは、**現行アプリ+MySQLを本番系、複製アプリ+PostgreSQLを検証系として併存**させる
- 併存期間中の正式データ（正本）はMySQLとし、MySQLとPGの両方で本番入力を受け付けない
- PG検証側は、本番メール・通知・定期処理・外部サービス更新などの副作用を停止する

### 2-1-1. 新PC上の併存構成

```text
利用者
  ↓
現行アプリ（本番） ──→ MySQL（正式データ・正本）

MySQLから検証用に複製
  ↓
複製アプリ（検証） ──→ PostgreSQL（検証データ）
```

- 現行アプリ+MySQLは、そのまま本番系として稼働させる
- 複製アプリ+PGは別フォルダ・別ポートで起動し、本番利用者へ公開しない
- MySQLからPGへのコピー後にMySQLへ追加・更新されたデータは、自動ではPGへ反映されない
- 検証中は必要に応じてPGを再作成・再コピーし、最終切替時は利用停止後に最終データを移す
- PG切替前に、件数・代表値・在庫・計画在庫・進度・主要業務フローを突合する

### 2-3. 起動前の安全チェック

- Windows側アプリからは `DB_HOST=127.0.0.1`・`DB_PORT=15432`、同一Dockerネットワーク内のアプリからは `DB_HOST=pm-pg-rehearsal`・`DB_PORT=5432` を使う。DB名・ユーザー・ENGINEを含め検証PGを指していることを確認する
- default以外の接続（`ai_reader` 等）、直接接続コード、外部サービス設定も確認し、本番IP(10.0.1.232)や本番MySQLへ接続しないこと
- `.env.pg_rehearsal` がgit管理対象外であること
- メール送信、アプリ内通知、FCM等のプッシュ通知、定期スケジュール、自動発注、CSV自動取込、外部API更新を検証側で停止していること
- 検証側のログ・media・共有フォルダが本番側と分離されていること
- 検証用URL・ポートが一般利用者へ案内されておらず、本番入力を受け付けないこと

### 2-4. データのコピー方法

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **P: スキーマ=Django migrate、データ=pgloader(data only)** | スキーマはDjangoがPGに作り、pgloaderでデータだけ流す | Djangoのスキーマと一致する | migrateが通らない恐れ(§3) |
| **Q: pgloader等でスキーマ込み** | MySQLからスキーマ・データ・対応するmigration履歴を移行 | 過去migrationの全再実行を回避できる。管理対象外テーブルも移行対象に含める | 型・制約・履歴の整合確認が必要。ビュー等は別途移植。履歴コピーや `--fake` だけでは整合性を保証できない |
| R: `dumpdata`/`loaddata` | アプリ層で移行 | スキーマ作成はDjango | 遅い。巨大テーブルに不向き。型の扱いに注意 |

**選択手順**: まず P の前提(migrate)を空のPGで試験(§3-1)し、結果で決める。pgloaderがWindowsで動かない場合は、WSL2内またはDockerイメージで実行する。方式の切替(P→Q→R)は、そのつどBOSSに報告して承認を得る。

初回試験でPの前提が成立しないことを確認したため、次の検証候補はQとする。具体的な移行対象・型変換・履歴の扱いを確定し、検証結果をもって採否を判断する（§3-2-2）。

コピー元のMySQLは、**新規作成するSELECT専用ユーザー**で読む。作業終了後にそのユーザーを削除する(MySQL側の権限変更にあたるため、**BOSS承認事項**)。

### 2-5. 突合の方法

1. **件数**: 全テーブルの `COUNT(*)` をMySQLとPGで比較する(管理対象外3テーブルを含む)
2. **代表値の抜き取り**: 主要テーブル(LineBacklog / LineDemand / LinePlan / Order / OrderLine / 在庫・進度関連)で、日付・数量・ステータスの列の合計、最小・最大、NULL件数を比較する。抜き取り行は、主キー指定で全列を比較する
3. **計算結果の一致**: 同一入力で、在庫・計画在庫・進度の再計算結果をMySQL版とPG版で比較する。差分が出たら、**まずDBの実データで原因を切り分ける**(CLAUDE.mdの不整合調査手順に従い、生成ロジックは最後)
4. **挙動差の個別確認**(下表)

| 差異 | 内容 | 確認方法 |
|---|---|---|
| 文字比較の大文字小文字 | MySQLは区別しない。PGは区別する | 製品コード・顧客コードなどの検索・JOINで結果件数を比較 |
| NULLの並び順 | MySQLはNULLが先、PGはNULLが後(昇順) | ORDER BY を使う画面・APIの出力順を比較 |
| 整数の割り算 | PGは切り捨て。在庫計算に影響する可能性 | 割り算を含むSQL・ORMの式を洗い出し、結果を比較 |
| 不正な日付(0000-00-00) | PGは保持できない | MySQL側での該当行の有無を件数で確認(確認用SQLは付録) |
| `tinyint(1)` → boolean | 型変換 | 真偽列の値の分布を比較 |
| JSON → jsonb | キーの順序・重複・空白が変わる | JSONFieldの読み書きと、JSON_VALUE系ビューの結果を比較 |

#### 移管モデル全体に関する問題(2026-10-16 全アプリ全面調査・完了)

旧 `orders` から `production`・`quality`・`shipping`・`ai` へ移したモデルは複数ある。`orders.0042_remove_migrated_models` では、DBを変更せずDjangoのモデル状態から旧所有を削除している(`SeparateDatabaseAndState`でDeleteModelをstateのみ適用、DB操作なし)。つまり**orders側は意図通りstateだけ掃除済みだが、移管先アプリの受け側で通常の`CreateModel`を使っているものは、空DBへの全履歴再実行で重複作成エラーになる**。

全app(accounts, ai, consumables, masters, notifications, orders, outsource, overtime, production, proposals, purchase, quality, shifts, shipping, system_settings)のmigrationsを対象に`db_table`の重複CreateModelを全面調査した結果、**実テーブル作成が2回以上あるdb_tableは合計12件**。purchase/notifications/proposals/consumables/outsource/overtime/shifts/system_settingsには`orders`への依存自体がなく、同種パターンは無い。

### 3-2-2. 対応方法：既存DBの移行と将来の空DB構築

次の候補は、現在のMySQLの実スキーマ・データ・`django_migrations` を整合した同一時点で取得し、PGへ変換する方式Qとする。採用・実行は未確定であり、承認後に検証する。初回試験の途中DBに追加投入せず、別の検証DBへ移行する。途中DBの削除・再作成が必要な場合は対象を明示して別途確認する。

方式Qの実行前に、対象テーブル一覧、型・既定値・制約の変換表、ビューの移植DDL、migrationごとの実オブジェクト／履歴対応表、シーケンス調整、投入・突合・再実行の具体的な手順を作成する。現時点では未作成であり、本節の方針だけを本番実行手順として使用しない。

1. コピー元MySQLの実テーブル、型、主キー・外部キー、一意制約、索引、ビュー、管理対象外テーブル、migration適用履歴を棚卸しする。
2. 対応するGitコミットとデータ取得日時を固定し、スキーマ・データ・履歴をPGへ移す。MySQL専用SQL、ビュー、DBロール等は個別にPG対応する。
3. PGの実スキーマがDjangoの期待する状態と一致することを確認する。`django_migrations` は実行記録であり、コピーしても型・制約・ビューを修復しない。PGで未作成のオブジェクトに対応する履歴を無条件に適用済み扱いにしない。
4. 件数・主キー・外部キー・制約・型・シーケンス・代表行を比較する。`migrate --plan` で想定外の未適用履歴がないこと、`makemigrations --check --dry-run` でモデルとmigration状態の想定外差分がないことを確認する。両コマンドだけでは実DBスキーマ一致を保証できないため、実DB比較も必須とする。
5. 同一データで在庫・計画在庫・進度・主要APIを比較し、追加登録も試してシーケンスの重複がないことを確認する。

`orders.0008` だけの場当たり的な `--fake`、対象テーブルの手動削除、既存MySQLの適用履歴の直接変更は採用しない。履歴調整が必要な場合は、対象migration・対応する実DDL・調整理由を明示して検証する。

将来の空DB構築には、現在の正しいアプリ所属を基準にしたbaseline（初期状態を定義するmigration）または履歴整理を別工程で検討する。旧履歴の単純削除や `squashmigrations` の実行だけで解決するとは扱わない。データmigrationの初期値、ビュー、管理対象外テーブル、アプリ間依存、既存PGを新履歴へ引き継ぐ方法まで設計し、空DB構築と既存DBからの更新を検証する。物理テーブル名は原則維持する。


4. MySQLとPGを**同じ取得時点のデータ**で比較する。開発MySQLを更新してもPGは自動同期されない。新しい本番データを取り込んだ場合は、PGも対応するデータへ更新してから再比較する。
5. 検証結果には取得時点を明記する。古い開発コピーの合格を、最新本番データの移行合格とは扱わない。

本番がPGへ切り替わった後は、本番PGから開発PGへバックアップを復元する運用に切り替える。旧MySQL開発系への逆変換は通常運用には含めず、保持期間終了まで比較資料として保管する。

### 4-1. PC入替(B案のステップ1、MySQLのまま)

1. 新PCにWSL2 + Docker Engineを構築(旧PCは稼働継続)
2. 本番のダンプを取得し、新PCのMySQLへ復元。件数突合。新PC側は検証用接続先・保存先を適用し、メール・通知・定期処理・外部更新を起動前に停止する（DB内設定も対象）

4. 切替: 旧PCのPMへの入力・定期処理・外部取込など全書き込み元を停止 → 最終整合バックアップを取得 → 新PCの検証データを最終データで置き換え → 突合。具体的な取得・復元コマンドと所要時間はリハーサルで確定する。未設計の「差分反映」で代用しない

6. **旧PC・旧MySQLを復旧用に保持する**。新PCで入力開始後は旧PCのデータが古くなるため、単純に旧PCを起動して戻してはならない(§4-3)。保持期間は§4-4

| migrateが通らない（初回確認済み） | 空DBを現行履歴だけでは構築できない | 案Y／方式Qを次の候補として検証。自動的に解決すると扱わず、採用・実行はBOSS承認 |

| 8GB機で分析実行 | メモリ不足 | 本番の分析実行は、新PC+PG後。それまで無効 |
| 本番MySQLと検証PGの同時入力 | データが分岐し、どちらが正本か判定できない | 併存中はMySQLのみを正本とし、PG検証側は本番入力を受け付けない |
| 検証側のメール・通知・定期処理 | 二重送信、二重発注、外部データ更新 | PC2移設前のMySQL検証側・PG検証側とも、副作用処理の停止と起動前チェックを必須化する |
| 新PCの商品仕様の矛盾 | 画面が映らない、想定構成と異なる | Ryzen 5 5500の表示用GPU、SSD、LAN、電源等を受入時に実機確認する |
| Windows 11 Homeの制約 | 標準RDPで遠隔接続先にできない | 遠隔保守方式を決め、必要ならPro化をBOSS判断とする |
| YOLO画像認識とOllama(ローカルLLM)が新PC(PC2)の同一GPU(RTX 3080、2026-10-20入荷)を共用する(マザーボード制約で大型カード不可) | 両者を同時稼働させた場合のVRAM不足・性能低下の可能性が未検証。RTX 5060 Ti 16GB以上を前提とした`社内AI・画像検査_詳細実装プラン.md`の要件も未達の可能性 | 実機でのYOLO単体・Ollama単体・同時稼働の性能検証を実装着手前に行う(**未実施**)。§5-1参照 |
