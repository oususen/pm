## 1. 順番の比較と推奨

### 前提(確認済み・BOSS指示)

- 本番PC入替は **2026年11月末ごろ**。PGへの切替はBOSSが決める方針
- 現行の本番PC: メモリ8GB、ディスク228GB(空き57GB)。Docker Desktop + 共通MySQLコンテナ + バックエンド(gunicorn 3) + nginx
- 分析実行は1件最大2GB。8GBではMySQLとPGの併走や分析実行に余裕がない

### 案

| | A: 現行PCで先にPG | B: 新PC入替を先、その後PG | C: 新PC入替と同時にPG |
|---|---|---|---|
| 概要 | 現行8GB機でMySQL→PGへ切替。その後PC入替 | 11月末に新PCへMySQLのまま移し、安定後にPGへ切替 | 11月末に新PC上でPG版を初稼働 |
| リスク | **高**。作業が2回(現行機で1回、PC入替で1回)。8GB機でPG移行リハ・pgloader・検証を行う負荷 | **低〜中**。変更が1つずつ。ただしPG切替が12月以降にずれる | **高**。PC・OS・Docker基盤・DBエンジンの変更が同時で、不具合の切り分けができない |
| 戻し方 | 旧MySQLのダンプを保持すれば戻せる。ただし切替後の入力データは戻せない(逆変換が必要) | PC入替: 旧PC・旧MySQLをそのまま残せば即戻せる。PG切替: 同様に新PC上のMySQLを残して戻せる | 旧PC・旧MySQLを残せば戻せる。ただし原因がPC側かPG側か判別できない |
| メモリ | **不足の恐れ**。切替の瞬間・移行中はMySQL+PG併存が必要になり得る(8GB) | 新PC上でMySQL+PG併存が可能(スペックは§5) | 新PC。併存の必要は少ないが、検証中の併走余裕は新PCのスペック次第 |
| 日程 | 10月中に現行機で切替→PC入替の準備が重なる | 11月末にPC入替、PG切替は12月〜年明けで余裕あり | 11月末に全部が集中。リハ完了が遅れると全体が遅れる |
| 分析実行の有効化 | PG移行後だが、8GB機では有効化の余裕なし | 新PC+PG切替後(12月以降) | 新PC+PG稼働後 |

### 推奨: **B**

理由:
1. 変更を1つずつにでき、不具合の原因を切り分けられる。
2. 戻し方が単純(旧PC・旧MySQLを残すだけ)。
3. 8GB機でPG移行作業を行わずに済む。
4. 11月末の期限を、PCの入替だけに絞れる。PG側の遅れが入替日程に影響しない。

代償: PGへの切替が12月以降になる。分析実行の本番有効化もその後になる。

**C に切り替えてよい条件**: リハーサル(§2)が11月上旬までに「突合の合格」「migrate/スキーマ作成方式の確定」「計算結果の一致」を満たし、新PCの納入・セットアップ日に余裕があること。満たさなければ B のまま。

A は、新PCの納入が大幅に遅れ、かつMySQL側に性能・安定性の緊急問題が出た場合のみ再検討する。

## 2. リハーサル環境の設計(開発PC)

### 2-1. 基本方針

- MySQL開発DBには**触れない**(コピー元として読み取りのみ)
- 本番の接続情報は一切入れない
- 名前に「wanoco」を使わない

### 2-2. 構成

| 項目 | 内容 |
|---|---|
| 基盤 | WSL2 Ubuntu-24.04 の Docker Engine(29.8.2、導入済み) |
| 置き場所 | `D:\pm_pg\`(リポジトリの外を推奨)。`.env` はコピーせず、専用 `.env.pg_rehearsal` を新規作成(`.gitignore` 対象) |
| compose プロジェクト名 | `pm_pg_rehearsal` |
| イメージ | `postgres:16`(固定。バージョンはv2に合わせる。**BOSS確認事項**) |
| ボリューム | `pm_pg_rehearsal_data`(名前付き) |
| ネットワーク | `pm_pg_rehearsal_net`(専用。`pm_internal` と `ts_pm_network_v2` には参加させない) |
| ポート | PG: `127.0.0.1:15432`(LAN非公開)。複製アプリ: バックエンド 18081 / フロント 18501 |
| DB・ロール | DB `pm_pg_rehearsal`。ロール `pm_pg_admin` / `pm_pg_ai_reader` / `pm_pg_ai_view_owner` |
| パスワード | 新規にランダム生成。既存 `.env`・本番の値は使わない |
| Redis | 6379(Memurai)を共用。複製側は **DB番号 `/1`** で分離。AI分析のlauncher(8091)は1つだけで同時1件のため、同時に分析を動かさない |

使用中のポート(確認済み): 3306(MySQL)、6379(Memurai)、8081、8501、8091。5432・15432は空き。

### 2-3. 起動前の安全チェック

- 複製側の `.env` の `DB_HOST` がコンテナ名またはループバックであり、3306・本番IP(10.0.1.232)でないこと
- `.env.pg_rehearsal` がgit管理対象外であること

### 2-4. データのコピー方法

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **P: スキーマ=Django migrate、データ=pgloader(data only)** | スキーマはDjangoがPGに作り、pgloaderでデータだけ流す | Djangoのスキーマと一致する | migrateが通らない恐れ(§3) |
| **Q: pgloaderでスキーマ込み** | MySQLからスキーマとデータを変換 | migrateに依存しない。管理対象外3テーブルも作られる | Djangoの制約・型とずれる恐れ。`migrate --fake` で履歴を合わせる必要(v2の手順3) |
| R: `dumpdata`/`loaddata` | アプリ層で移行 | スキーマ作成はDjango | 遅い。巨大テーブルに不向き。型の扱いに注意 |

**選択手順**: まず P の前提(migrate)を空のPGで試験(§3-1)し、結果で決める。pgloaderがWindowsで動かない場合は、WSL2内またはDockerイメージで実行する。方式の切替(P→Q→R)は、そのつどBOSSに報告して承認を得る。

コピー元のMySQLは、**新規作成するSELECT専用ユーザー**で読む。作業終了後にそのユーザーを削除する(MySQL側の権限変更にあたるため、**BOSS承認事項**)。

### 2-5. 突合の方法

1. **件数**: 全テーブルの `COUNT(*)` をMySQLとPGで比較する(管理対象外3テーブルを含む)
2. **代表値の抜き取り**: 主要テーブル(LineBacklog / LineDemand / LinePlan / Order / OrderLine / 在庫・進度関連)で、日付・数量・ステータスの列の合計、最小・最大、NULL件数を比較する。抜き取り行は、主キー指定で全列を比較する
3. **計算結果の一致**: 同一入力で、在庫・計画在庫・進度の再計算結果をMySQL版とPG版で比較する。差分が出たら、**まずDBの実データで原因を切り分ける**(CLAUDE.mdの不整合調査手順に従い、生成ロジックは最後)
4. **挙動差の個別確認**(下表)

| 差異 | 内容 | 確認方法 |
|---|---|---|
| 文字比較の大文字小文字 | MySQLは区別しない。PGは区別する | 製品コード・顧客コードなどの検索・JOINで結果件数を比較 |
| NULLの並び順 | MySQLはNULLが先、PGはNULLが後(昇順) | ORDER BY を使う画面・APIの出力順を比較 |
| 整数の割り算 | PGは切り捨て。在庫計算に影響する可能性 | 割り算を含むSQL・ORMの式を洗い出し、結果を比較 |
| 不正な日付(0000-00-00) | PGは保持できない | MySQL側での該当行の有無を件数で確認(確認用SQLは付録) |
| `tinyint(1)` → boolean | 型変換 | 真偽列の値の分布を比較 |
| JSON → jsonb | キーの順序・重複・空白が変わる | JSONFieldの読み書きと、JSON_VALUE系ビューの結果を比較 |

## 3. MySQL固有SQL・マイグレーションの対応方針

### 3-1. 調査済みの事実(読み取りで確認済み。数値は調査時点)

- マイグレーションにMySQL固有のSQLがある: **RunSQL 13箇所 / 9ファイル**、**JSON_VALUE系 12箇所 / 2ファイル**(AI用ビュー ai 0012〜0014を含む)
- `managed=False` のモデルが **3つ**あり、マイグレーションで作られないテーブルがある(以前、テストDB作成時に `t_scrap_record` が無くて失敗した)
- 生SQL: `cursor.execute` 24箇所 / 12ファイル、`.raw(` 7箇所 / 2ファイル、`FOR UPDATE` 1箇所。`ON DUPLICATE KEY`・`GROUP_CONCAT`・`IFNULL`・`DATE_FORMAT`系・`REPLACE INTO` は見つからなかった

**今回、私はこれらの数値を再確認していない**(依頼文からの転記)。着手時に再確認する。

### 3-2. 方針

| 段階 | 内容 | 承認 |
|---|---|---|
| S1 試験 | 空のPGへ複製側から `migrate` を**そのまま**実行し、落ちる箇所を記録のみする(コードは変更しない) | BOSS承認 |
| S2 方式決定 | 落ちた箇所の一覧をBOSSに報告し、**案X**(migrationを「MySQLの場合のみ実行」に分岐。複製側のコード変更)か**案Y**(pgloaderでスキーマ込み、§2-4のQ)かを決める | BOSS判断 |
| S3 修正 | 決定した案で修正。**現行 `pm/` は変更しない**。修正は複製側(別ブランチ、または `D:\pm_pg\` の複製) | BOSS承認 |
| S4 生SQL | 24+7+1箇所をPG互換に直す(バッククォート、`FOR UPDATE`、型・関数差など)。**フォールバック(MySQL/PG両対応の分岐の乱用)は、規約により事前同意なしに入れない** | 都度BOSS承認 |

### 3-3. 管理対象外テーブル3つ

- 3モデルのテーブル名と、DDLの取得元(実DBか、`予備資料/` のスキーマ定義か)を、**まず特定する**
- 取得元を確定できなければ、推測でDDLを作らず、BOSSへ報告する
- 案Xなら、DDLの取得元から複製側に作成手段を用意する。案Yなら、pgloaderが作る

### 3-4. AI分析層のPG対応(対応一覧は memory `project_ai_analysis_state` を正とする)

| 現行(MySQL) | PG |
|---|---|
| `mysql.connector.django`(ai_reader接続) | psycopg(要バージョン確認) |
| `analysis_execution_service.py` の `mysql.connector` 直接接続 | psycopg に置換 |
| `max_execution_time` / `lock_wait_timeout` | `statement_timeout` / `lock_timeout` |
| `CONSISTENT SNAPSHOT` | `REPEATABLE READ READ ONLY` |
| バッククォート | 二重引用符 |
| 中止 | cancel(`pg_cancel_backend` 等)が可能 |
| ai_reader の ENGINE(`settings.py`)、`AI_DB_*` 環境変数 | PG用に作り直し |
| migrations 0012〜0014 の JSON_VALUE ビュー | `->>` 等で書き直し(jsonb対応) |
| ビュー定義者 `pm_ai_view_owner` | ビュー所有者+GRANTで作り直し |

AI分析の**本番実行は、PC入替+PG移行+AI層移植の後**に有効化する(それまで無効)。

## 4. 本番切替の手順書(骨子)

> 骨子のみ。数値(停止時間・件数・容量)は、リハーサルと会社での確認の後に確定する。**ここには推測の数値を書かない**。

### 4-1. PC入替(B案のステップ1、MySQLのまま)

1. 新PCにWSL2 + Docker Engineを構築(旧PCは稼働継続)
2. 本番のダンプを取得し、新PCのMySQLへ復元。件数突合
3. 新PCでアプリを起動し、IP(10.0.1.232)・証明書(`pm-ui/certs/pm-prod.crt`)の扱いを確認(§6)
4. 切替: 旧PCを停止 → 最終差分を反映 → IPを新PCへ → 動作確認
5. **旧PC・旧MySQLは停止状態で残す**(戻し先)。残す期間は§4-4

### 4-2. PG切替(B案のステップ2)

v2のPHASE 6を基に、次の順で行う。

| 手順 | 内容 |
|---|---|
| 0 | 事前: 切替直前の全体バックアップ(mysqldump)を取得し、リストアできることを確認 |
| 1 | 利用停止の通知。MySQLを読み取り専用にし、データを確定 |
| 2 | 方式P/Qに従ってPGへ移行(§2-4) |
| 3 | 件数・代表値・計算結果の突合(§2-5) |
| 4 | `migrate --fake` で履歴を同期(方式Qの場合)、シーケンスの `setval` |
| 5 | アプリをPG設定で起動。主要業務フローの確認 |
| 6 | 切替完了の通知。分析実行の有効化は別途(§3-4の完了後) |

### 4-3. 戻す条件(案)

- 突合で重大な不一致(件数不一致、計算結果の不一致)が解消できない
- 主要業務フロー(受注展開、ガント、在庫・進度)が動かない
- 切替後の運用開始までに、一定時間内に原因を特定できない(**時間はBOSSが決める**)

戻し方: アプリの接続先をMySQLに戻す。PG稼働中に入力されたデータは、MySQLに反映されない。そのため、**運用開始前に戻すのが原則**で、運用開始後の戻しは、データ逆変換の手順を別途用意する必要がある(未設計)。

### 4-4. 旧PC・MySQLを残す期間

- **未決定(BOSS判断)**。目安として、PG切替後に1か月の月次処理を一巡するまでを提案する

### 4-5. 停止時間

- **未確定**。DBの容量(§6の確認項目)と、pgloaderの所要時間(リハーサルで測定)から算出する。リハーサルの実測値が出てから決める

## 6. 会社で確認する項目(来週)

| # | 項目 | 方法 | 目的 |
|---|---|---|---|
| 1 | コンテナのメモリ使用量 | `docker stats --no-stream` を、業務時間帯の複数回で取得 | §5の積み上げ |
| 2 | Docker Desktopのメモリ設定 | Docker Desktop の設定画面、または `%UserProfile%\.wslconfig` | §5・WSL上限の方針 |
| 3 | MySQLのDB容量 | 下記SQL | 停止時間・ディスク |
| 4 | 共通MySQLを他システムが使っているか | MySQL上の接続元・DB一覧の確認(下記SQL)。他システム側の担当への確認 | **使っていればMySQLを止められない/PG切替の影響範囲** |
| 5 | バックアップの現状 | 頻度・保存先・世代・リストア実績の有無 | §4の戻し条件 |
| 6 | モバイル(PWA)・他システム連携 | PWAの接続先、外部連携(CSV取込、API、メール、FCM等)の洗い出し | 切替の影響範囲 |
| 7 | 証明書・IP(10.0.1.232)の扱い | 証明書の有効期限、新PCへの引き継ぎ方法、IPの付け替え手順 | §4-1 |

確認用SQL(MySQL、読み取りのみ):

```sql
-- DB別容量(GB)とテーブル数
SELECT table_schema,
       ROUND(SUM(data_length + index_length) / 1024 / 1024 / 1024, 2) AS gb,
       COUNT(*) AS tables
FROM information_schema.tables
GROUP BY table_schema;

-- テーブル別容量の上位(巨大テーブルの特定)
SELECT table_name, table_rows,
       ROUND((data_length + index_length) / 1024 / 1024, 1) AS mb
FROM information_schema.tables
WHERE table_schema = 'pm_db'
ORDER BY (data_length + index_length) DESC
LIMIT 30;

-- 他システムの利用状況(接続中のユーザー・接続元・DB)
SELECT user, host, db, COUNT(*) AS conns
FROM information_schema.processlist
GROUP BY user, host, db;

-- 共通MySQL上のDB一覧とアカウント
SHOW DATABASES;
SELECT user, host FROM mysql.user;

-- 不正な日付(0000-00-00)の有無: 日付列ごとに実行(列・表名は要確認)
-- SELECT COUNT(*) FROM <表> WHERE <列> = '0000-00-00';
```

注: `processlist` は実行時点の接続のみ。他システムの利用有無は、数日間の取得または担当者への確認が必要。

## 8. リスクと、間に合わない場合の代案

| リスク | 影響 | 対応・代案 |
|---|---|---|
| migrateが通らない | スキーマ作成が遅れる | 案Y(pgloaderでスキーマ込み)へ切替。BOSS承認 |
| 管理対象外テーブルのDDL取得元が不明 | PGに作れない | 実DBから取得。確定できなければBOSSへ報告 |
| 挙動差(大文字小文字、整数割り算、NULL順) | 在庫・進度の数値ずれ | 突合で検出。ずれた箇所を実データで切り分けてから修正 |
| リハーサルの遅れ | 11月末に間に合わない | **B案ならPC入替に影響しない**。PG切替を12月以降に延期 |
| 新PCの納入が遅れる | 入替の遅れ | 旧PCでMySQL継続。PGは新PC後 |
| 共通MySQLを他システムが使用 | MySQLを止められない/PG化の影響 | §6-4で確認。使用していれば、PM専用のDBを分離して移行する案を別途提案 |
| PG切替後の戻し(データ逆変換) | 運用開始後の戻しが困難 | 運用開始前に戻す原則(§4-3)。逆変換の手順は別途用意 |
| 8GB機で分析実行 | メモリ不足 | 本番の分析実行は、新PC+PG後。それまで無効 |
| 本書の数値の多くが未確認 | 計画の精度 | §6の実測後に、本書を改訂する |
