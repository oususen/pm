# クボタ堺出荷便計画 仕様書

## 概要

クボタ堺向け出荷の納期調整・便割付・前工程需要日反映を行う機能。

### 背景

- クボタ堺向け製品は**内示と確定の乖離**が大きく、内示ベースで前工程を動かすとムダ/欠品リスクが高い
- 便ごとの積載制約（荷台サイズ）を考慮した割付が必要
- 便の出発日から逆算して**前工程の需要日**を決定する仕組みが必要（フロア配送の考え方を前工程にも適用）

### スコープ

- **対象**: クボタ**堺向け**のみ（`customer_code='000196'` かつ `ship_to_code='ZGHC'` かつ `status='OPEN'` の受注。`order_type` は FIRM / FORECAST 両方を対象）
- **積載計算精度**: 面積占有率方式（厳密な3D bin packingは行わない）
- **振り分け方式**: 業務員が**手動**で便選択（自動アルゴリズムなし）

## 業務フロー

```
①取込【営業担当】
   「取込」ボタンで ORDER_LINE → t_kubota_sakai_due_adjustment へ差分更新
   - 確定と内示が同日に共存していても、行は統合せず両方保持
   - 既存の delivery_qty は保持
     ↓
②納期調整【営業担当】
   - 納入数を入力して保存
   - 残量 = 累積(納入) - 累積(受注) をリアルタイム確認
     ↓
③便割付【業務/物流担当】
   - 調整後納期をもとに便を選択
   - 積載占有率を見ながら手動で便に割付
   - 分割積載可
     ↓
④前工程需要日反映
   便出発日 → クボタ配送ラインの LineBacklog 同期
   → 既存 pickup カスケードにより前工程ラインへ伝播
```

①②は同一画面（納期調整画面2）で実施。③は便計画画面で別ステップ。

### 2. KubotaSakaiDueAdjustment（納期調整・BACKLOG型）

配置: [pm_backend/apps/orders/core/models.py](../pm_backend/apps/orders/core/models.py)
DBテーブル: `t_kubota_sakai_due_adjustment`

**設計思想**: 生産計画の `LineBacklog` と同様の自立型テーブル。`ORDER_LINE` を直接参照せず、「取込」操作で受注データをスナップショットとして保持する。1行 = 品番 + 納入場所 + 注番 + 日付 の組み合わせ。

| フィールド | 型 | 用途 |
|---|---|---|
| product_code | varchar(50) | 品番 |
| ship_to_code | varchar(40), null可 | 納入場所コード |
| source_order_no | varchar(50), null可 | 注番（確定のみ。内示はNULL） |
| order_type | choice(FIRM/FORECAST) | 受注タイプ |
| due_date | date | 日付 |
| demand_qty | decimal(14,3) | 受注数（取込時にORDER_LINEから読み込み） |
| delivery_qty | decimal(14,3) | 納入数（画面で入力・保存） |
| remaining_qty | decimal(14,3) | 残量（保存時にサーバ再計算） |
| order_line | FK(OrderLine), null可 | 取込元の受注明細（参照用） |
| updated_by | FK(User, SET_NULL) | 更新者 |
| updated_at | datetime, null可 | 更新日時 |
| created_at | datetime(auto) | 作成日時 |

**制約**:
- `unique_together = [('product_code', 'ship_to_code', 'source_order_no', 'due_date')]`
- テーブルは初期状態で空。「取込」操作で ORDER_LINE からデータを投入する
- `source_order_no` は FIRM のみ設定。FORECAST は `NULL`
- `remaining_qty` は画面入力値を使わず、保存時にサーバ側で再計算して保存

**取込ルール（import_orders）**:
- 表示期間内のクボタ堺 `ORDER_LINE`（`customer_code='000196'`, `status='OPEN'`）を全品番対象で読み込み
- 品番 + 納入場所 + 注番 + 日付 でグルーピングし、`demand_qty` を合算
- **確定優先（需要集計）**: 同日・同品番・同納入場所で確定(FIRM)がある場合、内示(FORECAST)は `demand_qty` 集計対象から除外する（ダブル受注計上防止）
- **差分更新**: 既存の `delivery_qty` は保持したまま、`demand_qty` と `order_type` のみ更新
  - 新規注番の確定 → INSERT
  - 変更された内示数量 → `demand_qty` を UPDATE
  - 新規納入場所 → INSERT
- **内示→確定の遷移**: 同日・同品番・同納入場所で「需要として存在していた内示行（`demand_qty>0`）」が取込対象から消えた場合のみ、入力済み `delivery_qty` を確定行へ引き継いで内示行を削除する
- **受注消滅時の扱い**: 今回の取込結果に存在しない `FORECAST` 行は削除せず、`demand_qty=0` に更新して `delivery_qty` を保持する。`FIRM` 行は `delivery_qty=0` の未入力行のみ削除する

**remaining_qty 再計算ルール（保存時）**:
- 計算キー: `product_code + ship_to_code`（**注番をまたいで合算**）
- 日付昇順で全注番の `demand_qty` / `delivery_qty` を合算し累積
- `remaining(d) = remaining(d-1) + Σdelivery(d) - Σdemand(d)`
- 符号: 納入不足ならマイナス、過剰ならプラス
- 画面表示時、表示開始日より前のデータから「繰越残量」(`carry_remaining`)を算出し、一番上の行に表示

## 積載計算ロジック

配置: [pm_backend/apps/shipping/services/truck_load_calculator.py](../pm_backend/apps/shipping/services/truck_load_calculator.py)

```
トラック床面積 = truck.width × truck.depth
容器床面積 = container.width × container.depth
段数 = stackable ? min(truck.height // container.height, container.max_stack) : 1
実効床面積 = 容器床面積 / 段数
容器数 = ceil(qty / container.capacity)
占有率 = Σ(実効床面積 × 容器数) / トラック床面積
重量 = Σ(unit_weight × qty) ここで unit_weight = 比重 × 長さ × 幅 × 厚さ / 1,000,000
```

**エラー条件**:
- 占有率 > 100%
- 重量 > `truck.max_weight`
- **混載不可容器** を含みつつ複数品番が同一便にある → `mixed_blocked=True`

**戻り値**: `{occupancy_ratio, occupancy_percent, total_weight, mixed_blocked, errors[]}`

## API

### 便マスタ CRUD
- `GET/POST/PUT/DELETE /api/kubota-sakai-trucks/`

### 納期調整

- `POST /api/kubota-sakai-due-adjustments/import_orders/` — 受注取込（ORDER_LINEからの差分更新）
  - 入力: `{start_date, horizon_days}`
  - 処理: 表示期間内のクボタ堺ORDER_LINEを全品番対象で読み込み、テーブルへ差分更新
  - 戻り: `{created, updated, deleted_forecast, total_demand_rows}`

- `GET /api/kubota-sakai-due-adjustments/grid/` — テーブルからグリッドデータ取得
  - クエリ: `start_date`, `horizon_days`
  - 戻り: `{start_date, end_date, horizon_days, rows: [{group_key, product_code, ship_to_code, carry_remaining, lines: [{line_key, source_order_no, order_type, demand_by_date, delivery_by_date}]}]}`
  - `carry_remaining`: 表示開始日より前の累積残量（品番+納入場所単位、全注番合算）

- `POST /api/kubota-sakai-due-adjustments/bulk_save/` — 納入数保存
  - 入力: `{rows: [{line_key, delivery_by_date: {日付: 数量}}], change_reason?}`
  - `line_key` = `"product_code||ship_to_code||source_order_no"`
  - `change_reason` 指定時のみ、計画入力ロック日（`lock_days.kubota_sakai_due_plan`）以前の更新を許可
  - `lock_date.kubota_sakai_due`（締め日）は `change_reason` 指定時でも更新不可
  - `change_reason` 指定時は `production_plan_change_log` に変更履歴を保存
    - `line`: 「クボタ納期調整」固定
    - `process`: 「クボタ納期調整」固定
  - 保存後、品番+納入場所単位で `remaining_qty` を再計算してDB保存

### 便割付
- `GET /api/kubota-sakai-trip-assignments/grid/` — 指定日の割付状況取得
  - クエリ: `target_date`, `keyword`
  - データソース: `KubotaSakaiDueAdjustment` (`delivery_qty > 0` の行のみ)
  - 戻り: `{target_date, assignment_deadline_days, rows, trucks, truck_summaries}`
  - rows の各行: `{due_adjustment_id, due_date, product_code, product_name, ship_to_code, source_order_no, order_type, delivery_qty, assigned_qty, unassigned_qty, ...}`
- `POST /api/kubota-sakai-trip-assignments/bulk_save/` — 指定日の割付をまとめ保存
  - 入力: `{target_date, rows: [{due_adjustment_id, allocations: [{truck_id, qty}]}]}`
  - バリデーション: `Σ(qty) ≤ DueAdjustment.delivery_qty`
  - 保存後、`_sync_kubota_delivery_backlog_for_date` で `LineBacklog` へ同期（LinePlan不使用）
- `GET /api/kubota-sakai-trip-assignments/pickup-detail-pdf/` — 集荷明細表PDF（出発日別）
  - クエリ: `start_date`, `end_date`
  - 出力: PDF（`application/pdf`）
  - 明細列: `品番 / 品名 / 容器数 / 数量`
  - `容器数` は `ceil(数量 / capacity)` の整数で表示
  - 出発日判定:
    - `arrival_day_offset = 0` → 出発日 = 調整後納期
    - `arrival_day_offset >= 1` → 出発日 = 調整後納期から `offset` 営業日さかのぼり
    - 営業日判定は `kubota_sakai` カレンダ（未登録日は平日判定）を使用
- `GET /api/kubota-sakai-trip-assignments/display-settings/` — 便計画の表示順・色設定取得
  - 戻り: `{rows: [{product_code, ship_to_code, display_order, bg_color, text_color, plus_bg_color, plus_text_color}]}`
- `POST /api/kubota-sakai-trip-assignments/display-settings/` — 便計画の表示順・色設定一括保存
  - 入力: `{rows: [{product_code, ship_to_code, display_order, bg_color, text_color, plus_bg_color, plus_text_color}]}`
  - 生産計画とは独立し、便計画専用設定として保存する

### 共通出荷実行（新UI）

- `GET /api/shipping-trips/execution/` — 便確認（実行）画面用の便一覧・積み荷明細取得
  - クエリ: `departure_date`(必須), `business_type`(任意)
  - 戻り: `summary`（未着手/積込完了/出発済 件数）, `trips[]`（便ヘッダ + 明細）
- `POST /api/shipping-trips/execution/` — 便ステータス更新
  - 入力: `{trip_id, action}`
  - `action`:
    - `mark_loading`（積込完了）
    - `mark_departed`（出発、初回のみ実出発時刻を記録）
    - `reopen`（差戻し）
    - `register_actual`（便明細ごとの出荷実績登録）
      - 追加入力: `shipment_date`, `actuals: [{allocation_id, quantity}]`
      - `quantity<=0` は対象明細の便由来実績を削除
- `GET /api/shipping-trips/progress/` — 便進捗確認画面用の期間進捗取得
  - クエリ: `date_from`, `date_to`（必須）, `business_type`（任意）
  - 戻り: `daily_summary[]`, `trips[]`
  - クボタ堺の `arrival_day_offset >= 1` 便は、`departure_date` ではなく「実出発日（到着日から営業日で offset 日戻した日）」で期間判定・日別集計・一覧表示する
  - 同一論理便は `actual_departure_date + business_type + trip_ref` 単位で1行に統合する

すべて `customer_code='000196'` かつ `order_no` に `SAKAI` を含む `order_type='FIRM'` `status='OPEN'` で絞り込み。

**レイアウト**:
```
┌──────────────────────────────────────────────────────────────┐
│ 開始日:[4/17] 期間:[30日] 品番OR検索:[V0][6E] [取込][保存][表示] │
├──────────────────────────────────────────────────────────────┤
│         │ V053103705  ZGHC     │ V053143615  5476     │
│  日付   │ 注番  受注 納入 残量 │ 注番  受注 納入 残量 │
├──────────────────────────────────────────────────────────────┤
│  繰越   │                   0  │                  -48 │
│ 4/17金  │ 450.. 9  [9]     -9  │ 450.. 33 [33]   -81 │
│ 4/20月  │ 450.. 9  [ ]      0  │ 450.. 33 [ ]      0 │
│  ...    │                      │                      │
│  総残   │               -xxx   │               -xxx   │
└──────────────────────────────────────────────────────────────┘
```

**サブ列（1日付あたり）**:

| サブ列 | 意味 | 編集可否 |
|---|---|---|
| 注番 | 確定の注番 or「内示」 | 読取専用 |
| 受注 | 取込済みの `demand_qty` | 読取専用 |
| 納入 | `delivery_qty`（ユーザー入力） | 編集可 |
| 残量 | 品番+納入場所の全注番合算の累積残量 | 読取専用（リアルタイム計算） |

**操作フロー**:

1. **取込**: ORDER_LINEから表示期間の受注を差分更新でテーブルに取り込み（全品番対象）
2. **表示**: テーブルから読み込み表示（ORDER_LINE直接参照なし）
3. **納入数入力**: 納入列に数量を入力。Enterキーで下の行に移動
4. **保存**: `delivery_qty` をDB保存 + `remaining_qty` を品番+納入場所単位で再計算

**残量計算**:
- 計算単位: 品番+納入場所（注番をまたいで合算）
- `本日残量 = 前日残量 + 本日納入 - 本日受注`
- 符号: 納入不足ならマイナス、過剰ならプラス
- 繰越行: 表示開始日より前の累積残量を一番上に表示
- 画面上でリアルタイム計算（入力するたびに即座に反映）

**品番フィルター**:
- キーワード1・キーワード2のOR検索（部分一致）
- フィルターは表示の絞り込み用。取込対象には影響しない（取込は常に全品番）

## 前工程需要日反映ロジック

### 運用方針

- `LineDemand` は顧客確定/内示の元データとして保持し、**便割付結果で更新しない**
- 便割付結果は `LineBacklog` の **クボタ配送ライン**（`sequence_no > 0` の plan 行）へ反映する
- **LinePlan / LineGanttPlan は不使用**。LineBacklog のみ直接保存
- 進度・在庫計算は既存の共通ロジックをそのまま使用
- 前工程需要日は、便の `arrival_day_offset` に基づいて pickup カスケードが自動算出する

### 同期処理

配置: [pm_backend/apps/shipping/views_kubota_sakai_trip_assignment.py](../pm_backend/apps/shipping/views_kubota_sakai_trip_assignment.py) の `_sync_kubota_delivery_backlog_for_date`

**トリガー**: `POST /api/kubota-sakai-trip-assignments/bulk_save/` 実行時、積載検証OK後に同期

**処理内容**:

1. クボタ配送ライン/工程を解決（`line_code='L3102'` またはプロセス名に「クボタ配送」を含む、無ければ `KUBOTA_DELIVERY` で自動生成）
2. 対象日の `LineBacklog` 既存 plan 行（`sequence_no > 0`）を全削除
3. 対象日の `KubotaSakaiTripAssignment` をループし、1割付 = 1 LineBacklog plan 行として作成
   - `plan_date = 出発日`
   - `sequence_no = 品番ごとの連番`
   - `plan_qty = 割付数量`（整数丸め）
   - `plan_id = KBT_T{truck_id}_{product_code}_{YYYYMMDD}_{seq}`（便識別用）
   - `order_qty = 0`, `demand_qty_plan = 0`

### 前工程リードタイム（便ベース）

フロア配送が `sequence_no` で AM/PM 便を区別するのと同パターンで、クボタ配送ラインでは **`plan_id` に埋め込んだ `truck_id`** から便の `arrival_day_offset` を参照して LT を決定する。

| arrival_day_offset | 便の動き | 前工程 LT | 理由 |
|---|---|---|---|
| 0 | 当日朝出発→当日着 | **1営業日前** | 当日に準備すれば間に合う |
| 1 | 前日夕出発→翌日着 | **2営業日前** | 前日に準備が必要 |

計算式: `effective_lt = 1 + arrival_day_offset`

**注意**: フロア配送とは逆の考え方。フロア配送は「朝着=受け取り側の視点（LT=2）」、クボタ配送は「朝発=出す側の視点（LT=1）」。

pickup カスケードでの判定（[pm_backend/apps/production/views.py](../pm_backend/apps/production/views.py)）:

1. `_is_kubota_delivery_line()` でクボタ配送ラインを識別
2. `plan_id` のプレフィックス `KBT_T{truck_id}` から `truck_id` を抽出
3. `KubotaSakaiTruck.arrival_day_offset` を参照して `effective_lt = 1 + offset`
4. `shift_business_days(plan_date, effective_lt)` で前工程需要日を算出

### `LineBacklog_sequence_no` 規約

- `sequence_no = 0`: 需要専用行。`plan_qty = 0` 必須
- `sequence_no > 0`: 計画値専用行。実績値は入れない

詳細は [LineBacklog_sequence_no仕様.md](LineBacklog_sequence_no仕様.md) 参照。

## 統合付録（旧: クボタ堺納期調整_依頼書）

本節は `クボタ堺納期調整_依頼書.md` の要件を本仕様へ統合したもの。

### 目的

- クボタ堺の納期調整を「元受注を保持したバックログ」として運用し、調整後の納期・数量がどの注番/納入場所由来か追跡できるようにする。

### 前提

- 専用テーブル: `t_kubota_sakai_due_adjustment` を使用する
- `LineDemand` は更新しない
- `remaining_qty` は保存する（画面入力値は採用しない）

### テーブル要件（補足）

- `order_line FK` は追跡用として保持する
- 分割保存時も同一受注明細起点の調整行は同じ `order_line_id` を持つ
- `source_*` は表示/監査用スナップショット列として保持する
- 複数 `order_line` を1レコードへ集約しない（集約はUI/API側で実施）

### 保存ロジック要件（補足）

- 元データは `OrderLine` から読取（納期/数量/納入場所/注番）
- `remaining_qty` はサーバ側で時系列再計算して保存
- 一括入力（→）/手入力/保存API のいずれでもロック対象日は更新しない（計画変更理由付き解除時を除く）

### API要件（補足）

- `GET /api/kubota-sakai-due-adjustments/grid/` は `ship_to_code`, `source_order_no` を返却
- `POST /api/kubota-sakai-due-adjustments/bulk_save/` は入力の `remaining_qty` を受け付けず、保存後にDB再計算する

### 受入条件（統合）

1. FIRM は注番あり、FORECAST は注番 NULL で保存される
2. 納入場所別に調整できる
3. 再表示しても `remaining_qty` がぶれない（DB保存値）
4. 調整後データから注番追跡ができる
