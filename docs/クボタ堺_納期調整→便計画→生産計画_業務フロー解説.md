# クボタ堺 納期調整 → 便計画 → 生産計画 業務フロー解説

## 1. なぜ納期調整が必要か

クボタからの受注（内示・確定）は「この日にこれだけ欲しい」という顧客要求だが、
そのまま出荷計画には使えない。以下の理由から、**受注数（demand_qty）と実際に納入する数（delivery_qty）の間にギャップ**が生じるためである。

### 1-1. 受注数 ≠ 納入数になるケース

| 要因 | 説明 |
|---|---|
| 生産能力の制約 | 1日の要求数を全量生産できない場合、一部を前倒し・後ろ倒しで調整する |
| 在庫状況 | 手持ち在庫で当日分を賄えるか、足りなければ分割納入にするか判断が必要 |
| トラック積載制限 | 便の容量・重量に物理的な上限があり、全量を1便で送れない場合がある |

### 1-2. 内示→確定の変動吸収

クボタからはまず**内示（FORECAST）**が届き、後から**確定（FIRM）**に切り替わる。
確定時に数量や日付が変わることがあるため、その差分を管理する仕組みが必要になる。

- 納期調整テーブル（`t_kubota_sakai_due_adjustment`）で内示・確定を両方保持
- 確定が存在する日は確定を優先して需要集計
- 内示→確定への遷移時は既存の `delivery_qty` を引き継ぎ、旧内示行を削除

### 1-3. 残量（remaining_qty）の管理

受注数の累計に対して「まだ納入していない残り」をシステムが自動計算する。

```
残量 = 累積(受注数) − 累積(納入数)
```

これにより以下を把握できる：

- **残量 > 0** → 未納入分がある（納入漏れの可能性）
- **残量 < 0** → 前倒し納入している（先行出荷済み）
- **残量 = 0** → 受注と納入が一致

### 1-4. まとめ

納期調整は、**顧客の要求（いつ・いくつ欲しい）と自社の制約（作れる量・積める量）のギャップを人が判断して埋める工程**である。この工程がないと、便計画に渡す数量が決まらない。

```
顧客要求 (demand_qty)
    ↓  営業担当が判断・入力
納入数 (delivery_qty)  ← これが便計画の入力になる
    ↓
残量 (remaining_qty)   ← システムが自動計算（納入漏れ/前倒しの把握）
```
