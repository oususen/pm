# クボタ堺 納期調整 → 便計画 → 生産計画 業務フロー解説

## 1. なぜ納期調整が必要か

クボタからの受注（内示・確定）は「この日にこれだけ欲しい」という顧客要求だが、
そのまま出荷計画には使えない。以下の理由から、**受注数（demand_qty）と実際に納入する数（delivery_qty）の間にギャップ**が生じるためである。

### 1-1. 受注数 ≠ 納入数になるケース

| 要因 | 説明 |
|---|---|
| 生産能力の制約 | 1日の要求数を全量生産できない場合、一部を前倒し・後ろ倒しで調整する |
| 在庫状況 | 手持ち在庫で当日分を賄えるか、足りなければ分割納入にするか判断が必要 |
| トラック積載制限 | 便の容量・重量に物理的な上限があり、全量を1便で送れない場合がある |

### 1-2. 内示→確定の変動吸収

クボタからはまず**内示（FORECAST）**が届き、後から**確定（FIRM）**に切り替わる。
確定時に数量や日付が変わることがあるため、その差分を管理する仕組みが必要になる。

- 納期調整テーブル（`t_kubota_sakai_due_adjustment`）で内示・確定を両方保持
- 確定が存在する日は確定を優先して需要集計
- 内示→確定への遷移時は既存の `delivery_qty` を引き継ぎ、旧内示行を削除

### 1-3. 残量（remaining_qty）の管理

受注数の累計に対して「まだ納入していない残り」をシステムが自動計算する。

```
残量 = 累積(納入数) − 累積(受注数)
```

これにより以下を把握できる：

- **残量 > 0** → 先行分がある（前倒し納入済み）
- **残量 < 0** → 未納入分がある（納入遅れ）
- **残量 = 0** → 受注と納入が一致

### 1-4. クボタ堺特有の事情 — なぜ営業が担当しているか

**現状の運用**: 営業担当が週1回（火曜日）に納期調整を実施。

一般的な製造業では、納期調整は生産管理部門（生管）が担当する業務である。
判断に必要な情報（生産能力・在庫状況・積載制限）はすべて生産・物流側にあり、
調整結果が便計画→生産計画に直結するためである。

しかしクボタ堺については、**顧客側の注文が不規則**であるため営業が担当している。

| クボタの注文パターン | 問題 |
|---|---|
| まとめ注文 | 2日分を1日にまとめて発注してくる → 日別に振り分ける必要がある |
| 追加注文 | 急に翌日・当日納入を要求してくる → 在庫・生産で対応可能か即判断が必要 |
| 内示と確定の乖離が大きい | 内示の数量・日付が確定で大きく変わる → 差分を見て納入数を再調整 |

営業がこの業務を担う合理性は、**顧客の注文パターンや事情を把握しているのは営業**だという点にある。
生管では顧客側の注文変動の背景（なぜまとめて発注してきたか、追加注文の理由は何か）を判断できない。

つまり納期調整の本質は、**「顧客の不規則な注文を社内の生産・出荷に合わせて正常化する工程」** である。

### 1-5. 生産トラブル時の対応 — なぜ分業できないか

生産側のミス（例: 前工程の加工漏れで当日9台不足）が発生した場合でも、納期調整は営業が行う。

一見すると「生産のミスは生産側が調整すべき」だが、実際には分業できない理由がある。

- **「今日9台減らす」は生産でもできる** — 当日の不足は事実として明らか
- **「その9台をいつ届けるか」は営業でないと判断できない** — クボタの今後の注文予定、いつまでに必要としているか、残量でカバーできるかは営業が把握している

ただし生産にとっても判断はそんなに難しくない。

**営業は基本的に前倒しで納期調整している**ため、常に先行納入済み（残量がマイナスでない）状態を維持している。
生産トラブルで一時的に不足しても、前倒し分の「貯金」で吸収できる。

```
通常時:   残量 = +20（20台分 先行納入済み）
トラブル: 9台不足 → 残量 = +11（まだ11台の貯金 → 問題なし）
危険:     残量 < 0 → 納入遅れ → 顧客に迷惑がかかる
```

営業の判断基準はシンプルで、**「残量がプラスを維持しているか（＝納入遅れが発生していないか）」** だけである。

### 1-6. 生産トラブル時の連絡義務

生産トラブルにより納入数が変わる場合、**関係者へメールで連絡**しなければならない。
連絡なしに納入数を変更することは許されない。

**連絡責任は原因工程と最終工程の両方にある。**

- **原因工程（例: プレス）** — ミスの発生元として最も責任が大きい。自工程のミスが後工程・納入に影響を与えることを認識し、速やかに関係者へ連絡する義務がある
- **最終工程（マテハン1）** — 自分のミスでなくても、納入数を満たせない事実を把握した時点で関係者へ連絡する義務がある

| 連絡先 | 内容 |
|---|---|
| 営業 | 不足数と理由の報告。顧客への説明が必要かを判断してもらう |
| 便計画担当 | 積載数が変わるため、便割付の変更が必要か確認 |
| クボタ（顧客） | 納入数減の連絡（営業経由） |

### 1-7. あるべき姿 — 各担当の責任分担

現状は営業が納期調整を一括で担当しているが、本来は以下の責任分担で運用すべきである。

| 担当 | 責任 |
|---|---|
| **営業** | 顧客窓口、追加注文の受付・連絡、容器確保、顧客のまとめ注文をなくす交渉 |
| **生産側** | 納期調整（delivery_qtyの決定）。目標は**納入遅れなし**、かつ**できるだけ前倒し生産なし**（前倒しは調達に負担がかかる） |
| **原因工程（例: プレス）** | トラブル発生時の即時メール連絡。原因を作った工程として**最も責任が大きい** |
| **最終工程（マテハン1）** | 納入数不足発生時のメール連絡。**原因が自分のミスでなくても**連絡義務がある |
| **便計画担当** | 便割付、積載確認 |

#### 営業の役割の変化

納期調整の実務を生産側に移管した場合、営業の役割は以下に変わる。

- **容器確保**: 出荷に必要な容器が不足しないよう管理・調達する
- **まとめ注文をなくす交渉**: クボタに対して、2日分をまとめず日別に発注してもらうよう交渉する。まとめ注文が根本原因であるため、**注文の正常化こそ営業が取り組むべき本質的な課題**である

#### 生産側の目標

- **納入遅れなし**: 残量がマイナスにならないこと（最低限の要件）
- **前倒し生産の最小化**: 前倒し納入は安全だが、前倒し生産は調達（部品・材料の早期手配）に負担がかかる。必要以上の前倒しは避ける

#### 移管の実現方法 — 自動提案機能の実装方案

##### 課題: 納期調整・便計画・生産キャパの循環依存

納期調整（何台出すか）→ 便計画（どの便に積むか）→ 生産キャパ（作れるか）→ 納期調整に戻る、
という循環があり、3つを同時に判断する必要がある。

**AM/PMグループを製品ごとに固定すれば**、この循環は解消できる。
製品を見た時点で便グループ（AM/PM）が決まり、生産締切日が確定する。

```
Step 1: 製品 → AM/PMグループ（固定） → 生産締切日が確定
Step 2: 生産締切日の稼働時間 ÷ サイクルタイム → 日産上限が確定
Step 3: delivery_qty = min(demand_qty, 日産上限)
Step 4: AM内のどの便に積むか（2/3/5） → 便計画画面で解決（別ステップ）
```

##### 使用する既存データ

| データ | テーブル | フィールド |
|---|---|---|
| 受注数 | `t_kubota_sakai_due_adjustment` | `demand_qty` |
| AM/PMグループ | `m_kubota_sakai_pseudo_truck_product` | `product_code` → `truck` → AM/PM判定 |
| サイクルタイム | `m_routing_step`（最終工程） | `duration_min`（所要時間） |
| 稼働時間 | `m_calendar_day`（ライン別） | `work_minutes` |
| 残量 | 既存の累積計算ロジック | `remaining_qty` |

全て既存データで完結。新テーブル不要。

##### 自動提案ロジック

```
入力: 製品コード、対象日、demand_qty

1. AM/PM判定
   KubotaSakaiPseudoTruckProduct → truck → alias_name から AM/PM を判定
   AM → 生産締切日 = 納入日
   PM → 生産締切日 = 納入日の1営業日前

2. 日産上限の計算
   最終工程のRoutingStep → duration_min（サイクルタイム）
   ラインのCalendarDay → work_minutes（生産締切日の稼働時間）
   日産上限 = work_minutes ÷ duration_min

3. 提案値の決定
   delivery_qty = min(demand_qty, 日産上限)

4. 残量チェック
   提案値で累積残量を計算
   残量 < 0 → 赤警告（納入遅れ）
```

##### バックエンド実装

| 項目 | 内容 |
|---|---|
| エンドポイント | `POST /api/kubota-sakai-due-adjustments/auto_propose/` |
| 入力 | `start_date`, `horizon_days`（既存gridと同じパラメータ） |
| 出力 | 製品×日付ごとの `proposed_delivery_qty` と残量警告フラグ |
| 配置 | `views_kubota_sakai_due_adjustment.py` に `auto_propose` アクション追加 |
| 保存 | 提案値は画面に返すだけ。保存は既存の `bulk_save` をそのまま使用 |

##### フロントエンド実装

| 項目 | 内容 |
|---|---|
| 画面 | 既存の `KubotaSakaiDueAdjustment.vue` に「自動提案」ボタン追加 |
| 動作 | ボタン押下 → `auto_propose` API呼出 → delivery_qty セルに提案値を反映 |
| 警告表示 | 残量 < 0 の日を赤背景で強調 |
| 上書き保護 | 手動入力済みのセルは提案で上書きしない（未入力セルのみ反映） |
| 保存 | 既存の「保存」ボタンで `bulk_save`（変更なし） |

##### 人が判断する例外ケース

| ケース | 対応 |
|---|---|
| 容器不足 | 当日の容器数を確認して手動で減らす |
| 前工程部品不足 | 生産状況を確認して手動で減らす |
| 追加注文 | 営業から連絡を受けて手動で追加 |

### 1-8. まとめ

納期調整は、**顧客の要求（いつ・いくつ欲しい）と自社の制約（作れる量・積める量）のギャップを人が判断して埋める工程**である。この工程がないと、便計画に渡す数量が決まらない。

```
顧客要求 (demand_qty)  ← クボタの不規則な注文（まとめ発注・追加注文・内示乖離）
    ↓  現状: 営業が週1火曜に入力 → あるべき姿: 生産側が担当
納入数 (delivery_qty)  ← これが便計画の入力になる
    ↓
残量 (remaining_qty)   ← システムが自動計算（納入漏れ/前倒しの把握）
```

## 2. 便計画 — 何をどの便に積むか

### 2-1. 便計画とは

納期調整で確定した納入数（delivery_qty）を、**どのトラック（便）に・何台積むか**を決める工程。

```
納期調整の結果 (delivery_qty)
    ↓  業務/物流担当が便を選択・割付
便割付 (TripAssignment)  ← 製品×便×数量の組み合わせ
    ↓
トラック出発 → クボタ堺へ納入
```

### 2-2. 便の構成

クボタ堺向けには4便が運行している。

| 便名 | グループ | 出発 | 到着日 | 積載量 |
|---|---|---|---|---|
| 2便 (NO_2_10T) | AM | 当日朝/昼 | 当日着 | 10t |
| 3便 (NO_3_10T) | AM | 当日朝/昼 | 当日着 | 10t |
| 4便 (NO_4_10T) | PM | 前日夕方 | 翌日着 | 10t |
| 5便 (NO_5_10T) | AM | 当日朝/昼 | 当日着 | 4t |

**4便のみ前日出発（日ずれ+1日）。** 製品はAM/PMグループに事前に割り当てられており、基本固定。

### 2-3. 割付の制約

- **面積占有率**: 荷台の面積に対する製品の占有率で積載可否を判定（3D計算ではなく面積方式）
- **分割積載**: 1つの製品を複数便に分けて積むことが可能

### 2-4. 便計画の保存時に起こること

便割付を保存すると、以下が**同一トランザクション内で同時に実行**される。

1. **共通出荷テーブルへ同期** — ShippingRun / ShippingTrip / ShippingTripAllocation に出荷情報を記録
2. **LineBacklog へ同期** — クボタ配送ラインの生産計画（LineBacklog）に割付数量を書き込む
3. **配送進捗を再計算** — 納入予定に対する進捗状況を更新

この「LineBacklog への同期」が、便計画と生産計画をつなぐ要の仕組みである（次章で詳述）。

## 3. 生産計画への連携 — 便計画が前工程を動かす

### 3-1. 一般的な生産計画との違い

通常の生産計画は `LinePlan → LineBacklog` の流れで作られるが、
**クボタ堺は便割付から直接 LineBacklog に書き込む**特殊フローである。
LinePlan / LineGanttPlan は使用しない。

```
【通常の製品】
LinePlan → 工程展開 → LineBacklog → ガント生成

【クボタ堺】
TripAssignment → 直接 LineBacklog（クボタ配送ライン）
```

### 3-2. LineBacklog同期の仕組み

便割付保存時に、1割付＝1行として LineBacklog に書き込まれる。

- `plan_date` = 出発日
- `plan_id` = `KBT_T{truck_id}_{product_code}_{YYYYMMDD}_{seq}`（便を識別するプレフィックス）
- `plan_qty` = 割付数量

### 3-3. pickup カスケード — 前工程への自動伝播

LineBacklog に書き込まれた配送計画は、**pickup カスケード**により前工程に自動伝播する。

```
クボタ配送ライン LineBacklog（便割付の結果）
    ↓  pickup（後工程需要取込）
前工程ライン LineBacklog の order_qty に反映
    ↓
さらに前の工程へ…（BOM展開に沿って連鎖）
    ↓
在庫再計算 → ガント生成
```

前工程の需要日は、便の到着日オフセットから逆算される。

| 便 | 動き | 前工程の需要日 |
|---|---|---|
| 2便・3便・5便（AM） | 当日出発 → 当日着 | 出発日の1営業日前 |
| 4便（PM） | 前日夕方出発 → 翌日着 | 出発日の2営業日前 |

これにより、**便割付の結果が全製造工程に自動的に波及する**。

### 3-4. 全体フローまとめ

```
クボタ堺 確定/内示
    ↓
① 納期調整（営業 / 週1火曜 → あるべき姿: 生産側）
    demand_qty → delivery_qty を決定
    ↓
② 便計画（業務/物流担当）
    delivery_qty → どの便に何台積むかを決定
    ↓
③ LineBacklog 同期（自動）
    便割付 → クボタ配送ラインの LineBacklog に直接書き込み
    ↓
④ pickup カスケード（自動）
    配送ラインの計画 → 前工程の需要として自動伝播
    ↓
⑤ 在庫再計算・ガント生成（自動）
    全ラインの在庫・計画を更新
```
