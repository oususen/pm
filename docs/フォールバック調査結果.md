# フォールバック調査結果

更新日: 2026-09-22
メモ: `production` は `1-4-4` まで整理済み。`1-4-1` は画面実行前ガードを対応中、その他は対応済み。`1-4-5` 以降は未対応。

## 目的

この文書は、アプリ全体で不具合要因になりやすい「フォールバック」実装を洗い出し、
今後の見直し対象をアプリ別に整理するための調査メモである。

ここでいうフォールバックには、以下を含む。

- 別データソースへの代替参照
- 親権限・旧権限への代替判定
- カレンダ未設定時の `daiso` カレンダ代替
- 休日データ未取得時の土日判定代替
- 需要・計画・実績の欠損時に別数量を使う代替
- 画面/API/ルーティングでの設定未解決時の代替

## 調査方針

- 表示用の `'-'` や空文字補完は原則除外する
- 業務結果、数量、営業日、権限、保存先、需要元が変わるものを優先する
- アプリ別に整理し、今後は `production` から順に深掘る

## 横断的な高リスク項目

### 1. 親権限フォールバック

- 下位権限未設定時に親リソース権限へフォールバックする共通処理がある
- 画面単位で `fallbackToParent: false` が混在しており、期待と実装差が出やすい

対象:

- [pm-ui/src/router/index.js](<D:\pm\pm-ui\src\router\index.js:85>)
- [pm-ui/src/router/index.js](<D:\pm\pm-ui\src\router\index.js:100>)
- [pm-ui/src/router/index.js](<D:\pm\pm-ui\src\router\index.js:174>)

### 2. `daiso` カレンダ依存

- ライン/顧客/仕入先/設備ごとのカレンダが未解決の場合に `daiso` カレンダへ落とす実装が広範囲にある
- 個別カレンダ未整備や紐付け漏れが、すべて DAISO 営業日に吸収される

### 3. 休日データ未取得時の土日フォールバック

- フロント側でカレンダ API 取得失敗時、土日だけ休日扱いする実装が複数ある
- 祝日、会社休業日、特別出勤日のズレが発生しやすい

### 4. 需要/計画/実績の相互代替

- `order_qty` が無いとき `plan_qty` を使う
- 対象日の backlog が無いとき直近日を使う
- 需要源が無いとき別ライン/別工程/別ソースから補う

この系統は在庫・進度・前工程需要・購買需要で特に要注意。

### 1-1. 在庫計算

#### 1-1-1. 最終品需要の確定優先フォールバック（2026-08-22 解消済み）

- 旧動作:
  - `LineDemand` に同一 `(product_id, plan_date)` の `firm_qty` と `forecast_qty` がある場合、通常は `firm > 0` を優先し `forecast` を捨てていた
  - `is_shifted` 系フラグが立っている場合だけ `firm + forecast` を合算
- 旧動作の問題:
  - 受注展開時に同一 `(customer_id, product_code, ship_to_code, due_date)` の確定がある内示は既に除外されるため、`LineDemand` に firm/forecast が共存する場合は **異なる納入地からの別需要** である
  - 旧ロジックでは異なる納入地の forecast が firm 優先で消え、計画在庫の需要が過少になっていた
  - 実例: V053504641（クボタ配送ライン）9/7 で firm=40（確定）+ forecast=72（内示、別納入地）のうち forecast が落ち、計庫の需要が 40 しか計上されていなかった
  - 計画進度（`plan_qty = firm + forecast`）とは異なる需要値で計画在庫を計算していたため、計進と計庫で不整合が発生
- 2026-08-22対応:
  - `_build_demand_map()` のfirm優先・shift分岐を撤廃し、常に `firm_qty + forecast_qty` を合算するように修正
  - `stocktake_initializer.py` の同ロジック3箇所も同様に統一
- 対象:
  - [pm_backend/apps/production/inventory/inventory_calculator.py](<D:\pm\pm_backend\apps\production\inventory\inventory_calculator.py:224>)

#### 1-1-6. 通常親出庫の親参照日判定（2026-09-22 修正済み）

- 旧発動条件:
  - 子品番の計算対象日だけで過去/未来を判定していた
  - LTシフト後の親参照日が今日以降でも、親計画を使わず実績だけに固定していた
- 旧代替元/代替先:
  - 親製品ごとのLTシフト後の参照日に応じた出庫（過去=実績+仕損、今日以降=計画+仕損）
  - 子品番の計算対象日だけで親の実績/計画を一律に選択
- 問題:
  - 親参照日が過去で実績が無い場合に計画を出庫へ加算すると、未実施の親計画を控除して計画在庫が過小になる
  - 親参照日が今日以降の場合まで実績に固定すると、計画すべき親出庫が反映されない
  - 例: 2026-08-07、品番 `YD40008640+3097`（L2100・工程4001）は、親製品の実績 0 に対して計画 4 を出庫扱いし、計画在庫が 4 になっていた。本来は前日計画在庫 8 + 自工程実績 0 - 親実績出庫 0 = 8
- 2026-09-22対応:
  - `_calculate_parent_actual_or_plan_shipment()` は、親製品ごとにLTシフト後の親参照日を `business_today` と比較するよう修正
  - 親参照日が過去なら実績+仕損のみ（実績・仕損がともに0なら出庫0）、今日以降なら計画+仕損を使用する
  - 親が複数ある場合も各親を独立して判定し、BOM使用数を掛けて合算する

### 1-2. 進度計算

#### 1-2-1. 行が無い日のダミー backlog 補完

- 2026-08-23 時点の状況:
  - `LineBacklog` の日次連続性は、進度だけでなく在庫・計画在庫でも `sequence_no=0` の基礎行補完で揃える方針に変更済み
- 発動条件:
  - 対象期間の日付に `LineBacklog` 行が無い
  - または、その日に行はあるが `sequence_no=0` 行が無い
- 代替元/代替先:
  - 実行データなし
  - `sequence_no=0` のダミー行を生成し、在庫・計画在庫・進度・計画進度の基礎行として扱う
- 背景:
  - 進度も在庫も本質的には前日値からの累積計算であり、`前日 + 当日増減` の日次連続性が必要
  - そのため「進度だけ日付補完し、在庫は日付欠損を飛ばす」状態は不整合要因になる
- 想定リスク:
  - 「本当に行が無い日」と「0 の日」が同じように見える
  - 元データ欠損や未再計算日が、正常な日次レコードとして見えやすくなる
- 現時点の判断:
  - この救済補完は問題なしとする
  - 理由: 進度・在庫・計画在庫・計画進度はいずれも日次累積値であり、日付欠損を残すより `sequence_no=0` 基礎行で連続性を揃える方が整合的である
  - 実装上も、既存取得結果を再利用し、基礎行を実際に作成した場合だけ再取得する構成へ調整済み

#### 1-2-4. 需要無し時は 0 扱い ✅ 対応不要（業務上必要なフォールバック）

- 現時点の判断:
  - **業務上必要なフォールバックとして維持**
  - 理由: 本当に需要が無い正常日まで異常扱いすると、進度計算を継続できず運用不能になるため
- 扱いの考え方:
  - ここでいう「需要無し」は、当日の `LineDemand` に対象ライン・品番・工程の需要行が存在しない状態を指す
  - この場合でも進度計算は停止せず、当日の需要を `0` とみなして `前日進度 - 0 + 実績 + 調整` で継続する
  - つまり「空白だから未計算」にするのではなく、「その日は差し引く需要が無い日」として扱う
- 発動条件:
  - `LineDemand` に需要が存在しない
- 代替元/代替先:
  - 本来の需要値
  - 0
- 2026-08-24対応:
  - `0` フォールバック自体は維持
- 2026-09-05対応:
  - `需要0フォールバック` の `warning` ログを削除
  - 需要0は休日・受注なしなどで日常的に発生し、再計算対象日ごとの大量ログが異常監視として機能しないため
  - 製品需要があるのに工程需要を解決できない場合のエラーログ・管理者メール通知・計算中断は維持
- 想定リスク:
  - 展開漏れ・取得漏れが「需要なし」として処理され、進度が良く見える
- 運用方針:
  - これは「需要が無い日を 0 として扱う」ための継続条件であり、別ソースや別数量への置換フォールバックではない
  - そのため計算継続は許容し、このフォールバック自体を廃止対象にはしない
  - 需要が実際に無い正常ケースと需要生成漏れは需要0だけでは区別できないため、日次の需要0ログでは監視しない
  - 需要生成漏れを監視する場合は、受注と `LineDemand` の整合性チェックとして別途実施する
