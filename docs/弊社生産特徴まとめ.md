# 弊社生産特徴まとめ

## 概要

本システムは、段階BOM・セル工程・時間運用・ライン/購買LT対応の生産管理システムです。
複数の得意先から内示（FORECAST）と確定受注（FIRM）を受け、優先順位を制御しながら生産計画を立てます。

---

## 1. 受注管理の特徴

### 1.1 内示と確定の二元管理

弊社では、得意先から以下2種類の受注情報を受け取ります：

| 受注タイプ | 日本語 | 性質 | 更新頻度 | スケジューリング優先度 |
|-----------|--------|------|----------|----------------------|
| **FORECAST** | 内示 | 予測情報、変更される可能性が高い | 毎日 | 低（確定がない場合のみ使用） |
| **FIRM** | 確定 | 正式な受注、必ず生産する | 適宜 | 最高（必ず生産計画に含める） |

### 1.2 複数得意先・複数フォーマット対応

**ビジネス要件**:
弊社は複数の得意先から受注を受けており、各社独自のCSVフォーマットで納期・数量情報を提供します。

**システム要求**:

- 各得意先のCSVフォーマットを自動判別してインポートできること
- 複数のエンコーディング（日本語文字コード）に対応すること
- 得意先ごとに異なるフォーマット識別方法（データ区分、ファイル名など）を柔軟に処理できること

**対応得意先**:

| 得意先コード | 得意先名 | 内示 | 確定 | フォーマット識別方法 |
| ------------ | --------- | ------ | ------ | --------------------- |
| 000001 | ティエラ | ○ | ○ | データ区分（B17/Y55） |
| 000196 | クボタ（堺・枚方） | ○ | ○ | ファイル名 + データNO/No. |
| 000018 | リーデン | - | ○ | 発注コード（509） |

**期待される結果**:
各得意先から受け取ったCSVファイルを手動変換することなく、そのままシステムに取り込める。

**実装の詳細は [受注管理仕様書](受注管理仕様書.md) を参照してください。**

## 2. 受注管理の業務要件

### 2.1 内示の自動上書き（毎日更新）

**ビジネス要件**:
内示は毎日更新される予測データ。古い内示と新しい内示を併存させると混乱する。

**システム要求**:
新しい内示CSVがインポートされたら、**同じ得意先の既存内示を完全に置き換える**こと。

**期待される結果**:
常に最新の内示のみがシステムに保持され、データの整合性が保たれる。

### 2.2 確定受注による内示の自動無効化

**ビジネス要件**:
確定受注が来たら、その製品・納期については内示は不要になる。しかし、削除すると履歴が失われる。

**システム要求**:
確定受注CSVがインポートされたら、**同じ製品・同じ納期の内示を自動的に無効化**すること。
履歴として残すが、生産計画には使用しない。

**期待される結果**:

- 確定受注が優先される
- 内示は無効化されるが履歴として残る
- スケジューリング時には無効化された内示は無視される

## 3. 優先順位制御の要件

### 3.1 基本ルール

1. **status='OPEN'** の受注のみを使用
2. **確定（FIRM）を優先**
3. **確定がない製品・納期のみ、内示（FORECAST）を使用**

### 3.2 受注ステータスの意味

| status | 日本語 | スケジューリング | 説明 |
| ------ | ------ | ---------------- | ---- |
| `OPEN` | オープン | ○ 対象 | 有効な受注 |
| `SUPERSEDED` | 無効 | × 除外 | 確定受注により無効化された内示 |
| `CLOSED` | クローズ | × 除外 | 完了した受注 |
| `CANCELED` | キャンセル | × 除外 | キャンセルされた受注 |

**実装の詳細は [受注管理仕様書](受注管理仕様書.md) を参照してください。**

## 4. 生産構造の特徴

### 4.1 段階BOM

製品は複数階層の部品で構成される。

```
製品A (FINISHED)
├── 中間品B (SEMI_FINISHED)
│   ├── 原材料C (RAW_MATERIAL)
│   └── 原材料D (RAW_MATERIAL)
└── 購入品E (PURCHASED)
```

- 各階層ごとにBOMを定義
- `m_bom` (BOMヘッダ) と `m_bom_item` (BOM明細) で管理
- 展開時に全階層を再帰的に処理

#### BOMコピー機能

既存のBOMを別の親製品にコピーする機能。構成品目（明細）はすべて引き継がれ、親製品のみが変更される。

**用途**:

- 類似製品のBOM作成時の効率化
- 連産品の構成を別のセット品番に流用

### 4.2 セル工程（ルーティング）

製品ごとに工程順序と所要時間を定義。

```
製品A のルーティング:
1. プレス工程 (PRESS) - 10分/個
2. 溶接工程 (WELD) - 15分/個
3. 塗装工程 (PAINT) - 20分/個
4. 検査工程 (INSPECTION) - 5分/個
```

- `m_routing` (ルーティングヘッダ) と `m_routing_step` (工程明細) で管理
- 各工程には以下を定義：
  - 工程タイプ（製造 / 検査 / 移送）
  - 作業時間（分単位 or 日単位）
  - 段取時間、バッファ時間
  - 使用ライン

### 4.3 時間運用

#### 日替わり時刻（8時）

弊社では**日替わり時刻を8:00**としています。

- **1月19日 7:59** → **1月18日**として扱う
- **1月19日 8:00** → **1月19日**として扱う

この8時区切りは以下の処理に影響します：

- 実績の日付判定
- 在庫計算の「今日」判定
- 生産計画の開始日判定

#### 時間単位の混在

- **製造工程**: 分単位（10分/個、15分/個 など）
- **購買リードタイム**: 日単位（7日、14日 など）
- **移送時間**: 日単位（1日、2日 など）

`m_routing_step.time_unit` で `DAY` or `MINUTE` を指定。

#### スケジューリング計算

- 納期から逆算（バックワードスケジューリング）
- 工程ごとに所要時間を積算
- カレンダマスタで稼働日・非稼働日を考慮
- 日跨ぎ計算（分単位の作業が営業日をまたぐ場合）

### 4.4 ライン / 購買LT対応

#### 製造工程

- 各工程に使用ラインを指定（`m_routing_step.line_id`）
- ライン別に負荷を計算し、キャパシティを超えないように調整

#### 購買部品

- BOM明細で `procurement_type='PURCHASE'` を指定
- 購買リードタイム（`m_bom_item.purchase_lead_time_days`）を考慮
- 購買計画（発注日、納入日）を自動計算
- 製品で使う購買品は、その製品の得意先（受注先）から調達する想定とし、仕入先コードは得意先コードを流用してよい
- 得意先を直接仕入先として使えない場合は、その製品専用の擬似仕入先コードを作成して運用してもよい

#### レーザ切断 → ブレーキ曲げ（単品のまま流すパターン）

- レーザ切断工程のWIP品番: `YD40000680-16`（LT=1日）
- ブレーキ曲げ工程のWIP品番: `YD40000608-16B`（LT=1日）
- 両工程とも単品のまま流す。中間在庫を持たない場合は同一親品番のルーティング工程で管理し、中間在庫が必要な場合のみ上記WIP品番をBOM/ルートで受け渡す。

### 4.5 ライン最終品の概念

#### ライン最終品とは

**ライン最終品**: 各ラインの最終工程で加工される製品のこと。必ずしも出荷品（最終製品）ではない。

```
【例：タンクライン】
  Step 17: 最終組立 → YD60000441S（中間品）
  Step 18: タンク組立 → YD60000441（出荷品） ← ライン最終品

【例：ブレーキライン】
  Step 1: レーザ加工 → YD40000608-10（中間品）
  Step 2: ブレーキ加工 → YD40000608-10B（中間品） ← ライン最終品
  ※この後、タンクラインに投入される

【例：レーザーライン】
  Step 1: レーザ加工 → YD40000608-06（中間品） ← ライン最終品
  ※この後、ブレーキラインに投入される
```

#### ライン最終品の自動判定

**ビジネス要件**:
計画担当者がライン最終品を手動で指定すると、ルーティング変更時に整合性が取れなくなる可能性がある。

**システム要求**:
ルーティング情報から、各ラインの最終工程で加工される製品を自動的に判定すること。

**期待される結果**:

- マスタ入力の手間が不要
- ルーティング変更時も自動追従
- 各ラインの計画対象製品が明確

#### 出荷品フラグとの違い

| フラグ | 意味 | 例 |
|--------|------|-----|
| `m_product.is_final_product` | **出荷品フラグ**<br>得意先に出荷する製品 | YD60000441, YD60003386 |
| （自動判定） | **ライン最終品**<br>そのラインの最終工程で加工される製品 | YD40000608-10B（ブレーキライン）<br>YD60000441（タンクライン） |

**重要**: ライン最終品は中間品を含むが、出荷品は必ず最終製品のみ。

### 4.6 連産品（コプロダクト）の概念

#### 4.6.1 ビジネス要件

**連産品**: 1つの工程で複数の製品が同時に完成する生産方式。

**業務上の制約**:

- 出力比率は固定（例: 1セットで製品A×1、製品B×1、製品C×2）
- 需要は個別製品ごとに発生するが、生産は必ずセット単位で行う
- 在庫は個別製品ごとに管理し、過不足は在庫で吸収する

#### 4.6.2 システム要求

**計画管理**:

- 需要は子製品（A, B, C）単位で受け取る
- 計画は仮想セット品番（代表品番）で立てる
- 必要セット数は最大要求に合わせて自動計算する

**在庫・実績管理**:

- 仮想セット品番の在庫は持たない
- 実在庫は子製品ごとに管理する
- 実績入力はセット数で記録し、自動的に子製品の実績を展開する

**例（1セットでA/B/Cを同時生産）**:

```
親: SET-ABCD（仮想セット品番）
  子: 製品A × 1  ← 代表品（is_coproduct_driver=TRUE）
  子: 製品B × 1
  子: 製品C × 2
```

#### 4.6.3 連産品代表品（is_coproduct_driver）

**ビジネス要件**:

連産品の子製品のうち1つを「代表品」として指定し、計画展開のトリガーとする。

**問題となるケース**:

```
例：9733476S（共有部品）が複数の連産品に使われている場合

連産品A（SET-A）の子:
  - 製品X（固有品）
  - 9733476S（共有部品）

連産品B（SET-B）の子:
  - 製品Y（固有品）
  - 9733476S（共有部品）

→ 9733476Sの計画を展開すると、どちらの親に展開すべきか判別できない
```

**システム要求**:

- 連産品BOMの構成品目のうち1つを「代表品」（`is_coproduct_driver=TRUE`）として指定
- 代表品は他の連産品と共有されない固有品を選ぶ
- 計画展開時、代表品の計画のみが親（仮想セット品番）へ展開される
- 代表品以外の子製品はガントチャートに表示しない

**サイクルタイム計算**:

- 連産品のサイクルタイムは、代表品のBOM明細の`duration_min`を使用
- これにより連産品全体の加工時間を代表品で定義できる

#### 4.6.4 期待される結果

- 計画入力が簡素化される（セット単位で入力）
- 需要と生産の整合性が保たれる
- 子製品の過不足を可視化できる
- 共有部品があっても正しい連産品へ展開される

**実装の詳細は各仕様書を参照してください。**

## 6. 生産計画管理（LinePlanとLineBacklog）

### 6.1 二層構造の生産計画

弊社の生産計画は**二層構造**で管理されます：

#### LinePlan（ユーザー入力層）

ユーザーが直接入力する生産計画：

```
line_plan テーブル:
- plan_date: 計画日
- line_id: 対象ライン
- product_id: 製品（ライン最終品）
- process_id: 工程
- plan_qty: 計画数量
- sequence_no: 順序番号（同日複数ロット対応）
- plan_id: 計画ID（自動生成、一意識別子）
```

**特徴**:
- ライン最終品のみを登録
- 1日に複数ロット（順序番号）を登録可能
- 計画IDで計画を一意に識別（例: `ABC123_20250115_100_1`）

#### LineBacklog（展開・在庫管理層）

LinePlanから工程展開され、在庫計算が行われるテーブル：

```
line_backlog テーブル:
- plan_date: 計画日
- line_id: 対象ライン
- product_id: 製品（全工程の製品）
- process_id: 工程
- order_qty: 後工程需要
- plan_qty: 計画数量（LinePlanから展開）
- actual_qty: 実績数量
- stock_qty: 実在庫
- planned_stock_qty: 計画在庫
- adjust_qty: 調整数
- scrap_qty: 仕損数
- actual_shipment_qty: 実績出庫数
- sequence_no: 順序番号
- plan_id: 計画ID
```

**特徴**:
- LinePlanから自動展開（全工程の製品を含む）
- 在庫計算機能を持つ
- 需要展開結果を保持

### 6.2 データフロー

```
[ユーザー入力]
    ↓
LinePlan（ライン最終品のみ、複数ロット）
    ↓ 工程展開（expand_processes）
LineBacklog（全工程、plan_qty・plan_id・sequence_no）
    ↓ 在庫計算（recalculate_inventory）
LineBacklog（stock_qty・planned_stock_qty更新）
    ↓ 工程ガント生成（generate）
LineGanttPlan（時間軸計画）
```

**詳細は [生産計画仕様書](生産計画仕様書.md) と [在庫計算仕様書](在庫計算仕様書.md) を参照してください。**

### 6.3 需要展開の考え方：「後工程 = お客さん」

弊社の需要展開は、**「後工程 = お客さん」**という考え方で行います：

```
最終ライン（タンクライン）:
  お客さん = 得意先（ティエラ、クボタ等）
  需要 = 受注データ

前工程ライン（ブレーキライン）:
  お客さん = 後工程（タンクライン）
  需要 = タンクラインの計画 × BOM個数

前工程ライン（レーザーライン）:
  お客さん = 後工程（ブレーキライン）
  需要 = ブレーキラインの計画 × BOM個数
```

**重要な原則**:

1. 需要展開は逆順（最終ライン → 前工程）でライン一つずつ行う
2. 受注から全ラインの需要を一括計算するのではない
3. 各ラインは「後工程の計画」を見て自ラインの需要を決める

### 6.4 ライン最終品のみを対象とする理由

各ラインの計画は、**そのラインの最終品のみ**を対象とします。

**理由**:

1. **重複計算の防止**: 中間工程の製品も全て含めると、同じ製品が複数回計画される
2. **計画の明確化**: 各ラインで「何を何個作るか」が明確
3. **前工程への展開**: ライン最終品から前工程の需要を自動計算できる

**実装の詳細は [生産計画仕様書](生産計画仕様書.md) を参照してください。**

## 7. 在庫管理の業務要件

### 7.1 実在庫と計画在庫の二元管理

**ビジネス要件**:
過去の実績と未来の予測を明確に区別する必要がある。

**システム要求**:

- **実在庫（stock_qty）**: 過去〜今日までの実績ベースで計算
- **計画在庫（planned_stock_qty）**: 今日〜未来の計画ベースで計算

**期待される結果**:

- 現在の正確な在庫状況を把握できる
- 将来の在庫推移を予測できる
- 在庫不足を事前に検知できる

### 7.2 時制を考慮した在庫計算

**ビジネス要件**:
過去・今日・未来で計算ロジックを変える必要がある。

**システム要求**:

- **過去（plan_date < 今日）**: 実績数量・実績出庫・仕損を使用
- **今日（plan_date = 今日）**: 計画数量・計画出庫を使用
- **未来（plan_date > 今日）**: 計画数量のみ（仕損は予測不可）

**期待される結果**:
過去は確定値、未来は予測値として扱われ、データの信頼性が明確になる。

### 7.2.1 日替わり時刻と在庫計算の関係

**ビジネス要件**:
弊社では日替わり時刻を8:00としているため、在庫計算でも8時区切りを考慮する必要がある。

**問題となるケース**:

```
例：1月20日 8:01に在庫計算を実行する場合

- 7:59に実績入力 → これは「1月19日」の実績として扱われる
- しかし、1月19日の在庫はまだ7:59の実績が反映されていない可能性がある
- 単純に「前日の在庫」を起点にすると、最新の実績が反映されない
```

**システム要求**:

- 在庫計算の起点を**前々日の在庫**とする
- 前々日の在庫は確定しているので、そこから前日・今日を再計算すれば正しい値になる
- **前々日以前の在庫は更新しない**（過去の事実は変更しない）

**計算ロジック**:

| 日付 | 処理 |
|------|------|
| 前々日以前 | 既存の在庫値をそのまま使用（更新しない） |
| 前日 | 前々日の在庫を起点に再計算 |
| 今日以降 | 前日の在庫を起点に再計算 |

**期待される結果**:

- 7:59に実績入力 → 8:01に在庫計算しても正しく反映される
- 過去の在庫（事実）は変更されない
- 画面の開始日を変えても、在庫の値が一貫している

### 7.3 仕損（不良品）の自動反映

**ビジネス要件**:
製造過程で発生した不良品は、在庫から自動的に差し引く必要がある。

**システム要求**:

- 仕損記録（ScrapRecord）を入力したら、自動的にLineBacklogに集計
- 自工程仕損だけでなく、後工程仕損も前工程にBOM展開して反映
- 在庫計算時に仕損数を自動的に減算

**期待される結果**:
仕損の入力漏れや計算ミスがなくなり、正確な在庫が維持される。

### 7.4 調整数による手動補正

**ビジネス要件**:
棚卸差異や緊急の在庫調整に対応する必要がある。

**システム要求**:

- 調整数（adjust_qty）フィールドで手動調整可能
- 月次棚卸時の差異を入力
- 緊急の在庫補正（入出庫ミス等）を記録

**期待される結果**:
システム在庫と実在庫のズレを手動で補正でき、常に正確な在庫を維持できる。

**実装の詳細は [在庫計算仕様書](在庫計算仕様書.md) を参照してください。**

## 8. スケジューリングロジック概要

### 8.1 逆算ロジック（バックワード）

```
納期（due_date）
  ↓ 逆算
最終工程（検査）終了時刻
  ↓ 逆算（検査時間）
最終工程（検査）開始時刻
  ↓ 逆算（バッファ）
前工程（塗装）終了時刻
  ↓ 逆算（塗装時間）
前工程（塗装）開始時刻
  ...
  ↓
部品発注日（購買リードタイム考慮）
```

### 8.2 日跨ぎ計算

- 分単位の作業時間が営業日をまたぐ場合の処理
- カレンダマスタで稼働日を判定
- 非稼働日をスキップ

### 8.3 移送バッチ・バッファ制御

- 工程間の移送時間を考慮
- バッファ時間で余裕を持たせる
- ロットサイズによる移送バッチを設定
