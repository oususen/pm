# クボタ納入先コード5桁統一

## ルール

クボタ（顧客コード `000196`）の数値納入先コードを先頭ゼロで5桁に統一する。英数字と空欄は維持し、5桁以上は切り詰めない。リーデンの6桁コードは対象外。

取り込みは堺・枚方・枚方2027形式・KMTの内示／確定に共通関数 `normalize_kubota_ship_to_code` を使用する。

## 既存DB移行

MySQL用管理コマンド `normalize_kubota_ship_to_codes` を使用する。アプリの取り込み修正を反映し、取り込み・受注展開・出荷操作が重ならない時間帯に実行する。

```powershell
cd pm_backend
python manage.py normalize_kubota_ship_to_codes
python manage.py normalize_kubota_ship_to_codes --apply --backup logs/kubota_ship_to_before.jsonl
```

既定は読取専用の事前確認。`--apply` は退避先の指定が必須で、既存の退避ファイルは上書きしない。実行先はDjangoの接続先DB。テーブル定義の変更やマイグレーションは不要。

### 更新順序

1. 更新対象行、需要全件、全件再展開で更新する確定受注の展開フラグを含む受注明細をJSONLへ退避する。対象行はトランザクション内でロックする。
2. 一意キーの衝突・納入地設定の相違を検査する。想定外の競合は中止する。
3. 納入地設定を統合する。正式コードのIDがあればそれを残し、旧コードから未設定項目と色適用品番を引き継ぐ。異なる設定値を勝手に選択しない。
4. 日別ステージング・受注明細・出荷実績と履歴・出荷便と割付・クボタ専用納期調整と便表示設定等のコードをUPDATEする。出荷実績は顧客IDがNULLでも顧客コードから対象を判定する。
5. `stg_order_raw_kubota.raw_payload.ship_to` を更新する。原票の `row` / `v2_row` / `v3_row` 配列は変更しない。
6. 既存の `OrderExpansionService.expand_open_orders(clear_existing=True)` で需要を全件再展開する。この処理はクボタ以外も含むOPEN受注から需要を作り直す。旧コードの需要に実績値がある場合は引継ぎ確認のため中止する。
7. 対象納入先の出荷進度の重複を統合し、手動調整を合算して保持する。既存期間の最初の日から最後の日まで、同一の対象納入先に限定して既存サービスで再計算する。

DB更新・再展開・出荷進度再計算は一つのトランザクションで実行する。途中失敗時は全体をロールバックする。変更対象がなければ再展開は行わない。

### 検証

- クボタの業務用コードに5桁未満の数値が残っていないこと。
- `00971` のカレンダ・背景色・色適用品番が保持されていること。
- コードの桁数だけが違っていた同品番・同納期の確定／内示が、需要では確定優先になること。
- 出荷進度に旧コードの行が残っていないこと。他社・対象外納入先の出荷進度は変更しない。

退避JSONLは更新前の行データであり、自動復元コマンドではない。コミット後に復元する場合は後続の業務更新と照合して復元対象を決める。Gitには含めない。
