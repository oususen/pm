# 社内AI・画像検査 詳細実装プラン

## 1. 目的と方針

生産・業務管理アプリを全ラインへ展開する本番サーバーを整備し、次の二つを段階的に実装する。

1. **画像検査**: 現場カメラの画像をPC内でYOLOが判定する。
2. **社内AI**: 外部AI APIを利用し、社内文書の検索・回答、文書作成、業務データの説明を行う。

初期構成はRTX 5060 Ti 16GBとする。GPUは画像検査、YOLOの学習・検証、Whisper文字起こしに使用する。文章生成やRAG回答のLLMは外部AI APIを使用し、APIへ社内DBを直接接続させない。

将来、ローカルLLMの品質・処理量・社外秘データの取り扱いが課題となった場合は、RTX 5060 Tiを取り外してRTX 5090へ換装する。2枚同時搭載は本計画の対象外とする。

## 2. 到達像

```text
現場カメラ ──> 画像取込 ──> YOLO（RTX 5060 Ti） ──> 判定結果・画像・モデル版数
                                                        │
                                                        ▼
                                              生産・業務管理アプリDB
                                                        │
利用者 ──> 社内AIチャット画面 ──> アプリの固定集計・文書検索 ──> 外部AI API
                                                        │                    │
                                                        └──── 根拠・回答 ───┘
```

- カメラ画像は、判定時に外部AI APIへ送信しない。
- AI APIは社内DBへ直接接続しない。既存アプリが読み取り専用で取得・集計した結果だけを渡す。
- AI回答には、参照した社内文書名・該当箇所、またはアプリ集計のデータ元を表示する。
- AIの回答は補助情報とし、業務上の確定値・最終判断は既存アプリの確定データと担当者確認を基準とする。

## 3. 導入前に確定する事項

実装開始前に、以下をBOSSと関係部署で決める。未決定のままコード・データ連携を始めない。

| 項目 | 決める内容 | 決定者・協力者 |
| --- | --- | --- |
| 外部AI API | API事業者、利用モデル、契約者、請求先、月額上限、入力データの学習利用有無 | BOSS、経理、情報管理担当 |
| 社内AIの初期対象 | 最初に検索する文書群、回答させる業務質問、利用部署 | BOSS、各部門責任者 |
| 画像検査対象 | 最初の工程、検査対象品、良品・不良品の定義、合否判定の最終責任者 | 現場責任者、品質担当 |
| カメラ設備 | カメラ位置、照明、治具、撮影タイミング、ネットワーク、保存期間 | 現場、設備担当、品質担当 |
| 受入基準 | 見逃し、誤判定、判定時間、稼働率について現場が受け入れる基準 | 品質担当、現場責任者 |
| データ管理 | 送信可能なデータ、送信禁止データ、保存期間、閲覧権限、削除手順 | BOSS、情報管理担当 |

## 5. フェーズ1: 本番サーバー基盤の構築

### 5.1 構築対象

- Docker上でフロントエンド、Djangoバックエンド、既存DB接続、nginxを稼働させる。
- バックアップ、復元手順、監視、障害通知を整備する。
- 本番用の環境変数と秘密情報を開発環境から分離する。
- 既存アプリを新PCへ移行し、全ライン展開前に安定稼働を確認する。

### 5.2 バックアップと復元

| 対象 | 方式 | 確認内容 |
| --- | --- | --- |
| DB | 定期バックアップを取得 | 別環境へ復元してアプリが起動できること |
| 添付文書・画像・音声 | 保存先を決め、世代管理する | 任意ファイルを復元できること |
| アプリ設定 | Docker設定、環境変数の項目一覧、手順書を保管 | 新PCまたは障害復旧時に再構築できること |
| AI設定 | APIキーそのものは保存しない。キーの発行・失効・差し替え手順を保管 | キーを画面・ログ・ソースコードへ出さないこと |

### 5.3 本番移行の受入条件

- 現行の主要画面、受注、生産計画、工程実績、進度、在庫、発注、納入、検収が新PCで利用できる。
- バックアップからのDB・添付データ復元を1回実施して記録する。
- 現場端末からアクセスし、同時利用時の応答時間とエラーを確認する。
- 移行後は旧PCを停止する前に、切戻し手順を確認する。

## 6. フェーズ2: YOLOカメラ検査の実証

### 6.1 最初の対象を1工程に限定する

最初から全品番・全不良を対象にしない。以下を満たす1工程を選定する。

- 良品・不良品の差が画像で確認できる。
- カメラの向き、距離、照明、ワーク位置を固定できる。
- 品質担当が良否と不良分類を確定できる。
- 検査結果を既存工程へフィードバックできる。

### 6.2 画像データの準備

1. カメラ設置前に、撮影範囲、照明、背景、ワークの置き方を固定する。
2. 良品・不良品を収集し、撮影日時、品番、工程、ロット、不良種別を紐付ける。
3. 品質担当が画像に良否および不良箇所を付与する。YOLOの物体検出では不良箇所を矩形で囲み、不良種別を付ける。
4. 学習用、検証用、最終試験用の画像を分ける。同一ワークの連続画像が複数の区分に混在しないようにする。
5. 元画像、ラベル、学習条件、学習済みモデルを版数で管理する。

### 6.3 学習・検証の流れ

```text
画像収集 → 品質確認・ラベル付け → YOLO学習 → 検証画像で測定
      ↑                                           ↓
      └──────── 見逃し・誤判定の画像を追加 ────────┘
```

- RTX 5060 Ti 16GB上で初期学習・検証を行う。
- 学習時間だけでなく、見逃し、誤判定、品番別の偏りを品質担当と確認する。
- 改善は「画像追加」「ラベル修正」「撮影条件の安定化」を優先する。モデル設定だけで解決しようとしない。
- 受入基準を満たしたモデルだけを本番用として登録する。

### 6.4 本番判定の実装

| 処理 | 実装内容 |
| --- | --- |
| 撮影 | カメラまたは設備トリガーで画像を取得する。 |
| 推論 | ローカルGPUでYOLOを実行し、良否、不良種別、信頼度、判定時刻を返す。 |
| 保存 | 元画像または必要な判定画像、判定結果、モデル版数、信頼度を保存する。 |
| 現場表示 | 合否、要確認、カメラ異常、モデル異常を明確に表示する。 |
| 人による確認 | 要確認判定および初期導入時の不良判定は、品質担当が最終確認する。 |
| 改善データ | 確定した誤判定画像を次回学習データ候補として登録する。 |

### 6.5 実証の完了条件

- 現場で定めた見逃し・誤判定・判定時間の基準を満たす。
- カメラ停止、通信断、GPU処理失敗時に、現場が人による検査へ切り替えられる。
- 判定結果から元画像、モデル版数、品質担当の最終判断を追跡できる。

## 7. フェーズ3: 外部AI APIによる社内AIチャット

### 7.1 実装原則

- ブラウザーからAI APIを直接呼ばない。DjangoバックエンドがAPI呼び出しを仲介する。
- APIキーはサーバー側の環境変数または秘密情報管理に保存する。画面、Git、ログへ出力しない。
- AI APIは社内DBへ直接接続しない。
- アプリが実行する読み取り専用の固定集計と文書検索の結果だけを、質問とともにAPIへ渡す。
- 外部送信する情報は、決定した送信可能範囲に限定する。個人情報・取引先情報・添付ファイルの送信可否は事前に定義する。

### 7.2 初期ユースケース

| 優先 | 機能 | 入力 | 出力 |
| --- | --- | --- |
| 1 | 文書作成 | 利用者の指示、定型項目 | 幹部会報告、メール、手順書の下書き |
| 2 | 文書検索 | 質問、RAG検索結果 | 根拠文書付き回答 |
| 3 | 生産データ説明 | アプリの固定集計結果 | 数値の説明、傾向、報告書下書き |
| 4 | 通話要約 | 承認済み文字起こし | 要点、対応事項、検索用要約 |

### 7.3 アプリ側の処理順序

```text
利用者質問
  → 質問種別を画面・アプリ側で選択または判定
  → 固定集計またはRAG検索を実行
  → 取得元・期間・数値・参照文書を整理
  → 必要最小限の情報を外部AI APIへ送信
  → 回答と根拠を画面へ表示
```

数値回答では、AIがDBを推測して答える構成にしない。回答画面には、対象期間、データ元、集計条件、参照文書を表示する。

### 7.4 API運用管理

- 部門または利用者ごとに利用可否を管理する。
- 利用回数、入力・出力量、月額費用を集計する。
- 月額上限の手前でBOSSまたは管理者へ通知する。
- API障害時は、アプリの通常業務を継続し、AI機能だけが「利用不可」と分かる表示にする。
- API事業者のデータ保持・学習利用・リージョン・契約条件を定期的に確認する。

## 8. フェーズ4: RAG知識基盤

### 8.1 対象文書の優先順位

1. 現場作業標準、検査基準、設備操作手順
2. 不良・トラブル対策、改善記録
3. 社内規程、承認・申請手順
4. 通話文字起こしから承認されたナレッジ
5. 過去の報告書・メール・帳票

### 8.2 登録フロー

```text
文書選定 → 内容・版数確認 → テキスト抽出 → 分割 → メタデータ付与
      → ベクトル化 → PostgreSQL + pgvectorへ登録 → 検索テスト → 公開
```

メタデータには、少なくとも文書名、版数、作成日、部署、対象工程、公開状態、保存場所を持たせる。

### 8.3 Difyとpgvectorの構成決定

- DifyはAIワークフロー・チャット画面・ナレッジ登録の候補とする。
- PostgreSQL + pgvectorは社内管理するベクトルDB候補とする。
- 実装前に、採用するDifyの版でpgvectorを正式に利用できる構成を確認する。
- 同一文書をDify内蔵DBと別のpgvectorへ二重登録しない。検索基盤は1系統に決定する。
- 文書の閲覧権限を持たない利用者へ検索結果が出ないよう、検索前または検索結果で権限を適用する。

### 8.4 RAG受入試験

- 代表質問について、正しい文書と該当箇所が根拠として表示される。
- 古い版の文書が優先表示されない。
- 権限外の文書が検索・回答に混ざらない。
- 文書に根拠がない場合、AIが推測で断定せず「根拠文書なし」と表示できる。

## 9. フェーズ5: 通話文字起こし・IoT連携

### 9.1 Whisper文字起こし

- 音声データは社内PCでWhisperを実行し、RTX 5060 Tiを使用する。
- 音声、文字起こし、要約、承認状態を分けて保存する。
- RAGへ登録するのは、内容確認・公開承認を受けた文字起こしまたは要約だけとする。
- 録音対象者への周知、保存期間、閲覧権限、削除手順を別途定める。

### 9.2 IoT連携

- 最初は1設備から、稼働状態、サイクルタイム、停止要因、時刻を取得する。
- 設備データはAI APIへ常時送信しない。アプリDBに保存してから、期間集計や異常傾向の説明に必要な結果だけを渡す。
- 取得失敗・通信断・時刻ずれを画面または監視で検知する。

## 10. GPU・LLMの運用方針

| 用途 | 初期構成 | 将来判断 |
| --- | --- | --- |
| YOLO推論 | RTX 5060 Ti 16GB | カメラ台数・判定時間が課題なら上位GPUを検討 |
| YOLO学習 | RTX 5060 Ti 16GB | 学習の待ち時間が改善活動を阻害する場合に5090換装を検討 |
| Whisper | RTX 5060 Ti 16GB | 処理待ちが増える場合はキュー・実行時間を測定 |
| 社内AIチャット | 外部AI API | API費用・回線・機密要件を月次評価 |
| ローカルQwen | 必要時にQwen3 14B Q4までを検証 | 30B級を実用速度で使う必要が確定した時だけ5090へ換装 |

RTX 5060 Ti 16GBでは、YOLO常時判定とQwen3 14Bを同時常駐させない。ローカルQwenを評価する場合は、カメラ検査停止中またはGPU使用量を分離できる時間帯に実施する。

## 11. RTX 5090換装の判断基準

5090へ換装するのは、次のいずれかを実測で確認した場合だけとする。

| 判断材料 | 測定内容 |
| --- | --- |
| YOLO学習時間 | 画像追加からモデル評価完了までの実時間。改善サイクルを回せないほど長いか。 |
| 推論待ち | カメラ台数、画像解像度、判定待ち行列、GPU使用率、判定遅延。 |
| ローカルLLM品質 | Qwen3 14Bで必要な回答品質・文書作成品質を満たせるか。 |
| API回線 | API応答時間、障害時間、通信断の業務影響。 |
| API費用 | 月額利用料と利用量。ローカル化の投資判断に十分な実績があるか。 |
| 機密要件 | 外部APIへ送信できない業務範囲が、実際にどれだけあるか。 |

換装決定時は、現在の5060 Tiを取り外し、見積書で確認した同一PCの電源・ケース・マザーボードへ5090を搭載する。換装後はGPUドライバー、YOLO、Whisper、ローカルQwen、温度・電力を再試験する。

## 14. 実装上の禁止事項

- 外部AI APIへ社内DBの接続情報を渡さない。
- AIに任意SQLを生成・実行させない。
- AIの推測値を生産数、在庫、残業、品質の確定値として表示しない。
- 画像検査の初期段階で、人による確認なしに不良品の自動廃棄・自動停止を行わない。
- APIキー、顧客情報、個人情報、未承認の通話文字起こしを画面・ログ・ソースコードへ残さない。
- 5060 Tiの8GB版を採用しない。

## 15. 次の意思決定

本計画を開始するために、最初に決める事項は以下の3点である。
