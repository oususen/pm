# 53期 パフォーマンス改善計画: N+1クエリ問題の解消

## 背景

`inventory_calculator.py` の `_ensure_daily_base_backlogs` リファクタリング時に、
`select_related('product')` なしの再fetchでN+1クエリが発生する問題を発見・修正した。

これを契機にアプリ全体を調査した結果、同種のN+1問題が複数箇所に存在することが判明。
本計画書は調査結果と修正方針をまとめたものである。

### N+1クエリとは

```python
# 悪い例: ループ内でFKアクセスのたびにDBクエリが発生（N+1回）
backlogs = LineBacklog.objects.filter(...)  # 1回目
for b in backlogs:
    print(b.product.product_name)  # ← 毎回DBに飛ぶ（N回）

# 良い例: select_related でJOIN取得（1回で済む）
backlogs = LineBacklog.objects.filter(...).select_related('product')
for b in backlogs:
    print(b.product.product_name)  # ← クエリ不要（JOIN済み）
```

## 定時在庫再計算: 有効期間対応と高速化（53期追加計画）

### 背景・実測値

2026-09-18 の `INVENTORY_RECALC` 実行では、合計 **2,101.3秒（35分1秒）** を要した。

| 処理 | 件数 | 所要時間 |
|---|---:|---:|
| 生産ライン取込 | 27ライン | 423.2秒 |
| 購買取込 | 29ライン | 29.0秒 |
| 在庫・計画在庫・進度再計算 | 55ライン / 2,432品番 | 1,641.9秒 |

再計算時間の 70.6% は上位10ラインに集中した。主な対象は、000180（237品番、176.3秒）、L0801（274品番、175.6秒）、L0010（207品番、155.6秒）、L2100（134品番、118.4秒）である。

### 現状確認

1. `recalculate_inventory_for_line` は品番ごとに、実在庫・計画在庫・進度の3計算を順番に実行する。
2. 各計算は日付ごとに親BOM・後工程バックログを参照するため、品番数と日数に比例してDB参照が増える。
3. 設定期間は2026-09-18〜2026-10-20だが、LT・在庫起点のため最も早いラインでは2026-08-26から計算される。
4. 現行の親工程Routing絞り込みとBOM取得は、計算日を使った有効期間判定をしていない。
   - RoutingStep取得に `valid_from_datetime` / `valid_to_datetime` の条件がない。
   - BOM取得に `valid_from` / `valid_to` の条件がない。
   - このため、期間途中で版が切り替わる場合に、計算日ごとの正しい版を選べる保証がない。

### 53期の目的

1. 計算日ごとに有効なRouting・BOM版を必ず選択し、期間途中の版切替を正しく反映する。
2. 同じ日・同じ品番・同じ工程に対するDB検索を繰り返さない。
3. 計算結果を変えずに、定時再計算の所要時間を短縮する。

### 実装方針

#### フェーズ1: 有効期間判定の正規化（先行必須）

1. Routingは `(line_id, process_id, product_id, plan_date)` をキーとして、その計算日に有効な版だけを解決する。
2. BOMは `(child_product_id, plan_date)` をキーとして、その計算日に有効な版だけを解決する。
3. 同じ日に有効な版が複数存在する場合は、既定版・有効開始日時・版番号のどれを優先するかを業務ルールとして確定してから実装する。
4. 有効期間の空白日、重複日、親工程未解決は無条件に別版へフォールバックしない。対象日・品番・ライン・工程をエラーとして記録する。

#### フェーズ2: 日付付き参照マップの一括構築

1. 対象期間と重なるRouting・RoutingStep・BOM・BOMItemを一括取得する。
2. 取得した候補から、日付単位で有効な版を解決した参照マップを構築する。
3. 参照マップのキーは品番だけにせず、必ず `計算日` を含める。
   - 例: `(child_product_id, plan_date) → 有効BOM明細`
   - 例: `(line_id, process_id, product_id, plan_date) → 有効RoutingStep`
4. 版切替日をまたぐ期間でも、前日と翌日で異なる版を選べることを必須条件とする。

#### フェーズ3: 出庫計算のループ内クエリ削減

1. 対象のLineBacklogを必要な親品番・日付まで含めて一括取得し、`(line_id, product_id, plan_date)` の参照マップを構築する。
2. 実在庫・計画在庫・進度の各計算は、フェーズ2の有効版マップとバックログ参照マップを使用する。
3. ループ内の `BOMItem.objects.filter()`、`RoutingStep.objects.filter()`、`LineBacklog.objects.filter()` を段階的に置き換える。
4. 計算対象期間の短縮は主対策としない。LTと在庫累積の起点を維持する。

### 検証計画

1. 版切替の前日・切替日・翌日を含むテストデータで、選ばれたRouting/BOM版を確認する。
2. 有効期間の空白・重複・工程未解決で、エラー内容が対象日まで特定できることを確認する。
3. 修正前後で、対象ライン・品番・日付の `stock_qty`、`planned_stock_qty`、`progress_qty` をDBで比較する。
4. 2026-09-18と同等の実行範囲で、処理別・ライン別の所要時間を比較する。
5. `000034 / 8113793-01 / 2026-09-11` の工程需要未解決は、性能改善とは別にRouting需要データの整合性として調査する。

### 実装順序

1. 有効期間が重複した場合の業務上の優先ルールを確定する。
2. Routing/BOMの計算日有効判定を実装し、版切替テストを追加する。
3. 日付付き有効版マップを導入する。
4. 出庫計算のLineBacklog参照を一括取得へ置き換える。
5. 実データ比較と定時タスクの計測を実施する。
