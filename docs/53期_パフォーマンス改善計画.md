# 53期 パフォーマンス改善計画: N+1クエリ問題の解消

## 背景

`inventory_calculator.py` の `_ensure_daily_base_backlogs` リファクタリング時に、
`select_related('product')` なしの再fetchでN+1クエリが発生する問題を発見・修正した。

これを契機にアプリ全体を調査した結果、同種のN+1問題が複数箇所に存在することが判明。
本計画書は調査結果と修正方針をまとめたものである。

### N+1クエリとは

```python
# 悪い例: ループ内でFKアクセスのたびにDBクエリが発生（N+1回）
backlogs = LineBacklog.objects.filter(...)  # 1回目
for b in backlogs:
    print(b.product.product_name)  # ← 毎回DBに飛ぶ（N回）

# 良い例: select_related でJOIN取得（1回で済む）
backlogs = LineBacklog.objects.filter(...).select_related('product')
for b in backlogs:
    print(b.product.product_name)  # ← クエリ不要（JOIN済み）
```

## 発見箇所一覧

### HIGH: バッチ・再計算コード（最優先）

スケジューラやバッチ処理で全ライン×全製品を回すため、クエリ数が爆発的に増える。

#### 1. `production/inventory/inventory_calculator.py` — 在庫再計算

| 関数 | 行 | 問題 |
|------|-----|------|
| `_sum_parent_shipments` | ~604 | BOMアイテムループ内で `LineBacklog.objects.filter()` |
| `_calculate_parent_actual_shipment` | ~731 | 同上 + `_get_shipment_scrap_qty` |
| `_compute_planned_stock_lt_adjustment` | ~790 | 日数×BOMアイテムの二重ループ内でクエリ |
| `_calculate_parent_actual_or_plan_shipment` | ~893 | 同パターン |
| `_calculate_parent_planned_shipment` | ~973 | 同パターン |
| `calculate_actual_shipment` | ~1041 | 同パターン |
| `has_downstream_actual` | ~1084 | `bom_item.bom.parent_product` FK2段未解決 |

**修正方針**: 再計算開始時に対象(line, products, date_range)のLineBacklogを一括取得し、`(product_id, plan_date)` をキーとしたインメモリ辞書を構築。各出庫計算関数にはこの辞書を渡し、ループ内クエリを排除。

#### 3. `purchase/services_auto_order_send.py` — 自動発注

| 関数 | 行 | 問題 |
|------|-----|------|
| `_load_first_cycle_progress_basis` | 148-195 | product_idごとに2-4回のaggregate → O(製品数×4) |

**修正方針**: `.values('product_id').annotate(...)` でバルクaggregate化。

#### 4. `production/views_line_realtime.py` — ライン状況ダッシュボード

| メソッド | 行 | 問題 |
|---------|-----|------|
| `LineStatusViewSet.list_all` | 78-128 | 全アクティブラインをループし、各ラインで3クエリ → O(ライン数×3) |

**修正方針**: LineStatus/LineDemand/LineRealtimeRecordを一括取得してインメモリでマッチング。

#### 4. `production/serializers_process_realtime.py` — 仕損BOMツリー

| 関数 | 行 | 問題 |
|------|-----|------|
| `build_scrap_multiplier_map` | 49-78 | BOMツリー探索でノードごとに2クエリ |
| `build_scrap_multiplier_details` | 82-176 | 同上 + Supplier/Product個別取得 → ノードごとに4+クエリ |

**修正方針**: BOM/BOMItem/Supplierを一括prefetchし、ツリー探索はインメモリで実行。

### MEDIUM: API・画面系

#### 5. `masters/views.py` ProductViewSet（行394）

```python
# 現状: next_process が未解決
queryset = Product.objects.prefetch_related('stock_locations')

# 修正: select_related('next_process') を追加
queryset = Product.objects.select_related('next_process').prefetch_related('stock_locations')
```

製品一覧APIで全製品×1回の追加クエリ。**1行修正で解消**。

#### 6. `production/views_progress_compare.py` ProgressPdfAdjustView

| メソッド | 行 | 問題 |
|---------|-----|------|
| `_resolve_common` | 271-303 | itemsループ内で Product/Process を個別get |
| `put` | 319-336 | itemsループ内で LineBacklogAdjustment を個別filter |

**修正方針**: product_code/process_codeリストで一括取得し辞書化。

#### 7. `production/services/gantt_planning.py`（行~1251）

ネストループ内で `Product.objects.filter(id=...).first()`。
**修正方針**: 対象product_idを事前収集し、一括取得。
