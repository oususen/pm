# 工程作業入力「現在時刻のみ」高速化計画
作成日: 2026-05-26  
対象画面: `production/desktop-process-input`（必要に応じて `mobile-process-input` も同時確認）

## 1. 背景

- 現在、`現在時刻のみ` をONにした際の初期表示が遅いケースがある。
- 本来は `line_gantt_plans.processes_plan` から現在時刻スロット対象を即時表示できる。
- ただし現実装では、同一フロー内で追加の重い処理（backlog/pickup/BOM/画像等）も実行されるため、体感遅延が発生する。

## 2. 現状の主な遅延要因（Desktop）

- ガント取得後に以下処理を継続実行している。
1. `line_backlogs.getLineBacklogs` / `line_backlogs.pickup`
2. BOM展開（連産子判定・子品目展開）
3. 画像ロード
4. フロア表示マップ照合

## 3. 9月対応方針

- `現在時刻のみ` ON時は、初期表示を「ガント由来データ中心」に限定する。
- 重い処理は初期表示経路から切り離す（または後段へ移動）。
- UI挙動は `mobile-process-input` を正として、Desktopの時間スロット挙動を一致させる。

## 4. 実施範囲（9月）

1. `loadPlannedProducts()` の分岐整理
2. `filterCurrentTime=true` の高速経路を新設（早期return）
3. 低優先処理（BOM/画像/補助照合）の遅延実行化またはスキップ
4. Desktop/Mobileの挙動差分テスト追加（スロット移動・対象品番一致）
5. ログ計測追加（初期表示時間、API呼び出し回数）

## 5. 受け入れ基準（案）

1. `現在時刻のみ` ON時、初期表示が現行より明確に短縮されること
2. 同一ライン・同一工程・同一時刻で Desktop/Mobile の表示対象が一致すること
3. `« »` の時間スロット移動で、対象リスト更新が即時に近いこと
4. 通常表示（`現在時刻のみ` OFF）の既存挙動を壊さないこと

## 6. リスクと確認事項

- ガント側データ欠損時のフォールバック方針を要決定
- 連産・子品目・仕損入力時の対象判定差異が出ないか重点確認
- 既存運用で必要な補助情報（画像・補助実績）の表示タイミングを要調整

## 7. スケジュール（2026年9月）

1. 第1週: 詳細設計・影響調査
2. 第2週: 実装（高速経路・分岐整理）
3. 第3週: 結合テスト（Desktop/Mobile比較、実データ検証）
4. 第4週: 現場確認・微調整・本番反映判定

# 生産計画画面 需要表示見直し（53期対応メモ）

作成日: 2026-07-16  
対象画面: `production/plan-input`

## 1. 背景

- 生産計画画面の「需要」列は、従来 `LineBacklog.order_qty` をそのまま表示していた。
- `order_qty` はピックアップ時のスナップショット（後工程の `plan_qty` × BOM個数）であり、実績とは無関係。
- そのため過去日でも「後工程が計画通り作る前提」の値が表示され、実態と乖離していた。

## 2. 課題（当初検討）

1. `LineBacklog` には実在庫用の `actual_shipment_qty` はあるが、計画在庫用の出庫値列はない。
2. 計画在庫側の出庫値は、親品の複数候補、BOM数量、LT、営業日カレンダ、便判定を噛ませて都度計算している。
3. 一覧APIのレスポンス生成時に毎回その場計算すると、一ライン数百品番の画面で負荷が高い。
4. 当初案の `planned_shipment_qty`（計画在庫計算時の減算値を保存）は見送り、より軽量な方式を採用した。

## 3. 実装方式（2026-08-22 実装済み）

### 3-1. order_qty_actual フィールド追加

- `LineBacklog` に `order_qty_actual`（実績ベース需要）を追加。
- ピックアップ時に `order_qty` と同じタイミング・同じ取り方で計算。
- 違い: `order_qty` は後工程の `plan_qty` × BOM個数、`order_qty_actual` は後工程の `actual_qty` × BOM個数。
- `actual_qty` は `sequence_no=0` の行に保存されている。ピックアップ時、後工程の種類（フロア配送/クボタ配送/通常ライン）ごとにループ構造が異なるため、各分岐内で後工程の `sequence_no=0` 行から `actual_qty` を別途集計し、前工程ラインの `order_qty_actual` に反映する。`actual_qty` の集計ロジック自体は3分岐とも同一（`sequence_no=0` かつ `actual_qty > 0` → 日付別に加算）だが、`plan_qty` の取り方とLTシフトの仕組みがライン種別ごとに異なるためループが分かれている。

### 3-2. demand_qty_plan の判定ロジック変更

- 従来: `demand_qty_plan = order_qty`（常に同値、独立した意味なし）
- 変更後: 親の元 `plan_date` を追跡し、親単位で事前計算する方式に変更。

判定ルール:
1. **DEMAND特例（ORDER_QTY）設定あり** → `order_qty`（計画値）
2. **親日が過去（生産完了）** → `order_qty_actual`（実績ベース）
3. **親日が今日以降 or 親日付なし** → `order_qty`（計画値）

### 3-3. 画面の需要欄

- `order_qty` から `demand_qty_plan` に参照先を変更。
- `demand_qty_plan ?? order_qty ?? 0` でフォールバック。

## 4. フロア配送・クボタ配送での扱い

- フロア配送・クボタ配送の前工程にはDEMAND特例（ORDER_QTY）が設定されている。
- そのため `parent_plan_date` は渡さない（渡しても L2126 で先にDEMAND特例分岐に入り結果は変わらない）。
- 特例設定を外した場合は `parent_plan_date` が渡されるため、通常ラインと同じ動作になる。

## 5. 在庫計算・計画在庫計算・進度計算への影響

- **なし（表示専用の変更）**。
- `order_qty_actual` / `demand_qty_plan` はいずれも在庫計算・計画在庫計算・進度計算で参照されない。

## 6. 関連変更

- 計算特例に製品単位の粒度を追加（`productCode` フィールド）。詳細は `仕様書/フォールバック調査結果.md` 参照。
- ピックアップ開始日を `_resolve_inventory_effective_start_date` で営業日ベースに調整。

## 7. ステータス

- 2026-08-22 実装済み・コミット済み（`b56698de`）
- 本番デプロイ時にマイグレーション実行が必要: `docker exec -it pm-backend python manage.py migrate`

## 8. pickup 性能課題メモ（2026-08-24 追記）

### 8-1. 背景

- `production/plan-input` の `pickup` が、本番・開発ともに長時間化している。
- ブラウザ実測では、`recalculate_inventory` より `pickup` の方が支配的に長い。
- 2026-08-22 の需要表示見直しで `order_qty_actual` / `demand_qty_plan` 判定が追加されたが、実測上の主因がどこかを切り分ける必要があった。

### 8-2. 実測結果

開発環境で `pickup` に区間ログを追加して確認した結果、以下を確認した。

1. View内部処理だけでも約15秒かかっている
   - `phase=setup`: 1.231秒
   - `phase=intermediate_expand_routing`: 2.226秒
   - `phase=upsert_write`: 9.468秒
   - `pickup: total_time`: 15.176秒
2. `pickup` のHTTP完了はさらに遅く、View返却後にも大きな時間がある
   - `pickup: total_time` ログ時刻と `POST /api/line-backlogs/pickup/` 完了時刻の差から、JSONレンダリング/送信にも大きな時間を使っている
3. 需要判定ロジック自体は主犯ではない
   - `phase=upsert_load_rules`: 0.010秒
   - `phase=upsert_build_demand_plan`: 0.027秒

### 8-3. 現時点の原因整理

主因は次の2点である。

1. `pickup` が `sequence_no=0` 行を大量更新している
   - 実測では `update=4055` 件
   - `bulk_update(['order_qty', 'order_qty_actual', 'demand_qty_plan', 'plan_qty'])` の書き込みが約9.5秒を占めた
2. `pickup` が更新結果を巨大レスポンスで返している
   - 実測レスポンスは約3.3MB
   - View内部ログ後もHTTP完了まで長く、DRFのレンダリング/送信コストが大きい

補足:
- 2026-08-22 の `order_qty_actual` / `demand_qty_plan` 追加は正しい仕様変更であり、需要判定の数十ms〜数百ms自体は支配的ではない
- ただし、この変更により更新列が増え、全件更新コストが表面化・増幅した可能性は高い

### 8-4. 53期対応方針

1. `pickup` の更新対象を差分行に限定する
   - 値が変わらない `LineBacklog(sequence_no=0)` は `bulk_update` 対象から外す
   - 少なくとも `order_qty` / `order_qty_actual` / `demand_qty_plan` / `plan_qty` が全て不変の行は更新しない
2. `pickup` のレスポンスを軽量化する
   - 更新済み全件をそのまま返す方式をやめる
   - 返却は `updated_count` / `created_count` / `line_id` / `range` など最小限にする
   - 画面表示用データは別GET（既存 `line-backlogs` / `line-plans`）で再取得する
3. `pickup` の区間計測ログを維持し、改善効果を比較できるようにする
   - 少なくとも `setup` / `intermediate_expand_routing` / `upsert_write` / `serialize相当` は継続監視対象とする

### 8-5. 実装順序

1. 差分更新化
   - 更新不要行の除外
   - 更新件数と `upsert_write` 秒数の再計測
2. 軽量レスポンス化
   - `pickup` POST の返却内容見直し
   - 画面側の再取得フロー確認
3. 実測比較
   - 本番相当データで `pickup` / `recalculate_inventory` / 画面再表示まで通しで比較

### 8-6. 受け入れ基準

1. `pickup` の View内部時間が現状より明確に短縮されること
2. `upsert_write` がボトルネックでなくなること、または支配率が大きく下がること
3. `pickup` POST のレスポンスサイズが大幅に削減されること
4. 需要表示の業務仕様（`order_qty_actual` / `demand_qty_plan` 判定）が変わらないこと
5. `recalculate_inventory` より `pickup` が長い場合でも、業務上許容できる水準まで短縮されること

# クボタ内示/確定 仕様見直し（後日対応メモ）

作成日: 2026-06-02  
対象: クボタ（`customer_code=000196`）内示取込と出荷進度表示

## 1. 背景（現場課題）

- 遠い将来日の特定日に、補用（パーツセンター向け）で `FIRM` が1台だけ入るケースがある。
- 現行ロジックでは同一キーに `FIRM` があると内示が除外されるため、量産内示まで見えなくなる懸念がある。

## 2. 現行ロジック（確認済み）

1. クボタ堺内示取込（36番）時、同一「品番 + 納入先 + 納期」に `FIRM` があると当該 `FORECAST` を作成しない。
2. 内示再取込時は旧内示（OPEN）を `SUPERSEDED` 化して置換する（クボタは品番+納入先単位）。
3. 出荷進度照会画面は `FORECAST` を内示行、`FIRM`（または未設定）を確定行として集計表示する。

## 3. 検討論点（後日）

1. 「補用FIRMが存在しても量産内示は保持したい」という業務要件の正式化
2. 量産/補用の識別キー（データ上で何を根拠に分離するか）の確定
3. 内示除外条件の見直し方針
4. 進度・納期調整・便計画への波及影響

## 3-1. 補用FIRMの需要採用方針メモ（2026-06-03追記）

- 将来日の一部ケースでは、補用 `FIRM` と量産 `FORECAST` が同日に共存する。
- この場合、業務要件としては「`FIRM` で `FORECAST` を完全置換する」のではなく、`FORECAST + FIRM` で需要採用したい。
- 例: `FORECAST=111`、補用 `FIRM=2` の場合、需要は `113` として扱いたい。
- ただし現時点では、補用を安定して識別できる特徴量（注番規則、納入先、用途区分、ファイル種別、明細属性など）が未確定。
- そのため、現段階では実装しない。補用判定条件が確定した時点で、53期対応として実装方針を確定する。

## 3-2. G工程 / 外作候補の複数化メモ

### 経緯

- `pickup_purchase` 側で SUBCON 判定を行う際、現状は `RoutingStep` の工程情報を見て G工程 / 外作を拾っている。
- これまでは同一品番に対して、G工程 / 外作候補は実質1件前提で扱っていた。
- ただし今後のマスタ整備や工程追加により、同一品番に複数候補が発生する可能性がある。
- その場合、単純に先頭1件で決めると誤判定や需要漏れの原因になるため、事前に方針を残しておく。

### 対象箇所

- `pm_backend/apps/production/views.py`
  - `pickup_purchase()` 内の `RoutingStep.objects.filter(...)`
  - `subcon_product_process_map` を作成している判定部分
  - `child_process_id = subcon_product_process_map.get(child_id, process_id)` で工程を引き回す部分
- 参照元の工程判定
  - `process_code == 'G'`
  - `Process.is_outsource == True`

### 実装計画

1. 現状は単一候補前提のまま維持し、既存の需要計算・在庫計算への影響を最小化する。
2. 将来複数候補が確認された場合は、`RoutingStep` を複数件保持したうえで優先順を明示する。
3. 重複候補がある場合は、どの候補を採用したかをログまたは警告で追跡できるようにする。
4. 必要であれば、品番ごとの候補一覧を事前検証するチェック処理を追加する。
5. 53期実装時は、候補選定ルール（G工程優先、外作優先、手順番号優先など）を確定してからコード化する。

## 4. 方針候補（未決定）

1. 内示取込での `FIRM` 優先除外を弱め、内示データ自体は保持する
2. 需要採用時のみ `FIRM` 優先を維持する（表示/計算で使い分け）
3. 補用を識別できる場合のみ、補用FIRMを除外判定から外す
4. 補用を識別できる場合のみ、需要採用を `FORECAST + FIRM` に切り替える

## 5. 対応ステータス

- 本件は「特徴把握中」のため未実装
- 後日、実データ確認（対象品番・納期・納入先）後に設計確定して着手する
- 実装予定時期は 53期 とする

# 受注ファイル自動取込（後日対応メモ）

作成日: 2026-06-02  
対象: クボタ / ティエラ / リーデンの受注取込自動化

## 1. 前提運用

1. 受注ファイルを指定フォルダへ配置する作業は人が行う
2. システムは指定フォルダを定期監視して自動取込する

## 2. 希望要件

1. 得意先種別の判定はファイル名ではなく、できるだけファイル中身で判定する
2. 異常時は通知を送る
3. 監視周期は1時間ごととする

## 3. 識別方針（案）

1. 取込種別判定はファイル名依存を避け、CSV内容のヘッダ/管理番号/列構成/得意先コード/レコード形式で判定する
2. 判定不能時のみエラー扱いとして通知し、手動確認へ回す
3. 将来的にファイル名規則が変わっても取込継続できるよう、内容判定を主軸にする

## 4. 再取込ポリシー（案）

`ポリシー` は、同じ内容または似た内容のファイルが再度フォルダに入ったときの扱いを指す。

1. 重複判断はファイル名で行う
2. 同一ファイル名は再取込しない
3. 同一得意先・同一対象期間で別ファイル名かつ中身差分がある場合は差し替え取込とみなす
4. 差し替え取込時は、既存の `SUPERSEDED` ルールを適用する
5. 部分失敗後の再実行でも二重取込にならないよう、取込履歴を持つ

## 5. 通知方針（案）

1. 取込成功時も通知する
2. 取込失敗時も通知する
3. 判定不能時は通知する
4. 重複ファイル検知時は通知する
5. 件数急減などの異常値は通知する

## 6. 実装イメージ（案）

1. 定時タスクで1時間ごとに監視フォルダを走査
2. 未処理ファイルを内容判定して既存取込サービスへ振り分け
3. 取込結果を履歴へ保存
4. 成功/失敗/重複を通知へ連携

## 7. 後日決定事項

1. 監視対象フォルダの実パス
2. 取込後ファイルの保管先（`processed` / `error` / `duplicate` など）
3. 内容判定に使うキーの正式定義
4. 異常通知の送信先ユーザー/グループ

## 8. Docker前提の補足

1. 本番環境は Docker 起動のため、監視対象フォルダはコンテナから見えるよう `volumes` で明示的にマウントする必要がある
2. 自動取込を定時タスクで実行する場合、`pm-backend` だけでなく `pm-scheduler` からも同じ監視フォルダを参照できる必要がある

# LTマスタ保持対応（53期対応メモ）

作成日: 2026-07-19  
対象: 在庫計算 / 計画在庫計算 / 進度計算 / 定時タスク開始日決定 / LTマスタ管理

## 1. 背景

- 現状の在庫・進度再計算では、開始日決定時に製品ごとの `直LT` または `累積LT` をその場で取得している。
- 特に進度計算は `累積LT` が必要であり、対象製品数が多いタスクでは都度計算の負荷が大きい。
- 実測では、全製品総当たり時に `直LT` より `累積LT` の取得が大幅に重く、定時タスク全体時間にも影響する。
- また、開始日決定と実計算で別ロジック・別取得範囲を使うと、調整値や需要の取得範囲ずれが起きやすい。

## 2. 53期の方針

1. `LT計算` と `在庫/進度再計算` の責務を分離する。
2. `直LT` / `累積LT` は、実行時その場計算ではなくマスタ保持した値を参照する方式へ寄せる。
3. 在庫系は `直LT`、進度系は `累積LT` を使う方針自体は維持する。
4. 開始日決定に使うLT値と、実計算に必要な取得範囲は必ず同じ基準で統一する。
5. 53期では `LTをマスタに持たせる実装` を正式対応対象とする。

## 3. 実装イメージ

1. 製品単位、または `product × line/process` 単位で LT保持用マスタを持つ。
2. 保存候補値は少なくとも以下とする。
   - `direct_lt_days`
   - `cumulative_lt_days`
3. 既存マスタへの列追加か、専用LTマスタ新設かは53期で確定する。
4. BOM または Routing 更新時に、該当製品の LT再計算を行う。
5. 定時タスク・手動再計算・納入予定再計算は、保存済みLTを読むだけにする。
6. 実計算側では、開始日だけでなく以下の取得範囲も同じ LT基準にそろえる。
   - `LineBacklog`
   - `LineDemand`
   - 調整値

## 4. 実装計画

1. 現行の `直LT` / `累積LT` 参照箇所を棚卸しする。
2. LTを保持するマスタ構造を決める。
3. 既存 `m_product` 等への列追加か、専用LTマスタ新設かを比較して確定する。
4. BOM/Routing変更時の再集計トリガを決める。
5. 初回一括集計バッチを用意する。
6. 定時タスク・画面再計算の開始日決定を保存済みLT参照へ切り替える。
7. `取得範囲` と `計算範囲` が同一LT基準で同期していることをテストで保証する。

## 5. 期待効果

1. 進度再計算時の `累積LT` 都度計算を削減できる。
2. 大量製品を対象にした定時タスクの開始日決定が安定する。
3. `取得範囲` と `計算範囲` のずれによる不整合を減らせる。
4. 将来的な製品増加・ライン増加に対して性能劣化を抑えやすくなる。

## 6. 留意点

1. LTをマスタに保持する場合、BOM/Routing変更時の再集計漏れを防ぐ必要がある。
2. どの粒度で保存するか（製品単位か、ライン/工程込みか）は53期で詳細設計する。
3. 事前集計済みマスタへ移行しても、例外品番や未整備マスタのフォールバック方針は残しておく。

# 受注展開の工程別需要安定化（53期対応メモ）

作成日: 2026-08-25  
対象: `order_expansion.py` / `LineDemand` / 在庫再計算 / 進度再計算

## 1. 背景

- 現在の在庫/進度再計算は、`LineDemand` が `process_id` / `routing_step_id` 単位で需要を保持していることを前提にしている。
- 一方で、過去の受注展開結果には工程別需要が揃っていない日があり、同一中間品が複数工程で流れる構成で `routing_step需要未解決` が発生することが確認された。
- 調査の結果、問題の本体は再計算側の単純バグではなく、受注展開結果が現行前提の工程粒度と完全には揃っていないことにある。

## 2. 今回確認できた事象

1. `m_routing_step` 上では、同一中間品に対して複数工程が定義されている。
2. しかし対象日の `LineDemand` には、そのうち一部工程の需要しか存在しないケースがある。
3. その結果、`line_backlog` 側の工程構成と `LineDemand` 側の工程需要がずれ、進度再計算で工程需要を解決できない。
4. したがって、53期では「旧データ補正」ではなく、「受注展開が工程別需要を安定して作れること」を改善対象として管理する。

## 3. 53期の方針

1. 受注展開は、最終品だけでなく中間品についても `process_id` / `routing_step_id` 単位で一貫した需要を生成できることを正式要件とする。
2. 同一中間品が複数工程で流れる構成でも、工程別需要が欠落しないことを保証対象とする。
3. 在庫/進度再計算側へ曖昧なフォールバックを足すのではなく、受注展開結果の正規化を優先する。
4. 受注展開の改善計画と、既存 `LineDemand` の再作成/再展開手順は同じ計画の中で扱う。

## 4. 実装計画

1. 現行 `order_expansion.py` の工程別需要生成条件を棚卸しする。
   - ルーティング選定
   - `output_product` 採用
   - `process_id` / `routing_step_id` の保持
   - 同一中間品が複数工程に出る場合の集約単位
2. 工程別需要が欠落する条件を再現テスト化する。
   - 同一中間品が複数工程に存在するルーティング
   - 進度再計算で `routing_step需要未解決` になるケース
3. 受注展開の正規仕様を明文化する。
   - どの受注品番からどの中間品需要を作るか
   - 同一中間品が複数工程に出る場合の期待結果
4. 現行ロジックで不足がある場合は、受注展開側を修正する。
5. 修正後、既存 `LineDemand` の再展開対象期間と再処理手順を文書化する。

## 5. 留意点

1. 受注展開改善は、単なる性能改善ではなく、在庫/進度再計算の前提データ整合性改善である。
2. 過去期間を再展開する場合、当時の `OrderLine` / `Routing` / `BOM` が現在値へ更新済みでないかを事前確認する必要がある。
3. 再計算側に例外フォールバックを増やすと、工程需要の正規系が不明瞭になるため原則避ける。

# バックエンド権限制御の段階導入（53期対応メモ）

作成日: 2026-07-23  
対象: `accounts` / `production` / `purchase` / `shipping` / `system_settings` の更新系API

## 1. 背景

- 現状の権限制御は、基本的にフロントエンドUIとルータの `meta.resource` による制御が中心である。
- このため、通常操作やURL直打ちはかなり抑止できている。
- ただしバックエンドAPI側は、多くの画面で `IsAuthenticated` のみ、または一部 `AllowAny` で動作している。
- そのため、ログイン済みユーザーが開発者ツールやAPIクライアントから直接リクエストした場合、権限外の更新・削除・実行が通る余地がある。

## 2. 53期の方針

1. バックエンド権限制御は、危険度の高い `POST` / `PUT` / `PATCH` / `DELETE` / 実行系APIから段階導入する。
2. 権限キーは、既存フロントエンドで使用している `resource` と `effective_permissions` をそのまま流用する。
3. フロントエンドの表示制御は維持しつつ、最終判定はバックエンドで行う構成へ寄せる。
4. 初回導入では閲覧系 `GET` を全面対象にせず、更新・削除・実行系を優先する。
5. 53期では「全面一括置換」ではなく、「優先対象を絞った段階導入」を正式方針とする。

# ブレーキ/板金スポット 工程作業セッション統一（53期対応メモ）

作成日: 2026-07-26  
対象: ブレーキ実績入力 / スポット実績入力 / 生産実績照会 / 実績変更 / 勤務集計 / 実績サイクル時間集計

## 1. 背景

- `ブレーキ` と `板金スポット` は、他フロアの工程作業入力と異なり、実績の主保存先として `BrakeLineRecord` を継続利用している。
- 一方で、通常工程側は `ProcessRealtimeRecord` / `ProcessWorkSession` を基準に、照会・編集・集計が構成されている。
- 2026-07-26 時点では、ブレーキ/スポットは保存時に `ProcessWorkSession` へ同期していると整理していたが、2026-10-01 の再調査で現行コードでは同期していないことを確認した（2-2 参照）。参照系画面も専用テーブル前提のため、運用上「同じ工程実績なのに扱いが別」という不便が残っている。

## 2. 2026-07-26 調査結果

1. 入力保存の主経路は現時点でも `BrakeLineRecord` 系である。
   - `pm_backend/apps/production/views_brake_line.py`
   - `pm_backend/apps/production/views_spot_line.py`
2. ただし保存時に `ProcessRealtimeRecord` / `ProcessWorkSession` への同期処理は既に存在する。
   - `pm_backend/apps/production/services/brake_spot_session_sync.py`
3. ブレーキ/スポット由来の `ProcessWorkSession` には、開始/終了記録、設備紐付け、数量、作業者など、参照統一に必要な基本情報は入っている。
4. 不便の主因は「保存」よりも「参照・編集・集計」の分岐である。
5. 特に以下で、ブレーキ/スポットだけ別取得・別除外・別編集 API になっている。
   - `pm-ui/src/views/production/ProductionRecordInquiry.vue`
   - `pm-ui/src/views/production/ProductionRecordEdit.vue`
   - `pm-ui/src/views/overtime/OvertimeProductivityStats.vue`
   - `pm-ui/src/views/overtime/OvertimeMonthlyStats.vue`
   - `pm_backend/apps/production/views_actual_cycle_time.py`
6. `ProductionRecordInquiry.vue` には、ブレーキラインとスポットラインでデータソースが異なるため板金タブのライン絞り込みを制限している旨のコメントがあり、運用上の不便がコード上にも表れている。

## 2-2. 2026-10-01 再調査結果（上記 2・3 の訂正）

1. 同期関数 `sync_brake_spot_action_to_process_session`（`services/brake_spot_session_sync.py`）は存在するが、`views_brake_line.py` / `views_spot_line.py` からは呼ばれていない。両ビューが同モジュールから利用しているのは `find_equipment_active_product_conflict` と `lock_and_reject_duplicate_operator_action` のみ。
2. 本番DBで、`brake_line_record` の L0010（ブレーキ）/ L0013（スポット）で使われている工程について、2026-09 の `ProcessWorkSession` は0件だった。
3. したがって上記「2. 調査結果」の 2・3 にある「同期処理は既に存在する」「ブレーキ/スポット由来の `ProcessWorkSession` に基本情報は入っている」は現状と異なる。参照系を `ProcessWorkSession` 基準へ揃える前に、保存時の同期（または保存先の移行）を先に用意する必要がある。
4. `LineBacklog(sequence_no=0).actual_qty` は `BrakeLineRecord` から直接加算されており、2026-09 の実データで次の関係を確認した。
   - L0013: `END` + `PAUSE` の qty 合計 = actual_qty 合計（66,836）
   - L0010: `END` + `PAUSE` の qty 合計（82,021）− 実績入力済み仕損（`is_production_recorded=1`、180）= actual_qty 合計（81,841）
5. 一方、生産実績照会・社内AI用DB辞書ではブレーキの生産数を `END` のみとしており、`PAUSE` の扱いが LineBacklog と異なる。統一時にどちらを正とするか決める必要がある。
6. 生産実績整合チェック（`production_actual_reconcile.py`）は `ProcessWorkSession` / `ProcessRealtimeRecord` だけを期待値にするため、同期がない現状では L0010 / L0013 の期待値が0となり、全件が差分になる（2026-10-01 初回実行で L0010・L0013 の差分が各月数百〜千件）。同チェックの「修正」を実行すると正しい actual_qty が0に上書きされるため、統一完了まで比較のみで運用する。

## 3. 53期の方針

1. 53期では、`ブレーキ` と `板金スポット` の参照基盤を `ProcessWorkSession` 基準へ統一する。
2. ただし入力保存互換のため、初期段階では `BrakeLineRecord` 自体は残す。
3. 先に「見る・集計する・照会する」を統一し、入力保存口の完全統一は後段で判断する。
4. つまり53期の第一段階は、`BrakeLineRecord を廃止する` ことではなく、`ProcessWorkSession を正本として参照系を揃える` ことを目的とする。

## 4. 実装方針

1. `process-realtime-records/sessions` をセッション参照の正本 API とする。
2. `ProcessWorkSession` 一覧レスポンスに、由来判定用の情報を追加する。
   - 例: `record_source`, `source_system`, `start_record_id`, `end_record_id`
3. ブレーキ/スポット同期由来か、通常工程由来か、手入力由来かを API で判別できるようにする。
4. フロントエンドは、ブレーキ/スポット用の別セッション取得 API を直接マージしない構成へ寄せる。
5. 更新/削除系は当面互換維持し、由来に応じて既存の更新口へ振り分ける。
   - 通常工程: `process-realtime-records/sessions`
   - ブレーキ/スポット由来: `brake-line-sessions`

## 5. 実装計画

# PostGISによる位置情報基盤の構築（53期〜対応メモ）

作成日: 2026-08-19  
対象: PostgreSQL移行後のPostGIS拡張による工場内位置情報管理

## 1. 背景

- PostgreSQL移行後、PostGIS拡張を利用すれば空間データ（座標・領域・経路）をDB上でネイティブに管理できる。
- 工場内の設備・置場・棚の位置をデータ化することで、棚卸動線の最適化、設備配置の可視化、搬送ルート分析が可能になる。
- GPS座標ではなく、工場図面上のローカル座標系（メートル単位）を使用する。

## 2. 実装フェーズ

### フェーズ1: 空間データ基盤（PostgreSQL移行後すぐ）

1. PostGIS拡張の有効化（`CREATE EXTENSION postgis;`）
2. Django に `django.contrib.gis`（GeoDjango）を追加
3. 位置情報モデルの作成
   - `EquipmentLocation`: 設備の設置位置（`PointField`）
   - `StorageArea`: 置場・棚の領域（`PolygonField`）
   - `FactoryFloor`: フロア図面のメタ情報（原点・縮尺・画像）
4. 管理画面から座標を登録できるUIを用意
5. 難易度: 低〜中 / 期間目安: 1〜2週間

### フェーズ2: 設備配置可視化

1. Leaflet.js + `CRS.Simple`（ローカル座標系）で工場フロアマップを表示
2. フロア図面画像をベースレイヤーとして読み込み
3. 設備・置場・棚の位置をマーカー/ポリゴンで重畳表示
4. クリックで設備詳細（名称・稼働状態・担当ライン）をポップアップ表示
5. 難易度: 中 / 期間目安: 2〜3週間

### フェーズ3: 棚卸動線最適化（最優先の活用候補）

1. 棚卸対象の置場・棚の位置座標を取得
2. TSPアルゴリズム（Nearest Neighbor + 2-opt改善）で巡回順を最適化
3. 最適化されたルートをフロアマップ上に `LineString` で描画
4. 棚卸リストを最適順に並び替えて出力
5. 難易度: 中〜高 / 期間目安: 2〜3週間
6. 価値: 棚卸作業の移動距離を30〜40%削減可能（工場規模・配置による）

### フェーズ4: 搬送ルート分析（将来拡張）

1. AGV導入時の搬送ログ（出発地・到着地・経路・時刻）を蓄積
2. `ST_Distance`, `ST_DWithin` 等のPostGIS空間関数で距離・近接分析
3. ヒートマップで搬送頻度の高いエリアを可視化
4. 難易度: 高 / 期間目安: 3〜4週間
5. 前提: AGV導入・搬送ログの仕組みが整備されてから

## 3. 技術要素

| 要素 | 技術 |
|------|------|
| 空間DB | PostgreSQL + PostGIS |
| Django連携 | GeoDjango (`django.contrib.gis`) |
| モデルフィールド | `PointField`, `PolygonField`, `LineStringField` |
| 空間クエリ | `ST_Distance`, `ST_Within`, `ST_DWithin` |
| フロントエンド地図 | Leaflet.js + `CRS.Simple`（ローカル座標） |
| 経路最適化 | Nearest Neighbor + 2-opt（将来: OR-Tools） |
| 座標系 | 工場図面上のローカル座標（メートル単位、GPS不使用） |

## 4. 期待効果

1. **棚卸効率化**: 動線最適化により移動時間を大幅短縮、棚卸作業の工数削減
2. **設備配置の見える化**: 新人・外部作業者が設備位置を即座に把握可能
3. **搬送効率の分析**: AGV導入後の搬送ボトルネック特定と配置改善の根拠データ化
