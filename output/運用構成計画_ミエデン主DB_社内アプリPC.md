# 運用構成計画
## 開発中の社内運用・将来のミエデン移設

---

## 方針

- **開発中**: アプリの画面、API、定時処理、MySQLを**社内環境**で運用
  - 機能追加、DB変更、検証を迅速に実施できる状態を維持
- **将来**: 機能・更新手順・障害対応が定型化した後、**ミエデン遠隔地環境**への移設を検討
  - 移設範囲（DBのみ or アプリ全体）はその時点で決定

---

## 段階別の運用

| 段階 | 配置 | 目的 |
| --- | --- | --- |
| **開発・検証中（現在）** | 社内: 画面、API、定時処理、MySQL | 機能追加・修正・DB変更を迅速に検証 |
| **本番運用の定型化後（将来）** | ミエデン: DB、必要に応じてアプリ全体 | サーバー保守、バックアップ、監視を外部委託 |

---

## 将来の移設後構成

  - Django API
  - 定時処理（scheduler）
  - Docker

    v

  - 本番MySQL

  - DB監視・復旧

### パターンB: アプリ全体移設

```text
社内業務端末
    |
    | HTTPS（VPN等で暗号化）
    v
ミエデン遠隔地環境
  - Vue画面
  - Django API
  - 定時処理（scheduler）
  - Docker
  - 本番MySQL
  - バックアップ（DB・ファイル）
  - サーバー監視・復旧
```

## 将来の役割分担

### パターンA: DBのみ移設

| 対象 | 社内 | ミエデン |
| --- | --- | --- |
| ソースコード・機能改修 | 開発・テスト・リリース判断 | 変更内容の受領 |
| 社内アプリPC | 起動確認、更新実施 | HW・OS保守は要確認 |
| Docker環境 | 更新時の再構築・再起動 | 原則対象外 |
| 本番MySQL | データ利用・整合性確認 | 構築・監視・バックアップ・復旧 |
| VPN・DB接続経路 | 利用者・接続元の管理 | 構築・アクセス制御・監視 |
| DB障害 | 業務影響連絡・アプリ確認 | 原因調査・復旧 |

### パターンB: アプリ全体移設

| 対象 | 社内 | ミエデン |
| --- | --- | --- |
| ソースコード・機能改修 | 開発・テスト・リリース判断 | デプロイ・変更内容の受領 |
| アプリサーバー | 動作確認・リリース指示 | HW・OS・Docker保守・監視 |
| Docker環境 | 更新指示・構成管理 | 再構築・再起動・運用 |
| 本番MySQL | データ利用・整合性確認 | 構築・監視・バックアップ・復旧 |
| ネットワーク・VPN | 利用者・接続元の管理 | 構築・アクセス制御・監視 |
| サーバー・DB障害 | 業務影響連絡 | 原因調査・復旧 |

---

## 将来の接続・セキュリティ要件

- VPNまたはミエデン指定の**閉域・暗号化経路**で接続
- MySQL接続元は**固定IP**に限定
- MySQLを**インターネットへ直接公開しない**
- DB接続用アカウントは**アプリ専用**（管理者アカウント使用禁止）
- 接続先・ID・パスワードは**環境変数ファイル**で管理（Git登録禁止）
- ミエデン側で通信経路・アカウント・バックアップ暗号化・保管期間を設定

---

## 将来のアプリ更新手順

### パターンA: DBのみ移設

1. 社内でソースコード修正 → 開発環境で動作確認
2. Gitへ登録、リリース対象を確定
3. 社内アプリPCでソースコードを更新
4. Dockerイメージ再構築 → 画面・API・定時処理を再起動
5. DB変更がある場合 → **ミエデンのDBバックアップ完了を確認後**マイグレーション実行
6. 業務画面・DB接続・定時処理・帳票出力を確認 → リリース結果を記録

### パターンB: アプリ全体移設

1. 社内でソースコード修正 → 開発環境で動作確認
2. Gitへ登録、リリース対象を確定
3. ミエデン環境へデプロイ（Git push or 手動配置）
4. ミエデン環境でDockerイメージ再構築 → 画面・API・定時処理を再起動
5. DB変更がある場合 → **ミエデンのDBバックアップ完了を確認後**マイグレーション実行
6. 業務画面・DB接続・定時処理・帳票出力を確認 → リリース結果を記録

## 将来の障害時の対応

### パターンA: DBのみ移設

| 事象 | 一次対応 | 復旧担当 |
| --- | --- | --- |
| DB接続不可 | ネットワーク・ログ確認→ミエデン連絡 | ミエデン（VPN・DB調査） |
| DB障害・データ破損 | 業務停止→発生時刻・操作内容を連絡 | ミエデン（バックアップ復旧） |
| 社内アプリPC障害 | 代替PC or 復旧手順で再構築 | 社内（HW保守は別途契約） |
| 通信断 | アプリ利用停止→復旧待ち | 回線・VPN担当者 |

### パターンB: アプリ全体移設

| 事象 | 一次対応 | 復旧担当 |
| --- | --- | --- |
| DB接続不可 | ミエデン連絡 | ミエデン（サーバー内部調査） |
| DB障害・データ破損 | 業務停止→発生時刻・操作内容を連絡 | ミエデン（バックアップ復旧） |
| アプリサーバー障害 | ミエデン連絡 | ミエデン（HW・Docker復旧） |
| 通信断 | アプリ利用停止→復旧待ち | 回線・VPN担当者 |

## 将来のデータ保管の注意点

### パターンA: DBのみ移設

MySQLをミエデンへ移しても、以下は**社内アプリPC**に残る:

- 添付ファイル・アップロードファイル（`pm_backend/media/`）
- アプリログ（`pm_backend/logs/`）
- 帳票・出力ファイル（`output/`）
- 証明書・通知設定などの機密設定ファイル

**対応方針:**
- 添付ファイル・帳票 → ミエデンのバックアップ対象ストレージへ退避
- ログ → 社内で保持期間を定め、障害調査に必要な期間を保管

### パターンB: アプリ全体移設

すべてのデータがミエデン環境に集約される:

- DB・添付ファイル・ログ・帳票 → ミエデン側でバックアップ・保管
- 証明書・機密設定ファイル → ミエデン側で管理

**対応方針:**
- バックアップ対象・頻度・保持期間をミエデンと合意
- 社内にはソースコードと開発環境のみ保持

---

## ミエデン移設の導入手順

1. 開発・検証を完了し、機能・更新手順・障害対応を**定型化**
2. ミエデンと**責任分担・保守時間・障害連絡先・復旧目標**を合意
3. ミエデン側に本番MySQL・バックアップ・VPN・DBアカウントを用意
4. 移設範囲に応じてDocker実行環境を構築
5. テスト用データで画面・定時処理・帳票・バックアップ復元を確認
6. **本番データ移行** → 社内MySQL停止
7. 本番運用開始（導入後1か月は重点確認）

---

## 移設判断の条件

- 対象機能の開発・検証が**完了**していること
- リリース・DB変更・ロールバック・障害連絡の手順が**文書化**されていること
- 利用対象の現場・業務範囲と導入順序が**決定**していること
- ミエデン側の保守範囲・費用・責任分担が**合意**されていること

---

## 事前確認事項

- ミエデンがMySQL提供・運用保守、VPN・閉域接続に対応できるか
- 社内アプリPCの常時稼働を認めるか（停電対策・自動起動・保守担当）
- 社内アプリPCのHW・OS障害の対応者
- 添付ファイル・帳票出力の保管先をミエデン側に用意できるか
- DBバックアップの頻度・保持世代・復旧目標時間・連絡手順
- データ所在地・アクセス権限・監査ログ・個人情報の社内承認

---

## 判断

現在は**開発中**のため、ミエデンへの移設は行わない。

機能と運用が**定型化した後**に、
ミエデンへ**DBのみ**を移すか、**アプリ全体**を移すかを判断する。
